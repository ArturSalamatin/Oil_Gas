# /implement — реализация плана из vault

Аргумент: `$ARGUMENTS` — идентификатор задачи (`BUG-001`, `DEBT-003`, `FEAT-005`, `VAL-002`) или имя файла плана.

Результат: реализованный план — код, тесты, обновлённый vault, комментарий к GitHub issue — на ветке задачи в отдельном worktree. Влитие в базовую ветку — отдельной командой `/merge <ID>` по слову пользователя «мерж».

**Рабочая директория зависит от направления задачи.** Определи её до начала работы:

| Направление | Каталог | Пакет / исходники | Тесты | Конфиги | Базовая ветка |
|---|---|---|---|---|---|
| **PDE-солвер** (текущая разработка) | `numerical_solver/` | `gpn_multiphase_solver/` | `tests/` | `configs/` | `numerical_scheme/implementation` |
| **Метод моментов** (завершён, только справка) | `method_of_moments/` | `src/` | `tests/` | `configs/` | `master` |

Все пути в планах и отчётах — от корня проекта (например `numerical_solver/gpn_multiphase_solver/factory.py`).

По умолчанию новые задачи относятся к `numerical_solver/`. ⚠️ Задачи метода моментов этим процессом не выполняются: основной каталог стоит на `numerical_scheme/implementation`, и предварительный коммит (1.4) в `master` сделать некуда. Для них — СТОП, вопрос пользователю.

## Схема работы

Задача выполняется в отдельном worktree. Основной каталог проекта стоит на базовой ветке, его рабочую копию делят параллельные сессии.

| Что | Где правится | Куда коммитится |
|---|---|---|
| Подготовленное **до** реализации: план, материалы задачи (`vault/issues/<id>/` — тексты issue, скрипты проб), вспомогательные скрипты, общие файлы vault (реестры, `index.md`) | основной каталог | базовая ветка — предварительный коммит (1.4), до создания worktree |
| Код, тесты, README; vault, изменённый **во время** реализации (статус плана, запись задачи в реестре, заметки результатов, новые пробы, `05-comment-done.md`) | worktree | ветка задачи |
| Новые задачи, обнаруженные при реализации (2.5) | основной каталог | базовая ветка, сразу |
| Влитие, удаление worktree, отметка «влит» | основной каталог | базовая ветка — `/merge` |

Обозначения (в командах подставлять полностью):

- `<КОРЕНЬ>` = `D:\Lessons\Grants\2026\GPN\Oil_Gas` — основной каталог.
- `<W>` = `<КОРЕНЬ>\.worktrees\<id-lowercase>` — worktree задачи (например `.worktrees\debt-037`).
- `<PY>` = `<КОРЕНЬ>\numerical_solver\.venv\Scripts\python.exe` — venv один, в основном каталоге. В worktree своего `.venv` нет: относительный `.venv\Scripts\python` там не найдётся.

Переменные PowerShell (`$env:PYTHONPATH`, `$x = ...`) не переживают отдельный вызов инструмента — задавать в той же команде, что и запуск.

Команды pytest — из `<W>\numerical_solver` (pytest берёт код worktree: каталог запуска первым в `sys.path`, подготовки не нужно):
```powershell
cd <W>\numerical_solver
<PY> -m pytest tests/ -m "not slow" -q   # быстрый уровень, ~70 с
<PY> -m pytest tests/ -q                 # полный прогон, ~10 мин
<PY> -m pytest tests/ --collect-only -q  # только число тестов, ~3 с
```

Уровни прогона (DEBT-032): метку `slow` несут тесты на фикстуре `results` из `tests/test_examples.py` (ставится автоматически хуком в `tests/conftest.py`), `test_matrix_matches_reference` и тесты на сгущённой сетке. Полный прогон — один раз в конце реализации и на шагах, которые план помечает «Регресс: полный».

⚠️ Для `numerical_solver` тестам нужен прототип `radial_blackoil` — его подключает `tests/conftest.py` через `sys.path`. Скрипты вне pytest должны делать это сами (правило 3 ниже).

**Правка прототипа** (`numerical_solver/HydroSolverPrototype/Prototype_1.0.3/`): тесты `numerical_solver` её не ловят — у прототипа свои тесты и регрессия против эталона `regression/golden/`, сверенного с CMG IMEX (DEBT-029). Команды — из `<W>\numerical_solver\HydroSolverPrototype\Prototype_1.0.3`:
```powershell
<PY> -m pytest tests -q                  # тесты прототипа, 80 шт., ~45 с
<PY> regression\run_regression.py --quick # регрессия T00–T11 без T05, ~8 мин
<PY> regression\run_regression.py         # полная, с T05, ~45 мин
```
Выходы регрессии — `OUTPUT/REGRESSION_<время>/` в worktree (игнорируется git, удаляется вместе с worktree); итог — в отчёт.

### Правила работы в worktree

1. **Код правится только в `<W>`.** Read / Edit / Write — по абсолютному пути `<W>\...`. Относительные пути в обоих деревьях одинаковы: тот же путь от `<КОРЕНЬ>` молча изменит основной каталог, а не ветку задачи. В основном каталоге — только то, что «Схема работы» относит к базовой ветке.
2. **Контроль основного каталога.** На шаге 1.7 запомни `git -C <КОРЕНЬ> status --porcelain -- numerical_solver/`; после каждого шага сверяй. Новая строка — проверь, не своя ли это ошибочная правка: своя → перенести в `<W>`, в основном каталоге вернуть текст Edit-ом; чужая (параллельная сессия) — не трогать.
3. **Скрипты вне pytest** (`main.py` примеров, постобработка) без подготовки берут пакет `gpn_multiphase_solver` **основного** каталога: он установлен в venv в редактируемом режиме, а первым в `sys.path` стоит папка скрипта. Запуск — с `PYTHONPATH` на worktree и проверкой путей в той же команде:
   ```powershell
   cd <W>\numerical_solver; $env:PYTHONPATH = "<W>\numerical_solver;<W>\numerical_solver\HydroSolverPrototype\Prototype_1.0.3"; <PY> -c "import gpn_multiphase_solver as g, radial_blackoil as r; print(g.__file__, r.__file__)"; <PY> examples\<пример>\main.py
   ```
   Оба пути — в `<W>`; иначе результат недействителен.
4. **Пробы** `vault/issues/<id>/probes/` лежат в git с предварительного коммита (1.4) и есть в worktree. Запускать копию из `<W>`: пути, вычисленные от расположения скрипта, тогда указывают на код worktree. Если проба печатает пути импортированных пакетов — они должны быть в `<W>`. Новые пробы — в `<W>\vault\issues\<id>\probes\`, коммит на ветке задачи (`vault:`).
   Выходы проб: истории `.npz` и графики (`.png`, `.emf`, `.svg`) игнорируются git и **удалятся вместе с worktree** при `/merge` — они воспроизводимы. Текстовые выходы (`.txt`, `.csv`, `.json`) не игнорируются: закоммитить на ветке или удалить до конца реализации — иначе `git worktree remove` откажет.
5. **git задачи** — в `<W>` (`git -C <W> ...`). Коммиты кода и vault задачи — на ветке задачи.
6. **Коммит в базовую ветку** (1.4, 2.5, 4.3) — в `<КОРЕНЬ>`, с явными путями:
   ```powershell
   git -C <КОРЕНЬ> add -- <файлы>
   git -C <КОРЕНЬ> commit -m "<сообщение>" -- <файлы>
   ```
   Коммит с путями берёт только их и не захватывает то, что параллельная сессия уже добавила в индекс.
7. **`git stash` не использовать.** Список stash общий для всех worktree репозитория: спрятанное в worktree видно и применимо в основном каталоге и в чужих worktree. Незакоммиченное состояние worktree и так изолировано — его оставляют на месте.
8. **Встроенные `EnterWorktree` / `ExitWorktree` не использовать.** `EnterWorktree` создаёт worktree в `.claude/worktrees/` и по умолчанию ветвится от `origin/<ветка по умолчанию>` (`master`), `ExitWorktree remove` удаляет ветку. Worktree создаётся вручную (1.5).
9. **Игнорируемые git файлы worktree удаляются вместе с ним.** Всё, что нужно сохранить, — в отслеживаемых файлах, закоммичено на ветке.

## Фаза 1: Подготовка

Шаги 1.1–1.4 — в основном каталоге `<КОРЕНЬ>`.

### 1.1. Найти план

1. Если `$ARGUMENTS` — ID: `ls vault/plans/<id-lowercase>*` (в основном каталоге: план может быть ещё не закоммичен)
2. Если `$ARGUMENTS` — имя файла: `vault/plans/<имя>.md`
3. Если worktree задачи уже есть (`git worktree list`) — актуальный план в `<W>\vault\plans\` (возобновление, 2.7)
4. Если плана нет — предложи создать через `/plan-fix`, `/plan-feature`, `/plan-validate` или `/plan-improve`

### 1.2. Загрузить план

1. Прочитай план целиком
2. Извлеки из frontmatter: `issue`, `github`, `branch`, `status`, `worktree`
3. Проверь `status`:
   - `готов к реализации` → продолжай с шага 1.3
   - `в процессе` → возобновление, перейди к 2.7
   - `черновик` → предложи `/audit-plan`
   - `реализован` → предложи `/merge <ID>`
   - `заблокирован` → сообщи пользователю, не продолжай без подтверждения
4. Запомни: количество шагов, ветку, зависимости, критерии завершения

Пункт «Создай ветку» (`git checkout -b`) из секции плана «Как начать работу» **не выполнять**: ветку и worktree создаёт шаг 1.5. `git checkout -b` в основном каталоге увёл бы в ветку задачи коммиты параллельных сессий.

### 1.3. Проверить предусловия

1. **Блокирующие задачи завершены и влиты.** Для каждой задачи из «Зависит от» и блокеров из реестра: запись в реестре — «влит», ветка — предок базы: `git merge-base --is-ancestor <ветка зависимости> <базовая ветка>` (код возврата 0). Хоть одна не влита — **СТОП**: задача не выполняется, пока блокирующие задачи не завершены и не влиты. Ветвиться от ветки невлитой задачи нельзя.
2. **Основной каталог стоит на базовой ветке:** `git -C <КОРЕНЬ> branch --show-current`. Иначе — СТОП: предварительный коммит ушёл бы не в ту ветку.
3. **Ветки задачи и worktree нет:** `git branch --list "<branch>"`, `git worktree list`. Ветка есть при статусе `готов к реализации` — СТОП, вопрос пользователю (прежняя попытка? чужая работа?).
4. **`.worktrees/` исключён из git:** в `.git/info/exclude` есть строка `/.worktrees/` (`Select-String -Path .git/info/exclude -Pattern '^/?\.worktrees/?$'`). Нет — добавить.

### 1.4. Предварительный коммит в базовую ветку

План и материалы, подготовленные до реализации, — часть базовой ветки, и в worktree они должны быть: worktree создаётся от базы после этого коммита.

1. `git -C <КОРЕНЬ> status --porcelain` — изменения основного каталога.
2. Разбери по группам:

| Группа | Что | Действие |
|---|---|---|
| Материалы задачи | план `vault/plans/<id>*`; `vault/issues/<id>/` (тексты issue, скрипты проб; `.npz` и графики игнорируются git); заметки vault и вспомогательные скрипты, которые называет план | в коммит |
| Общие файлы vault | реестры `vault/roadmap/*.md`, `vault/00-home/index.md` — регистрация и краткие описания задач | в коммит **целиком**, даже если в файле правки других задач: им и так место в базовой ветке |
| Код задачи | незакоммиченные правки модулей пакета, тестов, прототипа, примеров (`main.py`, конфиги, README), относящиеся к задаче | **СТОП**, вопрос пользователю: в базу без зелёных тестов нельзя, а незакоммиченное в worktree не попадёт |
| Прочее | планы и материалы других задач, чужие правки кода | не трогать |

3. Обнови frontmatter плана: `status: в процессе`, `worktree: .worktrees/<id-lowercase>`.
4. Коммит — правило 6: `vault: <ID> начало реализации — план и материалы задачи`. Файлы вне `vault/` (вспомогательные скрипты) — отдельным коммитом того же шага: vault отдельно от кода.
5. Сообщи в чат: что вошло в коммит (по группам), что оставлено, hash.

### 1.5. Создать worktree

Базовая ветка: если план её указывает (секция «Ветка») — она; если нет — по таблице в шапке, с проверкой по факту, а не по имени:

```powershell
# содержит ли ветка каталог, который правит план?
git ls-tree <кандидат> --name-only | Select-String <рабочий каталог>
```

⚠️ `master` **не содержит** `numerical_solver/` — ветвление от него для задач солвера даст дерево без библиотеки. Ветки `main` в репозитории нет.

```powershell
git -C <КОРЕНЬ> worktree add .worktrees/<id-lowercase> -b <branch-from-plan> <базовая-ветка>
```

Проверка: `git -C <W> log --oneline -1` — предварительный коммит из 1.4; план в `<W>\vault\plans\` со статусом `в процессе`.

### 1.6. Загрузить контекст (из worktree)

Выполни секцию «Как начать работу по этому плану» из файла плана (кроме создания ветки — см. 1.2):
1. Прочитай связанные vault-заметки (`<W>\vault\...`)
2. Прочитай формулы из `.tex`, на которые ссылается план (offset + limit по нужному разделу)
3. Прочитай файлы, которые будут изменены (`<W>\...`, только нужные фрагменты)
4. Если есть GitHub issue — прочитай: `gh issue view <N> --repo ArturSalamatin/Oil_Gas` (могут быть комментарии с уточнениями от аудита или пользователя)

### 1.7. Baseline тестов (в worktree)

```powershell
cd <W>\<рабочий каталог>
<PY> -m pytest tests/ --collect-only -q   # число тестов
<PY> -m pytest tests/ -m "not slow" -q    # быстрый уровень
```

`<рабочий каталог>` — из таблицы в шапке (`numerical_solver` для задач PDE-солвера).

Запомни: общее число тестов, число и время быстрого уровня, pass/fail. Это baseline — с ним сверяется регрессия после каждого шага. Полный прогон здесь не нужен (DEBT-032): базовая ветка зелёная по правилу «новый код не мёржится без зелёных тестов», а быстрый уровень проверяет, что окружение (venv, прототип) не разъехалось. Если быстрый уровень на базе красный — СТОП: это не регрессия задачи, сообщи пользователю. Если план указывает baseline и он **не совпал** с фактическим — не игнорируй: план мог устареть, сверь и зафиксируй факт.

Если план меняет прототип — ещё baseline прототипа до первой правки: тесты прототипа и `run_regression.py --quick` (команды — шапка). Ожидается 80 passed и 11/11 PASS. Красная база прототипа — СТОП, как и для быстрого уровня: расхождение с эталоном до правки нельзя потом отличить от расхождения из-за правки.

Запомни снимок основного каталога для правила 2: `git -C <КОРЕНЬ> status --porcelain -- numerical_solver/`.

## Фаза 2: Реализация

Все правки — в `<W>`, кроме регистрации новых задач (2.5).

### 2.1. Порядок шагов

Следуй плану **строго по порядку шагов.** Не перескакивай. Не объединяй шаги.

Для каждого шага:

### 2.2. Выполнение шага

1. **Прочитай описание шага** из плана
2. **Прочитай файлы,** которые будут изменены (`<W>\...`, offset + limit, не целиком)
3. **Проверь актуальность:** номера строк совпадают? Функции существуют?
   - Если план устарел — адаптируй шаг, но **не меняй цель**
4. **Реализуй изменения** (абсолютные пути `<W>\...`, правило 1):
   - Edit для модификации существующих файлов
   - Write для новых файлов
   - Docstrings: одна строка + `\eqref{eq:...}` (если формула)
5. **Тесты шага** (из `<W>\numerical_solver`):
   - Создай/обнови тесты, если шаг это предусматривает
   - Запусти тест шага: `<PY> -m pytest tests/<file> -k "<name>" -v` (выбор по `-k` запускает тест и с меткой `slow`)
   - Запусти регрессию по полю «Регресс» шага в плане:
     - `быстрый` (по умолчанию, и если поля нет): `<PY> -m pytest tests/ -m "not slow" -q`
     - `полный`: `<PY> -m pytest tests/ -q`
     - шаг меняет только документы (`.md`, `.tex`, vault), не код и не тесты: `<PY> -m pytest tests/ --collect-only -q` — число тестов не изменилось
   - Шаг меняет прототип (`HydroSolverPrototype/`), даже если поля «Регресс прототипа» в плане нет: тесты прототипа и `run_regression.py --quick` (команды — шапка). Исход сверь с ожиданием плана (побитно / перечисленные кейсы). FAIL, которого план не ждал, — та же ситуация, что упавший тест: разобрать (с какого шага расходится, как затухает), эталон **не переснимать** — решение о пересъёме принимает пользователь
   - Ключ `-q`, не `-v`: при `-v` прогон отдаёт в контекст строку на каждый тест (1100+ строк)
6. **Если тест падает:**
   - **Из-за текущих изменений** (новый тест или сломан существующий):
     - Прочитай ошибку
     - Исправь код (не тест, если тест корректен)
     - Повтори запуск: сначала только упавшие — `<PY> -m pytest tests/ --lf -q` (pytest помнит их в `.pytest_cache`), после исправления — регрессию шага целиком
     - Максимум 3 итерации. Если не получается → «Не удаётся починить»
   - **По не связанной причине** (flaky, известный баг):
     - Проверь vault (`knowledge/debugging/`, реестр багов) — известная ли проблема?
     - Если известный flaky — продолжай, в коммите добавь: `(тест X flaky, см. BUG-NNN)`
   - **Не удаётся починить:**
     - Изменения остаются незакоммиченными в `<W>` — worktree изолирован; `git stash` не использовать (правило 7)
     - Зарегистрируй проблему как новый BUG (2.5)
     - Сообщи пользователю: что сломалось, почему, какие варианты
     - **Не коммить сломанное состояние**
7. **Сверь основной каталог** со снимком из 1.7 (правило 2)
8. **Коммит** — если шаг завершён и тесты зелёные (см. 2.3)
9. **Сообщи прогресс в чат:**
   ```
   Шаг N/M: <название> ✅
     Файлы: <список>
     Тесты: <passed>/<total>, уровень <быстрый | полный> (baseline того же уровня: <baseline>)
     Коммит: <hash> <message>
   ```

### 2.3. Стратегия коммитов

Коммиты — в `<W>`, на ветке задачи. Каждый коммит — самодостаточный блок. Критерии:

- [ ] Тесты проходят (или failing тесты явно задокументированы)
- [ ] Изменения логически связаны (один шаг плана = один или несколько коммитов)

Формат сообщения: `<тип>: <краткое описание>`
- Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `vault`
- Vault-изменения — **отдельным коммитом** от кода. Vault, изменённый во время реализации (план, запись задачи в реестре, заметки, пробы), — на ветке задачи; новые задачи — в базовой ветке (2.5)
- Stage по имени файла, **не** `git add .` или `git add -A`
- **Не** упоминай Claude в коммитах (без Co-Authored-By)

Когда коммитить:
- После каждого завершённого шага плана (если шаг затрагивает код)
- После группы мелких связанных шагов (если каждый по отдельности не имеет смысла)
- При обновлении vault — отдельный коммит

### 2.4. Правила реализации

- **Минимальные изменения:** не рефактори попутно, не добавляй «улучшения» сверх плана
- **Формулы → код:** каждая вычислительная строка — из `.tex`, на который ссылается план
- **Docstrings:** одна строка + ссылка на уравнение, не больше
- **Типизация:** type hints для публичных функций
- **Import-ы:** в начале файла, сгруппированные (stdlib / third-party / local)
- **Тесты:** pytest-стиль, понятные имена `test_<что>_<при_каких_условиях>`
- **Не трогай** файлы, не упомянутые в плане

### 2.5. Обнаружение новых проблем

В ходе реализации могут всплыть неожиданные проблемы. Новая задача — часть базовой ветки, а не ветки задачи. Протокол:

1. **Не уходи в сторону.** Не начинай чинить найденную проблему, если она не в плане
2. **Зарегистрируй в основном каталоге** (`<КОРЕНЬ>\vault\...`):
   - тип ясен (BUG/DEBT/FEAT/VAL) — запись в реестре по правилам CLAUDE.md («Реестры задач»), статус `🔴 ОТКРЫТ`, в описании «Обнаружено при реализации [[<план>]]»;
   - тип неясен — заметка в `vault/inbox/`:
     ```markdown
     ---
     tags: [inbox, обнаружено-при-реализации]
     date: <дата>
     source: <ID текущей задачи>
     ---
     # <суть проблемы>
     Обнаружено при реализации [[<план>]].
     <описание: что увидел, почему это проблема>
     ```
   - коммит сразу, в базовую ветку, правило 6: `vault: <NEW-ID> зарегистрирован — обнаружено при реализации <ID>`. Реестр — общий файл, коммитится целиком (как в 1.4)
3. **Оцени, блокирует ли** — мешает ли завершить текущий шаг?
   - Не блокирует → продолжай план
   - Блокирует → СТОП, сообщи пользователю, предложи варианты:
     a) Обходной путь в рамках плана
     b) Приостановить, создать `/issue` для блокера, вернуться после

### 2.6. Rollback-протокол

Если реализация зашла в тупик (тесты массово падают, блокирующая проблема):

1. **Не коммить сломанное состояние** кода
2. Незакоммиченные изменения остаются в `<W>` — `git stash` не использовать (правило 7)
3. Обнови frontmatter плана в `<W>`: `status: заблокирован`, добавь `blocker: <описание>`
4. Коммит на ветке задачи — только план: `git -C <W> commit -m "vault: <ID> заблокирован — <причина>" -- <план>`
5. Блокер — новая задача в базовой ветке (2.5)
6. Сообщи пользователю: что пошло не так, на каком шаге, какие варианты
7. Не используй `git checkout --` или `git reset` без явного разрешения пользователя

### 2.7. Возобновление после прерывания

Если сессия оборвалась (контекст потерян, пользователь вернулся позже):

1. Найди worktree: поле `worktree:` плана или `git worktree list`. Worktree удалён, а ветка есть — восстанови: `git -C <КОРЕНЬ> worktree add .worktrees/<id-lowercase> <branch>` (без `-b`)
2. Прочитай план в `<W>` — frontmatter покажет `status: в процессе`
3. `git -C <W> log --oneline <базовая-ветка>..HEAD` — какие шаги уже реализованы
4. Сопоставь изменённые файлы с шагами плана — определи последний завершённый шаг
5. Проверь `git -C <W> status` — есть ли незакоммиченные изменения (прерванный шаг)
6. Прогони быстрый уровень из `<W>\numerical_solver` — убедись, что текущее состояние зелёное
7. Сними заново снимок основного каталога (правило 2)
8. Продолжи со следующего шага

## Фаза 3: Верификация

### 3.1. Полный прогон тестов

```powershell
cd <W>\<рабочий каталог>
<PY> -m pytest tests/ -q
```

Это обязательный полный прогон задачи (DEBT-032): после шагов шёл быстрый уровень. Если полный прогон уже был на последнем шаге, меняющем код или тесты, и после него менялись только документы (`git -C <W> diff <коммит того шага>..HEAD -- <рабочий каталог>/` пуст) — повторять не нужно, сошлись на тот прогон.

Если задача меняла прототип — после полного прогона тестов ещё **полная** регрессия прототипа `run_regression.py` из `<W>` (с T05, ~45 мин; запускать в фоне). Перед запуском зафиксируй HEAD worktree и не меняй `<W>` (правки, переключения) до конца прогона: каждый кейс — отдельный процесс, импортирует код заново, и правка посреди прогона даёт смешанный результат. Влития в базовую ветку прогон из worktree не затрагивают. Итог — 17/17 PASS или расхождения, совпадающие с ожиданием плана; в отчёт — список кейсов и вывод. Пересъём эталона (если пользователь решит) — с записью в `CHANGELOG_1.0.3.md`, раздел «Local changes — GPN project».

Сравни с baseline:
- Количество тестов: было N, стало M (M ≥ N)
- Все pass: да/нет
- Время: заметный рост против последнего известного полного прогона — отметить в отчёте

Если падает тест, которого задача не касалась, — сначала проверь его на точке ветвления: дерево `<W>` чистое (иначе незакоммиченное уедет вместе с переключением) → `git -C <W> switch --detach $(git -C <W> merge-base <базовая-ветка> HEAD)` → `<PY> -m pytest <id упавших тестов из сводки> -q` → `git -C <W> switch <branch>`. Точка ветвления, а не текущая база: база могла уйти вперёд. Явные id, а не `--lf`: если записанных падений нет в выборке, `--lf` запускает выборку целиком — на базе это незаметно превратится в полный прогон. Падает и на базе — это дрейф окружения или чужая регрессия: не чинить в рамках задачи, сообщить пользователю. Падает только на ветке — найди виновный шаг по пошаговым коммитам (тот же приём с `git -C <W> switch --detach <коммит шага>`).

### 3.2. Чеклист критериев завершения

Проверь каждый пункт из секции «Критерии завершения» плана. Для каждого:
- ✅ выполнен — конкретное доказательство (номер теста, строка, файл)
- ❌ не выполнен — причина и план действий

### 3.3. Проверка по подводным камням

Пройди чеклист подводных камней из плана. Проверь каждый:
- Grep по изменённым функциям — все call sites обновлены?
- Граничные случаи покрыты тестами?
- Import-ы не создали циклов?

### 3.4. Обзор изменений

```powershell
git -C <W> log --oneline <базовая-ветка>..HEAD
git -C <W> diff --stat <базовая-ветка>...HEAD   # три точки — от точки ветвления: база могла уйти вперёд
```

Проверь:
- [ ] Нет случайных файлов (build-артефакты, __pycache__, .pytest_cache)
- [ ] Нет отладочного кода (print для отладки, временные хаки)
- [ ] Нет закомментированного старого кода
- [ ] Основной каталог не содержит твоих правок кода (правило 2)

### 3.5. Визуальная верификация (если план предусматривает)

1. Запусти визуализацию (скрипт из плана; правило 3 — `PYTHONPATH` на worktree)
2. Проверь: графики соответствуют ожиданиям (аналитика, предельные случаи)
3. Сохрани графики для отчёта

## Примечания

- **Коммить по мере выполнения** — после каждого шага (см. 2.3)

- Edit вместо Write для существующих файлов

- Не перечитывай файл после Edit
- Если план устарел — адаптируй шаги, но сообщи о расхождениях
- Если шаг сложнее ожидаемого — не молчи, сообщи
- PATH для gh: `$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User")`
