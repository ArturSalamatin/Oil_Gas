# Контрольные списки аудита плана

Контрольные списки дополняют [направления аудита](dimensions.md). Отмечай фактический результат и источник каждого применимого пункта. Если пункт неприменим или не проверен, укажи причину и влияние на вывод. Не считай наличие отметки в плане доказательством проверки.

## 1. Фокусы и завершение раундов

| Раунд | Фокус | Дополнительные вопросы |
|---|---|---|
| 1 | Предметная суть | Решает ли план исходную задачу? Подтверждены ли причина, формулы, знаки, размерности, критерии и эталон? |
| 2 | Реализуемость | Существуют ли точки изменений и интерфейсы? Согласованы ли блоки «было» и «стало», порядок шагов, тесты и их зависимости? |
| 3 | Инфраструктура | Воспроизводимы ли команды из указанного каталога и среды? Доступны ли зависимости и материалы в worktree? Совпадает ли предполагаемая база с фактической? |

Фокус не отменяет остальные направления: проверяй все применимые пункты каждого раунда и последствия предыдущих правок. После содержательной правки или исправления блокирующей находки проверяй новую версию независимо. Максимум три последовательных автоматических раунда за вызов планирования. Если после третьего версия остаётся непроверенной, сообщи об этом и предложи отдельный повторный аудит. Чистый прошлый раунд относится только к проверенному хешу.

## 2. Подготовка и доступность источников

- [ ] Найден и полностью прочитан план. Установлены ID, тип, статус, шаги, файлы и критерии завершения. Для отсутствующего плана назван соответствующий `plan-*`.
- [ ] Сверены запись реестра, черновик `00-draft.md` при наличии, issue при доступности, связанные решения и предметные материалы. Отсутствие старого черновика само по себе не блокирует аудит.
- [ ] Проверены ссылки плана и найден относящийся к задаче контекст, который мог быть пропущен. Недоступные источники и битые ссылки отражены в отчёте.
- [ ] Прочитаны применимые инструкции `AGENTS.md` и `.agents/project/`, включая `vault.md`, `notation.md` и `overview.md` по области работы.
- [ ] Вычислен SHA-256 полных байтов плана. Указаны ветка, состояние дерева, база реализации и ограничения проверки. Учтены пользовательские изменения и файлы, отсутствующие в worktree.
- [ ] Для автоматического раунда переданы абсолютные пути, ID, хеш, номер, фокус и путь отчёта. Аудитор запущен в чистом контексте, а не имитирован автором плана.

## 3. Зоны ответственности и решения

Аудитор фиксирует доказательства и рекомендации в отчёте. Он не изменяет план, реестр, исходники или GitHub, не создаёт коммиты и не запускает вложенных агентов. Основной агент оценивает рекомендации после получения отчёта.

Основной агент может исправить в рамках авторизованной работы однозначные расхождения, подтверждённые источниками: устаревшие пути и сигнатуры, несовпадающий фрагмент «было», пропущенную зависимость шага, неверную команду или измеренное исходное значение. Формулу или знак исправляй только при достаточном подтверждении постановкой либо воспроизводимым расчётом. Запиши основание и затем проверь изменённую версию по правилам цикла. Наличие рекомендации аудитора не освобождает от проверки.

Решение пользователя требуется, когда нельзя вывести ответ из утверждённой задачи и доступных источников: изменение согласованного объёма или модели, конкурирующие физические допущения, противоречащие друг другу решения, выбор существенно различающихся вариантов с неустановленными предпочтениями. Опиши варианты, последствия и блокирует ли вопрос работу. Не превращай однозначную техническую корректировку в обязательный запрос решения. Выполняемый или реализованный план автоматически не изменяй.

## 4. Контроль фактических проверок

Команды ниже – примеры для PowerShell из корня Oil_Gas, если не указан иной каталог. Они не заменяют выбор проверок по задаче и текущие команды из `AGENTS.md`. Не запускай расчёты, сборки или регрессии до изучения `.agents/project/overview.md` и их побочных эффектов.

### План, Git и исходники

```powershell
Get-FileHash -LiteralPath '<путь-плана>' -Algorithm SHA256
git branch --show-current
git status --short
git rev-list --left-right --count <базовая-ветка>...HEAD
git ls-tree <базовая-ветка> --name-only
rg -n '<имя-функции-или-метки>' <путь>
```

Сверь указанную в плане базу с правилами направления и наличием нужных файлов, а не только с именем ветки. Числа `rev-list` описывают коммиты по обе стороны, но не доказывают совпадение конкретных файлов. При необходимости отдельно сравни файлы и проверь, что локальные изменения доступны будущему worktree. Ошибка команды или неполный статус исключают вывод об отсутствии конфликта.

### Проверки `numerical_solver`

Команды выполняются из `numerical_solver/` в предусмотренном окружении:

```powershell
.venv\Scripts\python -m pytest tests/ --collect-only -q
.venv\Scripts\python -m pytest tests/ -m "not slow" -q
.venv\Scripts\python -m pytest tests/ -q
```

Проверь, какой уровень нужен для задачи и каждого шага. Не запускай полный прогон лишь из-за наличия команды в списке. Для прототипа проверь отдельные тесты и регрессию по актуальным инструкциям. До запуска установи последствия для результатов. Для проверок импорта используй каталог, окружение и команду из плана, не добавляя скрытую подготовку. Отдельно укажи, если импорт зависит от pytest или установки пакета.

### Формулы, текст и пробы

- [ ] Сверены обозначения, метки, знаки и размерности с актуальной постановкой и `.agents/project/notation.md`.
- [ ] Для сомнительного вывода выполнена безопасная аналитическая или численная проверка, если она нужна для вывода. Записаны параметры, результат и ограничения.
- [ ] Скрипты-пробы для задачи с ID находятся в `vault/issues/<id-lowercase>/probes/`, имеют понятное имя и воспроизводимый результат, не изменяют рабочий код и пользовательские данные. Для плана без ID место отчёта и проб согласуется с его расположением без выдуманного ID.
- [ ] Для затронутого текста предусмотрен `python .claude/text-check.py <файлы>`, если этого требуют правила проекта. Сборка выполняется только по необходимости и после проверки её побочных эффектов.
- [ ] Для каждой фактически выполненной команды зафиксированы рабочий каталог, результат и значимые ограничения. Прогнозные значения не записаны как измеренные.

## 5. Мысленный прогон

- [ ] Для каждого шага учтены результаты предыдущих шагов, включая изменение одного файла несколькими шагами.
- [ ] Объекты, импорты, зависимости, тесты и конфигурации существуют к моменту использования.
- [ ] Предусмотренные команды запускаются в нужном каталоге и окружении, а ожидаемая проверка действительно обнаруживает заявленный дефект.
- [ ] Порядок переноса и удаления сохраняет необходимые файлы. Промежуточное состояние допускает обязательные проверки.
- [ ] Итоговый результат удовлетворяет исходным требованиям и критериям завершения. Ограничения явно названы.

## 6. Контроль отчёта и передачи

- [ ] Отчёт сохранён отдельным файлом текущего раунда, а предыдущий не перезаписан. Все находки имеют степень, место, свидетельство, последствие, рекомендацию и состояние.
- [ ] Вопросы с вариантами и последствиями отдельно помечены как блокирующие или неблокирующие. Непроверенные области перечислены.
- [ ] Счётчики и вердикт соответствуют перечню находок и обязательным проверкам. Трёхстрочная сводка совпадает с отчётом.
- [ ] Основной агент сверил ожидаемый путь, ID, номер, фокус, хеш и полноту отчёта, затем повторно вычислил хеш плана. При несовпадении текущая версия не считается проверенной.
- [ ] Комментарий подготовлен по [шаблонам](templates.md). При наличии issue основной агент проверяет существование комментария аудита и обновляет его в рамках вызванного процесса, не создавая дубликат. Субагент не публикует комментарии.
