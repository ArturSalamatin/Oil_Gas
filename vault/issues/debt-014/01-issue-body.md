## Описание

Расписание `time.history` в конфигах примеров записано развёрнутой формой: каждый интервал записи — отдельный объект JSON, и большинство объектов текстуально одинаковы. Краткая форма записи уже поддержана парсером (FEAT-018, #50): `{"duration": ..., "dt_out": ...}` и `{"dt": ..., "repeat": N}` разворачиваются в тот же `list[HistoryInterval]`. По решению пользователя в рамках FEAT-018 конфиги не переводились — задача осталась ровно на перевод.

Механика отбора записей (DEBT-013, #26) верна и не меняется. Задача — только форма записи в конфиге: расчёт до и после перевода должен совпадать побитово.

## Анализ вариантов решения

### Способ перевода

**Вариант 1. Ручная правка 22 файлов.**
- Плюсы: ничего лишнего в репозитории.
- Минусы: 2337 объектов; у 13a/13b/15 по 15–30 ступеней со значениями вида `0.00020833333333333335` — ошибка переноса значения вероятна и глазами не ловится. Проверка эквивалентности всё равно нужна скриптом.

**Вариант 2. Одноразовый скрипт, заменяющий только текст секции `history` (рекомендуется).**
- Суть: подряд идущие одинаковые объекты группируются в блок; в файле заменяется только фрагмент `"history": [...]`, остальной текст сохраняется побайтно. Проверка: для каждого файла `load_config` старой версии (`git show HEAD:<путь>`) и новой даёт равные `time.history`, а сырые словари без `history` равны.
- Скрипт и вывод проверки — в `vault/issues/debt-014/probes/` (не в `examples/`: после перевода он не нужен).
- Плюсы: значения переносятся без перепечатывания; diff — только секция `history`; проверка эквивалентности — тем же скриптом.
- Минусы: разбор границ секции в тексте; на 22 файлах с одинаковой структурой — небольшой риск, проверка его закрывает.

**Вариант 3. Переписать файлы целиком `json.dumps(indent=2)`.**
- Плюсы: самый короткий скрипт.
- Минусы: 3 из 22 файлов (04a, 19, 21) не совпадают с форматом `json.dumps(indent=2, ensure_ascii=False)` — у них сменится форматирование остальных секций, diff выйдет за пределы задачи.

### Какая краткая форма

**А. `{duration, dt_out}` везде (рекомендуется).** Читается как задача словами («трое суток с записью раз в час»), её уже используют 16, 17, 20 и описывает таблица README 20. Минус — у 14 длительность `31104000.0` с (360 сут) менее наглядна, чем «12 записей по 30 сут».

**Б. `{dt, repeat}` везде.** Число записей видно сразу; длительность надо перемножать.

**В. По смыслу этапа.** Повтор длинного интервала (14: 12 × 30 сут) — `{dt, repeat}`; этап с частой записью — `{duration, dt_out}`. Минус — две формы в однотипных конфигах.

### Защита от возврата к развёрнутой форме (по желанию)

Тест: ни в одном `examples/*/config.json` (кроме 18) и `configs/**/*.json` нет двух подряд одинаковых объектов `history`. Плюс — генератор вроде `rewrite_history.py` не вернёт развёрнутую форму незаметно. Минус — запрещает законный, хоть и неудобный, способ записи. Решить в плане.

## План решения

1. **Подготовка.** Число тестов (`pytest --collect-only -q`) и быстрый уровень на базе. Снимок развёрнутых `time.history` всех 22 конфигов.
2. **Тесты, читающие сырую историю.** `_run_schedule` — исключать все ключи времени (`dt`, `repeat`, `duration`, `dt_out`). `test_baseline_as_blocks` — сравнение baseline с явным списком 96 интервалов в тесте; docstring без «конфиг не меняется».
3. **Перевод конфигов** скриптом варианта 2 и проверка эквивалентности по каждому файлу.
4. **Генератор и документация.** Удалить `examples/04a_high_gas_saturation/rewrite_history.py`; поправить README 04a и 15.
5. **Верификация.** Полный уровень тестов: истории побитово те же, поэтому пороги тестов примеров не сдвигаются; ожидаемое число тестов — как на базе.
