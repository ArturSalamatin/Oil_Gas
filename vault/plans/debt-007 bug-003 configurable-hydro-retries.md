# DEBT-007 + BUG-003: вынести `max_retries` A-retry в конфиг

## Резюме

Лимит дробления шага в A-retry (`max_retries`) жёстко зашит в
`PrototypeHydroAdapter` и не выведен в JSON-конфиг. Фактическое значение
всегда 5 (максимум $2^5 = 32$ подшага), потому что `SimulatorFactory`
создаёт адаптер тремя позиционными аргументами и параметр не передаёт.
Двум разным классам задач этого лимита не хватает, и обойти его можно
только присваиванием приватного поля `sim._hydro._max_retries` изнутри
пользовательского кода.

**Задачи объединены в один план сознательно** — это одна и та же правка
кода. Различаются только первопричины расходимости и достаточные значения
лимита:

| Задача | PVT | Первопричина | Достаточно |
|---|---|---|---|
| DEBT-007 (#23) | Стендинг | $d^2B_g/dp^2 \ne 0$, линейная модель Newton неточна | 7 при одном отягчающем факторе, **9 при двух** |
| BUG-003 (#24) | таблица | $S_g \approx 0.7$: $k_{ro} = 0.30$ и $k_{rg} = 6.9\cdot10^{-4}$ одновременно, якобиан плохо обусловлен по обеим переменным | 9 (512 подшагов) |

Значение по умолчанию — **9**, покрывает оба класса.

> **Уточнение к issue #23 (получено измерением, см. § «Измерения», п. 1).**
> Открытый вопрос «7 или 9» в #23 решается **не** ссылкой на BUG-003, как
> там предполагалось, а внутри самого сценария DEBT-007. Значение 7
> достаточно, только когда действует один отягчающий фактор — либо
> сгущение сетки, либо глубокая депрессия. При обоих сразу ($N = 75$ и
> $p_{wf} = 6$ МПа — оба значения штатные для примера 03) порог равен
> ровно 9. Это снимает главную слабость обоснования: выбор default = 9
> больше не опирается на BUG-003, верификация которого заблокирована
> отсутствием примера 04a (FEAT-015, #20).

**1. Порог достаточности на сценарии DEBT-007 — три конфигурации.**

Реестр (правка пользователя от 2026-09-08) указывает: отдельный конфиг
создавать не нужно, `examples/03_standing_corey/config.json` — ровно

достаточно опустить `history[0].p_wf` с 8 до 6 МПа. Это оказалось важнее

отягчающих фактора, и порог зависит от того, сколько их действует.**

| # | конфигурация | 5 | 6 | 7 | 8 | 9 | $p[0]$ при успехе |
|---|---|---|---|---|---|---|---|
| A | $N = 50$ (штатн.), $p_{wf} = 6$ МПа — формулировка DEBT-007 | ✗ | ✗ | **✓** | ✓ | ✓ | 6.188 МПа |
| B | $N = 75$, $p_{wf} = 8$ МПа (штатн.) — README примера 03 | ✗ | ✗ | **✓** | ✓ | ✓ | 8.093 МПа |

Выводы:

- **Порог 7 подтверждён** для A и B по отдельности — ровно как заявлено в
  DEBT-007 (128 подшагов) и в README примера 03.
- **Порог 9 достигается на чистом Standing-PVT**, без всякой высокой
  $S_g$: конфигурация C собрана из двух штатных значений самого примера
  03. Это и есть независимое обоснование `default = 9`.
- Результат от лимита не зависит: в A давление совпадает при 7, 8, 9, 10;
  в C — при 9 и 11. Лимит определяет достижимость решения, а не решение.

**Почему это меняет план.** В первой редакции обоснование `default = 9`
опиралось только на BUG-003, чья верификация заблокирована отсутствием
примера 04a. Теперь 9 доказывается воспроизводимо, на файле, который уже
в репозитории.

**2. Цена для уже сходящихся расчётов** — пример 03, штатная сетка

## Целевое состояние

1. `max_retries` — поле `NumericsConfig`, читается из JSON-секции
   `numerics`, передаётся Factory в конструктор адаптера.
2. Значение по умолчанию 9 — измеренный порог примера 03 при двух
   отягчающих факторах (§ «Измерения», п. 1, конфигурация C); столько же
   требует BUG-003.
3. Валидация: целое, $0 \le max\_retries \le 20$.
4. Текст `RuntimeError` называет параметр конфига и обе известные
   первопричины; вводящая в заблуждение подсказка «Уменьшите
   dt_integration» убрана — для BUG-003 она доказанно не помогает.
5. README примеров 03 и 10 описывают настройку через конфиг, а не через
   уменьшение `dt_integration`.

## Границы изменений — что НЕ трогать

- **Механизм A-retry** (`prototype_adapter.py:66-113`) — реализован верно,
  дробление стартует с состояния предыдущего подшага. Меняется только
  верхняя граница цикла через уже существующее поле `self._max_retries`.
- **Семантика `dt_min`** — вариант «дробить, пока `dt_sub > dt_min`»
  (вариант 3 в #23) отвергнут: `dt_min` относится к внешнему шагу
  интегрирования, переопределять его смысл в этой задаче нельзя.

  ⚠️ Уточнение аудита (раунд 4): grep показал, что `dt_min` и `dt_max`
  **вообще нигде не читаются** — они мёртвые, как `grid.type` и
  `output.format` из DEBT-008. При этом `P8-формат-ввода-json.md:188`
  обещает «`dt_min`, `dt_max` — для A-retry в Adapter». Отсюда и
  правдоподобие варианта 3: поле выглядит предназначенным ровно для
  этого, хотя не подключено. **Это не задача данного плана** —
  зафиксировано в DEBT-008 (запись дополнена 2026-09-08). Здесь
  `dt_min`/`dt_max` не трогать: правка их семантики смешала бы две
  задачи в одном PR.
- **Конфиги примеров** — `dt_integration = 3600` во всех десяти, обходной
  путь `= 600` нигде в JSON не зашит (проверено grep), удалять нечего.
- **`grid.type`, `output.format`** — мёртвые поля, это DEBT-008, не сюда.
- Существующие сигнатуры `PrototypeHydroAdapter.__init__` и
  `SimulatorFactory.from_config` остаются обратно совместимыми: новый
  параметр — с значением по умолчанию.

## Шаг 1: Воспроизвести отказ

**Цель:** убедиться, что дефект живой, до внесения правок.
**Файлы:** ничего не меняется.

**Контекст:**
`PrototypeHydroAdapter.solve` (`prototype_adapter.py:66`) перебирает
`attempt` в `range(self._max_retries + 1)`, `n_sub = 2**attempt`. При
`_max_retries = 5` максимум 32 подшага, дальше `raise RuntimeError`
(строки 115–118).

**Что сделать:**

Создать `numerical_solver/examples/03_standing_corey/check_retries.py`.
Скрипт покрывает все три конфигурации из § «Измерения» — важна именно
конфигурация C, она обосновывает значение по умолчанию 9. Конфиг берётся
готовый (`examples/03_standing_corey/config.json`), депрессия и сетка
задаются программно; создавать новый JSON не нужно (правка реестра
2026-09-08).

```python
import sys, time
from pathlib import Path
_ROOT = Path(__file__).parent.parent.parent

    умолчанию: он воспроизводим на конфиге, уже лежащем в репозитории,
    в отличие от сценария BUG-003 (пример 04a ещё не создан, FEAT-015).
    """

    def _config(self):
        """Пример 03 с обоими отягчающими факторами."""
        config = load_config(EXAMPLE_03)
        config.grid.N = 75                      # фактор 1: сгущение сетки
        config.time.history[0].p_wf = 6e6       # фактор 2: глубокая депрессия
        return config

    def test_converges_at_default_limit(self):
        """При штатном max_retries = 9 расчёт проходит без правки dt."""
        simulator, initial = SimulatorFactory.from_config(self._config())
        history = simulator.run(initial)
        state = history.states[-1]

        # Результат бит-в-бит устойчив по лимиту (проверено при аудите:
        # mr = 9, 10, 12 дают одно и то же), поэтому фиксируем жёстко —
        # это регрессионная привязка, а не проверка «примерно сошлось».
        assert state.p[0] == pytest.approx(6.126106e6, rel=1e-4)

        # Сценарий обязан быть двухфазным: p_wf = 6 МПа ниже p_b = 9.43 МПа,
        # газ выделяется. Без этого тест проверял бы однофазный режим,
        # где лимит дробления ни при чём.
        assert state.Sg.max() == pytest.approx(0.0996, rel=1e-2)

        # Расчёт дошёл до конца истории, а не оборвался раньше
        assert history.n_saved == 73

    def test_fails_one_below_threshold(self):
        """При max_retries = 8 тот же расчёт падает — порог равен 9.

        Тест фиксирует, что значение по умолчанию не завышено произвольно:
        уменьшение лимита на единицу возвращает отказ. Без этой проверки
        default = 9 выглядел бы догадкой.
        """
        config = self._config()
        config.numerics.max_retries = 8
        simulator, initial = SimulatorFactory.from_config(config)

        with pytest.raises(RuntimeError, match="не сошёлся"):
            simulator.run(initial)
```
