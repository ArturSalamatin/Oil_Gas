## 1. Суть задачи

### Что не так

`numerical_solver/gpn_multiphase_solver/energy/tridiag.py:281-284`:

```python
# Контур
if G_o[N] >= 0:
    R_conv[N] = G_o[N] * Rs[N - 1]
else:
    R_conv[N] = G_o[N] * Rs_old[-1]
```

`Rs` и `Rs_old` — массивы **по ячейкам**, размера $N$:
- `Rs = hydro_result.state.Rs` (`tridiag.py:46`) — новый слой $n+1$;
- `Rs_old = state_prev.Rs` (`tridiag.py:50`) — старый слой $n$.

Значит `Rs_old[-1]` — это **ячейка $j = N-1$ на старом слое**, а не контурное значение. Обе ветви указывают на одну и ту же ячейку и различаются лишь временным слоем.

### Как должно быть

Оператор против потока (eq. `upstream_operator`, `problem_statement.tex:1218-1226`) на контурной грани $f = N$:

$$\langle G^o R_s\rangle_{N+\frac12} = (G^o_N)^+\,R_{s,N-1} + (G^o_N)^-\,R_s\big|_{\text{ext}}, \qquad R_s\big|_{\text{ext}} = R_s^0 .$$

Ветви различаются тем, **какая величина** стоит выше по потоку:
- отток ($G^o_N \geqslant 0$, поток наружу) — последняя внутренняя ячейка $N-1$;
- приток ($G^o_N < 0$, поток к скважине) — **граничное условие $R_s^0$**.

Дефект — сторона грани. Несогласованность временных слоёв вторична: слой должен быть один, новый.

### Конвенция знаков (напоминание)

Положительное направление — **от скважины**, в сторону роста $r$. Поэтому при типичном режиме отбора приток с контура даёт $G^o[N] < 0$, и работает именно дефектная ветвь. См. `vault/knowledge/decisions/конвенции-знаков.md`.

### Требование постановки

`numerical_solver/doc/problem_statement.tex`:

| Место | Содержание |
|---|---|
| стр. 684, eq. `bc_Sg_ext` | $S_g(R_{ext},t) = 0$, $R_s(R_{ext},t) = R_s^0$ — состав притока постоянен во времени |
| стр. 1457–1460 | «источниковые члены на граничных гранях вычисляются по тем же формулам, что и на внутренних; значения за границей заменяются граничными условиями» |
| стр. 1469–1472 | «на контуре (правая грань ячейки $j = N{-}1$): давление $p_{\text{конт}} = p_{\text{пл}}$, $R_s = R_s^0$ (приток с контура имеет известный состав)» |
| стр. 1454–1455, eq. `bc_flux_ext_gas` | поток газового компонента через контур обусловлен растворённым газом с составом $R_s^0$ |

Свободы выбора нет: на контуре подставляется $R_s^0$.

### Гидро-часть уже делает правильно

`gpn_multiphase_solver/fluxes.py:127-142` — эталон на **той же грани**:

```python
if dp_e >= 0:
    Rs_up_e = Rs[N - 1]      # отток: upstream = ячейка N-1
else:
    Rs_up_e = bc.Rs_ext      # приток: upstream = контур
```

Дефект — рассогласование двух модулей на одной грани, а не вопрос интерпретации.

### Почему это долг, а не текущая ошибка

Измерено по всем десяти примерам: $\max|R_s^{old}[-1] - R_s[-1]| \le 7.1\cdot10^{-15}$, вклад в энергию $\le 3.3\cdot10^{-8}$ Дж при дегазационном члене $\sim 10^{9}$ Дж. Втекание через контур есть на всех 72 шагах во всех примерах, но контурная ячейка всюду насыщена ($\min p_{ext} \approx 1.99\cdot10^7$ Па — вдвое выше $p_b$), поэтому $R_{s,N-1} = R_s^0$ и совпадают **все три** величины.

Как только $p_{N-1} < p_b$ (больший $t_{end}$, меньший $r_e$, большая депрессия) — в ячейке $N-1$ начнётся разгазирование, $R_{s,N-1} < R_s^0$, и при втекании схема внесёт в контур состав дегазированной нефти вместо состава притока. Ошибка $O(1)$ по величине $R_s^0 - R_{s,N-1}$, а не $O(\Delta t)$. Физически — фиктивный источник растворённого газа на контуре и, через $-L\,\dot m$, фиктивный тепловой источник.

### Про порядок аппроксимации (важно не переусложнить)

В ветви оттока участвует **ровно одна** ячейка $N-1$. Пара «предпоследняя + последняя» ($N-2$, $N-1$) в схеме первого порядка не появляется — шаблон против потока одноточечный. Двухточечная реконструкция потребовалась бы только при переходе на второй порядок (MUSCL), которого в схеме нет и который в эту задачу не входит.

### Про забой — дыры нет

`tridiag.py:279`: `R_conv[0] = G_o[0] * Rs[0]` — без ветвления, и это **корректно**. При отборе ($G^o[0] < 0$) upstream — ячейка 0, что соответствует `problem_statement.tex:1465-1468`. При обратном знаке (закачка) ячейка 0 всё равно остаётся единственной соседней: за забоем нет пластовой области с заданным составом, в отличие от контура. Отдельного ГУ для $R_s$ на забое постановка не задаёт (стр. 690–694: «на забое условия для $S_g$ и $R_s$ **не задаются**»).

**Вывод:** в issue #29 п. 6 этапа 2 сформулирован как вопрос — здесь он закрыт: **забой не трогаем**. Отдельную запись в реестр не заводим.

## 3. Целевое состояние

```python
# Контур: upstream зависит от направления потока
if G_o[N] >= 0:
    # Отток из пласта наружу: выше по потоку — последняя ячейка
    R_conv[N] = G_o[N] * Rs[N - 1]
else:
    # Приток с контура: выше по потоку — контур, состав задан ГУ (eq. bc_Sg_ext)
    R_conv[N] = G_o[N] * Rs_ext
```

Энергетический модуль получает доступ к граничным условиям целиком, как это уже сделано у `HydroSolver.solve(state, dt, bc)` (`hydro/base.py:31`).

## 4. Варианты решения

### Вариант 1 — добавить скаляр `Rs_ext` рядом с `T_ext`

**Суть.** `solve(..., dt, T_ext, Rs_ext, collect=None)`; `compute_degassing(..., N, Rs_ext)`.

**Изменения.** `energy/base.py`, `energy/tridiag.py`, `simulator.py`, 2 прямых вызова `compute_degassing` в тестах, `examples/verify_balance_vs_solver.py`.

**Плюсы.** Диффузия минимальна. Если `Rs_ext` добавить со значением по умолчанию **после** `T_ext`, то 14 тестовых вызовов `solve(...)` с позиционным `T_ext` не ломаются.

**Минусы.** Значение по умолчанию для `Rs_ext` — это ровно та дыра, из-за которой возник дефект: при отсутствии аргумента придётся снова брать что-то не то. Без значения по умолчанию — правятся все 14 вызовов, и преимущество варианта исчезает. Каждое следующее ГУ снова расширяет сигнатуру.

**Риск.** Умолчание `Rs_ext=None` с fallback на `Rs[N-1]` воспроизведёт дефект в тихой форме.

**Трудоёмкость.** ~6 файлов, ~25 строк.

### Вариант 2 — передавать `bc` целиком ✅ выбран

**Суть.** `solve(hydro_result, state_prev, dt, bc, collect=None)`; внутри `T_ext = bc.T_ext`, `Rs_ext = bc.Rs_ext`.

**Изменения.** `energy/base.py:27-30`, `energy/tridiag.py:37-40, 261, 75-76, 284`, `simulator.py:163-165`, 14 вызовов `solve(...)` в тестах, 2 вызова `compute_degassing(...)` в тестах, `examples/verify_balance_vs_solver.py:56, 79-82`.

**Плюсы.**
- Устраняет **первопричину**: у энергетического модуля не было доступа к ГУ, и на месте недостающего значения оказалась ближайшая доступная величина.
- Выравнивает контракты решателей: `HydroSolver.solve(state, dt, bc)` уже принимает `bc` (`hydro/base.py:31`, `tests/test_hydro.py:91`).
- Будущие ГУ не меняют сигнатуру.
- Нет соблазна ввести опасное значение по умолчанию.

**Минусы.** Меняет контракт ABC шире; правит 14 тестовых вызовов (механически); больший diff.

**Риск.** Пропустить вызов → `AttributeError` или `TypeError` на этапе прогона. Ловится тестами сразу, молчаливой регрессии не даёт — кроме `examples/verify_balance_vs_solver.py`, который **не покрыт pytest** (см. подводный камень П-1).

**Трудоёмкость.** ~7 файлов, ~45 строк.

### Выбор

**Вариант 2.** Критерий «минимальность diff» здесь уступает критерию «устранение первопричины»: вариант 1 в безопасной форме (без умолчания) даёт почти тот же объём правки, а в компактной форме (с умолчанием) воспроизводит дефект. Дополнительный довод — согласование с уже существующим контрактом `HydroSolver`.

```python
    def test_inflow_uses_boundary_composition(self):
        """Приток с контура (G_o < 0): upstream = ГУ, а не ячейка N-1.

        Физика: через контур поступает нефть с составом Rs^0
        (eq. bc_Sg_ext, problem_statement.tex:1469-1472). Если в ячейке
        N-1 началось разгазирование (Rs < Rs^0), схема обязана взять
        на контурной грани состав ПРИТОКА, а не обеднённый состав
        последней ячейки. DEBT-009.
        """
        N_cells = 3
        grid = LogRadialGrid(R_WELL, R_EXT, H, N_cells, K_PERM)
        pvt = _make_pvt(L_degas=168000.0)
        solver = TridiagEnergySolver(grid, pvt, _rock())

        So = np.ones(N_cells)
        Sg = np.zeros(N_cells)
        # Ячейка N-1 обеднена газом: разгазирование у контура
        Rs = np.full(N_cells, RS0)
        Rs[-1] = 0.8 * RS0
        Rs_old = Rs.copy()          # временная часть нулевая: mdot_time = 0
        Bo = pvt.Bo(np.full(N_cells, P0), Rs)
        G_o = np.full(N_cells + 1, -0.01)   # втекание на всех гранях
        L = np.full(N_cells, 168000.0)

        Q_deg = solver.compute_degassing(
            So, Sg, Rs, Rs_old, Bo, G_o, L, DT, N_cells, RS0)

        # Поток на контурной грани должен быть G_o[N]*RS0.
        # Восстанавливаем R_conv[N] из Q_deg последней ячейки:
        #   mdot_time = 0  =>  Q_deg[-1] = -L * mdot_conv[-1]
        #   mdot_conv[-1] = -rho_g_std * (R_conv[N] - R_conv[N-1]) / V[-1]
        V = grid.volumes
        rho_g_std = pvt.rho_g_std
        # Внутренняя грань N-1: upstream при G_o < 0 — ячейка N-1
        R_conv_inner = G_o[N_cells - 1] * Rs[N_cells - 1]
        R_conv_ext_expected = G_o[N_cells] * RS0

        mdot_conv_expected = -rho_g_std * (
            R_conv_ext_expected - R_conv_inner) / V[-1]
        Q_deg_expected = -L[-1] * mdot_conv_expected

        np.testing.assert_allclose(Q_deg[-1], Q_deg_expected, rtol=1e-12)

        # Контрольная проверка: со старым (дефектным) поведением
        # на контуре стоял бы Rs[N-1] = 0.8*RS0, и Q_deg[-1] отличался бы.
        R_conv_ext_buggy = G_o[N_cells] * Rs[-1]
        mdot_conv_buggy = -rho_g_std * (R_conv_ext_buggy - R_conv_inner) / V[-1]
        Q_deg_buggy = -L[-1] * mdot_conv_buggy
        assert not np.isclose(Q_deg_expected, Q_deg_buggy), \
            "тест вырожден: дефектная и correct-ветви дают одно значение"
```

| `Q_deg_expected` (по ГУ, `RS0`) | $-1.847514\cdot10^{-1}$ |
| `Q_deg_buggy` (по ячейке $N-1$) | $0.0$ |
| Совпадает факт с `buggy`? | **True** |

Формула восстановления верна, включая `R_conv_inner` для внутренней грани (сверено с кодом: $-4.0\cdot10^{-1}$ в обоих случаях). **Тест падает на дефектном коде — требование плана выполнимо.**

#### ⚠️ Уменьшать `R_ext` бесполезно — установлено аудитом

Первая редакция плана предлагала «уменьшить $r_e$». Это **не работает**, и причина структурная, а не физическая. На логарифмической сетке центр последней ячейки всегда стоит на одной и той же доле ln-пути до контура, независимо от $R_{ext}$:

| $R_{ext}$, м | центр $r_{N-1}$, м | доля ln-пути | $(p_{ext}-p_{N-1})/(p_{ext}-p_{wf})$ |
|---|---|---|---|
| 50 | 47.11 | 0.99041 | 0.0096 |
| 10 | 9.563 | 0.99031 | 0.0097 |
| 5 | 4.813 | 0.99026 | 0.0097 |

Доля инвариантна ⇒ $p_{N-1}$ отстоит от $p_{ext}$ на ~1 % перепада при любой геометрии. Прямая проверка: при $R_{ext} = 50, 10, 5$ м результат `min p[N-1] = 1.9881e+07` **не меняется вовсе**; при $R_{ext} = 3$ и $2$ м прогон падает с `RuntimeError: HydroSolver не сошёлся после 512 подшагов`.

## 9. Обнаруженные проблемы

### НОВЫЙ БАГ: `verify_balance_vs_solver.py` сломан в текущем `HEAD`

**Обнаружено при подготовке плана, 2026-09-10, на `52e4588`.** Это не риск и не гипотеза — воспроизведено запуском:

```
TypeError: run_instrumented.<locals>.patched() got an unexpected keyword argument 'collect'
```

`simulator.py:129` создаёт `EnergyBalanceAccumulator` всегда и передаёт `collect=balance` (стр. 163-165); monkey-patch в скрипте (стр. 56) объявлен без `collect`. Диагностический инструмент, которым проверяют самосогласованность схемы (тот самый, что использовался при расследовании BUG-004), **нерабочий и об этом никто не знал** — он не покрыт pytest.

**Решение:** чинится в шаге 4 настоящего плана попутно, поскольку тот же шаг всё равно правит эту функцию. Отдельная запись BUG **не заводится** — дефект закрывается здесь же; факт фиксируется в отчёте по DEBT-009 и в комментарии к issue #29.

### Предложение на будущее (не в этой задаче)

Скрипт дублирует внутренности `TridiagEnergySolver.solve` через monkey-patch. Любое изменение сигнатуры или порядка подшагов ломает его молча — что и произошло. Это тот же класс проблемы, что породил BUG-004 (расхождение диагностики со схемой), и прямо родственно DEBT-013 (накопитель баланса внутри решателя вместо постобработки).

**Предложение:** завести запись DEBT о переводе скрипта на штатный `EnergyBalanceAccumulator` вместо monkey-patch, либо о покрытии его smoke-тестом (`pytest -m slow`, один пример, проверка что отрабатывает без исключения). **Регистрировать после завершения DEBT-009** — чтобы не расширять текущую задачу.
