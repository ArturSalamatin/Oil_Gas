# /merge — влитие ветки задачи в базовую ветку

Аргумент: `$ARGUMENTS` — идентификатор задачи (`BUG-001`, `DEBT-003`, `FEAT-005`, `VAL-002`). Без аргумента — задача, реализованная `/implement` в этой сессии.

Запускается только по слову пользователя: `/merge <ID>` или «мерж» после `/implement` в той же сессии — процедура одна.

Результат: ветка задачи влита в базовую (`--no-ff`), итог мержа проверен, worktree удалён, **ветка задачи сохранена**, vault отмечает «влит <hash>», GitHub issue закрыт. Push — пользователь.

Обозначения — как в `/implement` («Схема работы»): `<КОРЕНЬ>` — основной каталог `D:\Lessons\Grants\2026\GPN\Oil_Gas`, `<W>` — `<КОРЕНЬ>\.worktrees\<id-lowercase>`, `<PY>` — `<КОРЕНЬ>\numerical_solver\.venv\Scripts\python.exe`. Мерж и коммиты — в основном каталоге, на базовой ветке. Переменные PowerShell не переживают отдельный вызов инструмента — задавать в той же команде, что и использование.

## Фаза 1: Подготовка

### 1.1. Найти задачу

1. План: `<W>\vault\plans\<id-lowercase>*` (версия ветки задачи), если worktree есть; иначе `<КОРЕНЬ>\vault\plans\<id-lowercase>*`
2. Из frontmatter: `branch`, `github`, `status`, `worktree`. Базовая ветка — секция плана «Ветка» или таблица в шапке `/implement`
3. `status: реализован` — в любой из двух копий плана (задачи, начатые до worktree-правил `/implement`, вели vault в основном каталоге). Иначе — СТОП: реализация не завершена; сообщи, не продолжай без подтверждения

### 1.2. Проверки до мержа

1. **Основной каталог на базовой ветке:** `git -C <КОРЕНЬ> branch --show-current`. Иначе — СТОП.
2. **Ветка не влита:** `git -C <КОРЕНЬ> log --oneline <база>..<branch>` непуст. Пуст — ветка уже в базе: СТОП, сообщи (могут оставаться фазы 4–6 — по решению пользователя).
3. **Worktree чистый:** `git -C <W> status --porcelain` пуст (игнорируемые файлы не в счёт). Непуст — СТОП, покажи файлы: незакоммиченная работа, решает пользователь.
4. **Нет пересечения с незакоммиченными правками основного каталога:**
   ```powershell
   git -C <КОРЕНЬ> diff --name-only <база>...<branch>   # что меняет ветка
   git -C <КОРЕНЬ> status --porcelain                    # что не закоммичено в основном каталоге
   ```
   Пересечение непусто (включая неотслеживаемые `??`, которые ветка добавляет) — СТОП, перечисли файлы: мерж откажет («local changes would be overwritten») или смешает чужие правки с влитием. Обычно — дождаться коммита параллельной сессии; решает пользователь.
5. **Ушла ли база вперёд по коду с момента ветвления:**
   ```powershell
   $fork = git -C <КОРЕНЬ> merge-base <база> <branch>; git -C <КОРЕНЬ> diff --name-only $fork <база> -- numerical_solver/
   ```
   Непусто — итог мержа никем не проверен: фаза 3 обязательна. Пусто — код итога мержа совпадает с проверенным на ветке, фаза 3 не нужна.
6. **Сообщи в чат перед мержем:** ветка, база, число коммитов ветки, точка ветвления, нужна ли фаза 3.

## Фаза 2: Мерж

```powershell
git -C <КОРЕНЬ> merge --no-ff --no-edit <branch>
```

Сообщение по умолчанию — `Merge branch '<branch>' into <база>`, как у прежних влитий.

**Конфликт:**
- **Только в файлах `vault/`** — разрешить самому. В реестрах, `index.md`, планах оставить обе стороны: новые записи базы и статус с ветки. Строку, которую правили обе стороны, — свести, не выбрасывая содержание ни одной. Показать пользователю итог по каждому файлу (`git -C <КОРЕНЬ> diff -- <файл>`) **до коммита**; после согласия — `git -C <КОРЕНЬ> add -- <файлы>` и `git -C <КОРЕНЬ> commit --no-edit`.
- **Хоть один конфликт вне `vault/`** — СТОП. Мерж оставить как есть, перечислить файлы, предложить: разрешить вместе или `git merge --abort`. Решает пользователь; `--abort`, `reset`, `checkout --` — только с его разрешения.

Запомни: `<hash>` = `git -C <КОРЕНЬ> rev-parse --short HEAD`, родитель со стороны базы — `git -C <КОРЕНЬ> rev-parse --short HEAD^1`.

## Фаза 3: Проверка итога мержа

Только если база ушла вперёд по коду (1.2 п. 5).

Проверять в worktree задачи, а не в основном каталоге: в основном каталоге могут лежать незакоммиченные правки параллельных сессий, и прогон проверил бы не итог мержа.

```powershell
git -C <W> switch --detach <hash>
cd <W>\numerical_solver; <PY> -m pytest tests/ -m "not slow" -q
```

Если и ветка, и база с момента ветвления меняли `HydroSolverPrototype/` — ещё тесты прототипа (команды — шапка `/implement`); регрессию прототипа — по решению пользователя.

Красный — СТОП: мерж уже в базовой ветке (локально, не запушен). Сообщи: какие тесты, зелёные ли они по отдельности на ветке и на базе. Варианты — исправление новой задачей или откат мержа; откат (`git revert`, `git reset`) — только по решению пользователя. Worktree не удалять — он нужен для разбора.

## Фаза 4: Удаление worktree

```powershell
git -C <КОРЕНЬ> worktree remove .worktrees/<id-lowercase>
git -C <КОРЕНЬ> worktree prune
git -C <КОРЕНЬ> branch --list <branch>   # ветка на месте
```

- Без `--force`. Отказ — покажи причину и жди пользователя:
  - неотслеживаемые или изменённые файлы — что это, решает пользователь;
  - Windows: файл занят процессом (терминал VS Code в каталоге worktree, python, открытый в редакторе файл) — попроси закрыть, повтори.
- Игнорируемые файлы worktree (истории `.npz` и графики проб, `OUTPUT/` прототипа, `__pycache__`, `.pytest_cache`) удаляются вместе с ним — они воспроизводимы.
- **Ветку задачи не удалять** (`git branch -d` не выполнять): она остаётся для истории и ссылок из vault.
- `ExitWorktree` не использовать: он удаляет ветку.
- Worktree у задачи не было — фазу пропустить.

## Фаза 5: Отметка «влит» в vault

В основном каталоге, на базовой ветке. После мержа в базе — vault с ветки задачи.

1. **План:** во frontmatter — `merged: <hash> (<дата>)`; в `worktree:` дописать «; удалён после влития».
2. **Реестр**, запись задачи, строка «**Статус:**»: «не влит — ветка … в `.worktrees/<id>`» → «влит <дата> (`<hash>`, поверх `<родитель>`, <без конфликтов | конфликты в vault: <файлы>, разрешены>; <итог мержа: быстрый уровень N passed | база по коду не менялась>; worktree удалён, ветка оставлена) — ветка `<branch>` …». Образец — запись DEBT-039.
3. **`vault/00-home/index.md`** — строка плана задачи, если в ней есть статус.
4. **Коммит** с явными путями (правило 6 `/implement`; реестр и `index.md` — общие файлы, коммитятся целиком):
   ```powershell
   git -C <КОРЕНЬ> add -- <файлы>
   git -C <КОРЕНЬ> commit -m "vault: <ID> влит (<hash>)" -- <файлы>
   ```

## Фаза 6: Закрыть GitHub issue

Сам issue не закроется: ветка GitHub по умолчанию — `master`, влитие локальное.

```powershell
gh issue close <N> --repo ArturSalamatin/Oil_Gas --comment 'Влито в <база>: <hash> (<дата>). Ветка <branch> сохранена.'
```

Одинарные кавычки: в двойных PowerShell считает обратную кавычку экранированием.
