# Работа в worktree и контроль состояния

Эта инструкция дополняет `implement/SKILL.md`. Выполняй Git-команды в соответствующем каталоге и указывай явные пути. Не используй `git add .`, `git add -A`, общий `git stash`, принудительное удаление, `reset` или восстановление чужих файлов без полномочий.

## 1. Проверка базы и зависимостей

1. Установи корень основного каталога, базовую ветку, имя ветки задачи и абсолютный путь `.worktrees/<id-lowercase>`. Для задач `numerical_solver` база – `numerical_scheme/implementation`. Для метода моментов – `master`. Для vault и LaTeX без кода – `numerical_scheme/implementation`.
2. Проверь активную ветку основного каталога и наличие затронутого рабочего каталога в дереве предполагаемой базы. Предварительный коммит нельзя создавать в другой ветке. Если основную копию нельзя безопасно использовать для нужной базы, останови подготовку и сообщи фактическое состояние.
3. Для каждого блокирующего предшественника проверь запись реестра и доступность его результата в базе. При необходимости проверь `git merge-base --is-ancestor <ветка-зависимости> <база>`. Невлитая блокирующая задача не становится выполненной от того, что её ветка существует.
4. Сверь статус, индекс, локальные ветки и `git worktree list`. Существующая ветка или каталог требуют проверки на возобновление, а не создания ещё одной копии. Проверь, что `.worktrees/` исключён из отслеживания. Не меняй глобальные настройки пользователя.

## 2. Предварительный коммит в базе

Раздели фактические изменения на группы:

| Группа | Действие |
|---|---|
| План и подготовленные материалы текущей задачи | Включи по конкретным путям, если они необходимы реализации. |
| Общие файлы vault – `vault/roadmap/*.md`, `vault/00-home/index.md` | Предусмотренный проектом предварительный коммит включает такие файлы целиком. Проверь содержимое и не подменяй его более старой копией. |
| Подготовленные вспомогательные файлы вне vault | При необходимости отдельный коммит, поскольку vault и код не смешиваются. |
| Незакоммиченный код текущей задачи в основном каталоге | Не переноси его молча в базу и не считай доступным в worktree. Выясни происхождение и безопасный порядок работы. |
| Чужие планы, черновики, заметки и код | Не включай автоматически. Ссылка общего реестра на чужой черновик сама по себе не требует включать его в коммит. |

До подготовки коммита проверь индекс. Указывай пути и при добавлении, и при коммите, чтобы не захватить заранее индексированные материалы другой сессии. Сообщи хеш и состав коммита. Не меняй проверенные байты плана до сверки отчёта аудита. Для статуса начала используй реестр или отдельную заметку, чтобы не аннулировать проверенный хеш только служебной правкой.

## 3. Создание и использование worktree

Создай worktree от проверенного состояния базы после предварительного коммита. Убедись, что `HEAD`, имя ветки и план соответствуют ожидаемым. Код, тесты, документацию и материалы текущей реализации изменяй в worktree задачи. Регистрацию новых задач выполняй в основном vault на базе согласно `draft` и контракту `implement`.

Работай с абсолютными путями или явно указывай `git -C <worktree>` и рабочий каталог команды. Одинаковый относительный путь в основном каталоге и worktree обозначает разные файлы. Зафиксируй исходный статус основного каталога по затрагиваемым путям и сверяй его при обнаружении неожиданных изменений. Чужие изменения не исправляй и не переноси.

## 4. Среда и исходные проверки

До запуска прочитай `.agents/project/overview.md`. Для `numerical_solver` используй Python существующего окружения основного каталога и запускай pytest из `numerical_solver/` worktree. Запиши исходное число собранных тестов и результат быстрого уровня. Если быстрый уровень исходного дерева не проходит, не объявляй базу зелёной: выясни причину до реализации. Для изменений прототипа дополнительно установи его исходный результат тестов и быстрой регрессии по действующей инструкции.

Скрипты вне pytest могут импортировать установленные в режиме разработки пакеты основного каталога. Для них задай пути к пакетам из worktree в той же среде запуска и проверь `__file__` обоих импортов до расчёта. Не делай вывод о worktree по успешному запуску, если импорт фактически пришёл из основного каталога. Не меняй постоянную конфигурацию окружения без необходимости.

Пробы запускай из копии worktree и сохраняй воспроизводимые скрипты в `vault/issues/<id-lowercase>/probes/`. Записывай параметры и результат. Игнорируемые истории, рисунки и выходы регрессии не входят в Git и могут исчезнуть при удалении worktree. Нужные материалы заранее сохраняй в согласованном месте.

## 5. Возобновление и приостановка

При возобновлении сопоставь план в worktree, статус задачи, ветку, коммиты, незакоммиченные файлы и сохранённые результаты проверок. Определи последний завершённый шаг и проверь, какие результаты устарели из-за последующих изменений. Не повторяй автоматическое создание ветки и не перезаписывай незавершённую работу.

При регрессии сохрани вывод, локализуй её, исправь причину и повтори сначала затронутые тесты, затем требуемый уровень. Не записывай сломанный шаг как завершённый. Если продолжить нельзя, оставь незакоммиченные изменения в worktree, сообщи фактическое состояние, причину и варианты дальнейшей работы. Запрещено уничтожать или прятать изменения через общий stash ради продолжения.
