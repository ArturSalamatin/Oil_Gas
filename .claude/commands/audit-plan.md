# /audit-plan — аудит плана перед реализацией

Аргумент: `$ARGUMENTS` — идентификатор задачи (например `BUG-007`, `FEAT-003`, `VAL-001`, `DEBT-005`).

Результат: план проверен по 7 измерениям, найденные проблемы исправлены в файле плана, пользователю выдан отчёт.

**Когда запускать:** после `/plan-fix`, `/plan-improve`, `/plan-feature`, `/plan-validate` — перед `/implement`.

**Принцип:** команда — скептик, а не подтверждатель. Задача — найти то, что сломает реализацию.

**Рабочая директория зависит от направления задачи.** Определи её до начала работы:

| Направление | Каталог | Пакет / исходники | Тесты | Конфиги | Базовая ветка |
|---|---|---|---|---|---|
| **PDE-солвер** (текущая разработка) | `numerical_solver/` | `gpn_multiphase_solver/` | `tests/` | `configs/` | `numerical_scheme/implementation` |
| **Метод моментов** (завершён, только справка) | `method_of_moments/` | `src/` | `tests/` | `configs/` | `master` |

Все пути в планах и отчётах — от корня проекта (например `numerical_solver/gpn_multiphase_solver/factory.py`).

Команды pytest — из соответствующего каталога:
```powershell
cd numerical_solver ; .venv\Scripts\python -m pytest tests/ -v
```

⚠️ Для `numerical_solver` тестам нужен прототип `radial_blackoil` — его подключает `tests/conftest.py` через `sys.path`. Скрипты вне pytest должны делать это сами.

По умолчанию новые задачи относятся к `numerical_solver/`. Если задача явно про метод моментов — использовать вторую строку таблицы.

## Фаза 1: Загрузка плана

### 1.1. Найти план

```
ls vault/plans/<id-lowercase>*
```

Если план не найден — СТОП:
```
План для <ID> не найден. Сначала создай план:
- BUG → /plan-fix <ID>
- DEBT → /plan-improve <ID>
- FEAT → /plan-feature <ID>
- VAL → /plan-validate <ID>
```

### 1.2. Проверить статус

Из frontmatter:
- `готов к реализации` → аудит уместен, продолжай
- `в процессе` → предупреди: «План уже в реализации. Аудит может привести к правкам, конфликтующим с текущей работой. Продолжить?»
- `реализован` / `отменён` → СТОП, сообщи: «План в статусе <статус>, аудит не нужен»

Проверь поле `audit:` в frontmatter. Если аудит уже проводился — сообщи: «План уже проходил аудит <дата>. Провести повторный?» При повторном аудите — перезаписать поле `audit:`, не дублировать; добавить `round: N`.

**Повторный аудит не повторяет предыдущий.** Чистый результат прошлого раунда не означает, что план чист — он означает, что найдено всё, что видно с прежнего ракурса. Смени угол:

| Раунд | Фокус |
|---|---|
| 1 | Предметная суть: формулы, параметры, физика, корректность анализа |
| 2 | Реализуемость: API, сигнатуры, порядок шагов, тесты |
| 3 | Инфраструктура: установка и разрешение зависимостей, ветка, окружение, воспроизводимость по инструкции плана |

Сместился фокус — сместился и класс находок. Прошлый раунд правил план: перепроверь, не устарели ли теперь метаданные (baseline, счётчики, статус) и не разъехалась ли структура (порядок секций, ссылки `§N`).

### 1.3. Прочитать план целиком

Прочитай файл плана от начала до конца. Запомни:
- Тип задачи (BUG/DEBT/FEAT/VAL)
- Количество этапов и шагов
- Список затронутых файлов
- Имя ветки
- Тестовую стратегию
- Критерии завершения

### 1.4. Загрузить связанный контекст

**Из плана (явные ссылки):**

1. Все vault-заметки, на которые ссылается план (`[[...]]`). Для каждой ссылки — проверь что файл существует. Битая ссылка = находка 🟡
2. Запись в соответствующем реестре roadmap
3. GitHub issue (если указан в frontmatter): `gh issue view <N> --repo ArturSalamatin/Oil_Gas`

**Активный поиск (контекст, который план мог пропустить):**

4. По каждому затронутому файлу/модулю — проверь, есть ли в vault заметки, которые план НЕ ссылается, но должен:
   - `vault/knowledge/science/` — если план затрагивает физику/математику
   - `vault/knowledge/numerics/` — если план затрагивает численные методы
   - `vault/knowledge/debugging/` — были ли похожие баги раньше? Grep по ключевым словам задачи
   - `vault/knowledge/decisions/` — есть ли решения, которые объясняют, почему код устроен так, как сейчас? (план может «исправлять» намеренное поведение)
5. Проверь `vault/roadmap/известные баги и технический долг.md` — есть ли другие BUG/DEBT, затрагивающие те же файлы? Если да — проверь, не конфликтуют ли планы

## Фаза 2: Аудит по 7 измерениям

**Порядок важен.** Измерения 1–2 — фундамент. Если измерение 1 находит критические проблемы (файл не существует, функция удалена), то в измерениях 2–6 пропускай чеки для затронутых шагов — они заведомо невалидны, пока не починен фундамент. Измерение 0 выполняется всегда.

Для каждого измерения — пройти все чеки, зафиксировать проблемы. Формат находки:

```
- 🔴/🟡/🔵 **[Измерение N, шаг M]** <суть проблемы>
  > <цитата из плана — строка, которая неверна>
  **Риск:** <что сломается при реализации>
  **Фикс:** <конкретное исправление или «требует решения пользователя»>
```

Для 🔵 мелких — допустим однострочный формат без цитаты и риска.

### Измерение 0: Соответствие исходной задаче и верность анализа

Сравни план с первоисточником задачи — запись в vault roadmap + GitHub issue + заметка в knowledge. Затем перепроверь анализ по коду.

**0A. Соответствие задаче:**

1. **Корневая причина.** Для BUG: план атакует именно ту причину, которая описана в задаче? Или чинит симптом / смежную проблему?
2. **Полнота скоупа.** Все ли аспекты задачи покрыты планом? Если issue описывает 3 проявления бага — план должен адресовать все 3, а не одно
3. **Избыточность скоупа.** Не делает ли план больше, чем просит задача? (рефакторинг «по дороге», расширение API, которое не требовалось)
4. **Критерии завершения vs задача.** Критерии из плана — действительно означают «задача решена»? Или план может быть «выполнен» при живом баге?

**0B. Верность анализа причин (для BUG/DEBT):**

Не доверяй анализу в плане на слово — перепроверь по коду.

1. **Цепочка причинно-следственных связей.** План описывает «триггер → место ошибки → распространение → проявление». Пройди по этой цепочке в коде: действительно ли триггер вызывает описанный эффект? Нет ли другого пути распространения, который план не учитывает?
2. **Выбор варианта решения.** План описывает N вариантов и выбирает один. Проверь:
   - Отвергнутые варианты действительно имеют описанные минусы? (а не отвергнуты ради упрощения)
   - Выбранный вариант действительно имеет описанные плюсы?
   - Нет ли варианта, который план вообще не рассмотрел?
3. **Место фикса.** Правильное ли место в коде выбрано для исправления? Может быть, проблему лучше решить выше/ниже по call stack? Фикс в месте проявления vs фикс в месте причины — план должен объяснить выбор

### Измерение 1: Корректность ссылок на код и синтаксис

Для КАЖДОГО шага плана:

**1A. Ссылки:**

1. **Файлы существуют.** Grep/Glob каждый файл из поля «Файлы»
2. **Функции/классы/методы существуют.** Grep каждый упомянутый идентификатор в кодовой базе
3. **Номера строк актуальны.** Если шаг ссылается на «строка ~N» — проверь grep-ом, что код на этой строке соответствует описанию. Допуск: ±10 строк. Если сдвиг > 10 — проблема
4. **Сигнатуры совпадают.** Если шаг модифицирует вызов функции — проверь текущую сигнатуру (параметры, типы, значения по умолчанию)
5. **Импорты.** Если шаг добавляет `import` / `from ... import` — проверь что модуль/объект существует
6. **pyproject.toml.** Если шаг добавляет зависимость — проверь что она указана в `pyproject.toml`
7. **Разрешимость импорта в ЦЕЛЕВОЙ среде.** Существования модуля на диске недостаточно — проверь, что он импортируется там, где будет работать артефакт, и **без ручной подготовки окружения**.

   Запусти голую проверку, не добавляя ничего от себя:
   ```powershell
   .venv\Scripts\python.exe -c "import <модуль>"
   ```
   Если падает — как модуль подключается сейчас? Типичные механизмы: установка в venv (`pip install -e .`), `.pth`-файл, `sys.path` в `conftest.py`, переменная `PYTHONPATH`.

   Ключевой вопрос: **распространяется ли этот механизм на новый артефакт?** `conftest.py` работает только для pytest. `PYTHONPATH` из инструкции README пользователь забудет.

   ⚠️ Частая ошибка аудита: сам аудит гоняет проверки с `PYTHONPATH=...` и делает вывод «работает». Это проверка не того сценария. Хотя бы один прогон делай ровно так, как это сделает пользователь по инструкции из плана.

   Если механизм не покрывает новый артефакт — 🔴, план должен подключать зависимость сам (кодом), а не инструкцией пользователю.

**1B. Синтаксическая корректность блоков «После:»:**

⚠️ Перед проверкой: **отсутствие блока «После:» — тоже находка.** Если план говорит «добавить функцию X», «написать модуль Y», но не приводит сигнатуру и контракт — реализация будет угадывать. Для каждого нового артефакта (функция, класс, файл, формат данных) план обязан задать:

- сигнатуру: имя, параметры с типами, тип возврата;
- где размещается (файл, рядом с чем);
- контракт: что делает, поведение на краевых входах (пустой массив, деление на ноль, отрицательные значения);
- для формата данных — полный перечень полей.

Проверь состав по коду: если функция сериализует dataclass — сверь список полей с определением класса (`grep -n "class X" -A 20`). Пропущенные поля = потеря данных, которую заметят только после реализации.

Отсутствие спецификации → 🟡, и аудит **дописывает контракт сам** (он знает код и может его вывести).

Блоки «После:» — это код, который будет вставлен в файл. Проверь каждый:

1. **Типы совместимы.** Переменные, параметры, возвращаемые значения — типы сходятся с окружающим кодом? Read окрестности ±20 строк от места вставки
2. **Области видимости.** Используемые переменные объявлены и доступны в scope вставки?
3. **Type hints.** Если код использует аннотации типов — корректны ли они?
4. **Docstring.** Содержит ли ссылку на формулу `\eqref{}` из `moments_method.tex` (правило из CLAUDE.md)?
5. **Отступы.** Python-отступы корректны (4 пробела)?
6. **Стиль.** Код в блоке «После:» стилистически совпадает с окружающим кодом (naming, line length ≤ 100)?

### Измерение 2: Логическая целостность

1. **Зависимости шагов.** Построй граф зависимостей. Проверь:
   - Нет циклов
   - Каждый шаг, указанный в «Требует», действительно предшествует
   - Нет неявных зависимостей (шаг B использует результат шага A, но зависимость не указана)
2. **Полнота покрытия файлов.** Каждый файл из списка «Затронутые файлы» должен быть упомянут хотя бы в одном шаге. И наоборот: каждый файл, модифицируемый в шагах, должен быть в списке
3. **Согласованность «До/После».** Для первого шага, затрагивающего файл — блок «До:» должен соответствовать текущему состоянию файла на диске (grep/read). Для последующих шагов, затрагивающих тот же файл — «До:» должен отражать состояние **после** предыдущего шага (иначе `Edit` не найдёт `old_string`)
4. **Кумулятивный эффект.** Если несколько шагов правят один файл — проверь, что правки не конфликтуют
5. **Пробелы.** Есть ли разрыв между описанием проблемы (фаза 2 плана) и предложенными шагами (фаза 3)? Все ли аспекты проблемы покрыты?

### Измерение 3: Физика и математика

Применимо только если план затрагивает уравнения, дискретизацию, физические модели.

1. **Знаки.** Проверь знаки в дискретных уравнениях (градиент давления, источниковые члены)
2. **Размерности.** Проверь согласованность единиц измерения в формулах (Па, м, с, К)
3. **Граничные условия.** Правильно ли обрабатываются краевые условия на rw и Rext
4. **Устойчивость.** Не нарушает ли изменение условия устойчивости ODE-решателя
5. **Законы сохранения.** Сохраняется ли баланс масс после изменения
6. **Вырожденные случаи.** Деление на ноль, Sg=0, Sg=1, p=pb, T→T0, rb→rw, rb→Rext
7. **Соответствие moments_method.tex.** Если план ссылается на формулу из `.tex` — проверь что формула верно переписана, `\label{}` корректен

### Измерение 4: Тестовая стратегия

**4A. Полнота тестов:**

1. **Покрытие.** Для каждого изменения в коде — есть ли тест, который его верифицирует?
2. **Тест-воспроизводитель** (для BUG). Описан ли тест, который падает без фикса и проходит с фиксом?
3. **Edge cases.** Проверены ли граничные случаи из измерения 3 (нули, экстремальные значения, вырожденные конфигурации)?
4. **Regression.** Перечислены ли конкретно тесты, которые не должны сломаться?
5. **Visual.** Предусмотрен ли matplotlib export для ключевых сценариев?
6. **Tolerance.** Если в тестах есть числовые tolerance — обоснованы ли они? Слишком мягкие (всё проходит) или слишком жёсткие (ложные падения)?
7. **Негативные тесты.** Если код должен корректно обрабатывать невалидные входы — есть ли тесты на это?

**4B. Реализуемость тестов:**

8. **Инфраструктура.** Если тест описывает сравнение с аналитическим решением — существует ли в коде функция аналитического решения? Если нет — план должен включать шаг создания
9. **Существующие тесты.** Для каждого шага: тест, указанный в секции «Проверка», существует? Grep по имени теста в `<рабочий каталог>/tests/`. Если тест ещё не создан (создаётся в более позднем шаге) — убедись, что порядок шагов это учитывает
10. **Что именно тест проверяет.** Если шаг ссылается на существующий тест как проверку — прочитай тест. Действительно ли он проверяет то, что утверждает план?

### Измерение 5: Подводные камни, риски и новые проблемы

**5A. Перепроверка чеклиста плана:**

1. **Чеклист подводных камней из плана.** Найди в плане раздел «Поиск подводных камней» (ищи по заголовку, не по номеру). Пройди каждый пункт повторно. Отметки ✅ — перепроверь: действительно ли безопасно?
2. **Отсутствующие пункты.** Чего НЕТ в чеклисте, но должно быть? (Специфичные для данной задачи риски)

**5B. Побочные эффекты (не создаёт ли план новые проблемы):**

Для КАЖДОЙ функции/класса, которые план модифицирует:

3. **Все вызывающие.** Grep по имени — кто вызывает? Прочитай каждый call site (±5 строк). Изменение сигнатуры, семантики возврата, побочных эффектов — сломает ли вызывающий код?
4. **Контракты и предусловия.** Вызывающий код может полагаться на неявные гарантии: «функция всегда возвращает >0», «массив всегда непустой». Не нарушает ли план эти контракты?
5. **Обходные пути.** Grep по BUG/DEBT/workaround/hack/TODO/FIXME в файлах, затронутых планом. Есть ли workaround-ы, которые зависят от текущего (ошибочного) поведения?
6. **Каскадные эффекты.** Если план меняет структуру данных (добавляет/удаляет поле, меняет тип) — grep по типу, найди все места использования. Все ли обновлены в плане?
7. **Параллельные пути вычисления.** Если план меняет единицы, размерность или способ вычисления величины — найди ВСЕ альтернативные пути, где та же величина вычисляется другим способом (диагностика, баланс масс, вывод). Если основной путь изменён, а проверочный — нет, невязка неизбежна

**5C. Системные риски:**

8. **Связь с другими задачами.** Проверь roadmap — нет ли конфликта с другими задачами в работе? Проверь другие ветки: `git branch --list "fix/*" "feat/*" "val/*"` — может ли параллельная работа конфликтовать?
9. **Неожиданные зависимости.** Пройди по import-цепочке — не тянет ли изменение за собой правки в других модулях `<рабочий каталог>/<пакет>/`?
10. **Регрессия производительности.** Если план добавляет вычисления в горячий цикл (интегрирование, вычисление коэффициентов ODE, solver step) — оценена ли стоимость? Аллокации массивов в цикле? Лишние пересчёты PVT?
11. **Рабочая ветка и база ветвления.** Указана ли ветка в плане и в реестре (конвенция проекта — поле «Ветка» у каждой задачи)? Проверь `git rev-parse --abbrev-ref HEAD`: если сейчас активна ветка **другой** задачи, план должен явно требовать создать свою — иначе коммиты смешаются.

    **Базовую ветку определяй по факту, а не по имени.** `master` — не всегда актуальная линия разработки. В этом репозитории направления живут в долгоживущих ветках (`numerical_scheme/implementation` содержит `numerical_solver/` и опережает `master` на десятки коммитов; `master` этой папки не содержит вовсе). Ветвление от «главной по названию» ветки может дать дерево без нужного кода.

    Как проверить:
    ```powershell
    # содержит ли ветка каталог, который правит план?
    git ls-tree <ветка> --name-only | Select-String <каталог>
    # насколько кандидат опережает master?
    git rev-list --count master..<ветка>
    # от чего ответвлялись предыдущие задачи этого же направления?
    git merge-base <ветка-кандидат> <ветка-похожей-задачи>
    ```
    База правильная, если содержит рабочий каталог плана и от неё же ответвлены соседние задачи направления. Расхождение с тем, что написано в плане, — 🟡.
12. **Копирование «мёртвых» полей конфига.** Если план приводит примеры JSON/YAML, скопированные из существующих конфигов — проверь grep-ом, что каждое поле реально читается кодом. Поле, объявленное в dataclass, но нигде не используемое, в новых примерах вводит пользователя в заблуждение (он решит, что оно на что-то влияет).

    Обратная проверка: есть ли работающие поля, которые план **не** использует, хотя они решают его задачу? (например, поле, прореживающее вывод, при жалобах на размер файлов)

### Измерение 6: Автономность и читаемость

Представь: Claude в новой сессии, compact-сжатый контекст, никаких воспоминаний о текущем разговоре.

1. **Самодостаточность шагов.** Каждый шаг понятен без контекста предыдущих?
2. **Термины.** Все специфические термины расшифрованы при первом упоминании?
3. **ПОЧЕМУ vs ЧТО.** Объяснена ли причина каждого изменения, а не только действие?
4. **Физический контекст.** Есть ли необходимые формулы, ссылки на vault и `moments_method.tex`?
5. **Полные пути.** Все пути к файлам — от корня проекта?
6. **Секция «Как начать».** Содержит ли конкретные команды (активация venv, pytest, воспроизведение)?
7. **Baseline.** Зафиксированы ли количество тестов и время — и **верны ли они**? Не проверяй наличие поля, проверяй число: запусти `pytest tests/ -q` и сверь. Неверный baseline хуже отсутствующего: по нему нельзя отследить регрессию, а доверие ложное.

   То же правило для любых конкретных чисел в плане (число файлов, размер вывода, длительность): если число можно проверить одной командой — проверь. План — не источник истины о состоянии репозитория, репозиторий источник.
8. **Порядок чтения.** Можно ли читать план сверху вниз без возврата? Нет ли forward references на шаги, которые описаны позже?

### Прогон в коде (перед мысленным прогоном)

Мысленный прогон ловит логику, но не ловит среду: ненайденный модуль, неверный baseline, изменившийся API, отсутствие обещанного физического эффекта. Поэтому сначала — **исполни план настолько, насколько это возможно без записи в проект**. Работай в scratchpad-директории; проект, venv и git не трогай.

Обязательный минимум:

1. **Baseline.** `pytest tests/ -q` — записать число тестов и время, сверить с планом.
2. **Голый импорт.** Для каждой внешней зависимости: `python -c "import X"` **без** `PYTHONPATH` и прочей подготовки среды. Падает — см. Измерение 1A.7.
3. **Ключевой сценарий.** Собрать в scratchpad минимальный рабочий пример из плана (конфиг, вызов API) и запустить. Ловит: неверные параметры, изменившиеся сигнатуры, расходимость решателя, отсутствие ожидаемого эффекта.
4. **Числа плана.** Если план обещает конкретные значения (физическая величина, число шагов, размер файла, время) — проверить хотя бы выборочно.
5. **Цепочка артефактов.** Если план создаёт файлы (CSV, графики, отчёты) — прогнать создание в scratchpad и посмотреть результат, а не только на отсутствие исключения.

Правило: **утверждение плана, которое проверяется командой за минуту, должно быть проверено, а не принято на веру.** Особенно если оно звучит правдоподобно — правдоподобные ошибки живут в планах дольше всего.

Отдельно: если аудит для своей проверки подготавливает окружение (переменные, пути, флаги), которого нет в инструкции плана, — он проверяет **не тот** сценарий. Хотя бы один прогон сделай ровно так, как это сделает пользователь по плану.

### Мысленный прогон (после всех измерений)

Пройди план от шага 1 до последнего шага, моделируя состояние кода после каждого шага.

Для каждого шага:
1. Применить блок «После:» мысленно к текущему состоянию файла
2. Проверить: код исполняется? (типы, импорты, scope, отступы)
3. Проверить: тесты, указанные в «Проверка после шага», пройдут?
4. Обновить «текущее состояние» — следующий шаг работает с результатом предыдущего

Что ловит мысленный прогон:
- **Порядковые ошибки:** шаг 3 ожидает результат шага 5
- **Кумулятивные конфликты:** шаг 2 и шаг 4 правят один модуль, но шаг 4 не учитывает изменений шага 2
- **Разрыв работоспособности:** после шага N код не запускается, а тесты запланированы только в шаге N+2
- **Неполнота:** после последнего шага код в целевом состоянии? Все ли изменения, необходимые для решения задачи, выполнены?
- **Адекватность оценок.** Для каждого шага: оценка «~N строк» соответствует реальному объёму работы?

Если прогон обнаруживает проблемы — зафиксируй как находки соответствующего измерения (обычно измерение 2 — логическая целостность).

## Фаза 3: Исправление плана

### 3.1. Приоритизация

Отсортируй находки:
1. 🔴 Критические — план нереализуем без фикса (несуществующий файл, неверная формула, отсутствующий тест-воспроизводитель)
2. 🟡 Существенные — реализация возможна, но высок риск ошибки (устаревшие строки, неявные зависимости, слабые тесты)
3. 🔵 Мелкие — качество плана страдает, но реализация не пострадает (терминология, форматирование, недостающий контекст)

### 3.2. Автоматическое исправление

Исправь в файле плана все найденные проблемы. Принцип: если аудит нашёл проблему и знает, как её решить — исправляй, не перекладывай на пользователя.

**Исправлять (механические правки):**
- Устаревшие номера строк → обновить на актуальные (grep)
- Переименованные функции/классы → исправить имена на текущие
- Расхождения «До/После» с реальным кодом → обновить блоки «До:»
- Неуказанные зависимости между шагами → добавить в поле «Зависимости»
- Недостающие файлы в списке «Затронутые файлы» → добавить
- Ошибки порядка шагов, обнаруженные мысленным прогоном → переупорядочить
- Синтаксические ошибки в блоках «После:» (типы, scope, отступы) → исправить код

**Исправлять (содержательные дополнения — аудит знает ответ):**
- Неполные «Подводные камни» → дополнить чеклист находками из аудита
- Недостающие тесты на edge cases → добавить описания тестов в тестовую стратегию, добавить шаги реализации тестов
- Недостающие вызывающие, которых план не учёл → добавить шаги обновления call sites
- Обходные пути (workaround-ы), которые сломает фикс → добавить шаг удаления/обновления workaround-а
- Каскадные эффекты → добавить шаги
- Недостающий контекст для автономности → дополнить секции «Контекст» в шагах
- Формулы: очевидные опечатки (знак, индекс) → исправить. Если неуверен — НЕ исправляй, отметь в отчёте

**НЕ исправлять (только отметить в отчёте с пометкой «🔴 требует решения пользователя»):**
- Принципиальные ошибки в анализе причин (план чинит не ту проблему)
- Неверный выбор варианта решения (отвергнутый вариант был лучше)
- Спорные физические/математические решения, в которых аудит не уверен
- Конфликт с параллельной работой на другой ветке (решение — за пользователем)
- Блокирующие баги, которые делают план нереализуемым

### 3.3. Метка аудита

После исправления добавь в frontmatter плана:

```yaml
audit:
  date: <дата>
  found: <N>           # найдено в последнем запуске
  auto-fixed: <N>
  manual-required: <N>
```

## Фаза 5: Обновление GitHub issue

Если в frontmatter плана поле `github:` отсутствует или равно `null` — пропусти эту фазу.

### 5.1. Проверить повторный аудит

Прочитай комментарии issue:
```powershell
gh issue view <N> --repo ArturSalamatin/Oil_Gas --comments
```

Если уже есть комментарий с заголовком `## Аудит плана` — это повторный аудит. Не добавляй новый комментарий, а **обнови существующий** через `gh api`:
1. Сохрани новый текст комментария в scratchpad-файл
2. Обнови:
```powershell
gh api repos/ArturSalamatin/Oil_Gas/issues/comments/<comment_id> -X PATCH -F body=@<path-to-file>
```

Если комментария с аудитом нет — создай новый.

### 5.2. Прокомментировать результат аудита

Сохрани текст комментария во временный файл (scratchpad) и добавь через:
```powershell
gh issue comment <N> --repo ArturSalamatin/Oil_Gas --body-file <path-to-comment-file>
```

Формат комментария (только результат текущего запуска):

```
## Аудит плана

Найдено: 🔴 <N> 🟡 <N> 🔵 <N> | Автофикс: <N> | Требует решения: <N>
**Вердикт:** ✅ / ⚠️ / ❌
```

Если найдено 0:
```
## Аудит плана

✅ Проблем не найдено. Готов к `/implement`.
```

### 5.3. Добавить label (если есть критические проблемы)

Если вердикт ❌ (не готов):
```powershell
gh issue edit <N> --repo ArturSalamatin/Oil_Gas --add-label "needs-rework"
```

Если вердикт ✅ (готов) и label `needs-rework` стоит — снять:
```powershell
gh issue edit <N> --repo ArturSalamatin/Oil_Gas --remove-label "needs-rework"
```
