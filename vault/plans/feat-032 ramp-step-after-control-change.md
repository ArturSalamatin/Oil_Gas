# FEAT-032: нарастающий шаг после смены управления скважиной

## Цель

После смены управления скважиной (останов, скачок $p_{wf}$ или дебита) решатель сейчас начинает интервал сразу с полного шага `time.dt_integration`. Мельче шаг становится только при отказе Ньютона (локальное дробление G1a, [[DEBT-015]]). Первый час останова примеров 16 и 17 считается одним шагом 3600 с. На сценарии VAL-004 это занижает подъём $T(r_w)$ за час на 15 % (−0.230 К).

Результат задачи:
1. **Поле конфига `time.dt_after_control_change`** (с; `null` — выключено, по умолчанию). На первом шаге интервала, где управление скважиной отличается от предыдущего интервала, локальное дробление начинает не с полного шага $dt$, а с подшага $dt/2^m \le h_0$, и дальше штатный рост ×2 с выравниванием доводит его до $dt/2$: $h_0', h_0', 2h_0', \dots, dt/2$.
2. **Управления сравниваются по значению**: `PressureControl.__eq__`, `RateControl.__eq__`. Без этого граничные условия соседних интервалов различны всегда: фабрика создаёт новый объект на каждый интервал.
3. **Примеры 16 и 17**: поле включено, $h_0$ = 2 с (первый подшаг 1.76 с). Их тесты и README пересчитаны по замеру планирования.
4. **Тесты**: +38 (1826 → 1864 на базе `7f8d879`), из них 36 быстрых.
5. **Найдено при планировании**: [[BUG-028]] — зарегистрирован. Мелкий первый шаг добычи из равновесия в примерах 19 и 21 не сходится.

Схема по времени не меняется: новых формул нет.

**Чего задача не делает** (против записи реестра FEAT-032, поле «Тесты»): требование «$R_s(r_w)$ на 1 ч сходится» снято. При $h_0$ = 2 с $R_s(r_w)$ через час −7.0 от предела (одним шагом −6.4) — его задаёт длина первого подшага ([[BUG-026]]). Исправил бы $h_0 \le 0.44$ с, но такой подшаг упирается в пол [[BUG-025]] (раздел 1.5). Пользователь выбрал 2 с, зная это (решение 0.3, при выборе было сказано «$R_s$ не хуже, чем сейчас»).

## 0. Решения пользователя (2026-10-11)

1. **Первый интервал расчёта сменой управления не считается.** Нарастание — только между интервалами. Причина — [[BUG-028]]: на старте добычи из равновесия примеры 19 и 21 не сходятся ни при каком $h_0$ (7.04 / 1.76 / 0.44 с). Примеры без смены управления (01–12, 14, 19–21) не меняются.
2. **По умолчанию выключено** (`null`). Включено в примерах **16 и 17**. Прежние конфиги и тест VAL-004 побитово как сейчас.
3. **$h_0$ = 2 с** (в примерах и как рекомендация в документации). При шаге 3600 с первый подшаг $3600/2^{11}$ = 1.758 с.
4. **[[BUG-028]] зарегистрировать** (сделано при планировании, без issue).

**Решения планировщика** (не обсуждались отдельно; аудит может оспорить):
- Вариант реализации — 2 из issue #103 (начальная глубина G1a), раздел 2.1.
- Имя и место поля — `time.dt_after_control_change`, рядом с `time.dt_integration`: оба задают шаг по времени. Секция `numerics` — параметры решателя (Ньютон, `max_retries`).
- Смена управления — неравенство `BoundaryConditions` соседних интервалов. Изменение `min_bhp` при том же дебите — тоже смена.
- Глубина дробления отказа — `max_retries` уровней **ниже начального подшага**: `n_units` = $2^{\text{max\_retries}+m}$.
- Отказ на нарастании — `RuntimeError`, как у любого шага. Отката «на шаг без нарастания» нет: он молча снижал бы точность. Текст отказа называет поле и как его выключить.

`ramp_probe.py` подменяет `sim._advance` экземпляра копией G1a с начальной глубиной $m$: `n_units = 2**(max_retries + m)`, `size = 2**max_retries`. Пакет не правится. **При $m = 0$ эмуляция побитово равна штатному `_advance`**: отпечаток истории примера 16 — `9c24357b60853dea` в обоих случаях (`ex16_first0.out.txt`). ### 1.2. Прототип шаг при смене управления не сбрасывает

`HydroSolverPrototype/Prototype_1.0.3/radial_blackoil/simulation.py:42-107` (`simulate_schedule`). Прототип стартует с `DT initial` (1 мин в книге руководителя группы) **только при $t = 0$**. Дальше шаг растёт множителем по числу итераций Ньютона: ×1.5, ×1.15 или ×0.75 (`_grow_dt`, `:23-26`), до `DTMAX`. На границе строки SCHEDULE попытка обрезается до границы, но сам шаг не сбрасывается. Мелкие шаги после скачка $p_{wf}$ в примере 18 появляются только потому, что книга задаёт строки SCHEDULE через 10 с.

Поправка к записи реестра FEAT-032: «как прототип: от 1 мин до 60 мин» верно только для старта расчёта. Пример 18 нарастание не включает: он сверяется с прототипом (max|Δp| 0.005 бар), а нарастание сдвинуло бы $p(r_w)$ на 1 бар через 10 с после скачка (`ex18_first0.out.txt`).

### 2.2. Что считается сменой управления

Интервал $k \ge 1$ — смена, если `intervals[k].bc != intervals[k-1].bc`. Сравнение — по значению: `BoundaryConditions` — dataclass с `eq=True`, сравнивает `well`, `p_ext`, `T_ext`, `Rs_ext`, `Sg_ext`. `well` сравнивается через новые `__eq__`: `PressureControl` — по `p_wf`, `RateControl` — по (`q_oil`, `min_bhp`), разные типы не равны. `p_ext` и прочие условия на контуре фабрика задаёт одинаковыми для всех интервалов (`factory.py:643-649`), так что на практике сравнивается управление.

- Интервалы, развёрнутые из одного блока `{duration, dt_out}`, равны друг другу — смены внутри блока нет.
- Интервал 0 — не смена (решение 0.1).
- Нарастание только на **первом** шаге интервала (`step == 0`); остальные `n_sub − 1` шагов — полные.

### 2.3. Глубина $m$ и единицы дробления

$m$ — наименьшее целое $\ge 0$, при котором $dt/2^m \le h_0$; $dt$ — фактический шаг интервала (`substeps(k)[1]`), а не `dt_integration`. Цикл `while dt / 2**m > h0: m += 1` конечен при $h_0 > 0$. Если $h_0 \ge dt$ — $m = 0$, нарастания нет.

В `_advance`: `n_units = 2**(max_retries + m)`, начальный `size = 2**max_retries`, подшаг `h = dt / (n_units // size)` = $dt/2^m$ — деление на степень двойки точно. Рост ×2 с выравниванием (`done % (2*size) == 0`) даёт $h, h, 2h, \dots, dt/2$ — $m + 1$ подшагов. Отказ делится до $dt/2^{m+\text{max\_retries}}$, то есть на `max_retries` уровней ниже начального подшага. При $m = 0$ — `n_units = size = 2**max_retries`, код побитово прежний.

        if not isinstance(other, PressureControl):

    def __hash__(self):

        return hash((PressureControl, self._p_wf))

        """Глубина m первого подшага dt/2**m на первом шаге интервала со сменой управления (FEAT-032)."""
        # Смена — граничные условия интервала не равны предыдущим; управление
        # сравнивается по значению (bc.py). Первый интервал сменой не считается
        # (решение пользователя): мелкий первый шаг добычи из равновесия в
        # примерах 19 и 21 не сходится (BUG-028). m — наименьшее, при котором
        # dt/2**m <= h0: подшаги вида dt/2**k стыкуются с дроблением отказов
        # (DEBT-015) без остатка, а h0 округляется вниз не более чем вдвое.
        h0 = self.dt_after_control_change
        if h0 is None or interval_idx == 0:
            return 0
        if self.intervals[interval_idx].bc == self.intervals[interval_idx - 1].bc:
            return 0
        _, dt = self.substeps(interval_idx)
        m = 0
        while dt / 2 ** m > h0:
            m += 1
        return m
