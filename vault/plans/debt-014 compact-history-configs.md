# DEBT-014: расписание истории в конфигах — краткой формой `{duration, dt_out}`

## Кратко

- **Что не так.** В 22 конфигах репозитория `time.history` записана развёрнутой формой: один объект JSON на интервал записи, подряд идущие объекты текстуально одинаковы. Всего **2337 объектов**; у примера 04a — 864 одинаковых объекта (4382 строки), у 15 — 360. Правка режима требует скрипта, замысел («трое суток с записью раз в час») в файле не виден. Парсер краткую форму уже принимает (FEAT-018, `_expand_history`), конфиги в FEAT-018 не переводились по решению пользователя — DEBT-014 остался ровно на перевод.
- **Что делается** (решения пользователя 2026-10-10, раздел 0):
  - 22 конфига переводятся скриптом `vault/issues/debt-014/probes/compact_history.py`: подряд идущие одинаковые объекты `{dt, <управление>}` → один `{duration = n·dt, dt_out = dt, <управление>}`; **2337 → 80 объектов**, ≈13 300 → ≈1 760 строк;
  - два теста, читающих сырую `time.history` в обход `load_config`, исправляются: `_run_schedule` отбрасывает все ключи времени (иначе на краткой форме — `ValueError`, а ступенчатое расписание молча становится 144 интервалами по 3600 с); `test_baseline_as_blocks` сверяет baseline с явным списком 96 интервалов (иначе тавтология);
  - генератор `examples/04a_high_gas_saturation/rewrite_history.py` удаляется — с краткой формой смена шага записи — правка одного `dt_out`;
  - 19 README примеров — где сказано, *какое поле править*, — скриптом `vault/issues/debt-014/probes/fix_readmes.py` (39 точных замен).
- **Числа не меняются.** У каждого конфига развёрнутый список интервалов поинтервально равен прежнему (`dt` = `dt_out` побитово, управление то же), остальное содержимое конфига не меняется — входы `SimulatorFactory` те же, истории всех примеров побитово прежние. Проверено при планировании (раздел 1).
- **Тесты:** 1679 → **1678** (−1: параметризованный `test_script_names_resolve[04a_high_gas_saturation/rewrite_history.py]` исчезает вместе со скриптом); быстрый уровень 1417 → 1416. Новых тестов нет (решение 3).
- **Шагов:** 6 (0 — подготовка, 5 — итог). Код пакета `gpn_multiphase_solver/` и прототип не меняются.
- **Оценка:** ~1 ч, из них ~10 мин — полный прогон.

1. **Форма — `{duration, dt_out}` во всех 22 конфигах.** Как в 16, 17, 20 и в таблице README 20; читается как задача словами. У 14 длительность — `31104000.0` с (360 сут при записи раз в 30 сут) — принято.
2. **`tests/data/*` не трогать.** Это замороженные воспроизведения багов (`bug016_example14` — 12 объектов, `bug019_k10` — 2, `bug018_rs500` — 1, `bug020_*` уже краткие); план BUG-024 опирается на то, что они «с примерами не обновляются».

4. **Пример 18 — как есть.** `config.json` пишет конвертер книги прототипа (`examples/18_prototype_input/prototype_input.py:155-187`), строка SCHEDULE $k$ ↔ интервал $k$ — на этом соответствии построены docstring `TestPrototypeInput` и сверка с прототипом; `test_files_reproduce_conversion` построчно сверяет файл с конвертацией.

Решения плана (по анализу; аудит 1 подтвердил 5–7 проверкой на копии дерева, раздел 1.7 — пользователь может отменить):

5. **`rewrite_history.py` удалить** (рекомендация issue #95; в реестре: «обновить или удалить»). Он выписывал 864 одинаковых объекта при смене `dt_integration`; с краткой формой это правка одного поля `dt_out`. На краткой форме он падает (`KeyError: 'dt'` на `:36`), а при обходе этой строки размножил бы объект `{duration, dt_out}` с добавленным `dt` → `ValueError`.
6. **Файл переписывается целиком `json.dumps(indent=2, ensure_ascii=False)`**, а не заменой текста секции. Поправка к issue #95: там сказано, что 04a, 19, 21 «не совпадают с форматом `json.dumps(indent=2)`» и перезапись изменила бы другие секции. Замер (раздел 1): все 22 файла равны `json.dumps(indent=2, ensure_ascii=False)` их же содержимого, у 04a, 19, 21 нет только перевода строки в конце. Перезапись добавит его — других изменений вне `history` нет; скрипт проверяет это до записи и иначе отказывает.
7. **Описательные строки README не трогаются.** «Расписание — 30 интервалов × 43 200 с», «все 72 интервала», «361 запись» после разворачивания верны. Меняются только места, где README говорит, *какое поле JSON править* (`time.history[].dt`, «число интервалов = число записей; 72 по 3600 с», программа пересборки 13b, `rewrite_history.py`).

`{a, b}` — `{"duration": a, "dt_out": b, ...}`. Строки — в формате `json.dumps` с переводом строки в конце.

Образцы объектов после перевода:
```json
{"duration": 259200.0, "dt_out": 300.0, "control": "pressure", "p_wf": 4000000.0}
{"duration": 86400.0, "dt_out": 3600.0, "control": "rate", "q_oil": 0.00020833333333333335, "min_bhp": 101325.0}

```
Порядок ключей — как у 16, 17, 20: сначала время, затем управление. $n \cdot dt$ точно: $n \le 864$, $dt$ — целое число секунд в double; парсер берёт `n = round(duration / dt_out)` и интервалы длиной ровно `dt_out` (`io/config.py:252-275`), поэтому `dt` развёрнутых интервалов побитово равен прежнему.

- Все 22 файла: `json.dumps(json.loads(текст), indent=2, ensure_ascii=False) + "\n"` равен тексту (после CRLF → LF). У 04a, 19, 21 нет перевода строки в конце — единственное отличие (длины: 04a 87518 байт в рабочей копии = 83138 + 4381 CR − 1).

### 2.1. Текущее состояние

`time.history` — расписание эксплуатации: список объектов, каждый задаёт интервал (или блок интервалов) и управление скважиной на нём. Запись результатов — на конце каждого развёрнутого интервала (DEBT-013, [[временная-сетка-и-история]]), поэтому частоту вывода задаёт структура истории. FEAT-018 ввёл три формы объекта ([[json-config-schema]], «Краткие формы»):

| форма | разворачивается в |
|---|---|
| `{dt}` | 1 интервал по `dt` |
| `{dt, repeat}` | `repeat` интервалов по `dt` |
| `{duration, dt_out}` | `duration / dt_out` интервалов по `dt_out` (некратность — `ValueError`) |

Остальные ключи объекта (`control`, `p_wf`, `q_oil`, `min_bhp`) копируются во все интервалы блока. Решатель о блоках не знает.

22 конфига (раздел 1.1) записаны формой `{dt}` — объект на интервал. 16, 17, 20 и `tests/data/bug020_*` уже краткие.

### 2.2. Целевое состояние

- 22 конфига: один объект `{duration, dt_out, <управление>}` на этап с постоянным управлением; 80 объектов.
- `load_config(...).time.history` каждого конфига поинтервально равен прежнему; всё остальное в конфиге — прежнее.
- `_run_schedule` берёт из объекта примера только управление, при любой форме.
- `test_baseline_as_blocks` сверяет baseline с явным списком 96 интервалов, построенным в тесте, и проверяет, что сам конфиг — краткой формой.
- `rewrite_history.py` нет; README 04a и ещё 18 README говорят, какое поле краткой формы править.
- API пакета, код `gpn_multiphase_solver/`, прототип — без изменений.

### 2.3. Варианты способа перевода

**Вариант 1. Ручная правка 22 файлов.** Минус: 2337 объектов, у 13a/13b/15 по 15–30 ступеней со значениями вида `0.00020833333333333335` — ошибка переноса вероятна и глазами не ловится; проверка эквивалентности всё равно нужна скриптом. Промежуточные состояния — любые, но каждое надо сверять.

**Вариант 2. Скрипт, заменяющий только текст секции `"history": [...]`.** Плюс — остальной текст побайтно. Минус — разбор границ секции в тексте; выигрыш над вариантом 3 — только отсутствие перевода строки в конце у трёх файлов (раздел 1.2).

**Вариант 3 (выбран). Скрипт, переписывающий файл `json.dumps(indent=2, ensure_ascii=False)`, с проверкой формата до записи.** Файлы уже в этом формате (1.2), поэтому вне `history` меняется только перевод строки в конце у 04a, 19, 21. Режим `--verify` после записи сверяет каждый файл с версией из git через полный `load_config`. Повторный запуск на уже переведённом файле — отказ («уже в краткой форме»), то есть скрипт не применится дважды.

### 2.4. Выбор
