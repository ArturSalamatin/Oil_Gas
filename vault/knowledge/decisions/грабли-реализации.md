# Потенциальные проблемы при реализации

Список конкретных мест, где легко допустить ошибку. Не абстрактные риски, а конкретные грабли.

## 1. Upstream для Rs в потоке газового компонента

Поток газового компонента (eq. 9):
```
G_g = T · [Rs_up · (kro/(μo·Bo))_up + (krg/(μg·Bg))_up] · Δp
```

`Rs_up` — из ячейки выше по потоку **нефтяной** фазы (не газовой). Rs — свойство нефтяной фазы, транспортируется с ней. При однонаправленном потоке (обе фазы к скважине) это совпадает с общим upstream. Но если газ и нефть текут в разные стороны — upstream для Rs определяется потоком нефти.

На практике в ПЗП обе фазы текут к скважине (dp/dr > 0 → потоки к r_w). Но реализация должна использовать upstream по знаку dp (= по направлению потока нефти), не по отдельной проверке.

## 2. Два разных upstream в EnergySolver

В EnergySolver есть две формулы с upstream-оператором:

a) Конвективный поток энергии (eq. 23): `<Φ_α · T>` — upstream по знаку расхода **фазы** Q_α, раздельно для каждой фазы.

b) Конвективный поток газосодержания для ṁ (eq. 32): `<G^o · Rs>` — upstream по знаку потока **нефтяного компонента** G^o.

Это разные upstream-операторы. В (a) upstream для T может различаться для нефти и газа. В (b) upstream для Rs определяется только потоком нефтяного компонента. Не путать.

## 3. Расход фазы Q_α vs поток компонента G^o

| Величина | Обозначение | Единицы | Где используется |
|---|---|---|---|
| Поток нефтяного компонента | G^o | м³ст/с | Балансы масс, ṁ |
| Поток газового компонента | G^g | м³ст/с | Балансы масс |
| Расход нефтяной фазы | Q_o | м³пл/с | Уравнение энергии |
| Расход газовой фазы | Q_g | м³пл/с | Уравнение энергии |

Связь: `Q_o = G^o · Bo_up` (в пластовых условиях). Из G_o в HydroResult EnergySolver вычисляет Q_o.

Или проще: `Q_o = T · (kro/μo)_up · Δp` (eq. 24) — не содержит Bo. Вычислять Q_o напрямую, не через G_o.

**Решение:** HydroResult хранит G_o, G_g, Q_o, Q_g, u_o, u_g, m_o, m_g — все потоки и скорости.

## 4. Знак потоков: конвенция

**Конвенция:** G > 0 = от скважины (рост r). При типичном потоке G < 0.

Формула: `G_o[f] = T_f · mob_up · (p[f-1] − p[f])`. При p[f] > p[f-1] → G < 0 (к скважине). ✓

Дебит: `q_o_std = −G_o[0] > 0`.

Невязка: `F[j] = accum + G[j+1] − G[j]`. При стационаре G = const < 0 → F = 0. ✓

Подробности: [[конвенции-знаков]].

**Тест:** при стационарном однофазном потоке все невязки = 0.

## 5. Индексация: грань f vs ячейка j

Полная конвенция зафиксирована в [[словарь-код-физика]].

Грань f (f=0..N): f=0 — забой, f=N — контур. Грань f расположена между ячейками f-1 и f.

Ячейка j (j=0..N-1): между гранями j (левая) и j+1 (правая).

`trans_internal[f]` — проводимость грани между ячейками f и f+1, f=0..N-2. Длина N-1.

Потоки `G_o[f]`, f=0..N. Невязка ячейки j: `accum + G[j+1] - G[j]`.

## 6. Перенос correlations.py: math → numpy

Модуль `method_of_moments/src/pvt/correlations.py` использует `math.log`, `math.exp`, скалярные операции. При переносе:

- `math.log(10)` → `np.log(10.0)` (скаляр, однократно)
- `math.exp(x)` → `np.exp(x)` (x может быть массивом)
- `10.0 ** a` → `np.power(10.0, a)` или `10.0 ** a` (numpy перегрузка работает)

**Опасность:** в `mu_g` (LGE) внутри формулы `rho_g_SI = rho_g_st / Bg(p, T)` — вызов Bg с двумя аргументами. Но в HydroPVT Bg(p) принимает только p (T = T0 = const). Нужно согласовать.

**Опасность:** `_api_gravity`, `_gas_specific_gravity` — вспомогательные функции, возвращают скаляры. Если rho_o_st — скаляр, а p — массив, то gamma_api — скаляр, и дальше всё работает (numpy broadcasting). Но нужно проверить.

## 7. Расходимость Ньютона при фиксированном dt

TimeSchedule не предусматривает адаптацию dt. Если HydroSolver (когда будет реализован) не сходится:
- Бросить исключение с информативным сообщением
- Пользователь уменьшает dt_integration в JSON
- **Не** передавать нефизичное состояние в EnergySolver

## 8. Глубокая копия в SimulationHistory

`history.append(state)` **обязан** делать глубокую копию (state.copy()). Иначе все записи будут ссылаться на последний объект state — мутабельные numpy-массивы.

Ловушка: `state.copy()` должен копировать все массивы. `dataclass` по умолчанию — поверхностная копия. Реализовать `copy()` явно через `np.copy()`.

## 9. Ветвление в PVT при p ≷ pb

Все функции Bo, dBo_dp, dBo_dRs, mu_o, dmu_o_dp должны иметь **согласованное** ветвление по mask = (p < pb). Если Bo ветвится, а dBo_dRs — нет, якобиан будет неконсистентным.

Чек-лист:
- Bo(p, Rs): ✓ ветвление
- dBo_dp(p, Rs): ✓ ветвление (0 при p<pb, -co·Bo при p≥pb)
- dBo_dRs(p, Rs): ✓ ветвление (Standing при p<pb, 0 при p≥pb)
- mu_o(p, Rs): ✓ ветвление (Beggs при p<pb, exp при p≥pb)
- dmu_o_dp(p, Rs): ✓ ветвление (0 при p<pb, cμ·μ_o(pb) при p≥pb)

**Тест:** непрерывность на pb: Bo(pb-ε) ≈ Bo(pb+ε), mu_o(pb-ε) ≈ mu_o(pb+ε).

## 10. ThermalPVT вызывается с p^{n+1}, T^n

В EnergySolver: `c_p_oil(p_new, T_old)`, **не** `(p_old, T_old)`. Для скалярных свойств это несущественно. Но при будущем расширении — принципиально. Передавать p^{n+1} в ThermalPVT.

## 11. λ_eff зависит от Sg

Эффективная теплопроводность: `λ_eff = (1-φ)·λ_s + φ·(So·λ_o + Sg·λ_g)`. Зависит от Sg — **переменная** по пространству и времени. Вычисляется в каждой ячейке на каждом шаге. Интерполяция на грань — гармоническое среднее. Grid предоставляет веса, но λ_eff вычисляет EnergySolver.

## 12. Первый шаг: скачок давления

При t=0: p = p0 > pb всюду. При первом шаге: p_wf < pb на забое. Скачок давления за один шаг может быть огромным (десятки МПа). Рекомендация в документации: **первый интервал истории — короткий** (dt = малый), чтобы переходный процесс был разрешён.

Для аналитической заглушки это не проблема (мгновенный стационар). Для Newton-солвера — потенциальная расходимость.
