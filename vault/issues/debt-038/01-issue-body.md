## Описание

CSV-путь фабрики (`model = "table"`) передаёт строки `oil_pvt.csv` в `BlackOilPVT` без проверки ветвей PVTO. XLSX-ридер прототипа такие таблицы отклоняет, CSV-путь — нет. Ошибка в таблице (пропущенная строка, опечатка в давлении или в $R_s$) не даёт понятного сообщения, а меняет $B_o$, $\mu_o$ недонасыщенной нефти. Через `PrototypePVTAdapter` это меняет и гидродинамику, и уравнение энергии.

Приоритет низкий: все 16 таблиц проекта корректны (проверено 2026-10-07, см. ниже).

## Текущее состояние

`_read_oil_pvt_csv` (`factory.py:371-395`) только разбирает строки. Фабрика сразу строит `BlackOilPVT(oil_rows, gas_rows)` (`factory.py:123-127`). После этого проверяется только $R_{s,0}$ в диапазоне ветвей (`_check_rs0_in_table`, BUG-017).

XLSX-ридер прототипа проверяет порядок строк в файле (`input_reader.py:60-64`):
- в ветви $R_s$ не меньше 2 строк;
- давление строго растёт внутри ветви.

Что происходит с CSV-таблицей с ошибкой (замер 2026-10-07 на `59e9eab`, после DEBT-036):

| Ошибка в таблице | Поведение `BlackOilPVT` | Сигнал пользователю |
|---|---|---|
| Ветвь из одной строки ($R_s$ = 30 между ветвями 0 и 60) | $B_o$ = 1.2 при 120, 200, 300 бар: выше $p_b$ нефть несжимаема, $\mu_o$ постоянна | Нет. `max_pressure_of_rs(30)` = 120 бар = $p_b$, поэтому возможно только предупреждение начального состояния «branch pressure above supplied range» (`_warn_initial_table_range`), и то лишь при $R_{s,0}$ около этой ветви. Причину оно не называет |
| Повтор давления внутри ветви (200 бар дважды, $B_o$ 1.29 и 1.27) | `BlackOilPVT` сортирует строки по $(p, B_o, \mu_o)$, а не по порядку в файле. Первой идёт строка с меньшим $B_o$, и $B_o$ скачет 1.270 → 1.290 при 200 бар. Значения поразрядно совпадают с `np.interp` | `RuntimeWarning: divide by zero` в `pvt.py:56`: столбец наклонов получает `inf`. Строку нулевой ширины `searchsorted(side='right')` не выбирает, поэтому на результат `inf` не влияет. Файла и ветви сообщение не называет |
| Давление в ветви идёт не по возрастанию (все давления разные) | Сортировка исправляет порядок молча | Нет. XLSX такую таблицу отклоняет |
| Одна ветвь $R_s$ на всю таблицу | `ValueError` в `_build_interp_tables` (DEBT-036) | Есть, в обоих путях |

Опечатка в $R_s$ (например, 30.01 вместо 30) создаёт лишнюю ветвь из одной строки. Это первая строка таблицы, и она молча меняет свойства нефти.

### Стандарт ECLIPSE / OPM

OPM Flow Reference Manual 2025-10 (`Refs/incoming/`, §8.3.245 PVTO, табл. 8.133, с. 1131–1133 PDF):
- недонасыщенные строки (PRSU) не обязательны;
- «there must be at least two entries for the last Rs value to enable the simulator to interpolate over the undersaturated pressure region».

Значит, ECLIPSE допускает ветви из одной строки везде, кроме последней. Требование XLSX-ридера «≥ 2 строки в каждой ветви» строже стандарта. Но прототип интерполирует такую ветвь не так, как ECLIPSE: $B_o$, $\mu_o$ выше $p_b$ у него постоянны. Как ECLIPSE и OPM достраивают ветвь из одной строки, в Manual не описано. По памяти, opm-common переносит относительный ход $B_o$, $\mu_o$ со следующей ветви, у которой есть недонасыщенные данные. Это не проверено, сверить с кодом opm-common, если вопрос встанет.

Вывод: принимать ветвь из одной строки при текущей интерполяции нельзя. Получится таблица формата ECLIPSE с физикой, которой в ECLIPSE нет.

## Целевое состояние

CSV-путь отклоняет таблицу с теми же ошибками, что и XLSX-ридер: `ValueError` с номером ветви $R_s$ и именем файла. Корректные таблицы проходят без изменений, результаты примеров не меняются.

## Анализ вариантов решения

### Вариант 1 — отдельная проверка в фабрике (рекомендуется)

**Суть.** Функция `_check_pvto_branches(oil_rows, oil_pvt_file)` рядом с `_check_rs0_in_table`. Вызов — между `_read_oil_pvt_csv` и `BlackOilPVT(...)` (`factory.py:123-127`). Строки проверяются в порядке файла, как в XLSX-ридере: в ветви не меньше 2 строк, давление строго растёт.

**Изменения.** `factory.py`: новая функция и одна строка вызова. Новые тесты в `test_factory_prototype.py`.

**Плюсы.**
- Прототип не меняется: регрессия 17/17 и поразрядная сверка DEBT-036 не затрагиваются.
- Ридер остаётся разбором, как `_read_gas_pvt_csv`. Тесты ридера с одной строкой на ветвь не трогаются.
- Тот же приём, что у `_check_rs0_in_table`, сообщение на русском.

**Минусы.**
- Прямой вызов `BlackOilPVT` (тесты, скрипты) не защищён.
- Логика проверки повторяет XLSX-ридер.

### Вариант 2 — проверка внутри `_read_oil_pvt_csv`

**Суть.** То же, но в ридере.

**Плюсы.** Проверка стоит рядом с чтением файла.

**Минусы.**
- Ридер смешивает разбор и проверку.
- `test_oil_pvt_csv_format` и `test_oil_csv_skips_blank_lines` придётся переписать: формат CSV они проверяют корректно, но на таблицах с одной строкой на ветвь.

### Вариант 3 — проверка в `BlackOilPVT.__init__`

**Суть.** Единая проверка для XLSX, CSV и прямых вызовов. Код прототипа править разрешено.

**Плюсы.** Один источник правды.

**Минусы.**
- Фикстура «one-row branch» в `test_pvto_vectorized.py` перестанет строиться: её нужно переделать, и сверка DEBT-036 потеряет случай ветви из одной строки.
- Проверка XLSX-ридера станет дублем, причём с другим типом исключения (`InputValidationError` против `ValueError`).
- Сообщения прототипа на английском, и в них нет имени файла: конструктор файла не знает.
- Нужен прогон регрессии прототипа.

### Вариант 4 — заполнение ветви из одной строки по правилу ECLIPSE (вне этой задачи)

**Суть.** Принимать ветви из одной строки, кроме последней, и достраивать их недонасыщенную часть по следующей ветви.

**Оценка.** Это меняет интерполяцию PVT, то есть это FEAT, а не DEBT. Регистрировать только при появлении реальных таблиц в формате ECLIPSE с такими ветвями.

### Рекомендация

Вариант 1. Два вопроса решить при планировании:
1. **Ветвь из одной строки** — отклонять, как XLSX (рекомендуется: при текущей интерполяции её физика неверна), или принимать, как ECLIPSE, кроме последней ветви. Второе возможно только вместе с вариантом 4.
2. **Различные давления не по возрастанию** — отклонять, как XLSX (рекомендуется: единые правила для двух путей), или допускать, раз `BlackOilPVT` их сортирует.

## План решения

1. **Подготовка (baseline).** `pytest tests/ -m "not slow" -q` — число тестов и время. Прогнать новую проверку по 16 таблицам проекта: все должны пройти.
2. **Тесты (до реализации)**, в `test_factory_prototype.py`. Для каждого ошибочного случая проверить, что `ValueError` называет $R_s$ ветви и имя файла:
   - ветвь из одной строки (в том числе последняя ветвь);
   - повтор давления внутри ветви;
   - давление не по возрастанию;
   - опечатка в $R_s$, которая дала лишнюю ветвь.

   Плюс тест, что корректная таблица `configs/table_pvt` проходит.
3. **Реализация.** `_check_pvto_branches` и вызов в ветви `model == "table"` до `BlackOilPVT(...)`. Тогда `RuntimeWarning` из `pvt.py:56` для CSV-пути больше не возникает.
4. **Сопутствующее.** Обновить комментарий в `test_pvto_vectorized.py:44`: CSV-путь теперь отклоняет ветвь из одной строки, а фикстура проверяет `BlackOilPVT` напрямую.
5. **Верификация.**
   - Быстрый уровень после каждого шага, полный в конце.
   - Результаты примеров не меняются: таблицы корректны.
   - Регрессия прототипа нужна только при варианте 3.
