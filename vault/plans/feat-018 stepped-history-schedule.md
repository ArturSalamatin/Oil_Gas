## Резюме для того, кто читает это без контекста

Частоту записи результатов задаёт только структура `time.history`: одна
запись — на конце каждого интервала (DEBT-013). Механика неравномерных
расписаний уже работает: интервалы могут быть любой длины. Неудобна только
**запись**: расписание «первый час по 300 с, потом 5 ч по 3600 с» выписывается
17 объектами, «трое суток раз в час» — 72 одинаковыми объектами.

Задача — две краткие формы объекта истории, которые парсер конфига
разворачивает в тот же `list[HistoryInterval]`:

| форма | пример | разворачивается в |
|---|---|---|
| `{dt}` (как сейчас) | `{"dt": 3600, "p_wf": 8e6}` | 1 интервал по 3600 с |
| `{dt, repeat}` | `{"dt": 300, "repeat": 72, "p_wf": 8e6}` | 72 интервала по 300 с |
| `{duration, dt_out}` | `{"duration": 18000, "dt_out": 3600, "p_wf": 8e6}` | 5 интервалов по 3600 с |

Ядро решателя (`simulator.py`, фабрика, адаптеры) **не меняется**.

### Решения пользователя (2026-10-03, при планировании)

| вопрос | решение |
|---|---|
| форма блока | **обе формы**: `{dt, repeat}` и `{duration, dt_out}`; `{dt}` остаётся |
| `duration` не кратна `dt_out` | **`ValueError`** с номером объекта в JSON; укороченного последнего интервала нет |
| свой `dt_integration` у блока | **нет** — только шаг вывода, ядро не трогаем |
| перевод существующих конфигов на краткую форму | **не трогать**; DEBT-014 остаётся открытым — перевод конфигов это отдельная задача |

Подтип: **инфраструктура** (I/O, конфиги). Уровень иерархии М.1–М.6 —
неприменимо. Новых формул нет; постановка
`numerical_solver/doc/problem_statement.tex` не меняется.

### Как история превращается в расписание

- `factory.py:390-413` `_create_schedule`: каждый `HistoryInterval` →
  `ScheduleInterval(dt, bc)`; `factory.py:256` берёт `history[0]` для
  начальной оценки `p_bhp` прототипа.
- `simulator.py:60-74` `TimeSchedule.substeps`:
  $n_{sub} = \max(1, \lceil \Delta t_{hist} / \Delta t_{int} \rceil)$,
  $\Delta t_{actual} = \Delta t_{hist} / n_{sub}$.
- `simulator.py:146-177`: двухуровневый цикл; запись только на последнем
  подшаге интервала (`:164`); между интервалами ничего не сбрасывается.
- `hydro/prototype_adapter.py:51-75`: управление скважиной
  (`set_bhp_control` / `set_oil_rate_control`) выставляется **на каждом
  подшаге**, независимо от границ интервалов; собственного состояния между
  вызовами у адаптера нет (`__init__`, строки 37–49, хранит только модель,
  сетку, PVT, `max_retries`).

### Ключевое свойство, на котором стоит тест решения

Структура истории влияет на расчёт **только через последовательность
подшагов**. Если длина каждого интервала обоих расписаний кратна
$\Delta t_{int}$, последовательности совпадают, и решение на общих моментах
записи совпадает побитово: те же вызовы с теми же аргументами в том же порядке.

⚠️ Если мелкий шаг записи **меньше** $\Delta t_{int}$, то
$\Delta t_{actual} \le \Delta t_{hist}$ автоматически мельчит и
интегрирование на этом участке — решение меняется (и должно меняться).
Тест обязан выбрать $\Delta t_{int}$, делящий все интервалы, иначе он
сравнит две разные схемы. Пример: примеры 14 и 19–21 считаются с
$\Delta t_{int}$ = 86 400 с; почасовой вывод в первые сутки там означал бы и
почасовое интегрирование.

**Замер аудита (2026-10-03)**, проба
`vault/issues/feat-018/probes/probe_stepped_vs_uniform.py` (код
`_expand_history` из шага 3 дословно, история подменяется на объекте
конфига; рабочий код не менялся). Пример 03, $N = 25$, 6 ч, расписания
шага 4 (72 × 300 с против 12 × 300 с + 5 × 3600 с):

| $\Delta t_{int}$ | расхождений на общих моментах | max $\lvert\Delta T\rvert$ | max $\lvert\Delta p\rvert$ |
|---|---|---|---|
| 300 с | **0** (03 и 04: `p`, `Sg`, `Rs`, `T`, `regime`, `WellData`, баланс) | 0 | 0 |
| 3600 с (из конфига) | 5 из 18, начиная с $t$ = 7200 с | 0.040 К | 0 |

Вторая строка — контроль чувствительности: тест шага 4 не пустой, он ловит
различие последовательностей подшагов. Давление совпадает и там: к концу
первого часа гидродинамика стационарна, различается только температура.

## Фаза 2. Анализ

### 2.1. Формулы → код

Новых формул нет. Единственная «формула» — правило разворачивания:

| форма | число интервалов $n$ | длина интервала | проверка |
|---|---|---|---|
| `{dt}` | 1 | `dt` | `dt > 0` |
| `{dt, repeat}` | `repeat` | `dt` | `repeat` — целое ≥ 1, не `bool`; `dt > 0` |
| `{duration, dt_out}` | `round(duration / dt_out)` | `dt_out` | `duration > 0`, `dt_out > 0`, $n \ge 1$, $|n \cdot dt_{out} - duration| \le 10^{-9} \cdot duration$ |

Единицы: `dt`, `duration`, `dt_out` — секунды; `repeat` — безразмерное.

Длина развёрнутого интервала — ровно `dt_out` (заданный пользователем шаг
записи), а не `duration / n`: моменты записи — $t_0 + k \cdot dt_{out}$, как
и задумано. Допуск $10^{-9}$ поглощает только двоичное округление десятичной
записи (`0.3 / 0.1 = 2.9999999999999996`); настоящая некратность отличается
на долю шага, то есть на много порядков больше допуска.

### 2.2. Обратная совместимость

- [x] Существующие конфиги (20 примеров, `configs/*`) — только форма `{dt}`;
  разбираются так же, сообщения об ошибках те же (номер объекта в JSON
  совпадает с номером интервала).
- [x] Существующие тесты проходят без изменений: сообщения сохраняют имена
  полей; `test_empty_history`, `test_dt_integration_zero` — порядок проверок

- [x] Фича — добавочная: новые ключи (`repeat`, `duration`, `dt_out`) раньше
  давали `TypeError` при распаковке в `HistoryInterval`, то есть ни один
  рабочий конфиг их не содержит.
- [x] API: `HistoryInterval`, `TimeConfig`, `load_config` — без изменений;

- [x] Изменение порядка ошибок: проверка интервалов переезжает из `_validate`
  в разбор истории, то есть **раньше** проверки `dt_integration`. Влияет
  только на конфиги с несколькими ошибками сразу; тестов на такой порядок нет.

### 2.3. Варианты реализации валидации

Проблема: после разворачивания блока номер объекта в JSON теряется. Ошибка
`history[37]: control='pressure', но p_wf не задано` для второго объекта
JSON, развёрнутого в 72 интервала, указывала бы не туда, где пользователь
правит конфиг.

**Вариант 1 — проверять прототип блока при разворачивании (выбран).**
Тело цикла 279–310 выносится в `_validate_interval(h, where)`. Разбор истории
строит один `HistoryInterval` на объект JSON (прототип), проверяет его с
`where = f"history[{i}]"` (номер объекта в JSON) и только потом размножает.
Цикл из `_validate` убирается: все интервалы `load_config` получает из
разбора, и каждый уже проверен.
- Плюсы: сообщение указывает место правки; проверка один раз на блок;
  логика проверок не дублируется (одна функция).
- Минусы: проверка интервалов уходит из `_validate` — меняется
  «одно место для всех проверок». Компенсируется комментарием в `_validate`.

**Вариант 2 — разворачивать как есть, проверять в `_validate`, хранить
таблицу «развёрнутый номер → номер объекта».**
- Минусы: лишнее поле в `TimeConfig` или параллельная структура ради
  сообщений; сообщение повторялось бы для каждого из $n$ интервалов, падало
  бы на первом. Отвергнут: абстракция сверх задачи.

**Вариант 3 — проверять дважды: прототип при разборе и все интервалы в
`_validate`.** Повторная проверка развёрнутых интервалов никогда не сработает
(они равны прототипу по всем полям), то есть это мёртвый код. Отвергнут.

### 2.4. Выбор

Вариант 1. Корректность: развёрнутые интервалы отличаются от прототипа
только тождеством объекта, поэтому проверка прототипа эквивалентна проверке
всех. Тестируемость: разбор проверяется на `_minimal_raw` за миллисекунды.

   ```python
   # скважиной (control, p_wf, q_oil, min_bhp); они передаются
   # в HistoryInterval без изменений.

   # Допустимые наборы ключей времени:
   #   {dt}               — один интервал (исходная форма, DEBT-013);
   #   {dt, repeat}       — repeat одинаковых интервалов по dt;
   #   {duration, dt_out} — этап duration с записью раз в dt_out.
   _HISTORY_FORMS = (
       frozenset({"dt"}),
       frozenset({"dt", "repeat"}),
       frozenset({"duration", "dt_out"}),
   )

   # Допуск кратности duration / dt_out. Поглощает только двоичное
   # округление десятичной записи (0.3 / 0.1 = 2.9999999999999996);
   # настоящая некратность отличается на долю шага — на много порядков больше.
   _MULTIPLE_RTOL = 1e-9


   def _expand_history(raw_history: list[dict]) -> list[HistoryInterval]:
       """Развернуть краткие формы time.history в список интервалов (FEAT-018)."""
       intervals: list[HistoryInterval] = []
       for i, raw_entry in enumerate(raw_history):
           where = f"history[{i}]"
           entry = dict(raw_entry)          # копия: не портим исходный словарь
           form = frozenset(entry) & _HISTORY_TIME_KEYS
           if form not in _HISTORY_FORMS:
               given = ", ".join(sorted(form)) or "нет ни dt, ни duration"
               raise ValueError(
                   f"{where}: неверный набор полей времени ({given}); "
                   f"допустимы dt, dt + repeat или duration + dt_out")

           if "duration" in form:
               # Этап duration с записью раз в dt_out → n интервалов по dt_out.
               # Длина интервала — ровно dt_out: моменты записи t0 + k·dt_out.
               duration = entry.pop("duration")
               dt = entry.pop("dt_out")
               if duration <= 0:
                   raise ValueError(
                       f"{where}.duration должна быть > 0, получено {duration}")
               if dt <= 0:
                   raise ValueError(
                       f"{where}.dt_out должен быть > 0, получено {dt}")
               n = round(duration / dt)
               # Некратность — ошибка, а не укороченный последний интервал:
               # иначе последний шаг записи молча отличался бы от заданного
               # (решение пользователя, FEAT-018). n < 1 — dt_out длиннее этапа.
               if n < 1 or abs(n * dt - duration) > _MULTIPLE_RTOL * duration:
                   raise ValueError(
                       f"{where}: duration = {duration} с не кратна "
                       f"dt_out = {dt} с (отношение {duration / dt:.6g}); "
                       f"задайте кратные значения или разбейте этап на блоки")
           else:
               dt = entry.pop("dt")
               n = entry.pop("repeat", 1)
               # repeat идёт в range(): bool исключается явно (подкласс int),
               # дробное отвергается — как у numerics.max_retries.
               if isinstance(n, bool) or not isinstance(n, int) or n < 1:
                   raise ValueError(
                       f"{where}.repeat должен быть целым >= 1, получено {n!r}")

           proto = HistoryInterval(dt=dt, **entry)
           # Проверка один раз на объект JSON: развёрнутые интервалы равны
           # прототипу по всем полям. Номер в сообщении — номер объекта
           # в JSON, то есть место, которое пользователь правит.
           _validate_interval(proto, where)
           # replace() — отдельный объект на каждый интервал: общий объект
           # в n позициях списка менял бы весь блок при правке одного
           # интервала (тесты правят history[k] после загрузки).
           intervals.extend(replace(proto) for _ in range(n))
       return intervals
   ```

```python
@pytest.mark.parametrize("example", ["03_standing_corey", "04_table_table"])
def test_stepped_schedule_matches_uniform(example, tmp_path):
    """Ступенчатое расписание даёт то же решение, что равномерное (FEAT-018).

    Одни и те же 6 ч записываются двумя способами:
      равномерно — 72 записи по 300 с (форма dt + repeat);
      ступенчато — 12 записей по 300 с в первый час, затем 5 по 3600 с
                   (две формы duration + dt_out).
    Последовательность подшагов одна и та же (см. _DT_INT_SCHEDULE), на
    границе интервала решатель ничего не сбрасывает, поэтому на общих
    моментах записи состояние, данные скважины и накопленный баланс
    совпадают ПОБИТОВО. Допуска нет намеренно: расхождение хоть в одном
    бите значит, что структура истории влияет на расчёт, — это дефект,
    его надо искать, а не прятать допуском.
    """
    uniform = _run_schedule(example, tmp_path, "uniform",
                            [{"dt": 300.0, "repeat": 72}])
    stepped = _run_schedule(example, tmp_path, "stepped",
                            [{"duration": 3600.0, "dt_out": 300.0},
                             {"duration": 18000.0, "dt_out": 3600.0}])

    # Состав истории: начальное состояние + по записи на интервал
    assert uniform.n_saved == 1 + 72
    assert stepped.n_saved == 1 + 12 + 5
    # 72 сложения по 300.0 точны в двоичной арифметике
    assert stepped.times[-1] == uniform.times[-1] == 21600.0

    index = {t: k for k, t in enumerate(uniform.times)}
    for j, t in enumerate(stepped.times):
        k = index[t]        # KeyError — момент записи ступенчатой истории сдвинулся
        for name in ("p", "Sg", "Rs", "T", "regime"):
            assert np.array_equal(getattr(stepped.states[j], name),
                                  getattr(uniform.states[k], name)), (t, name)
        assert stepped.well_data[j] == uniform.well_data[k], t
        assert stepped.balance[j] == uniform.balance[k], t
```
