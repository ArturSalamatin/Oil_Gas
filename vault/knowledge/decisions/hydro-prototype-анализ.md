# Анализ HydroSolverPrototype v1.0.3

Расположение: `numerical_solver/HydroSolverPrototype/Prototype_1.0.3/`
Пакет: `radial_blackoil` (15 .py файлов)
Тесты: 79 (unit) + 12 регрессионных кейсов (T00–T11)

## Структура пакета

```
radial_blackoil/
├── __init__.py         # экспортирует load_input, run_workbook
├── build_info.py       # VERSION = '1.0.3'
├── blackoil.py         # RadialBlackOilModel — ядро: Newton + active-set
├── simulation.py       # simulate_schedule — цикл по времени с адаптивным dt

├── grid.py             # RadialGrid — логарифмическая сетка
├── rock.py             # CompressibleRock — сжимаемая порода
├── pvt.py              # BlackOilPVT — табличные PVTO + газ (ECLIPSE-формат)
├── relperm.py          # TabulatedRelPerm — табличные ОФП
├── state.py            # BlackOilState — p, Rs, Sg, gas_active
├── schedule.py         # Schedule — расписание с переключением контролей
├── units.py            # Константы: BAR_TO_PA, CP_TO_PA_S, MD_TO_M2, DAY_TO_S

└── xlsxio.py           # Чтение Excel
```

## Ключевые архитектурные решения

### 1. Единицы: промысловые, не SI

| Величина | Единицы в коде | Наши единицы (SI) |
|---|---|---|
| Давление | **бар** | Па |
| Вязкость | **сП** | Па·с |
| Проницаемость | **мД** | м² |
| Время | **сут** (в Schedule), **с** (в dt) | с |
| Расходы | **м³ст/с** | м³ст/с |
| Газосодержание | м³ст/м³ст | м³ст/м³ст |

Конвертация BAR_TO_PA, CP_TO_PA_S, MD_TO_M2 — в units.py. Конвертация **внутри** формул (blackoil.py, строки 71, 88, 111, 119, 124).

**Проблема для интеграции:** наша библиотека работает в SI. Adapter должен конвертировать p из Па→бар на входе, из бар→Па на выходе.

### 2. PVT: табличные (ECLIPSE PVTO), не корреляции

BlackOilPVT принимает таблицы `oil_rows` (Rs, p, Bo, μ_o) и `gas_rows` (p, Bg, μ_g). Это формат ECLIPSE PVTO — кусочно-линейная интерполяция по ветвям Rs.

Интерполяция — все ячейки сразу (`_oil_props`, [[DEBT-036]]): строки ветвей с наклонами `np.interp`, карта «интервал объединённой сетки узлов → строка ветви»; результат побитово равен прежнему циклу по сегментам. `bo_mu_o` даёт $B_o$ и $\mu_o$ за один проход. Запасы старого состояния считаются один раз на шаг (`_old_inventories`, ключ — байты $p$, $R_s$, $S_g$). Таблица с одной ветвью $R_s$ отклоняется (`ValueError`); раньше она давала NaN. Невязка при $N = 350$ на таблице из 19 ветвей — 0.74 мс (было 3.49).

Нет аналитических корреляций (Standing, Beggs-Robinson). Нет аналитических производных — **якобиан конечно-разностный**.

**Проблема для интеграции:** наша FullPVT (c_p, μ_JT, L) не представлена в прототипе — он не знает про температуру. Для EnergySolver FullPVT нужна отдельная реализация, не из прототипа.

### 3. ОФП: табличные

TabulatedRelPerm: np.interp по таблице (Sg, kro, krg). Производные не вычисляются — не нужны для конечно-разностного якобиана.

Производные **нужны** для нашего ABC RelPermModel (для аналитического якобиана). Default fallback на конечные разности — совместим.

### 4. Порода: сжимаемая

CompressibleRock: φ(p) = φ_ref · exp(c_r · (p − p_ref)). В нашей постановке c_r = 0, но прототип поддерживает c_r ≠ 0. GPN передаёт φ_ref = `rock.porosity`, p_ref = $p_0$ (`factory.py`): пористость конфига задана при начальном давлении, опорного давления в конфиге нет ([[DEBT-008]]).

### 5. Вектор неизвестных: 2N, не 3N

Прототип использует **2 переменных на ячейку** (p, X), где X = Sg (режим 1, gas_active=True) или X = Rs (режим 2, gas_active=False). Вектор z = [p₀..p_{N-1}, X₀..X_{N-1}], размер 2N.

В нашей постановке (problem_statement.tex) — **3 переменные** (p, Sg, Rs) + замыкающее уравнение. Размер 3N.

Прототип решает ту же задачу, но с variable switching: одна переменная (не три) переключается между Sg и Rs. Это **эквивалентная** формулировка, более компактная.

### 6. Якобиан: конечно-разностный (не аналитический)

Два режима: `grouped` — 3-цветная раскраска столбцов (Кертис — Пауэлл — Рид): 2 блока × 3 цвета = 6 вычислений невязки (+1 базовое) при любом $N$, стоимость якобиана $O(N)$; `reference` — поколонный, $2N$ вычислений невязки, $O(N^2)$. Оба — конечные разности.

Нет аналитического якобиана. Это медленнее, но проще и надёжнее (нет ошибок в производных).

**DEBT-033 (2026-10-03):** `grouped` собирается векторно и сразу в CSC (`_fd_steps`, `coo_matrix(...).tocsc()`, `eliminate_zeros()`), без цикла Python по ячейкам и без плотной матрицы $2N \times 2N$; побитово равен `reference` (проба: 488 состояний Ньютона пяти примеров) и даёт SuperLU тот же вход. Пример 20 ($N = 350$): 14.6 → 6.0 с. Аналитический якобиан не нужен: тест Тейлора BUG-019 показал, что конечно-разностный якобиан согласован с невязкой; на табличном PVT время теперь определяют сами невязки (DEBT-036).

### 7. Newton с линейным поиском и active-set

`_newton_fixed_active_set`: стандартный Newton + backtracking line search (α уменьшается до 12 раз). Глобализация: проверка `_trial_is_reasonable` (p > 1 бар, Sg ∈ [-0.05, 0.98], Rs в допустимых). Нижняя граница $S_g$ — атрибут `_sg_lower_bound`: −0.05 в исходном алгоритме, в запасном пути `advance` снята ([[BUG-014]]). Сходимость по $\|F\|_\infty$ проверяется на каждом новом приближении — по невязке, которую уже посчитал линейный поиск, включая последнее ([[BUG-021]]). До BUG-021 проверка шла только в начале следующей итерации, и вызов, сошедшийся на 15-м обновлении, записывался отказом. С `cell_tol` (BUG-022; фабрика GPN передаёт `numerics.newton_cell_tol`) решение принимается, только если ещё в каждой ячейке $\max_c |F_{c,i}|\Delta t/V_{p,i} \le$ `cell_tol`; то же — в `_newton_switching` (ступень 4).

`_advance_phases`: внешний цикл по active set (до 12 итераций). Переключение режимов (activate/deactivate) с пересчётом Sg и Rs при переключении.

`advance` ([[BUG-014]], локальная правка): сначала `_advance_phases` без изменений; только при отказе — запасной путь: без нижней границы $S_g$ и (при управлении по давлению) с веткой скважины «открыта / закрыта», фиксированной на всё решение (`_well_branch`; старт по состоянию на начало шага, при неудаче — другая ветка, не более двух решений). Где исходный алгоритм сходится, результат побитово прежний.

### 8. Адаптивный шаг по времени

simulation.py: `_grow_dt` — адаптация по числу итераций Newton:
- ≥10 итераций → dt *= 0.75
- ≥6 итераций → dt *= 1.15
- <6 итераций → dt *= 1.5

Отказ → dt *= 0.5. Ниже dt_min → SimulationFailure.

**Конфликт с нашей схемой:** мы приняли фиксированный dt (TimeSchedule, n_sub·dt_actual = dt_hist). Прототип использует адаптивный dt с точными границами по расписанию. При интеграции нужно решить: кто управляет dt?

### 9. Конвенция знаков потоков

Конвенция прототипа **неоднородна** по типу грани:

| Тип грани | Формула | qoi > 0 означает |
|---|---|---|
| **well** | `qow = tw * lo * (p_0 - bhp) * BAR_TO_PA` | отток из ячейки 0 (к скважине) |
| **internal** | `qoi = T * lo * (p[i] - p[i+1]) * BAR_TO_PA` | поток вправо (от скважины) |
| **outer** | `qoo = To * lo * (p[-1] - p_outer) * BAR_TO_PA` | отток из пласта (от скважины) |

В net_component_outflow:
```python
oil[0] += f['oil_well']        # well: + = outflow
oil[:-1] += f['oil_internal']  # internal: + = outflow левой ячейки
oil[1:] -= f['oil_internal']   # internal: - = inflow правой ячейки
oil[-1] += f['oil_outer']      # outer: + = outflow последней ячейки
```

Для internal и outer: qoi > 0 = **от скважины** (совпадает с нашей конвенцией).
Для well: qow > 0 = **к скважине** (противоположно нашей конвенции).

При сборке в наш G_o[N+1]: инверсия знака **только для well**. Подробности: [[P1-адаптер-единицы]].

### 10. Формат ввода: Excel (XLSX)

5 листов: MODEL (параметры ключ-значение), SCHEDULE, OIL_PVT, GAS_PVT, RELPERM.

**Проблема для интеграции:** наша библиотека использует JSON. Нужен либо конвертер XLSX→JSON, либо поддержка обоих форматов в input_reader.

### 11. Schedule: переключение контролей

ScheduleRow содержит mode ('BHP' или 'OIL_RATE'), bhp_bar, oil_rate_sm3_day, min_bhp_bar. Контроль переключается между строками расписания.

Это **совпадает** с нашим ABC WellControl (PressureControl, RateControl). Прототип уже реализует оба варианта.

### 12. Вывод: CSV + JSON summary + PNG + XLSX

Профили (p, Sg, Rs по ячейкам и времени), дебиты, материальный баланс, run_summary.json с QC-проверками. Графики PNG (matplotlib).

## Проблемы для интеграции

### P1. Единицы: бар vs Па

Прототип хранит и обрабатывает давление в **барах**, вязкость в **сП**, проницаемость в **мД**. Конвертация в SI — через множители BAR_TO_PA, CP_TO_PA_S внутри формул.

Adapter должен:
- Принимать state в Па → конвертировать в бар → передать в прототип
- Получить state в бар → конвертировать в Па → вернуть

Риск: забыть конвертацию в одном месте → ошибка в 10⁵ раз.

### P2. Конвенция знаков: неоднородная в прототипе

Прототип: internal/outer — G > 0 = от скважины (совпадает с нашей); well — G > 0 = к скважине (противоположно). Adapter инвертирует знак **только well** потоков. Подробности: [[P1-адаптер-единицы]].

### P3. 2N vs 3N — разное представление состояния

Прототип: BlackOilState(p, Rs, Sg, gas_active). Наша: SimulationState(p, Sg, Rs, T, regime, t).

Маппинг:
- pressure_bar ↔ p (с конвертацией единиц)
- sg ↔ Sg
- rs_sm3_sm3 ↔ Rs
- gas_active ↔ (regime == 1)
- T — нет в прототипе (добавляем)
- t — нет в прототипе (управляется Simulator)

### P4. Адаптивный dt vs фиксированный

Прототип: адаптивный dt с точными границами по расписанию. Наша схема: фиксированный dt (TimeSchedule).

Варианты:
- (A) Использовать адаптивный dt прототипа, отказаться от TimeSchedule
- (B) Передавать фиксированный dt в прототип (один шаг advance())
- (C) Обернуть прототип: Adapter вызывает simulate_schedule для одного интервала

Вариант (B) — самый простой для Adapter. Но прототип может не сойтись при большом dt.

### P5. PVT: табличные vs корреляции

Прототип: табличные PVT (ECLIPSE PVTO). Наша: StandingPVT (корреляции).

Для тестирования: подставить табличные PVT из прототипа в EnergySolver.

Для полной задачи: PVT должны быть **одинаковы** в гидро и энергии. Если гидро использует табличные — энергия тоже должна использовать табличные (для согласованности). Или: реализовать PVTO-формат в нашем ABC HydroPVT.

### P6. Нет тепловых свойств

Прототип не знает про c_p, μ_JT, L, λ. Эти свойства — ответственность нашей библиотеки (FullPVT).

### P7. ОФП без производных

TabulatedRelPerm в прототипе не имеет методов dkro_dSg, dkrg_dSg. Наш ABC RelPermModel предоставляет default (конечные разности). Совместимо — Adapter обернёт табличные ОФП прототипа в наш ABC.

### P8. Входной формат: XLSX vs JSON

Прототип читает Excel. Наша библиотека — JSON. Нужен конвертер или поддержка обоих.

## Центры ячеек: различие

Прототип: `centers = √(faces[:-1] · faces[1:])` — геометрическое среднее граней.

Наша постановка до DEBT-063 (`eq:cell_center`): exp⟨ln r⟩ по площади слоя (ошибочно названная «центр масс», DEBT-060) — более сложная формула.

На логарифмической сетке разница мала, но **ненулевая**. Для согласования: использовать сетку прототипа (среднее геометрическое граней) или нашу (среднее геометрическое по площади слоя)?

Рекомендация: принять сетку прототипа при интеграции (√). Это проще, и прототип уже валидирован на ней.

**Принято DEBT-063** (2026-10-11): сетка прототипа (√) — для GPN тоже.
