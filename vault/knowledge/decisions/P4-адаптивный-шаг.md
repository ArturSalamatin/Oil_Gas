# P4. Адаптивный шаг по времени

> ⚠️ **Пересмотрено 2026-10-08 в рамках [[DEBT-015]].**
> - Дробление шага перенесено из адаптера в `Simulator` и стало **локальным**: делится пополам только не сошедшийся подшаг, после удачи подшаг растёт ×2 с выравниванием (G1a).
> - Адаптер делает один вызов `advance`; не сошёлся — `HydroConvergenceError`.
> - Поле `HydroResult.n_substeps`, повторный проход интервала, рекурсия `_advance` и ветка «предел вложенности» удалены.
>
> Прежнее решение (равномерное A-retry внутри адаптера) и его пересмотр в [[BUG-010]] — ниже, раздел «История».

## Принцип

Гидродинамический модуль — **один шаг по состоянию**: получает (state_n, dt, BC), возвращает (state_{n+1}, потоки) или бросает `HydroConvergenceError`, если шаг не сошёлся. Как он приходит к state_{n+1} (Newton, active-set, ступени `advance`) — его дело. **Сколько и каких подшагов нужно — решает `Simulator`**: только он знает, что после каждого подшага гидродинамики идёт шаг энергии и пополняются балансы.

EnergySolver использует:
- p^{n+1}, Sg^{n+1}, Rs^{n+1} — из HydroResult подшага (замороженные коэффициенты)
- p^n, Rs^n — из состояния начала подшага
- dt — длина **подшага** (тот же, что у гидродинамики)
- Потоки — мгновенные при state^{n+1} подшага

## Решение: локальное дробление в Simulator (DEBT-015)

Код — `numerical_solver/gpn_multiphase_solver/simulator.py`, `Simulator._advance`.

### Алгоритм G1a

Шаг $dt$ меряется в единицах наименьшего подшага: `n_units = 2**max_retries`. Состояние цикла — два целых: `done` (пройдено единиц) и `size` (текущий подшаг, всегда степень двойки).

```
size = n_units; done = 0
пока done < n_units:
    h = dt / (n_units // size)                  # деление на степень двойки — точно
    гидро(h): HydroConvergenceError → если size == 1: RuntimeError; иначе size //= 2; повторить
    принят → баланс массы, энергия(h), новое состояние; done += size
    если done < n_units и done % (2*size) == 0: size *= 2
```

- **Ловится только `HydroConvergenceError`**: ошибка кода в гидродинамике (иной `RuntimeError`) уходит наружу сразу, без повторов.
- **Откатывать нечего.** Отказ гидродинамики случается до энергии; в `EnergyBalanceAccumulator` и `MassBalanceAccumulator` попадают только принятые подшаги.
- **Допущение «гидродинамика не зависит от $T$» не нужно**: каждый подшаг гидро видит $T$, обновлённое предыдущими подшагами.
- **Выравнивание роста.** Удвоение разрешено, только если граница кратна удвоенному подшагу. Тогда подшаги всегда $dt/2^k$ и стыкуются без остатка. Без выравнивания (рост `min(2h, остаток)`) появляются подшаги 548 и 928 с при $dt$ = 1 сут, и останов 20B при 1 сут не проходит.
- **Лимит не меняет путь решения**: последовательность подшагов не зависит от `max_retries`, пока глубина ≤ лимита. Условие роста эквивалентно «граница кратна $2h$» в секундах. Минимальный `max_retries` = наибольшая глубина одного прогона — [[минимальный max_retries измеряется одним прогоном при умолчании — лимит не меняет путь решения]].

### Пример

dt = 3600 с, двойник отказывает на шагах > 1800 с, а с t = 1800 с — на шагах > 900 с:

`3600 ✗ → 1800 ✓ → 1800 ✗ → 900 ✓ → 900 ✓` — энергия 1800, 900, 900 с. Равномерное дробление дало бы 4 × 900 с и пересчитало бы первую половину.

### Параметры

| Параметр | Значение | Смысл |
|---|---|---|
| `max_retries` | 9 (`numerics.max_retries`, передаётся в `Simulator`) | Глубина дробления; допустимо 0…20 |
| Наименьший подшаг | dt / 2^max_retries | При dt = 3600 с → 7.03 с; при 1 сут → 168.75 с |

Значение 9 — запас, а не порог: таблицы README 03 и 04 требуют не больше 5 удвоений (DEBT-041; при локальном дроблении те же числа).

### Почему локальное, а не равномерное

Сходимость Ньютона прототипа по $\Delta t$ немонотонна ([[BUG-019]], [[BUG-020]]: 60 с ✓, 10 и 169 с ✗). Равномерное дробление требовало, чтобы сходился каждый из $2^k$ равных подшагов: один неудачный подшаг из 512 валил шаг. Локальное выбирает подшаг на каждом участке отдельно.

Замер (DEBT-015, 10 сут добычи + 3 сут останова; [[локальное дробление шага проходит останов при суточном dt_integration — равномерное падает на одном подшаге из 512]]):
- останов 20B при `dt_integration` = 3600 с — 376 → 241 с;
- при 1 сут останов 19B, 20B, 21B, 20A проходит при штатном `max_retries` = 9, равномерное падало на всех четырёх;
- 21 пример — побитово.

## Что возвращается

### Состояние

`Simulator._advance` возвращает state после **последнего подшага** — это state на момент t_{n+1} = t_n + dt.

### Потоки

`face_component_fluxes_sm3s(final_state)` — мгновенные потоки при p^{n+1}, Sg^{n+1} подшага. Это то, что нужно EnergySolver для конвекции (неявная схема: потоки на уровне n+1). `WellData` на записи истории — по последнему подшагу.

### Δp/Δt и ΔRs/Δt для EnergySolver

EnergySolver вычисляет:
```
Q_ad ∝ (p^{n+1} - p^n) / h          # адиабатический эффект
ṁ   ∝ (Rs^{n+1} - Rs^n) / h         # темп дегазации (временная часть)
```

Здесь h — подшаг, p^n — начало подшага, p^{n+1} — его конец. Приближение первого порядка по времени — совместимо с первым порядком неявной схемы.

## Логирование

| Уровень | Что |
|---|---|
| DEBUG | Каждый отказавший подшаг: h, текст `HydroConvergenceError` (dt, t, итерации, невязка) |
| INFO | Шаг раздроблен: число подшагов, наименьший подшаг, число отказов гидродинамики |
| ERROR | Не сошлось и на dt/2^max_retries → RuntimeError «HydroSolver не сошёлся при дроблении шага до dt/N = …» |

## Взаимодействие с TimeSchedule

TimeSchedule задаёт dt_actual = dt_hist / n_sub. Simulator вызывает `_advance` на каждом таком шаге и дробит его сам. Состав истории не меняется: записи только на концах интервалов расписания (DEBT-013).

## Проверенные нюансы

### Повтор с начала подшага

Отказавший подшаг повторяется из состояния своего начала. Принятые подшаги не пересчитываются. Прежнее равномерное A-retry начинало каждую попытку с state_n и пересчитывало всё.

### Управление скважиной

`set_bhp_control` / `set_oil_rate_control` адаптер вызывает в каждом `solve` (идемпотентно). Дебит (OIL_RATE) постоянен на шаге расписания, добыча за подшаг пропорциональна h.

### Отказ на наименьшем подшаге

Если при dt/2^max_retries Newton не сходится — лимита не хватает либо задача слишком жёсткая. Текст отказа называет глубину, $t$ подшага, число двухфазных ячеек, $\max S_g$ и оба рычага (`numerics.max_retries` и `time.dt_integration`), а причину не называет. Отказ бывает и не из-за величины шага ([[BUG-017]], [[BUG-018]] до исправления, [[BUG-019]]).

### Режимы (gas_active) между подшагами

Подшаг передаёт state с обновлённым regime следующему. advance использует gas_active как начальное приближение и сам определяет набор фаз. Корректно.

## История

### До DEBT-015: равномерное A-retry в адаптере

Adapter при расходимости сам дробил dt на $2^{attempt}$ **равных** подшагов, attempt ≤ `max_retries`, каждая попытка — с исходного state_n. Наружу — один HydroResult. Исчерпание — RuntimeError «HydroSolver не сошёлся после N подшагов …».

### Пересмотр 2026-09-19, BUG-010

**Что было не так.** Положение «EnergySolver не знает о внутренних подшагах гидро» означало: когда гидродинамика дробила dt на n_sub подшагов, энергия всё равно решалась **одним** шагом по полному dt. Расщепление «гидро → энергия» имеет порядок O(dt) и применялось на интервале, который одна из его половин уже забраковала.

Измерено на примере 07, первый шаг dt = 450 с, при **идентичном** гидро-состоянии (p совпадает побитово):

| способ | T[0] | ошибка против эталона |
|---|---|---|
| эталон (9 × 50 с) | 352.322361 К | — |
| энергия 1 × 450 с (как было) | 350.934699 К | **−1.387663 К** |
| энергия 2 × 225 с | 352.262752 К | **−0.059609 К** |

Улучшение в 11.8 раза при тех же потоках — меняется только число шагов энергии. Ошибка была немонотонной по dt_integration: dt = 450 с давал результат в 11 раз хуже, чем dt = 900 с.

**Что сделали тогда.** `HydroResult.n_substeps` сообщал наружу фактическое дробление. `Simulator._advance` при `n_substeps > 1` отбрасывал пробный результат и проходил интервал заново, гидро и энергию вместе (рекурсия с `allow_subdivision=False`, вложенность — один уровень). Гидро-подшаги считались дважды.

**Баланс массы (DEBT-039).** Адаптер интегрировал потоки через забой и контур по своим подшагам в `HydroResult.int_G_*`. Без этого невязка шага была бы $8.7\cdot10^{-2}$ вместо $6.5\cdot10^{-12}$. После DEBT-015 подшаг у адаптера один и интеграл равен dt·G, но поле остаётся: оно нужно решателю с внутренними подшагами.

**Что осталось в силе.** Потоки — мгновенные при n+1: поток последнего подшага ближе к эталонному мгновенному (1.59e-04), чем среднее по подшагам (5.43e-04).

**Остаточный долг** — повторный проход и обратный канал `n_substeps` — закрыт [[DEBT-015]].
