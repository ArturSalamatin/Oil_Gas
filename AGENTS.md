## Описание проекта

Теоретическая разработка математической модели призабойной зоны пласта (ПЗП) в окрестности нефтедобывающей скважины. Модель фильтрации в рамках подхода Black Oil. При необходимости уточнить детали, читай two_phase_energy.tex. Он находится в папке method_of_moments.

- **Фазы:** нефть с растворённым газом (o) и свободный газ (g). Воды нет.
- **Температура:** определяется балансом энергии многофазной системы. Ключевые эффекты: Джоуля--Томсона, адиабатический, скрытая теплота разгазирования, изменение фазового состава.
- **Стадия проекта:** проектирование и реализация PDE-солвера `numerical_solver/` (FVM на радиальной сетке). Метод моментов (`method_of_moments/`) – завершённый, нерабочий подход; только для справки, никаких зависимостей от него.
- **Язык документов:** русский (LaTeX).
- **Язык кода:** Python 3.10+ (numpy, scipy, matplotlib).

### Конвенция знаков (numerical_solver)

**Положительное направление – от скважины, в сторону роста радиальной координаты r.**

Это относится ко всем величинам:

| Величина | Обозначение | > 0 означает | При типичном потоке |
|---|---|---|---|
| Скорость Дарси | $u_\alpha$ | от скважины | < 0 |
| Объёмный расход фазы | $Q_\alpha$ | от скважины | < 0 |
| Поток компонента | $G^o$, $G^g$ | от скважины | < 0 |
| Массовый расход фазы | $m_\alpha$ | от скважины | < 0 |
| Конвективный коэффициент | $\Phi_\alpha$ | от скважины | < 0 |

Дебит скважины: $q_{o,\text{ст}} = -G^o_{\text{забой}} > 0$.

Невязка баланса массы: $F_j = \text{accum} + G_{j+1} - G_j$.

Подробности: `vault/knowledge/decisions/конвенции-знаков.md`, `vault/knowledge/decisions/словарь-код-физика.md`.

## Физическая суть задачи

Моделируемые процессы:
1. **Фильтрация нефти с растворённым газом** – закон Дарси, ОФП, PVT-свойства (Black Oil).
2. **Разгазирование** – при $P < P_{b}$ газ выделяется из нефти; газосодержание $R_s(P,T)$ по корреляции Стендинга.
3. **Теплоперенос** – конвекция, теплопроводность, эффект Джоуля--Томсона, скрытая теплота дегазации.
4. **Динамика газовой шапки** – материальный баланс (0D) или приближение Дюпюи (PDE).

Рассматриваемые варианты моделей (simplefied_approaches/cooling_models.tex):
- М.1: JT-оценка (алгебраическая)
- М.2: Энергобаланс разгазирования (алгебраическая)
- М.3: Стационарный энтальпийный баланс (нелинейное уравнение)
- М.4: Нестационарный энтальпийный баланс (система ОДУ)
- М.5: Пространственная задача с заданным давлением (1 PDE для T)
- М.6: GORM + дегазация + температура (2–3 PDE)

Дополнительные подходы:
- Безнапорная фильтрация с запертым газом (GORM_2/)
- Метод интегральных соотношений Баренблатта (method_of_moments_isotermal/)

## LaTeX

Основной инструмент проекта – LaTeX. Все математические выкладки, постановки задач и отчёты пишутся в `.tex`.

Правила:
- Язык документов: русский.
- Кодировка: UTF-8, пакеты `inputenc`, `fontenc` (T2A), `babel` (russian).
- Формулы: `amsmath`, `amssymb`. Ключевые формулы в `\boxed{}`.
- Нумерация уравнений: `\eqref{}` для ссылок.
- Перекрёстные ссылки между моделями: указывать номер уравнения и модели.
- **Без англицизмов.** Использовать русские термины. Конкретные замены:
  - transmissibility / трансмиссибильность → **проводимость грани**
  - upstream / upwind → **против потока**, **выше по потоку** (ячейка)
  - ghost cell → **фиктивная ячейка**
  - damping → **демпфирование** или **ограничение шага**
  - solver → **решатель**
  - baseline → **базовый вариант**
  Если русский аналог неочевиден – спросить пользователя, не транслитерировать.

## Качество формулировок

Действует для любого текста проекта: постановки `numerical_solver/doc/problem_statement.tex` и других `.tex`,
README и журнала изменений решателя, заметок vault, сообщений коммитов и ответов в чате. Разделы
«Перевод и кальки» и «Стиль научного текста» ниже уточняют его для перевода и для связного научного текста.

**Сначала мысль, потом слова.** Перед абзацем сформулировать его тезис одним предложением. Если тезис
не формулируется, писать рано: сначала установить, что именно утверждается.

**Утверждение не сильнее оснований.** Каждое утверждение – либо факт со ссылкой на источник, формулу
или расчёт, либо вывод из названных посылок. Гипотеза подаётся как гипотеза. Частный случай
не обобщается на класс задач, «лучше» пишется только при наличии сравнения. Если данные выдерживают
лишь более слабую формулировку, ослабить её.

**О чужих работах.** Утверждение о первенстве («ввели задачу», «впервые предложили») пишется только
после проверки по первоисточнику. Без такой проверки употребляется нейтральный глагол: «рассмотрели»,
«предложили».

**Страницы в ссылках.** Ссылка на литературу даётся без номера страницы: «(Konieczek, 1990)»,
`\cite{<ключ>}`. Страница ставится при прямой цитате в кавычках и когда её требует стандарт
(ГОСТ Р 7.0.5). Страница, по которой утверждение сверено с источником, записывается в заметку
источника в vault, а не в текст.

**Измеримое вместо оценочного.** Не «существенно», «заметно», «весьма важный», а число или проверяемый
признак: «в 2,3 раза», «на 15%», «в пределах погрешности». Не «известно, что», а ссылка.

**Ложная категоричность.** «Зависимость отсутствует», «других режимов нет» пишутся, только если это
установлено. Недостаток данных не выдаётся за свойство явления: либо измерено, либо не утверждается.

**Порядок изложения.** Известное идёт до нового, определение – до употребления, посылка – до вывода.
Порядок разделов и абзацев следует логической зависимости, а не хронологии работы.

**Скачки уровня.** Переход от измерения к интерпретации и от частного случая к общему утверждению
предупреждается явно: «отсюда следует», «в общем случае».

**Глагол вместо отглагольного существительного.** «Осуществление проверки выполнения условий» →
«проверка условий», «производится вычисление» → «вычисляется», «производить расчёт» → «рассчитывать».
Цепочку из четырёх и более родительных падежей перестроить через предлог или глагол.

**Пустые обороты.** «Следует отметить, что», «представляет особый интерес», «играет важную роль»,
«необходимо подчеркнуть» снимаются: важность мысли видна из её содержания. Оборот, который держит
переход между мыслями, допустим. Один и тот же оборот три и более раз на документ – дефект.
Анонс раздела («В этом разделе рассматривается…», «В разделе формулируется…») снимается: раздел
начинается с содержания. Строение документа описывается один раз, в конце введения.

**Анафора без опоры.** «Это», «данный», «такой», «он» в начале предложения заменяются существительным,
если отсылка допускает два прочтения. Местоимения «его», «их», «она» читатель относит к ближайшему
подходящему существительному. Если референт стоит дальше, перестраивается порядок слов: «вычисление
на гранях потоков и порядок их суммирования», а не «вычисление потоков на гранях и порядок их
суммирования». Причастный оборот с зависимыми словами ставится после определяемого слова: «число ячеек,
попавших в двухфазную зону».

**Отсылка после смены темы.** В абзаце, открывающем новую тему или подраздел, «эти работы», «здесь»,
голое «уравнение» заменяются явной отсылкой: «работы, названные выше», «ниже», «уравнение энергии».

**Неполные конструкции.** Зависимое слово не опускается: «методы решения задач», а не «методы для задач»,
«критерий сходимости», «дебит за сутки». Предложение без глагола («Отсюда два вывода»)
достраивается глаголом: «Отсюда следуют два вывода».

**Регистр.** Текст описывает установленное, а не отношение автора к нему. Без антропоморфизма
(«решатель хочет», «схема стремится»), оценочности («величина скромная», «крайне важный»)
и разговорных оборотов («легко видеть», «грубо говоря»). Разговорное «меняется» заменяется
на «изменяется».

**Тире.** Тире только среднее «–» (U+2013) в любом тексте на любом языке: постановке, отчёте, заметке
vault, документации, комментарии в коде, сообщении коммита, ответе в чате. Длинное «—» (U+2014)
не ставится и не предлагается взамен среднего. В LaTeX тире набирается `~--`, а не `~---`.
Минус в формулах (−, U+2212) и дефис тире не являются. Правило не адаптируется ни к проекту, ни к журналу.
Исключения – служебные форматы, а не выбор тире: заголовок выпуска `## X.Y.Z — <дата>`
в `numerical_solver/CHANGELOG.md` пишет и разбирает `tools/release.py` – его не менять;
в комментариях параметров книги Excel тире нет вообще, только дефис (`tests/test_workbook_format.py`).

**Ответы в чате** подчиняются тем же правилам. Суть – в первом предложении. Утверждение не сильнее
оснований, связь между мыслями названа, кальки и пустые обороты исключены. Краткость не оправдывает
рубленого стиля и пропущенных связей.

## Перевод и кальки

**Кальки запрещены.** Калька переносит в текст конструкцию, термин или оборот другого языка,
переведённые по словам. Запрет действует в любом тексте проекта: при переводе, при пересказе
иноязычного источника и при письме на русском, если фраза построена по английской модели.

**Передавать смысл, а не слова.** Передаются все утверждения источника,
без добавлений и упрощений. Строй фраз при этом свой. Сначала установить, что утверждает исходный
текст, затем изложить так, как написал бы носитель языка в работе той же области. Число и порядок
предложений могут не совпадать с исходными. Сверка с оригиналом идёт по содержанию, а не по словам.

**Термины.** Для каждого понятия берётся термин, принятый в профильной литературе на языке текста,
а не словарный эквивалент. Если принятого термина нет, понятие описывается словами, а не новой калькой.
Типовые кальки и замены: «базируется на» → «основан на», «в терминах» → «через», «адресовать задачу» →
«рассматривать задачу», «драматически» → «резко», «многократно». Пары проекта – список «Без англицизмов»
раздела «LaTeX». Найденные при работе пары добавлять в тот список.

**Найденную кальку не латать.** Замена одного слова оставляет кальку в строе фразы. Предложение
переписывается заново, исходя из смысла.

**Аннотация на втором языке** передаёт содержание основной без добавлений и пропусков, но строится
заново по нормам своего языка.

## Стиль научного текста

Правила для постановки `numerical_solver/doc/problem_statement.tex`, других документов `.tex`, отчётов
и любого связного текста на русском. Правила о строении изложения («Перечисления» в части списков,
«Переходы между абзацами», «Заголовки», «Подразделы», «Выкладки», «Образец изложения») относятся
к научному тексту – постановке, отчётам, статьям – и на заметки vault, README и журнал изменений
не распространяются. В постановке, написанной до этих правил (на 2026-10-21 – 61 `\paragraph`,
23 списка), строение перестраивается при правке соответствующего раздела, а не отдельной массовой правкой.
Частоты считаются на документ.
Механическая проверка: `python .claude/text-check.py <файлы>` (маски раскрывает сам скрипт).

**Точка с запятой.** Не сцепляет самостоятельные предложения. Если две мысли связаны, связь
выражается союзом или вводным словом. Если не связаны, ставится точка. Точка с запятой допустима
только внутри перечня, элементы которого сами содержат запятые.

**Перечисления.** Перечень через тире или точку с запятой не заменяет рассуждение. Элементы перечня
одного логического уровня. Разнородные элементы – это не перечень, а несколько предложений.
В научном тексте списки (`enumerate`, `itemize`, маркированные списки md) не используются: пункты
встраиваются в текст. Допущения модели, этапы процесса, условия задачи излагаются связными
предложениями, каждое вместе со своим обоснованием. Исключение – список обозначений.

**Связность.** Соседние предложения соединяются явно: причина, следствие, противопоставление,
уточнение, условие. Проверка: если между предложениями не встаёт ни «поэтому», ни «однако»,
ни «то есть», связи нет и абзац перестраивается. Абзац раскрывает одну мысль, первое предложение
её называет.

**Переходы между абзацами.** Начало абзаца следует из конца предыдущего. Первое предложение
показывает, как новая мысль связана со сказанным: это следствие, следующий шаг вывода,
противоположный случай, проверка результата. Абзац, который можно переставить без потери смысла,
с соседями не связан и перестраивается. Подраздел заканчивается переходом к следующему: что получено
и для чего это понадобится дальше. Ссылка вперёд на ещё не введённую формулу или величину –
признак нарушенного порядка изложения.

**Заголовки.** Заголовки получают только разделы и подразделы (`\section`, `\subsection`;
`##`, `###` в md). Промежуточным абзацам заголовки не даются: ни `\paragraph{...}`, ни жирное
начало абзаца («**Первый этап.** …»). Если абзацу понадобился заголовок, значит, не хватает связки
с предыдущим абзацем, и писать нужно её. Окружения `remark` и подобные не заменяют связное изложение.

**Подразделы.** Подраздел раскрывает законченный шаг рассуждения целиком: постановку, вывод,
результат и его смысл. Подраздел из одного-двух абзацев объединяется с соседним. Ориентир –
не меньше половины страницы. `text-check.py` отмечает подразделы `.tex` короче 1000 знаков
исходного текста вместе с формулами.

**Выкладки.** Выкладки излагаются подробно и с пояснениями, так чтобы
читатель мог их воспроизвести. Показываются общее решение уравнения и выбор постоянных из граничных
условий, условия сопряжения в явном виде до их решения, подстановки и замены переменных,
интегрирование по частям и найденные первообразные, приравнивание коэффициентов при одинаковых
степенях малого параметра. Перед формулой сказано, что и зачем выводится, после неё – что получено.
Результат проверяется предельными случаями и согласованием с известными решениями. Оборот
«после преобразований получим» допустим, только если пропущенные шаги элементарны. При переносе
текста из источника шаги, опущенные в нём, восстанавливаются, если следуют из его формул.
Новых утверждений при этом не добавляется.

**Постановка в общем виде.** Модель и метод излагаются через обозначения: «$N$ ячеек радиальной сетки»,
а не «200 ячеек». Числа конкретного расчёта (параметры пласта примера, даты, пороги) приводятся
в разделе примеров или результатов. Конкретика в постановке представляет работу как решение частной задачи.

**Образец изложения.** Физическая картина процесса излагается до формул. Каждое
допущение модели называется вместе с обоснованием и ссылкой. Для масштабов и критериев подобия
указывается физический смысл. После результата обсуждается, что он означает и в какие известные
решения переходит в предельных случаях. Изложение ведётся в форме «введём», «подставим», «получим».

**Связки.** Называть связь не значит ставить связку в каждое предложение. Прежде чем написать
«поэтому», «при этом», «тем самым», проверить, не названа ли причина предыдущим предложением.
Если названа, связка снимается. Одна связка встречается не чаще, чем в одном предложении
из пятнадцати на документ. При правке связку не синонимизировать, а снимать.

**Связка внутри предложения.** Связка между подлежащим и сказуемым или после сказуемого
(«Интегральный баланс энергии поэтому считается суммированием по ячейкам») смещает логическое ударение
на то, что стоит после неё. Приём оправдан, только где это ударение нужно, и допустим два-три раза
на документ. По умолчанию связка стоит в начале предложения.

**Длина предложения.** Ориентир – до 25 слов. Предложение свыше 35 слов разбивается. Три и более
коротких предложения подряд (5–8 слов) дают рубленый ритм, их надо объединить.

**Союз «что».** Не более одного «что» на предложение. При двух и более заменить придаточное
отглагольным существительным, разбить предложение или употребить «поскольку», «так как», «тогда как».
Если «что» читается и как союз, и как местоимение, смысл уточняется: «показывает, что именно даёт эффект».

**Вставные конструкции.** Не вкладывать тире в тире и скобки в скобки. Одна вставная конструкция
на предложение.

**Тире вместо связки.** Фраза вида «Цена этого – время» разворачивается в полное предложение с глаголом.

**Деепричастия.** Деепричастный оборот относится к подлежащему предложения.
«Решая уравнение численно, погрешность оценивается…» – ошибка.

**Время изложения.** Сделанное в работе передаётся прошедшим временем или кратким причастием:
«рассмотрено», «учтена», «оценивалась». Настоящее время страдательного залога («рассматривается»,
«учитывается», «используется») для действий авторов не употребляется. Свойства модели, данных
и алгоритма описываются настоящим временем: «давление насыщения определяется газосодержанием»,
«капиллярное давление не учитывается». Чужие работы излагаются прошедшим временем («рассмотрели»,
«предложили») или неопределённо-личной формой («как правило, минимизируют»).

**Формула в предложении.** Выключная формула служит членом предложения. Если в ней есть знак
равенства, сказуемое перед ней не ставится: не «Дебит нефти составляет \[q_o = …\]»,
а «Дебит нефти \[q_o = …\]». Короткая ненумерованная формула, на которую нет ссылок, набирается
в строку.

**Числа.** Количественные числительные, записанные цифрами, пишутся без падежных наращений:
«из 17 кейсов», «от 5 до 16 ячеек», а не «17-ти», «5-ти» (справочники Мильчина и Розенталя).
Порядковые получают наращение по общему правилу: «5-й», «$m$-го», «1990-х».
Десятичный разделитель – точка («0.44 с») в русском и английском тексте; он единообразен в тексте,
таблицах и на рисунках. Запятая (в формуле LaTeX – `0{,}44`) – только по решению журнала или издателя.
Диапазоны и единицы записываются единообразно по всему тексту.

**Повторы.** Однокоренные слова не стоят в одном предложении и в соседних: «решатель решает систему»,
«рассчитанный расчёт». Один результат формулируется один раз на документ своими словами, в остальных
местах – ссылка на пункт или уравнение.

**Подписи к рисункам и таблицам.** Подпись объясняет, как читать рисунок или таблицу: единицы,
обозначения, условия расчёта или опыта. Выводы и интерпретация остаются в тексте. Подпись
не дублирует соседний абзац. Формула в подписи не даётся там, где хватает словесного определения.

**Термины.** Один термин – одно значение по всему тексту. Пары-двойники проекта – список «Без англицизмов»
раздела «LaTeX». Аббревиатура расшифровывается при первом употреблении и дальше пишется единообразно.
Синоним, принятый в части литературы, даётся в скобках при первом определении – «газосодержание
(растворимость газа в нефти)» – без пояснений «в литературе также называют». Организация при первом
упоминании называется полным официальным названием, а не аббревиатурой.

**Набор в LaTeX.** Пустая строка в исходнике начинает новый абзац. Поэтому её нет
перед выключной формулой и после формулы, за которой продолжается предложение («где …»), а `\noindent`
вместо этого не ставится. Закомментированные фрагменты удаляются до передачи текста заказчику:
исходник читают, а не только PDF. Перед сборкой запускается статическая проверка исходника –
`numerical_solver/tests/test_eq_references.py` (метки и ссылки на уравнения); сборка –
`pdflatex -interaction=nonstopmode -halt-on-error` (её же делает `tools/handover.py` при передаче).

**Перед выдачей текста** перечитать написанное и проверить по разделам «Качество формулировок»,
«Перевод и кальки» и этому, затем запустить `python .claude/text-check.py <изменённый документ>`.
Особое внимание – точке с запятой, числу «что», длине предложений и связкам: их частоте и положению
в предложении. Отдельно проверить наращения при числах, десятичный разделитель, тире и время глаголов
в изложении сделанного. Для научного текста также проверить, что нет списков и заголовков
у абзацев, каждый абзац следует из предыдущего, подразделы не раздроблены, а выкладки не сжаты.

### math vs numpy

Всегда `numpy`, никогда `math`. Весь код работает с массивами (`solve_ivp`, PVT-корреляции на сетке), `numpy` покрывает и скаляры, и массивы. Использовать `np.log`, `np.exp`, `np.sqrt` и т.д. Если в коде или плане встречается `math.*` – заменять на `np.*`.

### Связь формула → код

Каждая функция в `src/` содержит в docstring ссылку на уравнение из `.tex`:
```python
def compute_Cp(p, T, Sg, fluid, rock):
    """Коэффициент ёмкости C_p. Ур. (eq:Cp) moments_method.tex."""
```

Ссылка даётся **меткой** `\label{}` – `Ур. (eq:<метка>) <файл>.tex` в докстринге, `(eq:<метка>)` в комментарии, – не номером уравнения (`eq. 12`), не номером рядом с меткой (`eq:x (74)`, DEBT-062) и не номером строки (`problem_statement.tex:1334`): номера сдвигаются молча при любой вставке выше по документу (DEBT-010: к моменту проверки все 27 числовых ссылок `numerical_solver/` указывали не туда). Формула без собственной метки – ссылкой на ближайшую: «определение под `eq:<метка>`». Уравнение чужой статьи – словами: «формула (5) у Coats 1999». В `numerical_solver/` правило проверяет `tests/test_eq_references.py` (докстринги, комментарии, тесты, примеры, README примеров); он же – заметки `vault/knowledge/`, кроме `literature/` (DEBT-074): ссылка на постановку там тоже меткой, параграф – `ssec:<метка>`.

При изменении формулы в `.tex` – обновить соответствующую функцию.

Таблица соответствий поддерживается в планах `/plan-feature` (секция «Связь формула → код»).

## Тестирование

Пирамида тестов (pytest):

| Уровень | Что тестирует | Пример |
|---|---|---|
| Unit | Один модуль изолированно | `test_pvt.py`: Rs(p,T) при известных p,T |
| Граничные | Предельные случаи | Sg=0, p=pb, T=T0 |
| Согласованность | Физические инварианты | So+Sg=1, энергобаланс |
| Интеграционный | solve_ivp с полной системой | `test_solver.py`: rb растёт, Sg∈[0,1] |
| Валидационный | Сравнение с эталоном | VAL-001: Дюпюи, VAL-002: vs PDE |

Правила:
- Тест пишется **до или одновременно** с реализацией.
- Новый код не мёржится без зелёных тестов.
- Регрессии блокируют работу – сначала починить.

Уровни прогона (DEBT-032, `numerical_solver`, команды из `numerical_solver/`):

| Уровень | Команда | Время | Когда |
|---|---|---|---|
| Число тестов | `.venv\Scripts\python -m pytest tests/ --collect-only -q` | ~3 с | baseline в `/audit-plan`; шаги, меняющие только документы |
| Быстрый | `.venv\Scripts\python -m pytest tests/ -m "not slow" -q` | ~70 с | после каждого шага; baseline в `/implement` |
| Полный | `.venv\Scripts\python -m pytest tests/ -q` | ~10 мин | конец `/implement`; шаги с «Регресс: полный» |

- Метка `slow`: тесты на фикстуре `results` (`tests/test_examples.py`; ставится автоматически хуком в `tests/conftest.py`), `test_matrix_matches_reference`, тесты на сгущённой сетке.
- После падения – `pytest tests/ --lf -q`: только упавшие в прошлый раз.
- Ключ `-q`, не `-v`: построчный вывод 1100+ тестов засоряет контекст.

### Комментарии в коде

Комментарии нужны и полезны. Не удаляй существующие комментарии без причины. Пиши комментарии в следующих случаях:

- **Физический смысл:** что вычисляет формула, к какому уравнению относится, какие единицы.
- **Почему так:** неочевидные решения, ограничения, workaround-ы.
- **Структура:** разделение логических блоков (`# ── Внутренние грани ──`, `# ── Забой ──`).
- **Тесты:** что именно проверяется, какие физические условия заданы, какой результат ожидается и почему. Тест без комментария через месяц непонятен.
- **Конвенция знаков:** при вычислении потоков всегда указывать, какой знак ожидается и почему.
- **Upstream-логика:** какая ячейка выбирается и при каком условии.

Не пиши комментарии, которые дублируют код: `x = x + 1  # увеличить x на 1`.

## Коммиты

Пользователь коммитит сам. Никогда не создавай коммиты без явной просьбы. Не используй `git add`, `git commit`, `git push` без прямого указания.
Исключения: `/implement` и `/merge` коммитят автоматически (это часть их контракта):
- `/implement` – сначала коммитит в базовую ветку план и материалы задачи, подготовленные до реализации; затем работает в отдельном worktree `.worktrees/<id>` и коммитит код и vault задачи на её ветке. Новые задачи, обнаруженные по ходу, регистрируются в базовой ветке.
- `/merge` – запускается по слову пользователя «мерж»: push ветки задачи, `--no-ff` в базовую ветку, удаление worktree (**ветка задачи остаётся**), отметка «влит» в vault, push базовой ветки, закрытие issue. Это единственный случай, когда push делается без отдельной просьбы; `--force` – никогда.
- `tools/release.py` (FEAT-038) – выпуск: коммиты `release: X.Y.Z` и `release: начало X.Y.(Z+1).dev0` и метка в базовой ветке, один push ветки с меткой, публикация в Releases. Запускает пользователь или Claude по прямой просьбе; `/implement` его не запускает.

Если пользователь попросит коммит:
- Формат: `<тип>: <краткое описание>`
- Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `vault`, `release` (только коммиты `tools/release.py`)
- В сообщениях коммитов не упоминай себя (без "Co-Authored-By", без "Claude")
- Vault-изменения – отдельным коммитом от кода
- Stage по имени файла, не `git add .` или `git add -A`
- Не пропускай хуки (`--no-verify`) без явной просьбы
- Рабочие ветки стартуют от **базовой ветки своего направления** в отдельном worktree `.worktrees/<id>` и мёржатся обратно в неё (`--no-ff`, `/merge`); ветки после влития не удаляются

### Реестры задач (vault/roadmap/)

Каждая задача **сначала регистрируется** в локальном vault-реестре. Реестр – единственный источник правды о списке задач проекта. GitHub issue создаётся позже командой `/issue` и ссылается на запись в реестре.

**Три файла реестра** (разделение по категориям):

| Файл | Типы задач | Шаблон ID |
|---|---|---|
| `vault/roadmap/известные баги и технический долг.md` | BUG, DEBT | `BUG-NNN`, `DEBT-NNN` |
| `vault/roadmap/планируемые фичи.md` | FEAT | `FEAT-NNN` |
| `vault/roadmap/валидационные кейсы.md` | VAL | `VAL-NNN` |

**Как зарегистрировать задачу:**

1. Определи тип: BUG (дефект), DEBT (техдолг/рефакторинг), FEAT (новая функциональность), VAL (верификационный кейс).
2. Открой соответствующий файл реестра.
3. Найди максимальный номер существующих записей (grep `### <PREFIX>-`), присвой следующий.
4. Добавь секцию `### <ID>: Краткое описание` по шаблону из заголовка файла (секция «Формат записи»).
5. Статус новой записи: `🔴 ОТКРЫТ`.

**Что обязательно заполнить при регистрации** (минимум):
- **BUG:** симптом, файл, воспроизведение
- **DEBT:** текущее состояние, мотивация, затронутые модули
- **FEAT:** описание, формулы (ссылки на уравнения из `.tex`), модуль
- **VAL:** эталон, сценарий, метрика

Поля **GitHub:**, **Ветка:**, **План:** – заполняются позже соответствующими командами (`/issue`, `/plan-*`).

Нумерация сквозная внутри каждого префикса. BUG и DEBT живут в одном файле, но нумеруются независимо.

### Порядок работы над задачей

Обязательная последовательность. Не пропускай шаги, не перескакивай.

0. **Регистрация** – записать задачу в vault-реестр (см. «Реестры задач» выше). Без записи в реестре нельзя переходить к `/issue`.
1. **`/issue <ID>`** – создать GitHub issue по записи в реестре. `/issue` также принимает свободный текст – тогда регистрация и создание issue происходят за один вызов.
2. **`/plan-*`** – детальный план (`/plan-feature`, `/plan-fix`, `/plan-improve`, `/plan-validate`).
3. **`/audit-plan`** – аудит плана перед реализацией.
4. **`/implement`** – реализация по плану.
5. **`/run`** – запуск и проверка.
6. **`/merge <ID>`** – по слову пользователя «мерж»: push ветки задачи, влитие в базовую ветку, удаление worktree, push базовой ветки, закрытие issue.

Когда пользователь спрашивает «что дальше» – определи, на каком шаге остановилась задача, и предложи следующий шаг. Если для задачи нет записи в реестре – предложи зарегистрировать. Если запись есть, но нет GitHub issue – предложи `/issue`.
