# JSON-конфиг numerical_solver — структура и соглашения

> **SUPERSEDED** частично. Актуальная структура JSON: [[P8-формат-ввода-json]]. Эта заметка содержит полезные детали по валидации и описанию отдельных секций, но структура секций обновлена в P8.

## Принципы

1. **Всё в SI**: Па, К, м, с, кг. Конвертация единиц — на входе, не внутри кода.
2. **Группировка по физике**: geometry, grid, rock, pvt, relperm, thermal, initial_conditions, boundary_conditions, numerics, output.
3. **Без дублирования**: PVT-параметры задаются один раз. Разделение на «гидро-PVT» и «тепловой PVT» — ответственность кода.
4. **Валидация при чтении**: dataclasses в Python, проверка в конструкторах.

### rock

| Поле | Тип | Ед. | Описание |
|---|---|---|---|
| `porosity` | float | — | Пористость φ |
| `permeability` | float | м² | Абсолютная проницаемость k |
| `rho_cp_solid` | float | Дж/(м³·К) | Объёмная теплоёмкость скелета |

### pvt

| Поле | Тип | Описание |
|---|---|---|
| `model` | str | `"standing"`, `"table"`, `"custom"` |
| `rho_o_std` | float | Плотность нефтяного компонента при ст. условиях, кг/м³ |
| `rho_g_std` | float | Плотность газового компонента при ст. условиях, кг/м³ |
| `co_undersaturated` | float | Сжимаемость недонасыщенной нефти при p > pb, 1/Па; по умолчанию 0 (B_o выше pb не меняется). Только `"standing"` |
| `mu_o_undersaturated` | str | Вязкость нефти при p > pb(Rs): `"none"` (по умолчанию) — только через Rs (Беггс–Робинсон); `"beal"` — линейный рост с p по Билу–Стендингу (FEAT-027, [[pvt-корреляции-стендинг]]). Только `"standing"`: при `"table"` значение `"beal"` → `ValueError` |

Для `"standing"`: параметры корреляции (gamma_o, gamma_g, ...).
Для `"table"`: `oil_pvt_file` (PVTO нефти) и `gas_pvt_file` (газ), CSV в СИ — формат и требования к ветвям в [[P8-формат-ввода-json]].
Для `"custom"`: `module_path` + `class_name` (importlib).

### thermal

| Поле | Тип | Ед. | Описание |

### initial_conditions

| Поле | Тип | Ед. | Описание |
|---|---|---|---|
| `p0` | float | Па | Начальное пластовое давление |
| `T0` | float | К | Начальная температура |
| `Rs0` | float | м³ст/м³ст | Начальное газосодержание (обязательно) |

Начальное состояние однофазное ($S_g = 0$), поэтому нефть на старте недонасыщенная: `Rs0 <= Rs_eq(p0)` (то есть `p0 >= pb(Rs0)`), допуск $10^{-5}$ м³ст/м³ст. Для табличной PVT `Rs0` должен лежать в диапазоне веток `oil_pvt.csv`. Обе проверки — `SimulatorFactory.from_config`, нарушение — `ValueError` (BUG-017). До них проверяются ветви `oil_pvt.csv`: не меньше двух строк, давление строго растёт, $p_b$ растёт с $R_s$ (DEBT-038). Выход начального давления за газовую таблицу или ветки нефти — предупреждение в журнале.

### time (история + шаг интегрирования)

Аналог InjectorGPN: `t_minor_step` (шаг интегрирования) + `t_major_step` (шаги истории).

```json
"time": {
  "dt_integration": 3600,
  "history": [
    {"dt": 86400, "p_wf": 15000000},
    {"dt": 172800, "p_wf": 12000000},
    {"dt": 604800, "p_wf": 10000000}
  ]
}
```

| Поле | Тип | Ед. | Описание |
|---|---|---|---|
| `dt_integration` | float | с | Желаемый шаг интегрирования |
| `dt_after_control_change` | float или null | с | Первый подшаг после смены управления скважиной (FEAT-032); null — выключено (по умолчанию). Рекомендуется 2 с; меньше ~0.5 с — риск отказа (BUG-025) |
| `history` | list | — | Массив интервалов истории |
| `history[k].dt` | float | с | Длительность k-го интервала (шаг истории) |
| `history[k].repeat` | int | — | Число одинаковых интервалов по `dt`, ≥ 1 (по умолчанию 1; FEAT-018) |
| `history[k].duration` | float | с | Длительность этапа — вместо `dt`, в паре с `dt_out` (FEAT-018) |
| `history[k].dt_out` | float | с | Шаг записи этапа `duration` (FEAT-018) |
| `history[k].p_wf` | float | Па | Забойное давление на k-м интервале |

**Краткие формы (FEAT-018).** Объект истории задаёт время одним из трёх наборов полей; остальные поля (`control`, `p_wf`, `q_oil`, `min_bhp`) общие для всех интервалов объекта:

| форма | пример | разворачивается в |
|---|---|---|
| `{dt}` | `{"dt": 3600, "p_wf": 8e6}` | 1 интервал по 3600 с |
| `{dt, repeat}` | `{"dt": 300, "repeat": 72, "p_wf": 8e6}` | 72 интервала по 300 с |
| `{duration, dt_out}` | `{"duration": 18000, "dt_out": 3600, "p_wf": 8e6}` | 5 интервалов по 3600 с |

Разворачивает парсер (`io/config.py`, `_expand_history`) в тот же список `HistoryInterval`; решатель о блоках не знает, записи — на концах развёрнутых интервалов. Ступенчатое расписание «первый час по 300 с, далее 5 ч по 3600 с» — два объекта `{duration, dt_out}` вместо 17 явных.

Конфиги репозитория записаны краткой формой `{duration, dt_out}` (DEBT-014): 22 конфига `examples/` и `configs/` переведены скриптом `vault/issues/debt-014/probes/compact_history.py`, развёрнутые списки поинтервально прежние. Развёрнутая форма осталась у примера 18 (конфиг пишет конвертер книги прототипа: строка SCHEDULE — интервал) и у замороженных `tests/data/*`.

- Некратность `duration / dt_out` — `ValueError`; укороченного последнего интервала нет (решение пользователя 2026-10-03). Допуск $10^{-9}$ поглощает только двоичное округление десятичной записи (`0.3 / 0.1`).
- Смешанные и неполные наборы (`dt` + `duration`, `repeat` без `dt`, `duration` без `dt_out`, объект без времени) — `ValueError`. `repeat` — только целое: `72.0` и `true` отвергаются, как у `numerics.max_retries`.
- Номер в сообщении об ошибке — номер объекта в JSON, а не развёрнутого интервала.
- Каждый развёрнутый интервал — отдельный объект: правка `history[k]` после загрузки не задевает соседей.

⚠️ **Шаг записи и шаг интегрирования связаны в одну сторону.** При `dt_out < dt_integration` (или `dt < dt_integration`) подшаг на этом участке не больше шага записи: $\Delta t_{actual} = \Delta t_{hist} / \lceil \Delta t_{hist} / \Delta t_{int} \rceil \le \Delta t_{hist}$. Мелкий вывод мельчит и интегрирование, решение меняется: на примере 03 пара расписаний выше при `dt_integration = 3600` с расходится по $T$ до 0.040 К, при 300 с — совпадает побитово. Обратного — мелкого интегрирования при крупном выводе на части истории — нет: `dt_integration` один на всё расписание, свой у блока не вводился (решение пользователя 2026-10-03).

**Алгоритм подгонки шага:**
Для каждого интервала истории k с длительностью Δt_hist:
1. n_sub = ceil(Δt_hist / dt_integration) — число подшагов
2. dt_actual = Δt_hist / n_sub — фактический шаг (≤ dt_integration)
3. Выполнить n_sub шагов интегрирования с постоянным p_wf
4. Сохранить результат на конце интервала

Гарантии:
- dt_actual ≤ dt_integration (точность не хуже заданной)
- n_sub · dt_actual = Δt_hist ровно (нет накопления ошибки)
- Результаты на концах интервалов истории (не на каждом подшаге)

Ограничения: `dt_integration > 0`, `dt_after_control_change` — null или > 0, `history` не пуст, `dt > 0`, `p_wf > 0` для каждого элемента; `repeat` — целое ≥ 1; `duration > 0`, `dt_out > 0`, `duration` кратна `dt_out`.

| Поле | Тип | Описание |
|---|---|---|
| `log_level` | str | `DEBUG`, `INFO` (по умолчанию), `WARNING`, `ERROR`, `CRITICAL` без учёта регистра; иное — отказ (DEBT-008) |

структура `time.history`: число интервалов = число записей. Конфиг с этим
полем отвергается с `ValueError` — молчаливое игнорирование изменило бы
состав вывода без предупреждения. См. [[временная-сетка-и-история]].

## Реализация в Python

`config.py`:
- `json.load()` → dict
- Каждая секция → dataclass с `__post_init__` валидацией
- Верхний класс `SimulationConfig` агрегирует все секции
- При ошибке валидации — `ValueError` с понятным сообщением

## Расширяемость PVT

Три модели:
1. **standing** — встроенные корреляции Стендинга, Бэггса-Робинсона
2. **table** — CSV-таблицы (как в InjectorGPN для газа)
3. **custom** — пользовательский Python-класс, наследующий FullPVT

Для custom: `"module_path": "path/to/my_pvt.py"`, `"class_name": "MyPVT"`. Фабрика делает `importlib.import_module` + `getattr` + проверку `isinstance(obj, HydroPVT)`.
