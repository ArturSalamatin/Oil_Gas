## Описание

На контурной грани ($f = N$) уравнение энергии выбирает ячейку выше по потоку **без разбора знака потока**: свойства фаз всегда берутся из приконтурной ячейки $N-1$. При притоке с контура ($\mathcal{Q}_\alpha[N] < 0$ — штатный режим добычи) выше по потоку физически находится контур, и свойства должны вычисляться при условиях граничного условия.

Задача — **не столько точность, сколько единообразие**. В одном и том же файле `energy/tridiag.py` для одной и той же грани применены два разных уровня строгости: `compute_degassing` разбирает знак и подставляет ГУ, а `compute_convective_coefficients` и `compute_jt` — нет. За эталон принимается `compute_degassing`.

## Текущее состояние

`compute_convective_coefficients` (`energy/tridiag.py:189-196`):

```python
# Контур (f=N): upstream = ячейка N-1 (приближение).
Phi_o[N] = rho_o[N - 1] * c_p_o[N - 1] * Q_o[N]
Phi_g[N] = rho_g[N - 1] * c_p_g[N - 1] * Q_g[N]
```

`compute_jt` (`energy/tridiag.py:269-273`) — то же для $\mu_{\mathrm{JT},\alpha}$ и $p$:

```python
J_face[N] = (mu_JT_o[-1] * Phi_o[N] * p[-1]
             + mu_JT_g[-1] * Phi_g[N] * p[-1])
```

А `compute_degassing` (`energy/tridiag.py:315-326`) на той же грани делает это правильно:

```python
if G_o[N] >= 0:
    R_conv[N] = G_o[N] * Rs[N - 1]      # отток: upstream — ячейка N-1
else:
    R_conv[N] = G_o[N] * Rs_ext         # приток: состав задан ГУ
```

### Рассогласование с гидродинамикой — доказано прямым сравнением

`fluxes.py:124-145` на **той же грани** при **том же знаке потока** берёт контурные значения:

| Величина | `fluxes.py` при притоке | `energy/tridiag.py` при притоке |
|---|---|---|
| $\rho_o$ | `rho_o_ext` = `pvt.rho_o(p_ext, Rs_ext)` (стр. 51, 143) | `rho_o[N-1]` ❌ |
| $\rho_g$ | `0.0` — газовой фазы на контуре нет (стр. 145) | `rho_g[N-1]` ❌ |
| $R_s$ | `bc.Rs_ext` (стр. 142) | `Rs_ext` ✅ (в `compute_degassing`) |
| $k_{rg}$ | `0.0` — $S_g\big|_{ext} = 0$ (стр. 139) | — |

То есть $\mathcal{Q}_\alpha[N]$ приходит в энергию посчитанным по свойствам контура, а домножается на $\rho_\alpha c_{p,\alpha}$ из ячейки $N-1$. Величины $\Phi_\alpha = \rho_\alpha c_{p,\alpha} \mathcal{Q}_\alpha$ оказываются собраны из двух разных состояний.

## Целевое состояние

Разбор знака $\mathcal{Q}_\alpha[N]$ по образцу `compute_degassing` и `fluxes.py`:

- $\mathcal{Q}_\alpha[N] \geqslant 0$ (отток наружу) — свойства из ячейки $N-1$, как сейчас;
- $\mathcal{Q}_\alpha[N] < 0$ (приток с контура) — свойства при условиях ГУ:
  - $\rho_o(p_{ext}, R_s^{ext})$, $c_{p,o}(p_{ext}, T_{ext})$, $\mu_{\mathrm{JT},o}(p_{ext}, T_{ext})$;
  - газовая ветка **обнуляется**: на контуре $S_g\big|_{\Rext} = 0$, свободного газа нет;
  - в `compute_jt` давление в операторе против потока — $p_{ext}$, а не $p[N-1]$.

**Инфраструктура готова, менять контракты не нужно.** `BoundaryConditions` (`state.py:96-106`) уже несёт все четыре величины: `p_ext`, `T_ext`, `Rs_ext`, `Sg_ext`. Объект `bc` уже приходит в `solve` целиком (расширение контракта было сделано в рамках DEBT-009, #29). Требования постановки

`doc/problem_statement.tex`:
- строки 1461-1472 — общий принцип: «на граничной грани в операторе против потока значения за границей заменяются граничными условиями»;
- строки 1480-1485, `ssec:bc_disc`, подпараграф «Температура»: на $r = \Rext$ против потока берётся $T = \Tpl$ — принцип уже применён к $T$ и к $R_s$, но не к $\rho_\alpha$, $c_{p,\alpha}$, $\mu_{\mathrm{JT},\alpha}$;
- строки 1436-1437, 1450-1455, `eq:bc_flux_ext` — подвижность на контуре берётся из условий ГУ при $S_g = 0$, $k_{rg} = 0$.

Явной формулы для $\Phi_\alpha$ на контурной грани при притоке постановка не даёт — вероятно, её стоит дописать (см. этап 1).

## Анализ вариантов решения

### Вариант 1. Скалярные контурные свойства внутри `compute_convective_coefficients`

**Суть.** Передать `bc` в метод, вычислить $\rho_o^{ext}$, $c_{p,o}^{ext}$ по образцу `fluxes.py:46-55`, выбрать ветку по знаку $\mathcal{Q}_\alpha[N]$.

**Изменения.** Сигнатуры `compute_convective_coefficients` и `compute_jt` (+ вызовы в `solve`); ~15 строк.

**Плюсы.** Минимальная правка; прямая симметрия с `compute_degassing`; PVT на контуре считается один раз на шаг.
**Минусы.** Дублирует вычисление контурных PVT, уже сделанное в `fluxes.py` (два вызова `pvt.rho_o(p_ext, ...)` на шаг вместо одного).

### Вариант 2. Прокинуть готовые контурные свойства через `HydroResult`

**Суть.** `fluxes.py` уже посчитал `rho_o_ext` и знает `rho_g_up_e = 0.0`. Добавить их в `HydroResult` и использовать в энергии.

**Изменения.** `state.py` (`HydroResult`), `fluxes.py`, `hydro/prototype_adapter.py`, `energy/tridiag.py`.

**Плюсы.** Единственный источник истины для контурных свойств — рассогласование становится невозможным по конструкции.
**Минусы.** Расширяет контракт `HydroResult` (затрагивает адаптер прототипа и его тесты); в энергии нужны ещё $c_p$ и $\mu_{JT}$, которых гидродинамика не считает, — прокидывать пришлось бы только часть, и единство источника получится неполным.

### Вариант 3 (рекомендуемый). Вариант 1 + отдельный вспомогательный метод

**Суть.** Вариант 1, но контурные свойства считаются одним приватным методом `_ext_properties(bc)`, возвращающим словарь ($\rho_o$, $\rho_g = 0$, $c_{p,o}$, $c_{p,g}$, $\mu_{\mathrm{JT},o}$, $p$). Оба метода берут значения оттуда.

**Плюсы.** Одна точка истины внутри модуля энергии; `compute_jt` и `compute_convective_coefficients` не расходятся друг с другом (нынешняя проблема в миниатюре); PVT на контуре — один вызов на шаг; контракты `HydroResult` и ABC не трогаются.
**Минусы.** +1 метод в классе.

Рекомендуется **вариант 3**: он устраняет именно тот класс дефекта, из-за которого задача открыта, — расхождение двух мест, делающих одно и то же.

## План решения

### Этап 1. Подготовка и baseline
1. Зафиксировать baseline: полный набор 851 passed / ~360 с (текущий `HEAD`).
2. **Замерить масштаб дефекта на наблюдаемом сценарии.** Готовый рецепт из DEBT-009 (#29): пример 10 с `p0 = 15.05e6` опускает $p_{N-1}$ ниже $p_b$ при сохраняющемся притоке; для $R_s$ это давало $\Delta E_{deg} = 9.5\cdot10^6$ Дж (0.14 %). Прогнать до/после, получить число — **не оценивать умозрительно**.
3. Проверить, нужна ли правка `problem_statement.tex` (`ssec:bc_disc`): дописать формулу $\Phi_\alpha$ и $\mathcal{J}$ на контурной грани при притоке.

### Этап 2. Реализация
4. Добавить `_ext_properties(bc)` — контурные PVT по образцу `fluxes.py:46-55`, газовая ветка нулевая.
5. Правка `compute_convective_coefficients`: ветвление по знаку $\mathcal{Q}_\alpha[N]$.
6. Правка `compute_jt`: то же для $\mu_{\mathrm{JT},\alpha}$ и $p$ на грани $N$ — **согласованно**, иначе неединообразие переедет из одного метода в другой.
7. Обновить комментарии: убрать пометку «(приближение)» и ссылку на этот issue.

### Этап 3. Верификация
8. Обновить эталон в `tests/test_energy_matrix_examples.py` (`_ref_convective`, `_ref_jt`) **по постановке**, а не копированием кода ядра — иначе тест зафиксирует реализацию вместо постановки и перестанет ловить расхождение.
9. Прогнать DEBT-016 (14 тестов): падение до обновления эталона ожидаемо и является признаком, что тест работает.
10. Полный набор; пересмотреть эталонные значения в `test_examples.py`, если сдвиг превышает их tolerance.
11. **Обратный ход**: внести ошибку (взять ячейку $N-1$ при притоке) и убедиться, что обновлённый эталон её ловит — по образцу проверки DEBT-016.
12. Завести конфиг/тест, где ветка притока с $S_{g,N-1} > 0$ действительно нагружена: иначе правка останется непокрытой, как это было с DEBT-009.
