# Аудит плана

Проверяй план по семи направлениям из [references/dimensions.md](references/dimensions.md). Результат – отчёт раунда с основаниями, ограничениями и хешем проверенной версии. Самопроверка автора плана не заменяет независимый аудит субагентом после `plan-*`.

## Режимы

- **Автоматический:** основной агент после сохранения плана запускает `plan-auditor` последовательно, не более трёх раундов за вызов планирования. В Codex используй `collaboration.spawn_agent` с `fork_turns="none"`. Передай абсолютный корень проекта, путь к `AGENTS.md`, этому навыку и [контракту аудитора](../../agents/plan-auditor/agent.md), ID, путь и SHA-256 плана, номер, фокус и путь отчёта. Для других сред используй их доступный механизм запуска. Файл спецификации сам по себе агента не запускает.
- **Прямой вызов:** выполни аудит указанного ID или плана в основной беседе. Прямой аудит не выдавай за автоматический независимый раунд субагента.
- Если инструмент субагента недоступен или не вернул проверяемый результат, сообщи это. Не объявляй план прошедшим независимый аудит и не запускай `implement` автоматически.

## Порядок раунда

1. Найди план, запись задачи, связанные issue, черновик `vault/issues/<id-lowercase>/00-draft.md` при наличии, решения и файлы по области задачи. Для старого плана без черновика работай по имеющимся источникам. Не меняй реализованный или выполняемый план автоматически.
2. Зафиксируй полный SHA-256 байтов плана и состояние дерева. Если статус Git получен не полностью, не утверждай чистоту или отсутствие пересечений и отметь непроверенную область. Проверь направления 0–6, исполняя уместные безопасные проверки и фиксируя команды, пути и результат. Для `numerical_solver` используй актуальную постановку и уровни проверок `AGENTS.md`. Для прототипа используй его отдельные проверки. До запуска расчёта или сборки прочитай `.agents/project/overview.md`.
3. Каждую находку обоснуй: место плана, свидетельство, последствие, рекомендация и необходимость решения пользователя. Отделяй блокирующие, существенные и уточняющие замечания. Непроверенное указывай явно. Пробы помещай в `vault/issues/<id-lowercase>/probes/`, не изменяя рабочий код и пользовательские данные.
4. Сохрани отдельный отчёт `vault/issues/<id-lowercase>/audit-r<N>.md` по [references/report.md](references/report.md), не перезаписывая предыдущие. Субагент не правит план, реестр и GitHub, не коммитит и не запускает других агентов. По прямому запросу без ID согласуй путь отчёта с расположением проверяемого плана, не придумывая ID задачи.
5. Верни сводку по формату отчёта. Основной агент сверяет файл, ID, номер, счётчики и хеш с входом и повторно вычисляет хеш плана. Изменившийся план или неполный отчёт не считается проверенным.

## Завершение цикла

Основной агент рассматривает отчёт и вносит обоснованные исправления после завершения раунда. Вопросы, требующие решения пользователя, передаёт с основаниями. Содержательные изменения плана и исправления блокирующих находок требуют повторной проверки новой версии. Различай локальный хеш файла и хеш коммита. Проверенный хеш храни в отчёте, а не внутри хешируемого плана.

Вердикт «готов» допустим при совпадении текущего и проверенного хеша, выполнении обязательных проверок и отсутствии нерешённых блокирующих находок. «Условно» перечисляет неблокирующие ограничения, «не готов» – блокирующие проблемы или непроверенные существенные изменения. При исчерпании трёх раундов не объявляй непроверенные исправления готовыми: предложи отдельный повторный аудит.

Основной агент сохраняет текст комментария в `vault/issues/<id-lowercase>/04-comment-audit.md` и при наличии issue публикует или обновляет комментарий в рамках вызванного рабочего процесса. Не создавай дублирующий комментарий. Отчёт и комментарий не являются коммитом или push. `/implement` запускается отдельно по запросу пользователя.
