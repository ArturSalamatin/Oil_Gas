# Проверки и восстановление при влитии

## 1. Определение задачи и исходного состояния

- [ ] Найден актуальный план в worktree задачи или, если его нет, в основном каталоге. Установлены ID, статус, ветка задачи, базовая ветка, путь worktree и issue.
- [ ] Реализация завершена, известны результаты её проверок. Основной каталог находится на правильной базе. Для `numerical_solver` это `numerical_scheme/implementation`, а не `master` или `main`.
- [ ] Проверены `git worktree list`, состояние worktree и индекса, локальная ветка и её отношение к базе. Если ветка уже влита, не повторяй мерж: установи, какие последующие стадии уже выполнены.
- [ ] Сравнены изменённые веткой пути с незакоммиченными и неотслеживаемыми путями основного каталога. Пути с пробелами и кириллицей считываются как данные Git, а не разбираются по предполагаемым кавычкам. Незнакомые изменения не перезаписываются.
- [ ] В пересекающихся общих файлах vault (`vault/roadmap/*.md`, `vault/00-home/index.md`) предусмотренный проектом предварительный коммит содержит файлы целиком. Остальные планы, заметки, черновики и код автоматически не включаются. После коммита проверка пересечений повторяется.
- [ ] Игнорируемые результаты, которые нужно сохранить после удаления worktree, установлены и сохранены отдельно. Чистый `git status` не означает отсутствия игнорируемых файлов.

Пример чтения состояния из основного каталога:

```powershell
git branch --show-current
git worktree list
git status --porcelain
git diff --name-only <база>...<ветка-задачи>
git merge-base <база> <ветка-задачи>
git log --oneline <база>..<ветка-задачи>
```

Проверь коды возврата и полноту вывода. Перед мержем сообщи ветку, базу, точку ветвления, состав предварительного коммита общих файлов и необходимость проверки итогового дерева.

## 2. Проверка итогового дерева

Сравни изменения базы после точки ветвления с областью задачи и её зависимостями. Учитывай исходники, тесты, конфигурации, зависимости, прототип, документацию и настройки сборки. Если они могут повлиять на результат, итоговый мерж нуждается в проверке. Само отсутствие пересечения по именам файлов не доказывает независимость.

Проверяй итоговый коммит в изолированном worktree, чтобы незакоммиченные файлы основного каталога не исказили результат. Используй подходящий уровень тестов и отдельные проверки прототипа, если они затронуты. Проверь, что запускаются пакеты из дерева проверяемого коммита. Если базовая ветка локально уже содержит мерж, но обязательная проверка не прошла, не отправляй базу и не удаляй worktree. Зафиксируй результаты и сообщи состояние. `reset`, `revert` и другие способы отката выполняются только при соответствующем разрешении.

## 3. Конфликты

Сохраняй содержание обеих сторон. В реестрах и индексах проверь границы записей и принадлежность полей задачам. В `numerical_solver/CHANGELOG.md` при конфликте в разделе «Не выпущено» сохрани пункты обеих сторон, сведи одноимённые подразделы и проверь формат профильным тестом. Не считай конфликт разрешённым только из-за отсутствия маркеров.

Если смысл решения неоднозначен или затронута чужая работа, оставь состояние доступным для разбора и сообщи конкретные варианты. Не выполняй разрушительное восстановление, `git merge --abort` или `reset` без разрешения. Незавершённый мерж нельзя объявлять успешным.

## 4. Удаление worktree

1. Снова проверь статус worktree и наличие сохраняемых результатов. Незакоммиченные и неотслеживаемые материалы не удаляй. Проверь абсолютный целевой путь внутри `.worktrees/` проекта.
2. Выведи процессы и терминалы из удаляемого каталога. Используй `git worktree remove` без `--force`. Ветку задачи не удаляй.
3. Если удаление не удалось, проверь регистрацию worktree, остаток каталога и причину. При занятом файле или пользовательских данных не применяй принудительное удаление. Если Git уже снял регистрацию, не считай это доказательством безопасности остатка: отдельно проверь его и ранее сохранённые игнорируемые данные до любых последующих действий.
4. Проверь `git worktree list` и сохранность ветки. Результат фиксируй по факту, включая случай, когда каталог удалить не удалось.

## 5. Фиксация, отправка и issue

- [ ] Установлены хеш merge-коммита и его первого родителя. В плане и реестре указаны дата, результат проверки, статус worktree и сохранённая ветка. Индекс vault обновлён, если это требуется.
- [ ] Vault закоммичен отдельно и по явным путям. Список коммитов между удалённой и локальной базой просмотрен до push и отражён в отчёте.
- [ ] Ветка задачи отправлена до мержа. База отправлена после успешной проверки и отметки vault. Не используй `--force`, автоматический `pull` или `rebase` при отказе сервера.
- [ ] Issue закрывается только после успешной отправки базы. При отсутствии issue или ошибке закрытия это состояние указано пользователю. При повторном запуске не выполняй уже завершённые стадии повторно без проверки.

## 6. Шаблон итогового отчёта

```text
Задача: <ID>
Мерж: <ветка> → <база>, <хеш> поверх <первый родитель>
Предварительный коммит общих файлов: <хеш и пути / не потребовался>
Конфликты: <файлы и результат / нет>
Проверки итогового дерева: <команды и результаты / обоснование неприменимости>
Worktree: <путь и состояние>; ветка <сохранена / фактическое состояние>
Vault: <хеш коммита или незавершённое действие>
Push: <состояние ветки и базы, список отправленных коммитов>
Issue: <номер и состояние / отсутствует>
```
