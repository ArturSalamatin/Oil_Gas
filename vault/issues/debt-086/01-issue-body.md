## Описание

Описание выпуска на GitHub трудно читать. Каждый перенос строки в разделе журнала `numerical_solver/CHANGELOG.md` превращается в `<br>`, а пункт задачи – сплошной абзац из 3–8 предложений, в котором взгляду не за что зацепиться. Нужно, чтобы описание выпуска читалось по смысловым блокам: номер задачи выделен, суть видна в первой строке, «было», «стало» и изменившиеся числа отделены друг от друга.

Задача одна на всё оформление (решение пользователя 2026-10-22): механическую часть делает скрипт выпуска, смысловое деление пункта задаёт команда `/implement`, соответствие формы проверяет тест.

## Текущее состояние

`tools/release.py` (`build`) берёт текст раздела выпуска из журнала функцией `section_body` и без изменений пишет его в `notes.md`, а `gh release create --notes-file` публикует его как описание выпуска.

Строки пунктов журнала перенесены по ~76 знаков. В файле `.md` такой перенос мягкий: `CHANGELOG.md` на GitHub выглядит нормально. В описании выпуска GitHub ставит на месте каждого переноса `<br>`. Проверено на v1.0.6 (`gh api repos/ArturSalamatin/Oil_Gas/releases/tags/v1.0.6`, поле `body_html`): пункт FEAT-039 вышел 14 строками, каждая обрывается `<br>` в произвольном месте фразы.

Шаблон `/implement` 4.1 – `- **<ID>.** <Задача>. <План реализации>. <Результат>.` – даёт один абзац. Границы между задачей, решением и результатом не видны, изменившиеся числа примеров идут в той же строке, что и описание поведения.

Строка `NOTES_TAIL`, которой заканчивается каждое описание выпуска, содержит длинное тире «—» вопреки правилу «Тире» CLAUDE.md.

## Целевое состояние

Пункт журнала в разделе «Не выпущено»:

```markdown
- **FEAT-039.** Пуск скважины считается сменой режима.

  *Было.* Нарастающий шаг `time.dt_after_control_change` действовал только
  после смены режима. Пуск из равновесия шёл полным шагом `time.dt_integration`,
  и первая запись после пуска имела погрешность первого порядка по времени.

  *Стало.* При заданном поле первый шаг после пуска начинается с подшага
  не длиннее h0 и удваивается; в журнале расчёта – «первый шаг от … с (пуск)».
  Конфигурации без поля (`null`) считаются как прежде.

  *Числа.* Меняются первые записи после пуска, дальше отличия затухают.
  - пример 22, через 1 мин: дебит нефти 10.67 → 8.21 м³ст/сут, p(r_w) 151.79 → 151.38 бар
  - пример 17: T(r_w) +0.050 К на 1 сут, −0.0003 К на 30 сут
```

- первая строка – номер задачи жирным и суть одной фразой;
- блоки `*Было.*`, `*Стало.*`, `*Числа.*` – абзацы с отступом в 2 пробела, через пустую строку, метки курсивом (решение пользователя);
- `*Числа.*` – только если при тех же исходных данных меняются результаты (правило шапки журнала): какие величины и насколько, вложенным списком;
- между пунктами – пустая строка; десятичный разделитель – точка, тире – «–».

В описании выпуска строки каждого абзаца склеены в одну, поэтому `<br>` внутри абзацев нет. Разделы 1.0.0–1.0.6 журнала не меняются (решение пользователя), опубликованные выпуски – тоже.

## Анализ вариантов решения

**Вариант A – только скрипт.** `release.py` склеивает строки абзацев и при необходимости сам выделяет номер задачи.
- Плюсы: команды не меняются; исправляет и старые, и новые пункты.
- Минусы: пункт остаётся сплошным абзацем. Деление на «было», «стало» и «числа» – смысловое, по тексту абзаца скрипт его надёжно не выполнит.

**Вариант B – только команда.** `/implement` 4.1 пишет абзацы без переносов строк и делит пункт на блоки.
- Плюсы: кода нет.
- Минусы: `<br>` возвращается при первом переносе строки, а все пункты 1.0.0–1.0.6 перенесены – форма держится только на дисциплине; в одном файле смешиваются две формы строк; проверки нет.

**Вариант C – комбинированный (рекомендуется, решение пользователя).** Скрипт склеивает строки абзацев при сборке `notes.md`, команда задаёт блоки пункта, тест проверяет форму раздела «Не выпущено».
- Плюсы: форма задаётся исходным `CHANGELOG.md` – тем самым файлом, который получает заказчик при передаче; скрипт только устраняет особенность отображения описаний выпусков на GitHub; отступление от шаблона ловит тест, который `/implement` 4.1 уже запускает (шаг 3).
- Минусы: правки в четырёх местах.

Склейка: строка присоединяется к предыдущей через пробел, если предыдущая непустая, а текущая после снятия отступа не начинает новый элемент – не пустая, не `#`, не `- ` (в том числе вложенный список), не ограда кода. Продолжение вложенного пункта присоединяется к нему.

## План решения

1. **Подготовка.** Число тестов (`--collect-only`). Проба: `notes.md` выпуска 1.0.6 текущим и новым способом, отрисовка обоих через `gh api markdown` в режиме `gfm` (как у описаний выпусков, без публикации): после склейки внутри абзацев нет `<br>`, текст тот же.
2. **Скрипт.** `tools/release.py`: функция склейки при записи `notes.md`; «–» в `NOTES_TAIL`; в докстринге – пункты без номера задачи, которые Claude сводит по `git log` при выпуске, пишутся по форме `/implement` 4.1.
3. **Проверка формы.** `test_packaging.py`, группа `-k changelog`: пункт верхнего уровня начинается с `- **<ID>.** `, метки блоков – только `*Было.*`, `*Стало.*`, `*Числа.*`, между пунктами пустая строка, нет «—». На примере текста – что проверка ловит каждое нарушение: на пустом «Не выпущено» после выпуска она проходит без проверки.
4. **Команды.** `/implement` 4.1 – шаблон, правила блоков (что входит, объём), образец; `/merge` – пустая строка между пунктами при разрешении конфликта.
5. **Верификация.** Быстрый уровень тестов; проба шага 1 на новом коде. Задача меняет `numerical_solver/tests/`, поэтому оставляет пункт журнала – первый в новой форме.

К планированию:
- форма пунктов без номера задачи (правки README при выпуске);
- место теста склейки строк: в срезе заказчика (`tools/handover.py`) есть только `numerical_solver/`, корневого `tools/` нет – тест в `numerical_solver/tests/`, импортирующий `tools/release.py`, сломает приёмку среза.
