# Открытые вопросы проектирования

## Q1. Единицы в JSON — чистый SI или поддержка t_unit?

**Варианты:**
- (A) Всё в SI (Па, К, м, с). Простота, нет конвертации внутри.
- (B) Поддержать `t_unit: "d"/"h"/"s"` и конвертировать при чтении.

**Решение:** (A) — чистый SI. Принято 2026-08-25.

**Статус:** решено.

## Q2. Хранить ли потоки через грани в SimulationHistory?

**Первоначальное решение (2026-08-25):** хранить только WellData, полные массивы G_o[N+1] не хранить.

**Пересмотрено (2026-08-28):** SimulationHistory хранит полные HydroResult на сохранённых шагах. Это нужно для диагностики и визуализации пространственных профилей потоков. Объём памяти контролируется структурой `time.history`: записи делаются на концах интервалов, подшаги интегрирования не сохраняются (DEBT-013; ранее — через `save_every`, параметр удалён).

SimulationHistory = {times, states, hydro_results, well_data}. Подробности: [[контейнер-simulation-history]].

**Статус:** решено, 2026-08-28 (обновлено).

## Q3. Нужна ли numba/Cython для блочной прогонки?

Единственный цикл Python на N итераций — блочная прогонка 3×3 в HydroSolver. При N=100..500 — приемлемо. При N>1000 — может стать узким местом.

**Варианты:**
- (A) Чистый numpy. Начать с этого. Оптимизировать позже.
- (B) numba.jit для блочной прогонки с самого начала.

**Рекомендация:** (A). Не оптимизировать заранее. Profile-driven.

**Статус:** снят 2026-10-15 ([[DEBT-077]]) — блочной прогонки нет и не будет: гидродинамику решает прототип (разреженный якобиан, `splu`, [[DEBT-033]]). Прежнее решение — начинать с чистого numpy.

## Q4. Стратегия тестирования

Из CLAUDE.md — пирамида тестов. Для numerical_solver:

| Уровень | Что | Примеры |
|---|---|---|
| Unit | Один модуль | test_pvt: Rs(p) при известных p; test_grid: объёмы, проводимости |
| Граничные | Предельные случаи | Sg=0 (однофазная), p=pb, dt→0, N=3 (минимум) |
| Согласованность | Физические инварианты | So+Sg=1, баланс масс (сумма потоков = изменение массы) |
| Интеграционный | Полный шаг | Один шаг Ньютона сходится, T решается прогонкой |
| Валидационный | Сравнение с эталоном | Стационарный поток (аналитика), Buckley-Leverett, ODE-решатель |

**Статус:** решено. Детали: [[стратегия-тестирования]], [[порядок-реализации-модулей]]. 2026-08-25.

## Q5. Корреляции Стендинга — какой набор?

**Решение:** переиспользовать корреляции из method_of_moments/src/pvt/correlations.py, добавив:

| Свойство | Корреляция | Новое |
|---|---|---|
| Rs_eq(p) | Standing 1947 | переиспользовать, векторизовать (math→numpy) |
| Bo(p, Rs) | Standing (p<pb) + exp-сжимаемость co (p≥pb) | **добавить** ветку p≥pb |
| dBo/dp\|_{Rs} | 0 при p<pb, -co·Bo при p≥pb | **новое** |
| μ_o(p, Rs) | Beggs-Robinson (p<pb) + Бил–Стендинг (p>pb, опция `mu_o_undersaturated = "beal"`) | ✅ решено в FEAT-027 (2026-10-03); Васкес–Беггс отвергнут — расходится при pb → 0; dμ_o/dp в коде не нужна (FD-якобиан) |
| μ_g(p) | Lee-Gonzalez-Eakin | переиспользовать, **добавить** dμ_g/dp |
| Bg(p) | Идеальный газ (z=1) | переиспользовать |

Ключевое отличие: все функции vectorized (np.ndarray), все производные аналитические.

Параметр co_undersaturated (сжимаемость нефти при p>pb) — скаляр в JSON-секции pvt.

**Статус:** решено, 2026-08-25.

## Q8. Хранить ли EnergyResult в SimulationHistory?

Сейчас EnergySolver возвращает T_new[N], которая записывается в SimulationState.T. Отдельный EnergyResult не определён и в SimulationHistory не хранится.

**Проблема:** если EnergyResult расширится диагностическими полями (Q_cond, Q_jt, Q_deg, F_conv — профили тепловых вкладов по ячейкам), их негде будет хранить для постобработки.

**Варианты:**
- (A) EnergyResult = только T_new. T уже в state → отдельное хранение в истории не нужно.
- (B) EnergyResult = T_new + диагностика (Q_cond, Q_jt, Q_deg). Добавить `energy_results: list[EnergyResult]` в SimulationHistory.

**Когда решать:** при реализации EnergySolver (фаза 5). Сейчас не блокирует — SimulationHistory определяется без EnergyResult, добавить поле потом — обратно совместимо (optional field).

**Статус:** открыт, 2026-08-28.
