# /plan-improve — план рефакторинга, миграции или улучшения

Аргумент: `$ARGUMENTS` — идентификатор задачи (например `DEBT-003`, `DEBT-007`) или номер GitHub issue.

Результат: подробный, самодостаточный план в `vault/plans/`, готовый к автономной реализации в отдельной сессии без контекста.

**Рабочая директория:** код, тесты и конфиги находятся в `method_of_moments/` (не в корне проекта). Все пути к коду — от корня проекта: `method_of_moments/src/`, `method_of_moments/tests/`, `method_of_moments/configs/`. Команды pytest — из `method_of_moments/`: `cd method_of_moments && python -m pytest tests/ -v`.

## Фаза 1: Сбор контекста

### 1.1. Проверить существующий план

```
ls vault/plans/<id-lowercase>*
```
Если план уже существует — сообщи пользователю и спроси: обновить или создать новый.

### 1.2. Загрузить задачу

Если `$ARGUMENTS` — номер issue (`#N` или просто число):
1. `gh issue view <N> --repo ArturSalamatin/Oil_Gas` → из title извлеки ID (формат: `DEBT-NNN: описание`)
2. Далее работай с извлечённым ID

1. Найди запись в `vault/roadmap/известные баги и технический долг.md` по ID
2. Если есть поле **GitHub:** — прочитай issue через `gh issue view <N> --repo ArturSalamatin/Oil_Gas`
3. Прочитай подробную заметку из `knowledge/decisions/` (поле **Подробности**)
4. Если задачи нет в vault — предложи сначала `/issue $ARGUMENTS`

### 1.3. Определить подтип

| Подтип | Признак | Пример |
|---|---|---|
| **Рефакторинг** | «разбить», «выделить», «переименовать», «монолит» | DEBT-001: split pvt module |
| **Миграция** | «заменить библиотеку», «перейти на» | DEBT-002: scipy → custom solver |
| **Удаление** | «удалить», «убрать», «мёртвый код» | DEBT-003: unused helpers |
| **Реструктуризация** | «реорганизовать», «перенести», «переименовать модули» | DEBT-004: restructure method_of_moments/src/ |
| **Инфраструктура** | «pyproject.toml», «CI», «configs» | DEBT-005: add ruff linting |

Подтип определяет шаблон этапов на фазе 3.

### 1.4. Извлечь имя ветки

1. Из GitHub issue или vault-записи (если `/issue` уже генерировал)
2. Если нет — сгенерируй: `refactor/<id-lowercase>/<slug-2-5-слов>`
3. Проверь существование: `git branch --list "<имя>"`

### 1.5. Загрузить связанные заметки

1. Wiki-ссылки из заметки — прочитать каждую
2. Связанные BUG/DEBT/FEAT/VAL — может ли текущая задача сломать обход другого бага или конфликтовать с текущей работой?
3. `vault/roadmap/планируемые фичи.md` — какие FEAT зависят от затронутых модулей

### 1.6. Исследовать код

1. **Scope:** определи все файлы, которые будут затронуты. Для рефакторинга — grep по имени класса/функции во всём `method_of_moments/`. Для миграции — все import-ы и `method_of_moments/pyproject.toml`
2. **Зависимости:** кто использует затронутый модуль? Grep по import-ам в `method_of_moments/src/` и `method_of_moments/tests/`
3. **Тесты:** какие тесты покрывают затронутый код? Grep в `method_of_moments/tests/`
4. **Границы изменений:** что НЕ должно меняться? Определи «зону неприкосновенности»

## Фаза 2: Анализ и проработка

### 2.1. Текущее состояние (baseline)

Зафиксируй текущее поведение:
- Какие тесты зелёные (`.venv/Scripts/python -m pytest tests/ -v`)
- API/интерфейсы, которые используются другими модулями
- Если релевантно — производительность (время тестов, время расчёта)

### 2.2. Целевое состояние

Опиши, как должен выглядеть код после изменений:
- Какие файлы появятся / исчезнут / переименуются
- Как изменится структура зависимостей (import graph)
- Какие интерфейсы сохранятся / изменятся
- Что станет проще (тестировать, расширять, понимать)

### 2.3. Варианты решения

Для каждого варианта (минимум 2):
- **Суть** — стратегия преобразования
- **Конкретные изменения** — какие файлы, какие преобразования
- **Промежуточные состояния** — можно ли разбить на этапы, каждый из которых работает и тесты зелёные?
- **Плюсы/минусы**
- **Риски** — что может пойти не так
- **Трудоёмкость** — файлы, строки

### 2.4. Выбор варианта

Критерии для DEBT (отличаются от багов):
- **Минимальность diff** — меньше изменений = меньше риск
- **Инкрементальность** — каждый промежуточный коммит работает и тесты зелёные
- **Обратная совместимость** — внешний API не ломается
- **Тестируемость** — результат легче тестировать, чем исходник

### 2.5. Поиск подводных камней

Чеклист. Для каждого: ✅ безопасно | ⚠️ риск, адресован | ❌ проблема

- [ ] **Все call sites найдены:** grep по имени класса/функции, import-ы
- [ ] **Зависимости пакетов:** pyproject.toml, import paths
- [ ] **Обратная совместимость API:** вызывающий код не ломается
- [ ] **Тесты:** все существующие тесты продолжают проходить
- [ ] **Circular imports:** новая структура import-ов не создаёт циклов
- [ ] **Docstrings:** ссылки на `\eqref{}` корректны после переноса
- [ ] **Configs:** если меняются имена параметров — обновлены ли `method_of_moments/configs/*.json`?
- [ ] **Связь с другими задачами:** не конфликтует ли с обходами других BUG/DEBT/FEAT/VAL?
- [ ] **Производительность:** не деградирует ли (для миграций: новая реализация не медленнее)

### 2.6. Обнаружение новых проблем

В ходе анализа могут обнаружиться новые проблемы. Для каждой:
1. Зафиксируй в плане (раздел «Обнаруженные проблемы»)
2. Блокирует ли текущую задачу? Если да — включи в план как предварительный шаг
3. Если нет — после завершения плана добавь в соответствующий реестр

## Фаза 3: Детализация плана

### 3.1. Шаблон этапов по подтипу

#### Рефакторинг (выделение модуля):

1. **Подготовка** — ветка, зелёные тесты, baseline
2. **Создание нового модуля** — файл + `__init__.py`, пустые функции с docstrings
3. **Перенос кода** — по одной функции/классу: вырезать из старого → вставить в новый → адаптировать import-ы
4. **Адаптация вызовов** — обновить все import-ы в других модулях и тестах
5. **Тесты** — новые тесты для выделенного модуля
6. **Очистка** — удалить дублирующийся код, обновить vault

Ключевое правило: **после каждого шага все тесты зелёные.**

#### Миграция зависимости:

1. **Подготовка** — ветка, snapshot тестов и производительности
2. **Добавление зависимости** — pyproject.toml, pip install
3. **Адаптация кода** — изменить import-ы, вызовы API
4. **Тесты** — все тесты зелёные, производительность не хуже baseline
5. **Удаление старого** — удалить неиспользуемый код

#### Удаление мёртвого кода:

1. **Подготовка** — ветка, доказать что код мёртвый (grep, import graph)
2. **Удаление** — по одному файлу/функции, с проверкой тестов после каждого
3. **Очистка import-ов** — удалить неиспользуемые import-ы
4. **Тесты** — все зелёные
5. **Обновление vault**

#### Реструктуризация:

1. **Подготовка** — ветка, инвентаризация текущей структуры
2. **Перемещение** — по одному модулю: перенести, обновить import-ы
3. **Адаптация тестов** — обновить import-ы в method_of_moments/tests/
4. **Тесты** — все зелёные
5. **Очистка**

#### Инфраструктура:

1. **Подготовка** — ветка, понять текущее поведение
2. **Изменение** — pyproject.toml, configs, CI
3. **Тесты**
4. **Очистка**

### 3.2. Структура шага

```
### Шаг N: <название>

**Цель:** одно предложение

**Файлы:** <полные пути от корня проекта>

**Контекст:**
Для читателя без контекста: что есть сейчас, что хотим,
почему именно так. Ссылки на vault-заметки и moments_method.tex.

**Что сделать:**
1. Конкретное действие с файлом, функцией, строкой
2. ...

**Изменения (старый → новый код):**
До:
    <текущий код>
После:
    <новый код>

**Проверка после этого шага:**
- Тесты: `.venv/Scripts/python -m pytest tests/ -v`
- Все тесты должны остаться зелёными (поведение не изменилось)

**Подводные камни:**
- <ссылки на чеклист 2.5>

**Зависимости:**
- Требует: шаг M
- Блокирует: шаг K

**Оценка:** ~N строк, ~M минут
```

### 3.3. Тестовая стратегия

Для DEBT ключевое — **тесты неизменности поведения:**

1. **Regression:** все существующие тесты зелёные после каждого шага (перечислить конкретно, какие тесты покрывают затронутый код)
2. **Unit-тесты нового модуля:** если выделяется новый класс/модуль — написать pytest-тесты
3. **Smoke-тест миграции:** если меняется зависимость — тест что новая версия даёт те же результаты
4. **Инвариантные тесты:** если задача затрагивает вычисления — проверить что результаты идентичны baseline

Формат:
```
**Тест:** <имя функции test_...>
**Файл:** method_of_moments/tests/<файл>.py (существующий / новый)
**Сценарий:** <что проверяем — на уровне задачи>
**Setup:** <конфигурация — если применимо>
**Ожидание:** <конкретные числа, неравенства, или качественные свойства>
**Baseline:** <с чем сравниваем — существующие тесты, производительность>
**Предотвращает:** <какую регрессию ловит>
```

### 3.4. Критерии завершения

- [ ] Все шаги выполнены
- [ ] Все существующие тесты зелёные
- [ ] Новые тесты зелёные (если есть)
- [ ] Старый код удалён (если это было целью)
- [ ] Import graph чистый (нет ссылок на удалённое, нет циклов)
- [ ] Визуальная верификация пройдена (если задача затрагивает вычисления)
- [ ] Vault обновлён: статус задачи, заметки
- [ ] GitHub issue прокомментирован с результатом, закрывается при merge (если создан)
- [ ] Производительность не деградировала (если применимо)

### 3.5. Загрузка контекста при реализации

```
## Как начать работу по этому плану

1. Прочитай этот файл целиком
2. Прочитай связанные vault-заметки (ссылки ниже)
3. Создай ветку: `git checkout -b <branch>`
4. Активируй venv: `.venv/Scripts/activate` (Windows) или `source .venv/bin/activate` (Linux)
5. Прогони тесты (baseline): `python -m pytest tests/ -v`
6. Запомни количество тестов и время — это baseline
7. Начни с шага 1. После каждого шага: pytest
```

- [ ] Зависимости шагов — без циклов
- [ ] Все подводные камни (2.5) адресованы
- [ ] Критерии завершения проверяемы

### Раунд 2: Корректность

Общее (для каждого шага):

- [ ] Каждый шаг самодостаточен

## Примечания

- Не создавай коммитов — пользователь коммитит сам
- Не начинай реализацию — только план

- Избыточность лучше недосказанности
- Инкрементальность: после каждого шага все тесты зелёные
- Если >15 шагов — разбить на под-задачи
- PATH для gh: `$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User")`
