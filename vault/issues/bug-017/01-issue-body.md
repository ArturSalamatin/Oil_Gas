## Описание

При табличной PVT начальное газосодержание `Rs0` выше последней ветки `oil_pvt.csv` принимается без проверки. Расчёт падает на первом шаге с `RuntimeError` и советом увеличить `numerics.max_retries`. Совет ложный: при такой постановке у шага нет решения ни при каком $\Delta t$.

Штатные примеры не затронуты: у всех табличных `Rs0` внутри своей таблицы. Страдает диагностируемость ошибки ввода. Главный сценарий табличной PVT — своя лабораторная таблица, а `Rs0` — первый «рычаг», который предлагает README примера 04 («выше 30 не задать» — но код этого не запрещает).

## Симптомы

- Таблица примера 12: ветки $R_s \in \{0, 30\}$, $p_b(30) = 15$ МПа, $p_0 = 15.5$ МПа. С `Rs0 = 150` вместо 30 `load_config` и `SimulatorFactory.from_config` проходят молча, расчёт падает через 0.7 с:
  ```
  RuntimeError: HydroSolver не сошёлся после 512 подшагов (dt_sub=7.03e+00 s).
  Увеличьте numerics.max_retries (сейчас 9). ...
  ```
- `Rs0 = 40` — тот же отказ.
- У прототипа есть диагностика выхода за таблицы — `pvt_range_warnings` (`OIL_PVT Rs above table`), её вызывает собственный цикл прототипа (`radial_blackoil/simulation.py`). Наша обёртка её не вызывает — предупреждения нет.

## Корневая причина

1. **Нет проверки на входе.** `_validate` проверяет только $R_{s,0} \ge 0$. Сверки с диапазоном таблицы и условия недонасыщенного старта $p_0 \ge p_b(R_{s,0})$ нет нигде. Начальное состояние всегда однофазное ($S_g = 0$, `regime = 2`), приток на контуре идёт с тем же $R_{s,0}$.
2. **PVT молча обрезает $R_s$, баланс массы — нет.** `BlackOilPVT` ограничивает $R_s$ крайними ветками: $B_o$, $\mu_o$ — обрезкой, $R_s^{sat}(p)$ и $p_b(R_s)$ — краевыми значениями `np.interp`. Итог: $R_s^{sat}(p) \le 30$ при любом $p$; $p_b(150) = 15$ МПа (как у 30); $B_o(p, 150) = B_o(p, 30) = 1.1993$ при $p_0$. Запас газа считается с полным $R_s = 150$: 150 м³ст газа «растворены» в нефти объёмом от $R_s = 30$.
3. **Логика переключения фаз видит пересыщение при любом давлении.** Ячейка без свободного газа с $R_s > R_s^{sat}(p)$ активируется — все 50 ячеек сразу, включая контурные при $p = p_0$. Начальное $S_g$ выделения в закрытом сосуде: $d = 120$, $S_g = d B_g/(B_o + d B_g) \approx 0.44$ при 15.5 МПа.
4. **Двухфазного решения не существует.** При $\Delta t \to 0$ перетоки исчезают, каждая ячейка — закрытый сосуд: массы нефти и газа на 1 м³ст должны уместиться в прежний поровый объём,
   $$B_o(p) + (R_{s,0} - 30)\,B_g(p) = B_o(p_0) = 1.199.$$
   Минимум левой части по таблице (30 МПа, выше $B_g$ постоянно): $1.18 + 120 \cdot 0.004 = 1.66 > 1.199$ — ни при каком $p$. Однофазное состояние с $R_s = 150$ балансам удовлетворяет, но отвергается п. 3. Тупик; дробление шага его не снимает.
5. **Попутно:** в однофазном режиме проверка пробного вектора отвергает $R_s > 1.5\,R_s^{max} = 45$ — при `Rs0 = 150` все 12 делений шага отклоняются ещё до активации. Причина отказа не в этом пороге: при `Rs0 = 40 < 45` отказ тот же (закрытый сосуд: $1.18 + 10 \cdot 0.004 = 1.22 > 1.199$).

Трассировка первого шага (пример 12, $N = 50$, $\Delta t = 3600$ с):

| `Rs0` | исходный алгоритм | запасной путь BUG-014, скважина открыта | запасной путь, скважина закрыта |
|---|---|---|---|
| 150 | однофазный Ньютон: 12 отказов проверки → отказ | то же | однофазный сходится за 0 итераций (ничего не течёт) → 50/50 ячеек двухфазные → Ньютон: $S_g$ до 0.94, отказ |
| 40 | однофазный сходится (5 итераций) → 50/50 двухфазные → отказ (3 итерации) | то же | то же, $S_g$ до 0.95 |

## Воспроизведение

Из `numerical_solver`, PowerShell. `Rs0` задаётся в памяти, файл конфига не меняется:

```powershell
$env:PYTHONPATH = "HydroSolverPrototype/Prototype_1.0.3"
.venv\Scripts\python -c "from gpn_multiphase_solver.io.config import load_config; from gpn_multiphase_solver.factory import SimulatorFactory; c=load_config('examples/12_large_drainage_radius/config.json'); c.initial_conditions.Rs0=150.0; s,st=SimulatorFactory.from_config(c); s.run(st)"
```

## Анализ вариантов решения

### Вариант 1. Проверка диапазона таблицы в фабрике

- **Суть:** после построения `BlackOilPVT` (табличная ветка `_create_pvt`, `factory.py:113`) — `ValueError`, если `Rs0` вне `[rs_values[0], rs_values[-1]]`. Сообщение: диапазон $R_s$ таблицы, $p_b$ последней ветки, что делать (добавить ветки).
- **Нижняя граница** тоже нужна: при таблице, начинающейся с $R_s > 0$ (тестовые таблицы прототипа начинаются с 5), $R_s^{sat}(p) \ge R_{s,min}$, и нефть с `Rs0 < Rs_min` молча никогда не разгазируется.
- **Плюсы:** ловит ровно этот случай до расчёта; дёшево; одно место.
- **Минусы:** только табличная PVT; не ловит $p_0 < p_b(R_{s,0})$ внутри диапазона; доступ к `rs_values` сейчас только через приватную цепочку `pvt._hydro._pvt` — нужно публичное свойство (например, диапазон $R_s$ у `PrototypePVTAdapter` / `TableFullPVT`).

### Вариант 2. Проверка недонасыщенного старта $p_0 \ge p_b(R_{s,0})$

- **Суть:** для обеих моделей через `FullPVT.pb` (`pvt/base.py:64`) в `from_config` после `_create_pvt`.
- **Плюсы:** универсально и физически осмысленно — начальное состояние жёстко однофазное, инициализации со свободным газом нет. Покрывает и путь Стендинга, где при $p_0 < p_b(R_{s,0})$ старт тоже пересыщенный (`max_rs = Rs_eq(p0)`).
- **Минусы:** **в одиночку наш случай не ловит**: у таблицы $p_b(150) = p_b(30) = 15$ МПа $< p_0 = 15.5$ МПа из-за обрезки — проверка проходит. Только вместе с вариантом 1. Открытый вопрос — ошибка или предупреждение. Исход расчёта при $p_0 < p_b(R_{s,0})$ внутри таблицы не проверялся.

### Вариант 3. Вызов `pvt_range_warnings` прототипа

- **Суть:** в адаптере на начальном состоянии (и, возможно, на принятых шагах) → `user_log.warning`.
- **Плюсы:** готовый код с тестами прототипа (`tests/test_pvt_clamp.py`); заодно покрывает выход давления за газовую таблицу, за диапазон ветки, $S_g$ за таблицу ОФП.
- **Минусы:** только предупреждение — отказ не предотвращает; на пути Стендинга у `HydroPVTtoBlackOilAdapter` нет `gp` и `max_pressure_of_rs` — вызов упадёт `AttributeError`, значит только табличный путь; стоимость на каждом шаге.

### Вариант 4. Уточнение диагностики в адаптере при отказе

- **Суть:** перед `RuntimeError` проверить, не вне ли таблицы / не пересыщено ли состояние, и заменить совет.
- **Плюсы:** ловит то, что проскочило мимо проверок на входе.
- **Минусы:** постфактум (после 10 попыток), эвристика. При вариантах 1+2 старт гарантированно допустим, и для этого бага вариант избыточен. Текст ошибки неверен и в BUG-016 (#44) — его правка уместнее там.

**Рекомендация:** 1 + 2 — одна функция проверки начального состояния в фабрике после `_create_pvt`, обе проверки — ошибки. Вариант 3 — отдельное решение (полезен, но не закрывает баг). Вариант 4 — нет.

## План решения

1. **Минимальный фикс** — вариант 1: `ValueError` при `Rs0` вне диапазона таблицы. Тест: таблица примера 12 (копия в `tmp_path`) с `Rs0 = 150` → `ValueError` с `Rs0` в сообщении; `Rs0 = 30` — проходит.
2. **Архитектурное исправление** — вариант 2: $p_0 \ge p_b(R_{s,0})$ для обеих моделей PVT; диапазон таблицы — через публичное свойство, не приватную цепочку; сообщение называет таблицу, $p_b$ и способ исправить. Решить: ошибка или предупреждение.
3. **Верификация:**
   - unit-тесты обеих проверок для обеих моделей PVT;
   - граничные случаи: `Rs0` ровно на последней ветке — проходит; $p_0 = p_b(R_{s,0})$ — проходит (пример 11: $p_0 = 15.05$ МПа при $p_b = 15$ МПа); `Rs0 = 0` у Стендинга ($p_b < 0$, примеры 01, 02) — проходит;
   - все 16 примеров загружаются (`test_examples.py`); расчёт не трогается — результаты побитово те же;
   - полный `pytest` (базовый вариант — 1025 тестов).
