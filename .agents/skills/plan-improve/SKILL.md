# Планирование технического долга

Принимай `DEBT-NNN` или номер GitHub issue, из которого можно установить ID. Если задачи нет в реестре, предложи `/draft`. Не публикуй новую задачу автоматически. Составь самодостаточный план, сохрани его и запусти автоматический аудит через `audit-plan`. Не создавай ветку, worktree, коммит и push.

## Контекст и анализ

1. Найди DEBT в `vault/roadmap/известные баги и технический долг.md`, связанный issue с комментариями, `vault/issues/<id-lowercase>/00-draft.md` при наличии, существующий план и указанные заметки. Если issue ещё не создан, предложи `/issue <ID>` и не переходи к планированию: этап публикации обязателен по `AGENTS.md`. Ранее зарегистрированной задаче не требуется создавать отсутствующий черновик. Сохрани существующий план и чужие изменения. Не создавай второй план без основания.
2. Сопоставь факты и решения из черновика с реальным деревом, зависимыми задачами и `vault/knowledge/decisions/`. Отметь предварительные решения и устаревшие сведения. Укажи базовую ветку, предполагаемую ветку задачи и состояние Git, не меняя их.
3. Определи область изменения и подтип долга: рефакторинг, интерфейс, зависимости, конфигурация, производительность, документация или инструменты. Прочитай [references/checklist.md](references/checklist.md) для проверки затронутых поверхностей. Исследуй вызовы, тесты, примеры и документацию по фактической области.
4. Зафиксируй текущее и целевое состояние, сохраняемое поведение и намеренные изменения. Числа и наблюдения подтверждай выполненной командой, источником или пробой с условиями. Если есть содержательные альтернативы, сравни их и учти решение пользователя. Не выдумывай альтернативу ради формы. Для блокирующего выбора передай вопрос пользователю.
5. Для формул и физики используй `numerical_solver/doc/problem_statement.tex` и метки уравнений, а не номера строк. Для прототипа учитывай собственные тесты и регрессию. Если формулы не относятся к задаче, не требуй их. Новые проблемы отделяй от текущего плана и регистрируй локально через `draft`, не создавая issue автоматически.

## План и сохранение

Подготовь план по [references/template.md](references/template.md). Для каждого шага укажи цель, пути, действия, зависимости, проверку, рабочий каталог, ожидаемый результат и подходящий уровень регрессии. Различай измеренное и прогнозное. Для неоднозначной правки приводи достаточный контекст «было» и «стало», сверенный с диском. Учитывай публичный API, документацию и примеры, если они затронуты. Выделяй проверку физики и граничных условий по существу задачи.

Сохрани `vault/plans/<id-lowercase> <slug>.md`, обнови ссылку реестра и индекс проекта по применимым правилам. Если есть issue, сохрани текст в `vault/issues/<id-lowercase>/03-comment-plan.md` и опубликуй его согласно процессу задачи. Сохрани факты, решения и проверки в файлах до запуска аудитора: чистый контекст не содержит историю чата.

## Автоматический аудит

После сохранения плана примени `.agents/skills/audit-plan/SKILL.md`: вычисли SHA-256 полного файла, выбери свободный номер отчёта, запусти `plan-auditor` в чистом контексте и проверь сводку, отчёт и хеш. Аудитор не правит план. Основной агент применяет обоснованные изменения после завершения раунда, передаёт пользователю блокирующие решения и повторно проверяет содержательные исправления. Не более трёх последовательных автоматических раундов на текущий вызов. Изменённый после последней проверки план и неустранённые блокирующие находки не считаются готовыми.

Отчитайся о плане, проверенных раундах, ограничениях, хеше и следующем шаге. Если субагент не выполнил аудит, сообщи об этом. Самопроверка не заменяет независимый аудит. Не запускай `implement` без отдельного запроса.
