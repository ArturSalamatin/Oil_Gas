# Выполнение, проверки и завершение реализации

## 1. Подготовка каждого шага

- [ ] Прочитан шаг и необходимые фрагменты файлов именно в worktree. Найдены существующие интерфейсы, вызовы и тесты.
- [ ] Установлены зависимости от предыдущих шагов, цель и критерий проверки. Если код или контекст устарел, адаптация сохраняет утверждённую цель. Если требуется новое предметное решение, вопрос передаётся пользователю.
- [ ] Для нового поведения подготовлен или одновременно создаётся проверяющий его тест. Для исправления дефекта проверен сценарий воспроизведения, если он применим.
- [ ] Определены затронутые формулы, API, конфигурации, документация и примеры. Для вычислений проверяется связь кода с меткой постановки, знаки и единицы.

## 2. Исполнение и регрессия

Выполняй шаги в порядке зависимостей. После изменений запусти профильный тест и предусмотренный планом уровень регрессии из правильного каталога. Для `numerical_solver` используй уровни `AGENTS.md`: быстрый после шага, полный в конце и на обоснованных шагах с полной регрессией, сбор тестов для документационных шагов. Записывай количество тестов, исходный результат, текущий результат и ограничения. Не считай сбор тестов выполнением тестов.

Если изменён прототип, отдельно проверь его тесты и предусмотренную регрессию против эталона. Сопоставь результаты с заранее заданным ожиданием. При неожиданных расхождениях исследуй причину и сохрани результаты. Не переснимай эталон без решения пользователя. Применимость визуальной и физической проверки определяется планом и характером задачи, а не наличием графика как такового.

При сбое отличай дефект изменения от проблемы среды или исходной базы по свидетельствам. После исправления повтори затронутые тесты и регрессию шага. Неподтверждённый flaky не считается разрешением игнорировать падение. Если проблема остаётся, сохрани изменения и результаты в worktree и сообщи, что проверка не пройдена.

## 3. Коммиты и новые задачи

После завершённого проверенного шага создай предусмотренный планом логически связный коммит по явным путям. Vault коммить отдельно от кода. Коммит не должен включать чужой индекс, временные результаты или незавершённые изменения. Не обходи хуки. Сообщай шаг, результат проверки и хеш.

Обнаруженную побочную проблему не добавляй молча в объём текущей задачи. Зафиксируй её через `draft` в основном vault и, если контракт `implement` предусматривает, закоммить её материалы в базовой ветке отдельно. Свяжи новую задачу с текущей. Не создавай issue автоматически. Если проблема блокирует выполнение, останови затронутую работу и сообщи причину и варианты. Продолжать независимые безопасные действия можно, если они не маскируют блокировку.

## 4. Итоговая проверка

- [ ] Выполнены шаги и критерии плана, проверены зависимости, ранее названные риски и граничные случаи.
- [ ] Пройдены итоговые тесты и требуемая полная регрессия. Для прототипа выполнены его собственные итоговые проверки. Результаты и отклонения не заменены прогнозом.
- [ ] Проверены фактические изменения относительно базы: нет случайных файлов и материалов других задач. Формулы, код, документация, API и примеры согласованы по области изменения.
- [ ] Если затронута пользовательская функциональность решателя, обновлён соответствующий раздел `numerical_solver/CHANGELOG.md` по правилам проекта. Не добавляй запись, если она не применима.
- [ ] В worktree обновлены план и реестр с фактическим состоянием «реализовано, не влито», результатами и ограничениями. Vault закоммичен отдельно.
- [ ] Сохранён `vault/issues/<id-lowercase>/05-comment-done.md`, при наличии issue комментарий опубликован в рамках процесса. При сбое публикации сообщены сохранённый артефакт и фактическое состояние.
- [ ] Отчёт пользователю называет ветку, worktree, коммиты, проверки, известные ограничения и нерешённые проблемы. Влитие и push остаются отдельным вызовом `merge`.
