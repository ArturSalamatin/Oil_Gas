## Описание

После смены управления скважиной первый шаг интервала начинается с подшага не длиннее `time.dt_after_control_change` ($h_0$) и удваивается до шага интервала (FEAT-032, #103). Первый интервал расчёта – пуск скважины из равновесия – сменой управления не считается: `TimeSchedule.first_substep_depth` возвращает 0 при `interval_idx == 0`. Исключение введено решением пользователя 2026-10-11 из-за BUG-028 (#117): малые первые шаги добычи из равновесия у примеров 19 и 21 не сходились. BUG-028 закрыта 2026-10-14 (`13c51a2`): первый шаг 19 и 21 сходится ступенью 1 при всех $\Delta t$ от 0.01 до 86400 с. Причина исключения снята, а пуск – такой же резкий переходный процесс у забоя, как останов: первые записи после пуска считаются одним шагом `dt_integration` схемы первого порядка.

Задача – считать первый интервал сменой управления (переход «равновесие → первое управление») и решить на одной базе, с каким $h_0$, с каким умолчанием и в каких примерах.

## Мотивация

- Температура у забоя – главная величина проекта; первые записи после пуска – то, на что инженер смотрит первым.
- Замеры при планировании FEAT-032 (2026-10-11, `vault/issues/feat-032/probes/sweep_first1.table.md`): разность $T(r_w)$ с нарастанием и без него на первой записи – 0.17 К (03, запись через 1 ч), 0.28 К (20, 1 ч), 0.46–0.48 К (04a, запись через 5 мин).
- План BUG-028 (2026-10-14): 19 и 21 с нарастанием от 0.11 с – счёт 5.4 и 6.5 с, max $|\Delta T(r_w)|$ 0.047 и 0.025 К.
- Передача заказчику (FEAT-031, #114): ограничение должно быть либо снято, либо описано. Сейчас оно описано только в книге Excel («кроме момента t = 0»); в README пакета и в описании поля конфигурации о пуске не сказано.
- Фаза: точность расчёта по времени.

### Что в замерах нельзя принимать как есть

1. **Метрика.** В таблице FEAT-032 – разность «с нарастанием – без», а не ошибка относительно предела по сгущению. Это оценка снизу ошибки расчёта без нарастания, а не сама ошибка.
2. **База.** Замер 2026-10-11 сделан до DEBT-063 (сетка прототипа), BUG-025 (#105), BUG-026 (#109), BUG-028. Отказы 13b и 15 при $h_0$ = 0.44 с – на сменах управления внутри истории, вероятная причина – BUG-025 (исправлена 2026-10-13); на текущей базе перепроверить. 19 и 21 отказывали на первом шаге – BUG-028.
3. **Зависимость от $h_0$ на пуске слабая.** Для 01–09, 12, 14, 20 разность почти не меняется между $h_0$ = 7.04, 1.76 и 0.44 с (03: 0.1718 К при всех трёх). Значит, на пуске ошибку первой записи задаёт сам шаг 3600 с, а не мелкость $h_0$; для пуска может хватить $h_0$ крупнее 0.11 с. Исключения – 04a (0.461 → 0.480 К) и 18 (0.012 → 0.032 К). Поле одно на пуск и останов; если пуску нужен другой $h_0$, вопрос – одно значение (меньшее) или отдельное поле. Предпочтительно одно поле.
4. **Кого изменит снятие исключения.** Не только 16 и 17, как сказано в комментарии `simulator.py:96-97`: в книге Excel умолчание поля – 0.11 с (`io/workbook_format.py:214-221`), поэтому изменится и пример 22, и любой расчёт по книге.

## Физическое/математическое обоснование

Новых формул нет. Схема первого порядка по времени (`problem_statement.tex`, `ssec:time_scheme`): ошибка шага $O(\Delta t)$. После останова характерное время у забоя – доли секунды – секунды (BUG-026: $R_s$ у забоя задают первые доли секунды, газ растворяется 7–14 с) при шаге 3600 с; для пуска это время не мерено – его даст п. 1 плана. Начальное состояние – равновесие ($p = p_{\text{пл}}$, потоков нет), то есть физически пуск – смена управления «скважина закрыта → первое управление» того же рода, что останов «добыча → закрыта».

## Предлагаемый API

Новых имён нет. Меняется смысл существующего поля `time.dt_after_control_change`:

| | Сейчас | После |
|---|---|---|
| первый интервал (пуск из равновесия) | всегда полный шаг | от подшага $\le h_0$ с удвоением, если поле задано |
| `null` | нарастания нет нигде | нарастания нет нигде (истории побитово прежние) |
| умолчание в конфиге JSON | `null` | решается при планировании (варианты ниже) |
| умолчание в книге Excel | 0.11 с, «кроме t = 0» | 0.11 с (или по замеру), без оговорки о t = 0 |

### Варианты

**A. Снять исключение первого интервала, умолчание не менять.**
- Суть: в `first_substep_depth` интервал 0 считается сменой; при `null` путь прежний.
- Изменения: `simulator.py:101-103`, комментарии и сообщения, тексты поля, тесты `TestFirstSubstepDepth`, `TestRampAfterControlChange`.
- Плюсы: минимальная правка; истории примеров без поля побитово прежние; книга Excel получает нарастание на пуске сразу.
- Минусы: инженер с конфигом JSON без поля по-прежнему получает первые записи одним шагом.

**B. A + нарастание включено по умолчанию в JSON.**
- Плюсы: точные первые записи у всех без знания о поле.
- Минусы: меняются истории всех примеров, перемер десятков чисел README и тестов; +$\log_2(\Delta t/h_0)$ подшагов на каждую смену (≈15 при 3600 с и 0.11 с); риск отказов на сменах внутри истории (13b, 15 – перепроверить).

**C. A + предупреждение `load_config` при `null`.**
- Минусы: предупреждение у каждого конфига без поля – шум, который перестают читать.

**D. A + описание в README пакета и в докстринге поля: при `null` первые записи после пуска и смен – одним шагом, с порядком ошибки по замеру.**

**Рекомендация:** A + D; B – только если замер на одной базе покажет ошибку первой записи относительно предела по сгущению, недопустимую для типичного примера (порог – решение пользователя).

### Открыто к планированию

- $h_0$ для пуска – по сгущению ряда, как у останова в BUG-026 (с учётом п. 3 выше).
- Умолчание JSON: A / B / C / D.
- В каких примерах задавать поле: сейчас – 16, 17 (и 22 через книгу); поправку мерили на 03, 04a, 20 без поля.
- Предел числа подшагов: до BUG-028 пример 19 с нарастанием на старте считался > 35 мин (план FEAT-032, предпосылка П4 неверна) – проверить, что после BUG-028 этого нет; решить, нужен ли предел.
- Первый интервал с нулевым дебитом (скважина закрыта с начала): переходного процесса нет, нарастание безвредно, но тратит подшаги. Считать ли такой интервал сменой – решить (проще – считать).
