# Перенос команд в навыки сохраняет контекст задач на всех этапах

План фиксирует договорённости о переносе команд проекта в `.agents/skills/` и дальнейшую доработку `draft` и `issue`. Пользователь переносит остальные команды последовательно. План предназначен для следующих сессий и не является планом реализации отдельной задачи с ID.

## Принятые решения

- `draft` регистрирует задачу в локальном реестре и сохраняет контекст в `vault/issues/<id-lowercase>/00-draft.md`. Навык не создаёт GitHub issue.
- `issue` публикует зарегистрированную задачу по ID после отдельного запроса. Произвольное описание само по себе не запускает публикацию.
- Все команды следует рассматривать как доступные навыки в `.agents/skills/`. Пользователь выполняет перенос последовательно. Временные проверки и правила на переходный период не добавляются.
- `.claude/commands/` остаётся архивом и не изменяется. `CLAUDE.md` также остаётся архивным и существенно не перерабатывается.
- Актуальное направление – `numerical_solver`, постановка – `numerical_solver/doc/problem_statement.tex`. Метод моментов завершён и сохраняется как справочный материал.
- Публикация issue и комментариев через `gh` изменяет GitHub. Это отдельная операция от `git push`. В обычном процессе push ветки задачи и базовой ветки выполняется при `merge`. `/implement` создаёт предусмотренные процессом коммиты без push.
- Перед переносом общих файлов vault в коммит нельзя автоматически включать незакоммиченные материалы других задач лишь потому, что на них есть ссылки в реестре.

## Артефакты по этапам

| Этап | Файлы и результат | Git и GitHub |
|---|---|---|
| `draft` | Запись в `vault/roadmap/`, `vault/issues/<id-lowercase>/00-draft.md` | Локально, без issue и коммита |
| `issue` | `01-issue-body.md`, `02-comment-open.md`, URL и имя ветки в реестре | Создание issue и комментария через `gh`, без коммита и push |
| `plan-*` | План в `vault/plans/`, ссылка в реестре, при наличии issue – `03-comment-plan.md` | Публикация комментария в issue, без push |
| `audit-plan` | Изменённый план, при необходимости `probes/` и `04-comment-audit.md` | Создание или обновление комментария в issue, без push |
| `implement` | Подготовленные материалы задачи в базе. Код, результаты и `05-comment-done.md` в рабочем дереве задачи | Предварительный коммит в базовую ветку, коммиты на ветке задачи и комментарий issue, без push |
| `merge` | Отметка о влитии в плане и реестре | Push ветки задачи, слияние и проверка, push базы, закрытие issue |

## 1. Согласовать реестр и черновики при коммитах

При коммите общего реестра целиком в него может попасть ссылка на незакоммиченный черновик другой задачи. После отправки базы ссылка будет вести на отсутствующий в репозитории файл.

**Предлагаемое правило:** перед коммитом общего реестра определить новые и изменённые ссылки на черновики и проверить наличие каждого целевого файла в дереве будущего коммита. Если файла в нём нет, остановиться до коммита и показать запись и путь. Возможные решения – отдельно зафиксировать черновик или исключить связанную запись из данного коммита с сохранением её в рабочем каталоге. Автоматически добавлять материалы другой задачи нельзя. Старым записям без ссылки на черновик новый файл не требуется.

Правило требуется учесть в навыках `implement` и `merge`, включая регистрацию задачи во время реализации и коммит отметки о влитии. Выбор между остановкой и частичным включением реестра остаётся открытым. Исходное предложение для проработки – остановка, поскольку частичное включение может затронуть параллельную работу.

**Проверки:** текущая задача с новым черновиком, чужой неотслеживаемый черновик, уже закоммиченный черновик, отсутствующий файл, ссылка из задачи, найденной при реализации, и незакоммиченные изменения существующего черновика. Проверять дерево будущего коммита, а не только рабочий каталог. Использовать изолированный репозиторий внутри проекта без push.

## 2. Уточнить `draft`

1. Отделять проверенные факты с источником, условиями и датой проверки от сведений пользователя и гипотез.
2. Различать принятые, предварительные и отсутствующие решения. Сохранять открытые вопросы.
3. Если ветка или метки обсуждались, допускать их запись как предложений. При публикации проверять их заново.
4. Не выдумывать воспроизведение, эталон или допуск. Неизвестные сведения обозначать явно.
5. Явно запретить `draft` создавать issue, коммит и push. При найденном дубликате сообщать существующий ID без автоматического создания новой записи.

**Проверки:** четыре типа задач, краткое описание и итог обсуждения, задача без формул, предварительное решение и существующая задача. Проверить ссылку из реестра на черновик в Obsidian.

## 3. Восстановление после частичной публикации `issue`

Описать локальные файлы, публикацию issue и комментария, обновление реестра и порядок восстановления после ошибки. Если issue создан, сохранить и сообщить URL. При повторном вызове определить завершённые действия и предложить выполнить недостающие без создания дубликата. Если отправка комментария завершилась неопределённо, сначала проверить GitHub. Неоднозначность и расхождения в реестре показать пользователю, не затирая данные. `--dry` не изменяет файлы и GitHub.

**Проверки:** сбои до создания issue, после создания, при отправке комментария и при обновлении реестра. Повторить каждый сценарий с подменой ответов GitHub CLI, без настоящих публикаций. Включить случай неизвестного результата отправки.

## 4. Метки и вспомогательный скрипт

В `.agents/skills/issue/references/conventions.md` назначать `critical`, `workaround` и `blocking` по содержанию задачи. Статус 🟡 сам по себе не означает обходное решение, а заполненное поле «Блокирует» может содержать «ничего».

В `.agents/skills/issue/scripts/issue_helper.py`:

1. Явно обрабатывать ошибки `gh` и `git`, пустой или некорректный JSON там, где ожидается ответ.
2. Сопоставлять точный ID, не принимая `BUG-0010` за `BUG-001`.
3. Различать отсутствующие, пустые и заполненные поля реестра. Сохранять содержимое и форматирование остальных записей.
4. Проверять ссылку на конкретный issue, а не наличие произвольной ссылки на GitHub.
5. При проверке веток различать локальное состояние и локально известные удалённые ссылки. Последние могут устареть без обращения к серверу.

**Проверки:** ошибки команд и JSON, похожие ID, заполнители и заполненные поля, повторное обновление, чужие ссылки, ошибки Git и кириллица в путях Windows. Использовать отдельные тестовые файлы внутри проекта, а не рабочие реестры.

## 5. Передать черновик в последующие навыки

При переносе `plan-fix`, `plan-improve`, `plan-feature` и `plan-validate` предусмотреть чтение существующего `00-draft.md`. Решения, границы и открытые вопросы отражать в самодостаточном плане. Состояние файлов и формул проверять заново.

При переносе `implement` и `merge` учесть правило из раздела 1 и порядок коммитов и push, указанный выше.

**Проверки:** проследить новую задачу от `draft` до `merge` и старую задачу без `00-draft.md`. Сверить пути, номера комментариев и базовую ветку во всех навыках.

## 6. Описать артефакты и актуализировать шаблон реестра

В `vault/issues/README.md` добавить `00-draft.md`, различить локальные черновики, опубликованные тексты и диагностические пробы. Для каждого файла назвать создающий этап и момент включения в Git. Различить публикацию через `gh` и `git push`.

Сверить `.agents/project/vault.md` и шаблоны реестров с текущим процессом. В шаблоне FEAT реестра заменить устаревшее указание на `moments_method.tex` актуальной постановкой. Исторические записи сохранить.

## 7. Итоговые проверки

- Проверить структуру изменённых навыков и запустить `python .claude/text-check.py` для изменённых документов.
- Выполнить тесты `issue_helper.py` и сценарии с изолированным Git-репозиторием.
- Проверить `git diff --check` и изменения на отсутствие случайных правок рабочих реестров, чужих файлов и архивных команд.
- Убедиться, что проверки не создали issue, комментарий, коммит или push в рабочем репозитории.
- В отчёте отделить выполненные проверки от сценариев, рассмотренных только по инструкциям.
