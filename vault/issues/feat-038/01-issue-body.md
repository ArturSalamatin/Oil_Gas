## Описание

Регулярные выпуски решателя для испытаний внутри команды (возможно, только автор — установка в другом каталоге). Испытатель пользуется библиотекой только как установленным пакетом. Выпуск — в Releases самого репозитория `Oil_Gas` (личный аккаунт, закрытый): два колеса и архив примеров:

- `gpn_multiphase_solver-X.Y.Z-py3-none-any.whl`;
- `radial_blackoil-1.0.3+gpn.N-py3-none-any.whl` (чистый Python — одно колесо на все ОС);
- `examples-vX.Y.Z.zip`.

Выпуск делает одна команда `python tools/release.py X.Y.Z`: проверки → смена номеров → коммит и метка → сборка из метки → самопроверка → публикация → начало следующей разработки. Вручную — только содержание раздела «Не выпущено» в `numerical_solver/CHANGELOG.md` (черновик по `git log` от прошлой метки сводит Claude по просьбе).

Схема упрощена по просьбе пользователя 2026-10-18: отдельный репозиторий выпусков, приглашения, проверка в чистом окружении внутри скрипта, подкоманды, команда `/release`, `RELEASING.md` — отменены. Порядок выпуска — в докстринге скрипта.

## Мотивация

Фаза «поставка — регулярные выпуски». Сейчас пакет ставится только из исходного дерева (`pip install -e`); выпусков и меток нет (`git tag --list` пуст, `gh release list` пуст). Без выпуска нельзя проверить, что установленный пакет работает вне репозитория, и нельзя получать обновления без копирования дерева. Номер версии и журнал уже есть ([FEAT-037](https://github.com/ArturSalamatin/Oil_Gas/issues/134)) — не хватает процедуры, которая ставит номер, собирает и публикует.

Первый выпуск — сразу после влития FEAT-038, не ждёт FEAT-031: `1.0.0`, прототип `+gpn.2`. Номер для заказчика не важен — важна финальная версия со всеми изменениями (решение пользователя 2026-10-18).

## Предлагаемый API

Команда из корня репозитория: `python tools/release.py X.Y.Z` (интерпретатор — `numerical_solver\.venv\Scripts\python`: нужны `pytest`, `packaging`, `tomllib`, `gh`).

Шаги по записи реестра:

1. **Проверки:** в `numerical_solver/` нет незакоммиченных правок; `X.Y.Z` — без `.dev`, больше прошлого выпуска (последняя метка `v*`); метки `vX.Y.Z` нет; раздел «Не выпущено» не пуст.
2. **Номера:** `__version__ = "X.Y.Z"`; «## Не выпущено» → `## X.Y.Z — <дата>`; если код прототипа изменился с прошлой метки (у первого выпуска — с `29a1ffa`, DEBT-059), `+gpn.N` → `+gpn.N+1` в литерале `radial_blackoil/__init__.py` и в требовании `numerical_solver/pyproject.toml`; коммит `release: X.Y.Z`, метка `vX.Y.Z`, push.
3. **Сборка из метки** (`git archive`), не из рабочего каталога: `pip wheel --no-deps` — ровно два колеса; архив `examples/`; самопроверка — версии в именах колёс, `tests/test_packaging.py` дерева метки зелёный.
4. **Публикация:** `gh release create vX.Y.Z` с тремя файлами, заметки — раздел журнала.
5. **Следующая разработка:** `__version__ = "X.Y.(Z+1).dev0"`, пустой раздел «Не выпущено»; коммит `release: начало X.Y.(Z+1).dev0`, push.

**Установка и обновление** (в другом каталоге): `gh release download vX.Y.Z --repo ArturSalamatin/Oil_Gas --dir wheels`, затем `pip install` по путям обоих колёс одной командой. Правило: опубликованный выпуск не меняется, исправление — новый выпуск.

## Анализ вариантов порядка шагов

Найдено при открытии: в записи реестра push (шаг 2) идёт **до** сборки и самопроверки (шаг 3). Отказ самопроверки после push оставляет на `origin` коммит `release: X.Y.Z` и метку `vX.Y.Z` без выпуска; повторный запуск с тем же номером отвергнет проверка «метки нет», а правило «выпуск не меняется» запрещает переставить метку.

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| А — как в записи | коммит, метка, push → сборка → публикация | порядок записи | отказ сборки после push — метка без выпуска на `origin`, номер потерян |
| **Б — push после самопроверки (рекомендуется)** | коммит и метка локально → сборка из локальной метки → самопроверка → push ветки и метки → `gh release create` | отказ до push откатывается локально (`git tag -d`, `git reset --hard HEAD~1` — скрипт печатает команды, сам не выполняет) | — |
| В — Б + черновик выпуска | `gh release create --draft`, сверка имён файлов (`gh release view --json assets`), затем `gh release edit --draft=false` | ловит переименование файлов GitHub (см. «Подводные камни») | ещё два вызова `gh` |

Рекомендация: Б; В — только если при планировании подтвердится переименование имён файлов с `+`.

## Подводные камни (проверено при открытии на `ee2be23`)

1. **Неотслеживаемые файлы в `numerical_solver/`.** Сейчас там лежат `configs/INPUT_TEMPLATE_THERMAL_v1_14.10.2026.xlsx` и `deliverables/` (не в git). Проверка «нет незакоммиченных правок» через `git status --porcelain` без ключа заблокирует выпуск; сборка идёт из метки, неотслеживаемые файлы в неё не попадают — проверять только отслеживаемые: `git status --porcelain --untracked-files=no -- numerical_solver`.
2. **Ветка и `origin`.** Выпуск — только из базовой ветки `numerical_scheme/implementation` основного каталога (не из worktree), локальная ветка не позади `origin` — иначе push отвергнут уже после метки. В проверки шага 1.
3. **Коммит скрипта — по именам файлов** (`__init__.py` ×2, `pyproject.toml`, `CHANGELOG.md`), не `git commit -a`: в основном каталоге обычно лежат незакоммиченные общие файлы vault.
4. **Правка «Не выпущено» должна быть закоммичена до запуска** — иначе отказ проверки 1. Порядок для пользователя: правка журнала → коммит `docs: …` → `release.py`. Записать в докстринг.
5. **Изменение прототипа — по всему, что входит в колесо:** `radial_blackoil/` и `pyproject.toml` прототипа, не только `radial_blackoil/`. С `29a1ffa` код `radial_blackoil/` менялся в 13 коммитах — первый выпуск `+gpn.2` обоснован.
6. **Комментарий `numerical_solver/pyproject.toml:22`** называет «+gpn.1» буквально — после повышения номера устареет. Заменить на «+gpn.N» в составе задачи.
7. **Номер прототипа в README** — `numerical_solver/README.md:35` (в записи реестра — строка 34, сдвиг на 1), `numerical_solver/examples/README.md:248`, `HydroSolverPrototype/Prototype_1.0.3/README.md:83`. Решение пользователя: номер → ссылка на `radial_blackoil/__init__.py`; скрипт README не правит. Исторические записи `CHANGELOG_1.0.3.md` не трогаются.
8. **Архив примеров не самодостаточен.** `examples/18_prototype_input/prototype_input.py:21` читает файлы дерева прототипа (`HydroSolverPrototype/Prototype_1.0.3/INPUT_TEMPLATE.xlsx`, `regression/inputs/T07.xlsx`, `regression/reference_imex_normalized`) — в архиве `examples/` и в колесе прототипа их нет: у испытателя пример 18 упадёт. Конфиги `*.json` примеров на файлы вне `examples/` не ссылаются (проверено). Решение — к планированию: исключить пример 18 из архива, положить нужные файлы в архив или принять как известное ограничение в заметках выпуска.
9. **Имена файлов с `+` в Releases.** GitHub переименовывает файлы выпуска со «специальными символами»; заменяется ли `+` в `radial_blackoil-1.0.3+gpn.2-…whl` — **не подтверждено** (поиск ответа не дал). Если заменяется, pip отвергнет колесо: версия в имени не совпадёт с METADATA. Проверить при планировании на черновике выпуска (`--draft`, удаляется без следа).
10. **Сборка колёс в изолированном окружении** скачивает `setuptools>=68` — нужен интернет при выпуске.
11. **Каталог сборки — в проекте**, не во временном каталоге (CLAUDE.md, «Файлы и код»): например `dist/vX.Y.Z/` в корне — `dist/` уже в `.gitignore` (строка 31). Там же исходники из метки, колёса, архив и заметки выпуска для `gh --notes-file`.
12. Установка по имени с `--find-links` допускает подмену одноимённым пакетом с PyPI — ставить по путям файлов. Файлы выпусков закрытого репозитория скачиваются только с авторизацией (`gh auth login`).
13. `tests/test_packaging.py` на Python 3.10 пропускает тесты `pyproject.toml` (`importorskip("tomllib")`) — самопроверка прошла бы пропуском. В venv проекта Python 3.13 — не мешает; скрипт должен считать пропуск отказом (`-rs` и разбор итога или проверка числа passed).
