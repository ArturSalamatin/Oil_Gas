# /plan-fix – план исправления бага

Аргумент: `$ARGUMENTS` – идентификатор бага (например `BUG-001`, `BUG-002`) или номер GitHub issue (например `#1`).

Результат: подробный, самодостаточный план в `vault/plans/`, готовый к автономной реализации в отдельной сессии без контекста.

**Рабочая директория зависит от направления задачи.** Определи её до начала работы:

| Направление | Каталог | Пакет / исходники | Тесты | Конфиги | Базовая ветка |
|---|---|---|---|---|---|
| **PDE-солвер** (текущая разработка) | `numerical_solver/` | `gpn_multiphase_solver/` | `tests/` | `configs/` | `numerical_scheme/implementation` |
| **Метод моментов** (завершён, только справка) | `method_of_moments/` | `src/` | `tests/` | `configs/` | `master` |

Все пути в планах и отчётах – от корня проекта (например `numerical_solver/gpn_multiphase_solver/factory.py`).

Команды pytest – из соответствующего каталога:
```powershell
cd numerical_solver
.venv\Scripts\python -m pytest tests/ -m "not slow" -q   # быстрый уровень, ~70 с
.venv\Scripts\python -m pytest tests/ -q                 # полный прогон, ~10 мин
.venv\Scripts\python -m pytest tests/ --collect-only -q  # только число тестов, ~3 с
```

Уровни прогона (DEBT-032): метку `slow` несут тесты на фикстуре `results` из `tests/test_examples.py` (ставится автоматически хуком в `tests/conftest.py`), `test_matrix_matches_reference` и тесты на сгущённой сетке. Полный прогон – один раз в конце реализации и на шагах, которые план помечает «Регресс: полный».

⚠️ Для `numerical_solver` тестам нужен прототип `radial_blackoil` – pytest берёт его из того же дерева (`pythonpath` в `[tool.pytest.ini_options]` `numerical_solver/pyproject.toml`, DEBT-059). Скрипты вне pytest берут установленный дистрибутив `radial-blackoil` (`pip install -e HydroSolverPrototype/Prototype_1.0.3 -e ".[dev]"`); в worktree – `PYTHONPATH` на worktree (правило 3 `/implement`).

**Правка прототипа** (`numerical_solver/HydroSolverPrototype/Prototype_1.0.3/` – `radial_blackoil/`, `run_prototype.py`): тесты `numerical_solver` её не ловят – у прототипа свои тесты и своя регрессия против эталона `regression/golden/`, сверенного с CMG IMEX (DEBT-029: правки BUG-014/016/018 месяц проверялись только на примерах GPN, расхождение с эталоном нашлось позже). Команды – из `numerical_solver/HydroSolverPrototype/Prototype_1.0.3`:
```powershell
..\..\.venv\Scripts\python -m pytest tests -q                  # тесты прототипа, 97 шт. на 2026-10-10, ~45 с
..\..\.venv\Scripts\python regression\run_regression.py --quick # регрессия T00–T11 без T05, ~8 мин
..\..\.venv\Scripts\python regression\run_regression.py         # полная, с T05, ~45 мин
```
- Сравнение с эталоном – почти побитовое (abs 2e-7 / rel 2e-10): любая смена последовательности шагов по времени даёт FAIL. Если фикс задуман как «побитно там, где исходный алгоритм сходится», регрессия это и проверяет.
- FAIL – не повод переснимать эталон: разобрать расхождение (с какого шага, как затухает), сверить с IMEX метриками `regression/evidence/FINAL_REGRESSION_METRICS_20260825a.json` на приёмочных отметках 1–30 сут (как в DEBT-029), решение о пересъёме – за пользователем; пересъём и правка – запись в `CHANGELOG_1.0.3.md` (раздел «Local changes – GPN project»).
- Перед полной регрессией зафиксировать HEAD: каждый кейс – отдельный процесс, импортирует код заново; влитая посреди прогона ветка с правкой прототипа даёт смешанный прогон.
- Выходы – `OUTPUT/REGRESSION_<время>/` (игнорируется git), удалить после разбора.

По умолчанию новые задачи относятся к `numerical_solver/`. Если задача явно про метод моментов – использовать вторую строку таблицы.

## Фаза 1: Сбор контекста

### 1.1. Проверить существующий план

```
ls vault/plans/<id-lowercase>*
```
Если план уже существует – сообщи пользователю путь и спроси: обновить или создать новый.

### 1.2. Загрузить задачу

Если `$ARGUMENTS` – номер issue (`#N` или просто число):
1. `gh issue view <N> --repo ArturSalamatin/Oil_Gas` → из title извлеки ID
2. Далее работай с извлечённым ID

1. Найди запись в `vault/roadmap/известные баги и технический долг.md` по ID
2. Если есть поле **GitHub:** – прочитай issue через `gh issue view <N> --repo ArturSalamatin/Oil_Gas`
3. Прочитай подробную заметку из `knowledge/debugging/` (поле **Подробности**)
4. Если задачи нет в vault – предложи сначала `/issue $ARGUMENTS`

### 1.3. Извлечь имя ветки

1. Из GitHub issue или vault-записи (если `/issue` уже генерировал)
2. Если нет – сгенерируй: `fix/<id-lowercase>/<slug-2-5-слов>`
3. Проверь существование: `git branch --list "<имя>"`

### 1.4. Загрузить связанные заметки

1. Из подробной заметки найди все wiki-ссылки `[[...]]`
2. Прочитай каждую связанную заметку (science, numerics, decisions)
3. Проверь, есть ли связанные BUG/DEBT/FEAT/VAL – прочитай их тоже

### 1.5. Исследовать код

Для каждого файла, упомянутого в задаче:

1. **Валидация:** проверь, что файл существует, строки актуальны
2. **Контекст:** Read окрестности ±30 строк от проблемного места
3. **Вызовы вверх:** grep – кто вызывает проблемную функцию?
4. **Вызовы вниз:** что вызывается из проблемного кода?
5. **Аналогичные паттерны:** есть ли в проекте похожий механизм, работающий правильно?
6. **Существующие тесты:** grep по именам функций в `<рабочий каталог>/tests/`
7. **Инварианты:** какие физические/математические свойства должны соблюдаться? (из vault и `moments_method.tex`)
8. **Границы изменений:** что НЕ должно меняться?

## Фаза 2: Анализ и проработка

### 2.1. Воспроизведение бага

- Какой тест воспроизводит баг (имя, файл)
- Команда запуска: `.venv/Scripts/python -m pytest tests/<file> -k "<pattern>" -v`
- Ожидаемое поведение vs фактическое
- Если теста нет – описать, как создать минимальный воспроизводящий тест

### 2.2. Цепочка причинно-следственных связей

1. Что вызывает проблему (входные данные, состояние)
2. Где именно возникает ошибка (файл, строка, переменная)
3. Как ошибка распространяется
4. Где проявляется (exception, NaN, неверный результат)

### 2.3. Целевое состояние

- Ожидаемое поведение после фикса
- Какие тесты должны стать зелёными
- Какие инварианты должны соблюдаться

### 2.4. Варианты решения

Для каждого варианта (минимум 2):
- **Суть** – что менять, в каких файлах
- **Конкретные изменения** – псевдокод или diff-like
- **Плюсы/минусы**
- **Риски**
- **Совместимость** – ломает ли существующее?
- **Трудоёмкость** – файлы, строки

### 2.5. Выбор варианта

Обоснуй выбор. Если варианты комбинируются – объясни порядок и зависимости.

### 2.6. Поиск подводных камней

Чеклист. Для каждого: ✅ безопасно | ⚠️ риск, адресован | ❌ проблема

- [ ] **Побочные эффекты:** grep по имени изменяемых функций – вызываются ли из других мест?
- [ ] **Граничные случаи:** Sg=0, Sg=1, p=pb, T→T0, rb→rw, rb→Rext, деление на ноль, NaN
- [ ] **Производительность:** аллокации внутри горячих циклов (интегрирование, ODE step)?
- [ ] **Обратная совместимость:** изменится ли поведение для рабочих сценариев?
- [ ] **Порядок вызовов:** зависимость от порядка инициализации?
- [ ] **Состояние при ошибке:** raise/early return – объект остаётся в валидном состоянии?
- [ ] **Численная устойчивость:** tolerance, overflow/underflow, catastrophic cancellation
- [ ] **Связь с другими задачами:** конфликт с BUG/DEBT/FEAT/VAL?
- [ ] **Import-цепочки:** не ломает ли фикс import-ы в других модулях?
- [ ] **Соответствие формулам:** код после фикса соответствует `moments_method.tex`?
- [ ] **Прототип:** меняет ли фикс `HydroSolverPrototype/`? → тесты прототипа и его регрессия против эталона в плане (шапка, «Правка прототипа»); ожидаемый исход регрессии (побитно / какие кейсы и почему разойдутся) – записать заранее

### 2.7. Обнаружение новых проблем

Для каждой: зафиксируй в плане; если блокирует – включи как предварительный шаг; если нет – после завершения плана добавь в реестр.

## Фаза 3: Детализация плана

### 3.1. Этапы для бага

1. **Подготовка** – ветка, прогнать тесты, воспроизвести баг
2. **Минимальный фикс** – наименьшее изменение, чтобы тест стал зелёным
3. **Тесты минимального фикса** – новые тесты
4. **Архитектурное решение** – правильная реализация (если отличается)
5. **Тесты архитектуры** – unit + integration + regression
6. **Верификация** – сравнение с аналитикой/эталоном, визуализация
7. **Очистка** – удалить workaround-ы, обновить vault, прокомментировать issue

### 3.2. Структура шага

```
### Шаг N: <название>

**Цель:** одно предложение
**Файлы:** <полные пути от корня проекта>

**Контекст:**
Что делает текущий код, почему проблема, что хотим.
Ссылки: [[vault-заметка]], `moments_method.tex` `\eqref{}`.

**Что сделать:**
1. В файле `<рабочий каталог>/<пакет>/X.py`, функция `Y()`, строка ~N: действие
2. ...

**Изменения:**
До:
    <текущий код>
После:
    <новый код>

**Проверка после шага:**
- Тест: `.venv/Scripts/python -m pytest tests/<file> -k "<name>" -v`
- Регресс: быстрый | полный – <почему полный, если полный>
- Регресс прототипа (если шаг меняет `HydroSolverPrototype/`): тесты прототипа + `run_regression.py --quick`; ожидание – <побитно | список кейсов>

**Подводные камни:** <ссылки на 2.6>
**Зависимости:** Требует: шаг M. Блокирует: шаг K.
**Оценка:** ~N строк, ~M минут
```

Поле «Регресс» (DEBT-032): `быстрый` – `pytest tests/ -m "not slow" -q` (~70 с), по умолчанию. `полный` – `pytest tests/ -q` (~10 мин): только если ошибку шага ловят лишь тяжёлые тесты (метка `slow`) и искать её в конце дорого – шаг меняет сборку матрицы энергии (`test_matrix_matches_reference`), фикстуру `results` или `tests/conftest.py`. Ориентир – не больше одного-двух полных на план. Шаг, меняющий только документы, проверяется `--collect-only -q`. Итоговый полный прогон `/implement` делает сам (§3.1).

### 3.3. Тестовая стратегия

```
**Тест:** <test_function_name>
**Файл:** <рабочий каталог>/tests/<файл>.py (существующий / новый)
**Сценарий:** <что проверяем – на уровне физики>
**Setup:** <параметры, ГУ>
**Ожидание:** <числа, неравенства, свойства>
**Предотвращает:** <класс ошибок>
```

### 3.4. Критерии завершения

- [ ] Тест-воспроизводитель зелёный
- [ ] Все новые тесты зелёные
- [ ] Все существующие тесты зелёные
- [ ] Если менялся прототип: тесты прототипа зелёные; полная регрессия `run_regression.py` – PASS, либо расхождения разобраны (сверка с IMEX), эталон переснят по решению пользователя и записан в `CHANGELOG_1.0.3.md`
- [ ] Визуальная верификация (если применимо)
- [ ] Workaround-ы удалены
- [ ] Vault обновлён
- [ ] GitHub issue прокомментирован (если создан)

### 3.5. Загрузка контекста при реализации

```
## Как начать работу по этому плану

1. Прочитай этот файл целиком
2. Прочитай связанные vault-заметки (ссылки ниже)
3. Ветку `<branch>` и worktree `.worktrees/<id-lowercase>` создаёт `/implement` (§1.5) – вручную не создавать
4. Venv: `.venv\Scripts\Activate.ps1` (PowerShell) или Claude использует `.venv/Scripts/python` напрямую
5. Baseline: `.venv/Scripts/python -m pytest tests/ --collect-only -q` (число тестов) и `.venv/Scripts/python -m pytest tests/ -m "not slow" -q` (быстрый уровень). Если план меняет прототип – ещё до правки, из `numerical_solver/HydroSolverPrototype/Prototype_1.0.3`: `..\..\.venv\Scripts\python -m pytest tests -q` и `..\..\.venv\Scripts\python regression\run_regression.py --quick` (ожидается: все passed – 97 на 2026-10-10 – и 11/11 PASS)
6. Воспроизведи баг: `.venv/Scripts/python -m pytest tests/<file> -k "<test>" -v`
7. Начни с шага 1. После каждого шага: тест шага и регресс по полю «Регресс»; полный прогон – в конце (`/implement` §3.1)
```
