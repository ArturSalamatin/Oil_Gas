## Контракты новых модулей (задано аудитом р.2)

Проверено: сигнатуры дублирующихся функций **идентичны во всех копиях** — сведение не требует менять API. Но конвенция уже вынесенных модулей отличается от конвенции копий, и это надо решить осознанно.

### Конвенция трёх работающих общих модулей (образец)

```python
# rs_analytics.py, closed_form.py, relperm_plot.py
def report_rs(config, history, pvt) -> dict: ...
def report_closed(config, history, grid, simulator) -> dict: ...
def plot_relperm(config, history, output_dir: Path, title: str, ...) -> None: ...
def make_overlay_rs(config): ...            # возвращает callable(ax, history, grid, simulator)
```

Правила образца:
1. **`config` — первый аргумент.**
2. **`pvt` и `relperm` НЕ передаются, если есть `simulator`** — модуль достаёт их сам: `pvt = simulator._energy._pvt`, `relperm = _create_relperm(config)` (см. `closed_form._prepare`). Это гарантирует, что проверка видит ровно те объекты, которыми считалась задача.
3. `report_*` печатает отчёт и **возвращает dict** со сводкой.
4. `make_overlay_*(config)` возвращает функцию для наложения на профильный график.

### Расхождение копий с образцом

| функция в копиях | конвенция образца |
|---|---|
| `report(history, config, pvt, grid)` | `report_*(config, history, grid, simulator)` |
| `stationary_face_temperature(history, config, pvt, grid)` | `config` первым; `pvt` — из `simulator` |
| `compute_balance(history, grid, config)` | `config` первым |

**Решение для плана:** при выносе привести к конвенции образца — иначе `run_example` не сможет вызывать проверки единообразно, а четыре общих модуля будут иметь три разных стиля вызова.

Исключение — `compute_balance(history, grid, config)`: её сигнатуру **не менять**. Grep даёт **18 файлов**, упоминающих `compute_balance` или `plot_energy_balance`:

- 4 копии `energy_balance.py` (01, 02, 03, 05) — удаляются шагом 4;
- 5 копий `energy_balance_convergence.py` (01, 02, 03, 04, 05) — правятся шагом 5;
- 4 × `main.py` (01, 02, 03, 05) — только импорт, правится шагом 4;
- `examples/check_energy_balance_all.py`, `examples/verify_balance_vs_solver.py` — созданы в BUG-004;
- `tests/test_energy_balance_examples.py` — путь `sys.path` на `03_standing_corey` → на `examples/`;
- 2 × `README.md` (01, 02) — актуализируются шагом 8.

Переименование аргументов дало бы волну правок в 18 файлах без выигрыша. Достаточно добавить тонкую обёртку `report_energy_balance(config, history, grid, simulator) -> dict` для вызова из `run_example`.

### Целевые сигнатуры

```python
# examples/energy_balance.py  (шаг 4)
def _cell_properties(pvt, rock, p, Sg, Rs, T): ...        # без изменений
def compute_balance(history, grid, config) -> dict: ...    # сигнатура СОХРАНЯЕТСЯ
def plot_energy_balance(history, grid, config, output_dir: Path) -> float: ...
def report_energy_balance(config, history, grid, simulator) -> dict: ...  # НОВАЯ, для run_example

# Возвращаемый dict compute_balance — ПОЛНЫЙ набор ключей ВСЕГДА:
#   t, delta_E, cum_adiab, cum_conv, cum_jt, cum_deg, cum_cond,
#   total, residual, rel_residual
# Отсутствующие физически члены — нулевые массивы, не отсутствующие ключи.

# examples/temperature_asymptotics.py  (шаг 3)
def _face_coefficients(config, history, grid, simulator): ...
def stationary_face_temperature(config, history, grid, simulator): ...
def single_phase_asymptote(config, history): ...
def decompose_two_phase(config, history, grid, simulator, f_well=0, f_front=None): ...
def report_asymptotics(config, history, grid, simulator) -> dict: ...

# examples/convergence.py  (шаг 5)

def fit_order(values, errors) -> float: ...
def plot_convergence(results, x_label, title, out_path) -> float: ...
```

`run_series` — механика, общая для всех трёх видов сходимости: `apply(config, value)` выставляет параметр (`dt_integration` или `grid.N`), `measure(sim, history, config) -> float` возвращает метрику. Эталон и метрика остаются у примера, в общий модуль уходит только прогон + регрессия порядка + график.

**Краевые случаи для всех новых функций:** `n_steps == 1` (нет приращений — вернуть нули, не падать), `N == 1` (нет внутренних граней — проверено: `compute_conductive_transmissibility` возвращает `np.empty(0)` и `Q_T_ext = 0.0`, симулятор при `N = 1` собирается без ошибок), `Sg ≡ 0`, `λ = 0`, `L = 0`, `μ_JT = 0` — все обнуляются арифметикой без ветвлений.

```python
# в конце каждого общего модуля
def _resolve_example(name_or_prefix: str) -> Path:
    """examples/<имя>/ по полному имени или числовому префиксу ('03').

    Пользователю не нужно печатать '03_standing_corey' целиком.
    Ошибка при отсутствии или неоднозначности префикса.
    """
    exact = _EXAMPLES / name_or_prefix
    if exact.is_dir():
        return exact
    matches = sorted(d for d in _EXAMPLES.iterdir()
                     if d.is_dir() and d.name.startswith(name_or_prefix))
    if not matches:
        raise SystemExit(f"нет примера '{name_or_prefix}'")
    if len(matches) > 1:
        raise SystemExit(f"неоднозначно: {[m.name for m in matches]}")
    return matches[0]


if __name__ == "__main__":
    if len(sys.argv) < 2:
        raise SystemExit(
            "укажите пример: python examples\\energy_balance.py 03")
    folder = _resolve_example(sys.argv[1])
    config = load_config(folder / "config.json")
    sim, initial_state = SimulatorFactory.from_config(config)
    history = sim.run(initial_state)
    plot_energy_balance(history, sim._grid, config, folder / "output")
```

## Целевое состояние

0. **Все члены проверок считаются безусловно.** Никаких ветвлений «этот член нужен только если в конфиге λ ≠ 0 / L ≠ 0 / μ_JT ≠ 0». Член входит в формулу всегда и обнуляется арифметикой, когда соответствующий коэффициент равен нулю. Это требование первично по отношению к остальным: именно условное включение (докстринг копии 03: «кондуктивного члена нет, он и не нужен — в конфиге λ = 0») скрыло пропуск кондукции у примера 10 на 8.6 % невязки. Проверка «нужен ли член» не должна зависеть от того, посмотрел ли автор скрипта в конфиг.

1. Свойства, не зависящие от комбинации PVT × ОФП, проверяются **одним кодом** из `examples/`, а не N копиями.
2. Примеры 06–10 получают базовый набор проверок — через `example_runner.run_example`, автоматически, как это уже сделано для `plot_relperm`, `report_rs`, `report_closed`.
3. Специфичные для примера проверки остаются на месте, но их имена отражают, **что** они проверяют, а не только к какому примеру относятся.
4. `tests/test_examples.py` покрывает общие проверки для всех примеров.

### Границы изменений — что НЕ трогать

- ❌ `numerical_solver/gpn_multiphase_solver/` — вычислительное ядро; задача целиком в `examples/` и `tests/`.
- ❌ Конфиги примеров и PVT-таблицы — покрытие проверками не требует менять сценарии.
- ❌ `check_energy_balance_all.py` и `verify_balance_vs_solver.py` — только что созданы в BUG-004, уже общие, работают. Не переписывать.
- ❌ `diag_bug005.py`, `diag_debt009.py` в примере 04 — диагностика открытого DEBT-009, не дублирование. Не выносить и не удалять.
- ❌ Физика проверок: ни одна формула не меняется. Если при сведении версий обнаружится, что две копии считают **по-разному** — это находка для отдельного BUG, а не повод «выбрать одну».

## Варианты решения

### Вариант 1 — общий модуль на группу, с параметризацией по сценарию

**Суть.** Для каждой группы дублирующихся скриптов создать один модуль в `examples/` с функциями `report_*(config, history, grid, simulator)` и `make_overlay_*(config)`. Различия между примерами уходят в аргументы и в автоопределение по конфигу (`Rs0 > 0`, `lambda == 0`, `mu_JT == 0`, `L == 0`), как уже сделано в `example_runner.py:112-114, 128-132`.

**Изменения.** Новые `examples/energy_balance.py` (сведение 4 версий), `examples/temperature_asymptotics.py`, `examples/convergence.py`; правки в `example_runner.run_example`; удаление копий из папок примеров.

**Плюсы.** Ровно тот приём, что уже применён и работает (`relperm_plot`, `closed_form`, `rs_analytics`) — единый стиль. Подключение к 06–10 бесплатно. Один код — один фикс.
**Минусы.** Сведение 4 версий `compute_balance` требует понять, чем они отличаются по существу, а не механически взять версию 03.
**Риск.** Автоопределение по конфигу может ошибиться на будущем сценарии — смягчается тем, что пример всегда может передать явный аргумент (приоритет у явного, как в `overlays`).

### Вариант 2 — оставить копии, добавить только подключение к 06–10

**Суть.** Не выносить ничего, а в примеры 06–10 добавить скрипты-обёртки, импортирующие проверки из 03.

**Плюсы.** Минимум правок, ничего не ломается.
**Минусы.** Дублирование остаётся, и **растёт**: вместо 4 копий станет 9 точек, зависящих от 03. Именно так и возникла текущая ситуация. Не решает задачу, только маскирует.

### Вариант 3 — вынести всё, включая специфичное

**Суть.** Свести все скрипты в `examples/`, включая `check_jt_terms`, `compare_with_corey`, `pressure_gor_closure`.

**Плюсы.** Полная унификация, папки примеров содержат только конфиг + README + main.
**Минусы.** Эти проверки **осмысленны только для своего сценария**: `check_jt_terms` — про изоляцию JT (пример 02), `compare_with_corey` — про сравнение табличной ОФП с Corey (05). Вынос в общий модуль сделает их «общими» формально, но неприменимыми к 8 из 10 примеров, и потребует заглушек «здесь не проверяется». Это ухудшит читаемость.

### Рекомендация

**Вариант 1**, с явным списком того, что остаётся на месте. Порядок: сначала группы с наибольшей долей идентичных функций (`temperature_asymptotics` — 4/5) как отработка приёма, затем самая ценная по покрытию (`energy_balance` — она нужна 06–10), затем сходимость. ### Шаг 4а: Добавить кондуктивный член в общий баланс

**Цель:** закрыть пропущенный член — иначе общий модуль наследует дефект, который на примере 10 даёт 8.6 % невязки.
**Файлы:** `numerical_solver/examples/energy_balance.py` (созданный шагом 4)

Для примера 03 это верно, но **общий модуль применяется ко всем десяти**, а у `10_deep_degassing` теплопроводность включена: $\lambda_{solid} = 1.5$, $\lambda_{oil} = 0.14$, $\lambda_{gas} = 0.04$ Вт/(м·К). Единственный такой пример.

**Измерено (аудит р.1, `scratchpad/audit016_conduction.py` и `audit016_order10.py`) — не предсказание, а факт.**

Эффект при штатном шаге $\Delta t = 3600$ с:

| величина | пример 10 | пример 09 (λ = 0, контроль) |
|---|---|---|
| $\Delta E$ | $-3.0871\cdot10^{10}$ Дж | $-1.8673\cdot10^{10}$ Дж |
| невязка без кондукции | 4.744e-03 | 2.263e-03 |
| **невязка с кондукцией** | **4.337e-03** | 2.263e-03 (без изменений) |
| `cum_cond` | $+1.2678\cdot10^{7}$ Дж | **$0$ ровно** |

⚠️ **Улучшение при штатном шаге — всего 8.6 %, а не «в четыре раза».** Ранняя версия плана обещала падение до ~1.2e-03; это была арифметическая ошибка (вычитание абсолютной величины члена из невязки). Фактически 4.744e-03 → 4.337e-03.

**Настоящая ценность правки — восстановление порядка сходимости.** `cum_cond` почти не зависит от $\Delta t$ ($1.268 / 1.319 / 1.321 \cdot 10^{7}$ Дж при $\Delta t = 3600/900/360$ с), то есть это **систематический** член. При измельчении шага он начинает доминировать над убывающей ошибкой расщепления:

| $\Delta t$, с | без кондукции | с кондукцией |
|---|---|---|
| 3600 | 4.7439e-03 | 4.3369e-03 |
| 900 | 1.5098e-03 | 1.1109e-03 |
| 360 | 8.5474e-04 | **4.5453e-04** |
| **порядок** | **+0.751** | **+0.980** |

При $\Delta t = 360$ с пропущенный член составляет почти половину невязки. Порядок восстанавливается с 0.751 до 0.980 — то есть после правки остаток примера 10 становится чистой ошибкой расщепления $O(\Delta t)$, как у остальных примеров (09 без кондукции даёт 0.915). Дефекта в решателе нет.

Это подтверждает предупреждение докстринга копии 03 («порядок падает ... до 0.967»), но эффект сильнее заявленного там.

**Формула.** Внутренние грани телескопируются (поток из ячейки в ячейку сокращается при суммировании по объёму), остаётся только контур — Дирихле $T = T_{ext}$:
$$E_{\text{cond}} = \sum_n Q_T^{ext}\,\bigl(T_{ext} - T^{n-1}_{N-1}\bigr)\,\Delta t_n$$

где $Q_T^{ext}$ берётся у решателя тем же методом, что он использует сам:
`energy.compute_conductive_transmissibility(props["lambda_eff"], N)` → второй элемент кортежа. Это гарантирует, что баланс использует ту же проводимость, что и схема, включая исправление BUG-002 (двойной `ln`).

**Что сделать:**
1. В общий `compute_balance` добавить накопление `cum_cond` по формуле выше; `lambda_eff` и `Q_T_ext` брать через `simulator._energy.compute_cell_properties` и `compute_conductive_transmissibility`, а не пересчитывать формулы заново (иначе разойдётся с решателем, как это уже было с накоплением в BUG-004).
2. Включить `cum_cond` в `total` и вернуть в dict новым ключом.

   🔴 **Член считается ВСЕГДА и БЕЗУСЛОВНО — никаких `if lambda != 0`.** При $\lambda = 0$ проводимость грани тождественно нулевая (`compute_conductive_transmissibility` при $\lambda = 0$ даёт $2\pi h/\infty = 0$, см. `tridiag.py:170-172` — там это специально обработано через `errstate`), и вклад обнуляется сам, арифметикой. Условное включение по признаку конфига — ровно тот класс ошибок, из которого выросла эта находка: девять примеров с $\lambda = 0$ маскировали пропуск члена у десятого. Проверка «нужен ли член» не должна зависеть от того, догадался ли автор скрипта посмотреть в конфиг.

   То же правило распространяется на остальные члены общего модуля: JT, адиабатика и скрытая теплота считаются безусловно и обнуляются сами при $\mu_{JT} = 0$ и $L = 0$ (примеры 01, 07, 08, 09) — без ветвлений по конфигу. Единственное, что остаётся условным, — набор **ключей** в возвращаемом dict должен быть полным всегда (подводный камень #2), то есть нулевые массивы вместо отсутствующих ключей.
3. Обновить докстринг: убрать утверждение «кондуктивного члена нет и не нужно», заменить на описание члена и указание, что при $\lambda = 0$ он обнуляется сам.
4. Обновить эталон примера 10 в `check_energy_balance_all.py` с `4.74e-03` на **`4.34e-03`** (измерено). Эталоны остальных девяти **не менять** — у них `cum_cond` ровно ноль, невязки не сдвигаются ни в одной цифре (проверено на всех десяти).
5. Обновить `plot_energy_balance`: добавить кривую кондукции на панель (a). При $\lambda = 0$ она будет лежать на нуле — это нормально и наглядно показывает, что член учтён.

## Новые проблемы, обнаруженные при планировании

### Расхождение записи реестра с фактом (исправить при реализации)

Запись FEAT-016 содержит три неточности, выявленные при планировании:
1. Таблица покрытия устарела — у 04 появились `energy_balance_convergence` и два диагностических скрипта.
2. «`energy_balance.py` у 03 и 05 совпадает побитово по AST» — **уже неверно**, `compute_balance` в двух версиях (частично из-за правок BUG-004).
3. «`check_stationary.py` в 03 и `check_stationary_T.py` в 05 — это одна и та же проверка под разными именами» — **неверно**, это разные проверки; переименование в одно имя было бы ошибкой.

Реестр стоит поправить в шаге 10 вместе с закрытием задачи.

### Кандидат в DEBT: автономный запуск скриптов ломается при выносе

Сейчас каждый вспомогательный скрипт запускается отдельной командой, документированной в его докстринге. После выноса в общий модуль команды вида `python examples\03_standing_corey\energy_balance.py` перестают существовать. Нужна единая конвенция запуска общих проверок для конкретного примера (аргумент командной строки или отдельный CLI). Пока это не решено системно, каждый вынос требует ручной правки документации — адресовано шагом 8, но как конвенция не зафиксировано.
