# /plan-improve – план рефакторинга, миграции или улучшения

Аргумент: `$ARGUMENTS` – идентификатор задачи (например `DEBT-003`, `DEBT-007`) или номер GitHub issue.

Результат: подробный, самодостаточный план в `vault/plans/`, готовый к автономной реализации в отдельной сессии без контекста.

**Рабочая директория зависит от направления задачи.** Определи её до начала работы:

| Направление | Каталог | Пакет / исходники | Тесты | Конфиги | Базовая ветка |
|---|---|---|---|---|---|
| **PDE-солвер** (текущая разработка) | `numerical_solver/` | `gpn_multiphase_solver/` | `tests/` | `configs/` | `numerical_scheme/implementation` |
| **Метод моментов** (завершён, только справка) | `method_of_moments/` | `src/` | `tests/` | `configs/` | `master` |

Все пути в планах и отчётах – от корня проекта (например `numerical_solver/gpn_multiphase_solver/factory.py`).

Команды pytest – из соответствующего каталога:
```powershell
cd numerical_solver
.venv\Scripts\python -m pytest tests/ -m "not slow" -q   # быстрый уровень, ~70 с
.venv\Scripts\python -m pytest tests/ -q                 # полный прогон, ~10 мин
.venv\Scripts\python -m pytest tests/ --collect-only -q  # только число тестов, ~3 с
```

Уровни прогона (DEBT-032): метку `slow` несут тесты на фикстуре `results` из `tests/test_examples.py` (ставится автоматически хуком в `tests/conftest.py`), `test_matrix_matches_reference` и тесты на сгущённой сетке. Полный прогон – один раз в конце реализации и на шагах, которые план помечает «Регресс: полный».

⚠️ Для `numerical_solver` тестам нужен прототип `radial_blackoil` – pytest берёт его из того же дерева (`pythonpath` в `[tool.pytest.ini_options]` `numerical_solver/pyproject.toml`, DEBT-059). Скрипты вне pytest берут установленный дистрибутив `radial-blackoil` (`pip install -e HydroSolverPrototype/Prototype_1.0.3 -e ".[dev]"`); в worktree – `PYTHONPATH` на worktree (правило 3 `/implement`).

**Правка прототипа** (`numerical_solver/HydroSolverPrototype/Prototype_1.0.3/` – `radial_blackoil/`, `run_prototype.py`): тесты `numerical_solver` её не ловят – у прототипа свои тесты и своя регрессия против эталона `regression/golden/`, сверенного с CMG IMEX (DEBT-029: правки BUG-014/016/018 месяц проверялись только на примерах GPN, расхождение с эталоном нашлось позже). Команды – из `numerical_solver/HydroSolverPrototype/Prototype_1.0.3`:
```powershell
..\..\.venv\Scripts\python -m pytest tests -q                  # тесты прототипа, 97 шт. на 2026-10-10, ~45 с
..\..\.venv\Scripts\python regression\run_regression.py --quick # регрессия T00–T11 без T05, ~8 мин
..\..\.venv\Scripts\python regression\run_regression.py         # полная, с T05, ~45 мин
```
- Сравнение с эталоном – почти побитовое (abs 2e-7 / rel 2e-10): любая смена последовательности шагов по времени даёт FAIL. Если правка задумана как «побитно там, где исходный алгоритм сходится», регрессия это и проверяет.
- FAIL – не повод переснимать эталон: разобрать расхождение (с какого шага, как затухает), сверить с IMEX метриками `regression/evidence/FINAL_REGRESSION_METRICS_20260825a.json` на приёмочных отметках 1–30 сут (как в DEBT-029), решение о пересъёме – за пользователем; пересъём и правка – запись в `CHANGELOG_1.0.3.md` (раздел «Local changes – GPN project»).
- Перед полной регрессией зафиксировать HEAD: каждый кейс – отдельный процесс, импортирует код заново; влитая посреди прогона ветка с правкой прототипа даёт смешанный прогон.
- Выходы – `OUTPUT/REGRESSION_<время>/` (игнорируется git), удалить после разбора.

По умолчанию новые задачи относятся к `numerical_solver/`. Если задача явно про метод моментов – использовать вторую строку таблицы.

## Фаза 2: Анализ и проработка

### 2.1. Текущее состояние (baseline)

Зафиксируй текущее поведение:
- Число тестов (`.venv/Scripts/python -m pytest tests/ --collect-only -q`); база зелёная по правилу мёржа – полный прогон при планировании не нужен (DEBT-032)
- API/интерфейсы, которые используются другими модулями
- Если релевантно – производительность (время тестов, время расчёта)

### 2.2. Целевое состояние

Опиши, как должен выглядеть код после изменений:
- Какие файлы появятся / исчезнут / переименуются
- Как изменится структура зависимостей (import graph)
- Какие интерфейсы сохранятся / изменятся
- Что станет проще (тестировать, расширять, понимать)

### 2.3. Варианты решения

Для каждого варианта (минимум 2):
- **Суть** – стратегия преобразования
- **Конкретные изменения** – какие файлы, какие преобразования
- **Промежуточные состояния** – можно ли разбить на этапы, каждый из которых работает и тесты зелёные?
- **Плюсы/минусы**
- **Риски** – что может пойти не так
- **Трудоёмкость** – файлы, строки

### 2.4. Выбор варианта

Критерии для DEBT (отличаются от багов):
- **Минимальность diff** – меньше изменений = меньше риск
- **Инкрементальность** – каждый промежуточный коммит работает и тесты зелёные
- **Обратная совместимость** – внешний API не ломается
- **Тестируемость** – результат легче тестировать, чем исходник

### 2.5. Поиск подводных камней

Чеклист. Для каждого: ✅ безопасно | ⚠️ риск, адресован | ❌ проблема

- [ ] **Все call sites найдены:** grep по имени класса/функции, import-ы
- [ ] **Зависимости пакетов:** pyproject.toml, import paths
- [ ] **Обратная совместимость API:** вызывающий код не ломается
- [ ] **Состояние при ошибке:** raise/early return – объект остаётся в валидном состоянии?
- [ ] **Тесты:** все существующие тесты продолжают проходить
- [ ] **Circular imports:** новая структура import-ов не создаёт циклов
- [ ] **Docstrings:** ссылки на `\eqref{}` корректны после переноса
- [ ] **Configs:** если меняются имена параметров – обновлены ли `<рабочий каталог>/configs/*.json`?
- [ ] **Связь с другими задачами:** не конфликтует ли с обходами других BUG/DEBT/FEAT/VAL?
- [ ] **Производительность:** не деградирует ли (для миграций: новая реализация не медленнее)
- [ ] **Прототип:** меняет ли правка `HydroSolverPrototype/`? → тесты прототипа и его регрессия против эталона в плане (шапка, «Правка прототипа»); ожидаемый исход регрессии (побитно / какие кейсы и почему разойдутся) – записать заранее

### 2.6. Обнаружение новых проблем

В ходе анализа могут обнаружиться новые проблемы. Для каждой:
1. Зафиксируй в плане (раздел «Обнаруженные проблемы»)

3. Если нет – после завершения плана добавь в соответствующий реестр

## Фаза 3: Детализация плана

### 3.1. Шаблон этапов по подтипу

#### Рефакторинг (выделение модуля):

1. **Подготовка** – ветка, зелёные тесты, baseline
2. **Создание нового модуля** – файл + `__init__.py`, пустые функции с docstrings
3. **Перенос кода** – по одной функции/классу: вырезать из старого → вставить в новый → адаптировать import-ы
4. **Адаптация вызовов** – обновить все import-ы в других модулях и тестах
5. **Тесты** – новые тесты для выделенного модуля
6. **Очистка** – удалить дублирующийся код, обновить vault

Ключевое правило: **после каждого шага все тесты зелёные.**

#### Миграция зависимости:

1. **Подготовка** – ветка, snapshot тестов и производительности
2. **Добавление зависимости** – pyproject.toml, pip install
3. **Адаптация кода** – изменить import-ы, вызовы API
4. **Тесты** – все тесты зелёные, производительность не хуже baseline
5. **Удаление старого** – удалить неиспользуемый код

#### Удаление мёртвого кода:

1. **Подготовка** – ветка, доказать что код мёртвый (grep, import graph)
2. **Удаление** – по одному файлу/функции, с проверкой тестов после каждого
3. **Очистка import-ов** – удалить неиспользуемые import-ы
4. **Тесты** – все зелёные
5. **Обновление vault**

#### Реструктуризация:

1. **Подготовка** – ветка, инвентаризация текущей структуры
2. **Перемещение** – по одному модулю: перенести, обновить import-ы
3. **Адаптация тестов** – обновить import-ы в <рабочий каталог>/tests/
4. **Тесты** – все зелёные
5. **Очистка**

#### Инфраструктура:

1. **Подготовка** – ветка, понять текущее поведение
2. **Изменение** – pyproject.toml, configs, CI
3. **Тесты**
4. **Очистка**

### 3.2. Структура шага

```

**Цель:** одно предложение

**Файлы:** <полные пути от корня проекта>

**Контекст:**
Для читателя без контекста: что есть сейчас, что хотим,

2. ...

**Изменения (старый → новый код):**
До:
    <текущий код>
После:
    <новый код>

**Проверка после этого шага:**
- Регресс: быстрый | полный – <почему полный, если полный>
- Регресс прототипа (если шаг меняет `HydroSolverPrototype/`): тесты прототипа + `run_regression.py --quick`; ожидание – <побитно | список кейсов>

**Подводные камни:**
- <ссылки на чеклист 2.5>

**Зависимости:**
- Требует: шаг M
- Блокирует: шаг K
```

Поле «Регресс» (DEBT-032): `быстрый` – `pytest tests/ -m "not slow" -q` (~70 с), по умолчанию. `полный` – `pytest tests/ -q` (~10 мин): только если ошибку шага ловят лишь тяжёлые тесты (метка `slow`) и искать её в конце дорого – шаг меняет сборку матрицы энергии (`test_matrix_matches_reference`), фикстуру `results` или `tests/conftest.py`. Ориентир – не больше одного-двух полных на план. Шаг, меняющий только документы, проверяется `--collect-only -q`. Итоговый полный прогон `/implement` делает сам (§3.1).

### 3.3. Тестовая стратегия

Для DEBT ключевое – **тесты неизменности поведения:**

1. **Regression:** все существующие тесты зелёные после каждого шага (перечислить конкретно, какие тесты покрывают затронутый код)
2. **Unit-тесты нового модуля:** если выделяется новый класс/модуль – написать pytest-тесты
3. **Smoke-тест миграции:** если меняется зависимость – тест что новая версия даёт те же результаты
4. **Инвариантные тесты:** если задача затрагивает вычисления – проверить что результаты идентичны baseline

Формат:
```
**Тест:** <имя функции test_...>
**Файл:** <рабочий каталог>/tests/<файл>.py (существующий / новый)
**Сценарий:** <что проверяем – на уровне задачи>
**Setup:** <конфигурация – если применимо>
**Ожидание:** <конкретные числа, неравенства, или качественные свойства>
**Baseline:** <с чем сравниваем – существующие тесты, производительность>
**Предотвращает:** <какую регрессию ловит>
```
