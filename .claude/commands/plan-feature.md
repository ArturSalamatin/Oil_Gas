# /plan-feature – план реализации новой фичи

Аргумент: `$ARGUMENTS` – идентификатор фичи (например `FEAT-001`, `FEAT-003`) или номер GitHub issue.

Результат: подробный, самодостаточный план в `vault/plans/`, готовый к автономной реализации в отдельной сессии без контекста.

**Рабочая директория зависит от направления задачи.** Определи её до начала работы:

| Направление | Каталог | Пакет / исходники | Тесты | Конфиги | Базовая ветка |
|---|---|---|---|---|---|
| **PDE-солвер** (текущая разработка) | `numerical_solver/` | `gpn_multiphase_solver/` | `tests/` | `configs/` | `numerical_scheme/implementation` |
| **Метод моментов** (завершён, только справка) | `method_of_moments/` | `src/` | `tests/` | `configs/` | `master` |

Все пути в планах и отчётах – от корня проекта (например `numerical_solver/gpn_multiphase_solver/factory.py`).

Команды pytest – из соответствующего каталога:
```powershell
cd numerical_solver
.venv\Scripts\python -m pytest tests/ -m "not slow" -q   # быстрый уровень, ~70 с
.venv\Scripts\python -m pytest tests/ -q                 # полный прогон, ~10 мин
.venv\Scripts\python -m pytest tests/ --collect-only -q  # только число тестов, ~3 с
```

Уровни прогона (DEBT-032): метку `slow` несут тесты на фикстуре `results` из `tests/test_examples.py` (ставится автоматически хуком в `tests/conftest.py`), `test_matrix_matches_reference` и тесты на сгущённой сетке. Полный прогон – один раз в конце реализации и на шагах, которые план помечает «Регресс: полный».

⚠️ Для `numerical_solver` тестам нужен прототип `radial_blackoil` – pytest берёт его из того же дерева (`pythonpath` в `[tool.pytest.ini_options]` `numerical_solver/pyproject.toml`, DEBT-059). Скрипты вне pytest берут установленный дистрибутив `radial-blackoil` (`pip install -e HydroSolverPrototype/Prototype_1.0.3 -e ".[dev]"`); в worktree – `PYTHONPATH` на worktree (правило 3 `/implement`).

**Правка прототипа** (`numerical_solver/HydroSolverPrototype/Prototype_1.0.3/` – `radial_blackoil/`, `run_prototype.py`): тесты `numerical_solver` её не ловят – у прототипа свои тесты и своя регрессия против эталона `regression/golden/`, сверенного с CMG IMEX (DEBT-029: правки BUG-014/016/018 месяц проверялись только на примерах GPN, расхождение с эталоном нашлось позже). Команды – из `numerical_solver/HydroSolverPrototype/Prototype_1.0.3`:
```powershell
..\..\.venv\Scripts\python -m pytest tests -q                  # тесты прототипа, 97 шт. на 2026-10-10, ~45 с
..\..\.venv\Scripts\python regression\run_regression.py --quick # регрессия T00–T11 без T05, ~8 мин
..\..\.venv\Scripts\python regression\run_regression.py         # полная, с T05, ~45 мин
```
- Сравнение с эталоном – почти побитовое (abs 2e-7 / rel 2e-10): любая смена последовательности шагов по времени даёт FAIL. Если правка задумана как «побитно там, где исходный алгоритм сходится», регрессия это и проверяет.
- FAIL – не повод переснимать эталон: разобрать расхождение (с какого шага, как затухает), сверить с IMEX метриками `regression/evidence/FINAL_REGRESSION_METRICS_20260825a.json` на приёмочных отметках 1–30 сут (как в DEBT-029), решение о пересъёме – за пользователем; пересъём и правка – запись в `CHANGELOG_1.0.3.md` (раздел «Local changes – GPN project»).
- Перед полной регрессией зафиксировать HEAD: каждый кейс – отдельный процесс, импортирует код заново; влитая посреди прогона ветка с правкой прототипа даёт смешанный прогон.
- Выходы – `OUTPUT/REGRESSION_<время>/` (игнорируется git), удалить после разбора.

По умолчанию новые задачи относятся к `numerical_solver/`. Если задача явно про метод моментов – использовать вторую строку таблицы.

## Фаза 2: Анализ и проработка

### 2.1. Формулы → код (для подтипов Физика/Режим/Модель)

Для каждого уравнения/члена, вводимого фичей:

| Формула | Уравнение в tex | Python-функция | Модуль | Тест |
|---|---|---|---|---|
| ... | `\eqref{eq:...}` | `func_name()` | `<рабочий каталог>/<пакет>/module.py` | `test_func()` |

Проверь:
- Все ли формулы из tex учтены?
- Корректны ли обозначения (vault нотация)?
- Есть ли аналитические решения для верификации?

### 2.2. Обратная совместимость

Ключевой вопрос: **можно ли включить фичу, не ломая существующее?**

Чеклист:
- [ ] Существующие тесты пройдут без изменений?
- [ ] Существующие конфиги работают без изменений?
- [ ] Фича – opt-in (включается флагом/параметром)?
- [ ] API существующих функций не меняется (или расширяется совместимо)?
- [ ] ODE система правой части не меняет размерность для существующих режимов?

### 2.3. Варианты решения

Для каждого варианта (минимум 2):
- **Суть** – архитектурный подход
- **Какие модули затрагиваются**
- **Как встраивается в ODE-систему** (если физика/модель)
- **Обратная совместимость** – ломает ли существующее?
- **Тестируемость** – можно ли тестировать изолированно?
- **Плюсы/минусы**
- **Трудоёмкость**

### 2.4. Выбор варианта

Критерии для фичей:
- **Корректность физики** – приоритет №1
- **Тестируемость** – изолированные unit-тесты на уровне отдельных формул
- **Расширяемость** – к следующему уровню модели (М.N → М.N+1)
- **Обратная совместимость** – не ломает существующее

### 2.5. Поиск подводных камней

Чеклист. Для каждого: ✅ безопасно | ⚠️ риск, адресован | ❌ проблема

- [ ] **Размерности:** единицы измерения во всех новых формулах корректны
- [ ] **Граничные случаи:** Sg=0, Sg=1, p=pb, T→T0, rb→rw, rb→Rext
- [ ] **Численная устойчивость:** деление, overflow, catastrophic cancellation
- [ ] **ODE совместимость:** если добавляется новое ODE – совместимо с интегратором?
- [ ] **PVT зависимости:** если фича зависит от PVT – при каких p, T корреляции валидны?
- [ ] **Обратная совместимость:** все существующие тесты зелёные
- [ ] **Состояние при ошибке:** raise/early return – объект остаётся в валидном состоянии?
- [ ] **Import-цепочки:** не создаёт circular imports
- [ ] **Производительность:** вычисление в горячих циклах не деградирует
- [ ] **Связь с другими задачами:** конфликт с BUG/DEBT/FEAT/VAL?
- [ ] **Формулы vs код:** каждая новая строка вычислений – из moments_method.tex
- [ ] **Прототип:** меняет ли фича `HydroSolverPrototype/`? → тесты прототипа и его регрессия против эталона в плане (шапка, «Правка прототипа»); ожидаемый исход регрессии (побитно / какие кейсы и почему разойдутся) – записать заранее

### 2.6. Обнаружение новых проблем

Для каждой: зафиксируй в плане. Блокирующие → предварительный шаг. Неблокирующие → после завершения в реестр.

## Фаза 3: Детализация плана

### 3.1. Шаблон этапов по подтипу

#### Физика (новое уравнение / член):

1. **Подготовка** – ветка, зелёные тесты, формулы зафиксированы
2. **Вспомогательные функции** – PVT, свойства, коэффициенты
3. **Тесты вспомогательных** – unit-тесты отдельных функций
4. **Интеграция в ODE** – правая часть, начальные условия
5. **Тесты интеграции** – полный прогон ODE
6. **Верификация** – сравнение с аналитикой/предельными случаями
7. **Визуализация** – графики для отчёта
8. **Документация** – vault, docstrings с `\eqref{}`

#### Режим (новые ГУ / IC):

1. **Подготовка** – ветка, формулы
2. **Конфигурация режима** – параметры, условия включения
3. **Реализация режима** – ODE правая часть, ГУ, IC
4. **Тесты** – unit + integration
5. **Верификация** – аналитика или предельные случаи

#### Модель (новый уровень М.N):

1. **Подготовка** – ветка, анализ М.(N-1)
2. **Расширение модели** – новые уравнения, члены
3. **PVT расширение** – новые свойства (если нужно)
4. **Тесты** – unit + integration
5. **Валидация** – сравнение М.N с М.(N-1) в предельных случаях
6. **Визуализация**

#### Вычисление:

1. **Подготовка** – ветка, benchmark текущей реализации
2. **Реализация** – новый метод / алгоритм
3. **Тесты** – корректность + производительность
4. **Интеграция** – подключение к существующему решателю
5. **Benchmark** – сравнение с baseline

#### Инфраструктура:

1. **Подготовка** – ветка, ТЗ
2. **Реализация**
3. **Тесты**
4. **Документация** – vault, AGENTS.md (если меняется workflow)

Поле «Регресс» (DEBT-032): `быстрый` – `pytest tests/ -m "not slow" -q` (~70 с), по умолчанию. `полный` – `pytest tests/ -q` (~10 мин): только если ошибку шага ловят лишь тяжёлые тесты (метка `slow`) и искать её в конце дорого – шаг меняет сборку матрицы энергии (`test_matrix_matches_reference`), фикстуру `results` или `tests/conftest.py`. Ориентир – не больше одного-двух полных на план. Шаг, меняющий только документы, проверяется `--collect-only -q`. Итоговый полный прогон `/implement` делает сам (§3.1).

### 3.3. Тестовая стратегия

```
**Тест:** <test_function_name>
**Файл:** <рабочий каталог>/tests/<файл>.py (существующий / новый)
**Сценарий:** <что проверяем – на уровне физики/математики>
**Setup:** <параметры: p, T, Sg, rb, rw, ...>
**Ожидание:** <конкретные числа/неравенства с единицами измерения>
**Формула:** `\eqref{eq:...}` – откуда ожидание
**Предотвращает:** <класс ошибок>
```

Категории тестов:
1. **Unit:** отдельные функции (PVT, правая часть, коэффициенты)
2. **Аналитические:** сравнение с точным решением (если существует)
3. **Предельные случаи:** Sg→0, Sg→1, T=const, однофазный режим
4. **Сходимость:** уменьшение шага → уменьшение ошибки
5. **Инвариантные:** баланс массы, энергии, монотонность
6. **Регрессия:** все существующие тесты зелёные
