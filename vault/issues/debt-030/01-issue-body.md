## Описание

Когда шаг прототипа не проходит ни одной из трёх ступеней `advance`, в журнал шагов `step_log.csv`, в блок `failure` файла `run_summary.json` и в отладочное сообщение гидро-адаптера попадает отчёт **последнего** вызова `_advance_phases`. При контроле по забойному давлению (BHP) это часто ветка `shut`: на неизменном состоянии она «сходится» за 0 итераций с невязкой 0 и сразу отбрасывается как несогласованная ($p_0 > p_{BHP}$). Отказ выглядит в журнале как «0 итераций, невязка 0», сведения о настоящем отказе теряются.

На расчёт не влияет: при отказе шаг делится пополам независимо от содержимого отчёта (`simulation.py:84`). Задача — диагностика отказов шага. Приоритет низкий.

## Текущее состояние

Цепочка `advance` (`blackoil.py:294-321`):

1. исходный алгоритм — `_advance_phases` (`:298`);
2. запасной путь BUG-014 — `_fallback` (`:308`). При BHP перебирает ветки скважины: начинает с ветки старого состояния, принимает только согласованный результат, другую ветку пробует один раз (`:335-347`). Если не подошла ни одна — `rep.converged=False; return new,rep` (`:345-346`) с отчётом **последней перебранной ветки**;
3. третья ступень BUG-016 — тот же `_fallback` с линейным поиском по $\|F\|_2$ и ограничением шага $S_g$ (`:316-321`); отчёт возвращается как есть, с `globalized=True`.

Отчёты исходного алгоритма и неудачных веток затираются. Ветка `shut` из равновесного начального состояния имеет нулевую невязку уже на начальном приближении — отсюда 0 итераций.

## Анализ вариантов решения

### Вариант 1. При общем отказе — отчёт исходного алгоритма

- **Суть.** В `advance` сохранить отчёт первого вызова `_advance_phases`; если третья ступень не сошлась — вернуть его, выставив `fallback=True`, `globalized=True` (флаги показывают, что ступени пройдены).
- **Изменения.** `blackoil.py`, `advance` — несколько строк.
- **Плюсы.** Минимальная правка. Возвращает отклонённым строкам `step_log.csv` смысл, который был до BUG-014: в T05S_N200_DT5m они должны снова совпасть с эталоном (гипотеза, проверить). Правило однозначное. Формат `step_log.csv` и `run_summary.json` не меняется. `test_all_three_stages_fail` остаётся верным.
- **Минусы.** Сведения о запасных ступенях теряются. Для отказов вида BUG-016, где исходный алгоритм и запасные ступени отказывают по-разному, этого может не хватить.

### Вариант 2. Отчёт ступени с наименьшей невязкой

- **Суть.** Среди отказов Ньютона (без «сошедшихся, но несогласованных» веток) выбрать отчёт с наименьшей $\|F\|_\infty$.
- **Плюсы.** Формат тот же.
- **Минусы.** Невязки разных ступеней — невязки разных задач (свободное правило скважины или закреплённая ветка; линейный поиск по $\|F\|_\infty$ или $\|F\|_2$). При чтении журнала непонятно, какая ступень записана. Несогласованные ветки нужно исключать явно (их невязка 0), при равенстве нужно ещё одно правило.

### Вариант 3. Сводка по ступеням в отчёте

- **Суть.** В `BlackOilNewtonReport` — поле со списком попыток (ступень, ветка, сошлась, согласована, итераций, $\|F\|_\infty$). Адаптер печатает сводку в отладочное сообщение; в `step_log.csv` — дополнительная колонка (по желанию).
- **Плюсы.** Полная картина отказа без отдельных проб: разбор BUG-016 и BUG-019 шёл через пробы со своей трассировкой ступеней.
- **Минусы.** Больше кода. Новая колонка меняет формат вывода прототипа (в эталоне её нет; в сравнение `step_log.csv` не входит). Список в отчёте каждого принятого шага — лишняя работа, если заполнять всегда.
