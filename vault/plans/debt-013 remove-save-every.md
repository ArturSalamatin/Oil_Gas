# DEBT-013: удаление `save_every` + перенос накопления баланса энергии в ядро

## Резюме для того, кто читает это без контекста

Задача состоит из двух связанных частей. Вторая появилась при подготовке
плана и была принята пользователем как расширение исходной.

**Часть A — удалить `save_every`.** Состав `SimulationHistory` сейчас
определяют **два независимых механизма**: структура интервалов `time.history`
и параметр `output.save_every`. Второй перебивает первый и трижды сломал
рекуррентную постобработку. Решение пользователя: `save_every` удаляется,
частота вывода задаётся только структурой `history`.

**Часть B — перенести накопление баланса энергии в ядро.** Баланс сейчас
живёт в `examples/energy_balance.py` и восстанавливает вклады постфактум по
записям истории. Это работает, только пока запись = подшаг схемы. Требование
пользователя: **баланс должен считаться всегда**, при любой структуре истории,
включая будущий переменный шаг (мелкий на старте, где давление и температура
меняются резко; крупный на стационаре). Решение: накапливать вклады на каждом
подшаге внутри симулятора, а в историю класть накопленные суммы.

**Целевой сценарий проекта** (для ориентира, прогонять в рамках этой задачи
не требуется): история эксплуатации до 10 лет с записью раз в месяц.
Первоочередная же цель — **валидация схемы на примерах**, и часть B нужна
именно для неё.

## Почему часть B необходима — измерено, не предположено

### Восстановление постфактум не работает

`compute_balance` умножает **мгновенные** потоки из `hydro_results[n]` на шаг
между записями (`energy_balance.py:175`). Пока записи совпадают с подшагами,
это согласовано со схемой. При разреженной истории поток последнего подшага
интервала умножается на всю его длину.

Замер на 04a, `dt_integration = 300` с во всех вариантах (решение побитово
одно и то же, различается только состав истории) —
`examples/04a_high_gas_saturation/diag_balance_intervals.py`:

| состав истории | записей | шаг истории | отн. невязка |
|---|---|---|---|
| все подшаги | 865 | 300 с | **9.98e-04** |
| концы интервалов | 73 | 3600 с | **2.14e-01** |
| концы интервалов | 4 | 86400 с | **1.44e-01** |

### Повышение порядка квадратуры не спасает

Проверена гипотеза «это просто грубость первого порядка, трапеции починят» —
`examples/04a_high_gas_saturation/diag_balance_quadrature.py`:

| шаг истории | левые прямоугольники | трапеции | эталон |
|---|---|---|---|
| 600 с | 1.20e-01 | 8.97e-02 | 9.98e-04 |
| 3600 с | 8.28e-01 | 4.31e-01 | 9.98e-04 |
| 14400 с | 1.04e+00 | 4.00e+00 | 9.98e-04 |
| 86400 с | 9.70e-01 | 2.92e+01 | 9.98e-04 |

Трапеции не приближают к эталону, а на крупных шагах расходятся. Причина:
внутри интервала укладывается 12 (или 288) подшагов, потоки за это время
существенно меняются, и **интерполяция по двум концевым точкам этой
информации не содержит**. Восстанавливать нечего — надо не терять.

### Накопление вкладов на подшагах решает задачу полностью

Проверено пересборкой пошаговых вкладов по группам — это в точности то, что
делал бы накопитель внутри симулятора
(`examples/04a_high_gas_saturation/diag_balance_accum.py`):

| шаг истории | записей | макс. невязка |
|---|---|---|
| 300 с (все подшаги) | 865 | 6.81e-03 |
| 1800 с | 145 | 2.66e-03 |
| 3600 с | 73 | 2.02e-03 |
| 86400 с | 4 | 1.00e-03 |
| 259200 с (только концы) | 2 | 9.98e-04 |
| **неравномерный, 300 с → 19500 с** | **12** | **6.81e-03** |

Невязка **одного порядка при любой структуре истории**, включая
неравномерную. (Это максимум по всем шагам, а не финальное значение: на
ранних шагах накопленная энергия ещё мала, поэтому относительная невязка там
выше — то же самое видно и на полной истории в первой строке.)

**Три порядка разницы** с восстановлением постфактум. Отсюда два следствия
для плана:

1. Защита в `compute_balance` не нужна **ни в каком виде** — ни по конфигу,
   ни по флагу. Баланс становится корректен при любой истории.
2. Признак `substep_resolved`, фигурировавший в первой редакции этого плана,
   **отменяется**. Он был подпоркой под схему с восстановлением; при
   накоплении различать «полную» и «разреженную» историю незачем.

## Прочее, выясненное при подготовке

**Оценка «затронут только 04a» — неверна.** У **всех одиннадцати** примеров
`time.history` состоит из одного интервала (259 200 с), а 73 записи давал
`save_every = 1`, сохранявший все подшаги. После удаления параметра такой
конфиг даст 2 записи. Решение пользователя: **все** конфиги примеров
переписываются на 72 интервала по 3600 с, включая 04a.

**Следствие для 04a:** у него `dt_integration = 300` с (мельче необходимо при
`S_g ≈ 0.7`), поэтому в интервал 3600 с попадает 12 подшагов. С накопителем
(часть B) баланс на нём **начинает считаться** — сейчас он не считается
вовсе. Ожидаемая невязка ~2e-03 (строка «3600 с» таблицы выше), что проходит
порог 1e-2.

## Что известно про поведение кода (проверено, не предполагается)

1. **`substeps` делит точно.** `simulator.py:59-73`:
   `n_sub = ceil(dt_hist / dt_integration)`, `dt_actual = dt_hist / n_sub`,
   гарантия `n_sub · dt_actual = dt_hist` ровно. После сведения условия
   отбора к `if is_last_substep:` запись попадает точно на конец интервала
   при **любом** соотношении `dt_hist` и `dt_integration`; кратность не
   требуется.
2. **`save_every` на численное решение не влияет вовсе.** Прогон
   `diag_intervals.py`: состояния совпали **побитово**,
   `max|ΔT| = max|Δp| = max|ΔSg| = 0`, `T(r_w) = 346.346468 K`.
3. **Дизъюнкция поглощает задумку.** `simulator.py:169-170`:
   `if is_last_substep or (global_step % self._save_every == 0)`. При
   `save_every = 1` вторая половина истинна всегда.
4. **Парсер конфига строгий.** `config.py:211`: `OutputConfig(**raw["output"])`.
   После удаления поля старый конфиг упадёт с `TypeError`, а не с внятным
   сообщением — адресуется шагом 3.
5. **`numpy` в `state.py` уже импортирован** (строка 8).
6. **Сериализация безопасна.** `io/output.py:28-52` (`history_to_arrays`)
   собирает словарь по явному списку ключей; новые поля в NPZ/CSV не попадут
   автоматически — если баланс нужен в выходном файле, ключи добавляются
   явно (шаг 6).
7. **Точка встраивания накопителя удобная.** `TridiagEnergySolver.solve`
   (`energy/tridiag.py:32`) уже принимает `hydro_result`, `state_prev`, `dt`,
   `T_ext` — ровно то, из чего баланс считает члены, — и внутри себя считает
   свойства ячеек (`compute_cell_properties`, :85), конвективные Φ
   (`compute_convective_coefficients`, :118) и кондуктивную проводимость
   (`compute_conductive_transmissibility`, :152).

## Этап 2. Часть B: накопитель баланса в ядре

Делается **до** удаления `save_every`: пока параметр на месте, можно
сравнивать новый накопитель со старым `compute_balance` на полной истории,

### Шаг 2: модуль накопителя

**Цель:** перенести физику баланса из `examples/` в пакет, сохранив формулы
и накопленные в комментариях выводы BUG-004/FEAT-016.

**Файлы:** новый `numerical_solver/gpn_multiphase_solver/energy/balance.py`

**Контекст:** `examples/energy_balance.py` содержит не только формулы, но и
обоснования, добытые дорого: почему накопление считается по приращениям, а не
как разность запасов (BUG-004, 20 % невязки на табличном PVT); почему все
члены считаются безусловно, без ветвлений по конфигу (FEAT-016, пропуск
кондукции у примера 10); почему проводимость берётся у решателя, а не
пересчитывается (иначе баланс расходится со схемой). **Эти комментарии
переносятся вместе с кодом** — правило проекта: комментарии не удалять.

**Что сделать:**
1. Создать класс `EnergyBalanceAccumulator` с состоянием: кумулятивные
   `E_accum`, `conv`, `adiab`, `jt`, `deg`, `cond`.
2. Метод `add_substep(...)` — вклад одного подшага. Формулы переносятся из
   `compute_balance` (строки 145-281) **без изменений**, но без цикла по
   истории: тело цикла становится телом метода.
3. Метод `snapshot()` — вернуть текущие накопленные значения (для записи
   в историю на конце интервала).

**⚠️ Контракт (обязателен к соблюдению — выведен аудитом из кода):**

```python
class EnergyBalanceAccumulator:
    """Накопление членов баланса энергии по подшагам. DEBT-013.

    Восстановить вклады по разреженной истории нельзя (замеры в шапке
    плана), поэтому они считаются на каждом подшаге и суммируются.
    """

    def __init__(self, grid: Grid, pvt: FullPVT, rock: RockConfig,
                 T_ext: float) -> None: ...

    def add_substep(self, hydro_result: HydroResult,
                    state_prev: SimulationState, dt: float,
                    props: dict, Phi_o: np.ndarray, Phi_g: np.ndarray,
                    Q_T_ext: float, J_jt: np.ndarray,
                    Q_ad: np.ndarray, Q_deg: np.ndarray,
                    T_ext: float) -> None:
        """Вклад источников за подшаг. Коэффициенты приходят от решателя
        уже посчитанными — пересчитывать их нельзя (BUG-004)."""

    def add_accumulation(self, T_new: np.ndarray, T_prev: np.ndarray,
                         rho_cp_eff: np.ndarray) -> None:
        """Накопление ΔE и кондуктивный член — требуют T^{n+1},
        поэтому вызываются ПОСЛЕ решения СЛАУ (см. п. 3 ниже)."""

    def snapshot(self, t: float) -> dict:
        """Накопленные значения на текущий момент — СКАЛЯРЫ."""
```

### ⚠️ Форматы: скаляры на шаг против массивов по истории (находка аудита, раунд 2)

`snapshot(t)` возвращает **скаляры** — накопленные значения на один момент.
А `compute_balance` сегодня отдаёт **массивы длины `n_saved`** — замерено
на примере 03: все десять ключей имеют `shape=(73,), dtype=float64`.

От массивов зависят:
- `plot_energy_balance` (:308-322) — рисует кривые по всей истории;
- `plot_energy_balance` (:347-355) и `report_energy_balance` (:369-371) —
  индексируют `[-1]`;
- тесты (`test_examples.py`, `test_energy_balance_examples.py`) — тоже `[-1]`.

**Поэтому нужен явный переход, который план обязан задать:**

1. `Simulator` кладёт `accumulator.snapshot(t)` в `history.balance` —
   список словарей-скаляров, по одному на запись (шаг 3).
2. `compute_balance` (шаг 4) **собирает массивы** из этого списка:
   `{k: np.array([snap[k] for snap in history.balance]) for k in KEYS}`.
   Сигнатура и набор ключей сохраняются, вызывающие не трогаются.

**Полный набор — десять ключей:** `t`, `delta_E`, `cum_adiab`, `cum_conv`,
`cum_jt`, `cum_deg`, `cum_cond`, `total`, `residual`, `rel_residual`.

⚠️ **Три из них производные, их нельзя накапливать** — они считаются из
остальных в момент сборки:
- `total = cum_adiab + cum_conv + cum_jt + cum_deg + cum_cond`;
- `residual = delta_E − total`;
- `rel_residual = |residual| / scale`, где `scale = max(|delta_E|, |total|)`,
  и при `scale < 1e-10` заменяется на 1 (`energy_balance.py:286-289`) —
  иначе на первых шагах, где `ΔE` ещё мал, возник бы ложный всплеск.

Накапливать надо **шесть**: `delta_E`, `cum_adiab`, `cum_conv`, `cum_jt`,
`cum_deg`, `cum_cond`. Плюс `t` берётся из момента записи.

**⚠️ Откуда берутся коэффициенты — исправлено аудитом.** Первая редакция
плана предписывала накопителю вызывать `compute_cell_properties` и
`compute_conductive_transmissibility` заново. Это неверно по двум причинам:

1. **Дублирование.** `TridiagEnergySolver.solve` (`tridiag.py:32-79`) уже
   вычисляет **все** нужные величины и выбрасывает их после сборки СЛАУ:
   `props` (:51), `Phi_o`/`Phi_g` (:54-56), `Q_T_ext` (:59-60), `J_jt` (:63),
   `Q_ad` (:65), `Q_deg` (:69). Повторный вызов удваивает расчёт PVT на
   каждом подшаге — ровно тот риск производительности, который отмечен
   в шаге 3.
2. **Риск расхождения со схемой.** Пересчёт своими формулами — это то, что
   породило BUG-004. Есть и конкретное расхождение: `compute_jt` берёт
   `μ_JT` по **upstream-ячейке** (`tridiag.py:199`: `mu_JT_o[up_o]`), а
   `energy_balance.py:226-227` — по ячейке грани. При константных `μ_JT`
   (все PVT проекта) это неразличимо, но при `μ_JT = μ_JT(p, T)` даст
   расхождение, которое будет искаться как новый BUG-004.

### ✅ РЕШЕНИЕ ПРИНЯТО (2026-09-09, пользователем): вариант (в)

`EnergySolver.solve` принимает необязательный параметр-накопитель и сам
вызывает его, имея все коэффициенты под рукой. Пересчёт коэффициентов
накопителем **исключён**.

Отвергнуты: (а) возврат кортежа `(T_new, terms)` — ломает всех вызывающих
и размывает семантику метода; (б) отдельный метод `last_terms()` — вводит
скрытое состояние (что вернуть до первого `solve`, что при вклинившемся
вызове).

Определяющий довод в пользу (в): величины уходят в накопитель и в
`assemble_tridiag` из **одних и тех же локальных переменных**, строка через
строку. Расхождение баланса со схемой становится невозможным по построению,
а не по договорённости. Варианты (а) и (б) отдают те же величины через
промежуточное хранилище, где зазор остаётся.

**Целевая сигнатура ABC** (`energy/base.py:21`):

```python
@abstractmethod
def solve(self, hydro_result: HydroResult,
          state_prev: SimulationState,
          dt: float, T_ext: float,
          collect: "EnergyBalanceAccumulator | None" = None) -> np.ndarray:
    """Один шаг теплопереноса: T^n → T^{n+1}.

    collect — накопитель баланса энергии (DEBT-013). Если задан,
    реализация ОБЯЗАНА вызвать collect.add_substep(...), передав те же
    коэффициенты, которые пошли в СЛАУ. Пересчитывать их заново нельзя:
    расхождение баланса со схемой породило BUG-004.
    """
```

**Место вызова в `TridiagEnergySolver.solve`** — между `compute_degassing`
(`tridiag.py:69`) и `assemble_tridiag` (:73), где все величины уже
вычислены:

```python
        Q_deg = self.compute_degassing(
            So, Sg, Rs, Rs_old, props['Bo'], G_o, props['L'], dt, N)

        # Баланс энергии накапливается здесь, а не постобработкой (DEBT-013):
        # передаём ровно те коэффициенты, которые следующей строкой уходят
        # в СЛАУ. Восстановить их по разреженной истории нельзя (замеры
        # в шапке плана), а пересчитать заново — значит повторить BUG-004.
        if collect is not None:
            collect.add_substep(
                hydro_result=hydro_result, state_prev=state_prev, dt=dt,
                props=props, Phi_o=Phi_o, Phi_g=Phi_g,
                Q_T_ext=Q_T_ext, J_jt=J_jt, Q_ad=Q_ad, Q_deg=Q_deg,
                T_ext=T_ext)

        a, b, c, d = self.assemble_tridiag(...)
```

Соответственно `add_substep` принимает именно эти аргументы, а не
`energy_solver`, как было в первой редакции контракта выше.

⚠️ **Обязательства, вытекающие из решения:**
1. Совместимость: параметр со значением по умолчанию `None`, возвращаемый
   тип не меняется — существующие вызовы (`simulator.py:155`, `test_energy.py`)
   правок не требуют.
2. Контракт ABC расширяется: **всякая** будущая реализация `EnergySolver`
   обязана поддержать `collect`, иначе баланс на ней молча не посчитается.
   Требование записать в докстринг ABC явно (см. выше) и в
   [[модули-energy-tridiag]] (шаг 12).
3. ⚠️ **`T^{n+1}` на момент вызова ещё не вычислена** — она возвращается
   строкой 79, а `collect` вызывается перед `assemble_tridiag` (:73).
   Между тем накопление требует именно новой температуры:
   `ΔE += Σ (ρc_p)^n · V · (T^n − T^{n−1})` (`energy_balance.py:172-173`).

   **Решение — разделить вызов на две части:**

   ```python
   # перед assemble_tridiag: всё, что зависит от коэффициентов шага
   if collect is not None:
       collect.add_substep(hydro_result=..., state_prev=..., dt=dt,
                           props=props, Phi_o=Phi_o, Phi_g=Phi_g,
                           Q_T_ext=Q_T_ext, J_jt=J_jt, Q_ad=Q_ad,
                           Q_deg=Q_deg, T_ext=T_ext)

   T_new = self.solve_banded_system(a, b, c, d, N)

   # после решения СЛАУ: накопление ΔE по новой температуре
   if collect is not None:
       collect.add_accumulation(T_new, state_prev.T, props['rho_cp_eff'])

   return T_new
   ```

   Кондуктивный член тоже требует `T^n` (`energy_balance.py:275`:
   `Q_T_ext * (T_ext − st.T[N-1]) * dt`) — его вклад считается во второй
   части вместе с `ΔE`.

       """Баланс энергии по накопленным на подшагах вкладам (DEBT-013).

       scale = np.where(scale < 1e-10, 1.0, scale)
       out["rel_residual"] = np.abs(out["residual"]) / scale
       return out
