## Описание

Управление скважиной по заданному дебиту нефти `q_oil` (м³ст/с) вместо забойного давления `p_wf`, проброшенное через все слои решателя — конфиг → фабрика → граничные условия → адаптер гидродинамики → **уравнение энергии** → вывод. Плюс пример 14 `examples/14_oil_rate_ramp_up/`: пуск скважины с линейно растущим дебитом.

Прототип гидродинамики режим `OIL_RATE` уже умеет, но наш код его не пробрасывает: конфиг с `"control": "rate"` сейчас падает на создании модели (`TypeError` в `factory.py:191`, затем `ValueError` в `factory.py:345-350`, затем `NotImplementedError` в `hydro/prototype_adapter.py:60-65`).

Уравнение энергии и вывод берут `p_wf` не из результата гидродинамики, а из граничного условия (`energy/tridiag.py:118`, `simulator.py:165`). При управлении по дебиту `p_wf` до шага неизвестно — нужен единый источник: `HydroResult.p_wf`.

> **Поправка 2026-09-29 (замер при планировании).** Первая редакция issue утверждала, что «главный риск — температура: энергия считала бы с неверным `p_wf`». Это неверно. Вклад забойной грани в JT (`eq:QJT_disc`) входит с весом Φ⁺, а при добыче Φ < 0, поэтому `p_wf` на температуру не влияет вообще (прототип обратного потока не допускает). Замер: энергии подставлен `p_wf` = 1 атм вместо фактического — T побитово та же. Управление по дебиту влияет на T только через поля гидродинамики (p, S_g, R_s, Q), а они уже берутся из `HydroResult`. `HydroResult.p_wf` нужен для вывода p_wf(t), для принципа единого источника и для притока через забой (DEBT-019). Расхождение постановки и docstring-ов с формулой — BUG-015.

## Мотивация

Реальная скважина эксплуатируется по дебиту, забойное давление — результат расчёта. Все примеры 01–13а и все тесты работают при заданном `p_wf`. Целевой сценарий проекта — история работы скважины, и без управления по дебиту он не описывается.

Фаза: граничные условия / ядро + примеры.

## Физическое/математическое обоснование

Постановка `numerical_solver/doc/problem_statement.tex` описывает только управление по давлению: `eq:bc_p_well`, `eq:pwf_history` (строки 642-651). Поток нефти через забойную грань — `eq:bc_flux_well` (строка 1647):

G^o_{1/2} = T_{1/2} · (k_ro / (μ_o B_o))_0 · (p_wf − p_0),

где p_0 — давление в ячейке 0. Управление по дебиту задаёт G^o_{1/2} = −q_{o,ст} (конвенция: положительное — от скважины), откуда p_wf исключается алгебраически:

p_wf = p_0 − q_{o,ст} / (T_{1/2} λ_o^{(0)}),   λ_o = k_ro / (μ_o B_o).

Поток газа — по `eq:bc_flux_well_gas` при этом же p_wf. Так устроен прототип: `radial_blackoil/blackoil.py:52-90` (`_well_fluxes`, ветка `OIL_RATE`), с ограничением `min_bhp` и семантикой «только добыча» — при p_wf < p_min дебит срезается, при p_0 ≤ p_min скважина закрывается, реверса в нагнетание нет. p_wf вычисляется на состоянии n+1, внутри Ньютона — согласовано с неявной схемой.

**Связь с температурой.** По формуле `eq:QJT_disc` (`problem_statement.tex:1352-1362`) JT-вклад забойной грани в ячейку 0 равен Σ_α μ_JT,α · Φ⁺_{α,1/2} · (p_0 − p_wf). При добыче Φ⁺_{1/2} = 0, и вклад нулевой; текст постановки (`:1697-1701`, `:1815-1823`) утверждает обратное — BUG-015. Фактическое p_wf шага войдёт в энергию только при притоке через забой.

**Пробел в постановке:** управление по дебиту в `problem_statement.tex` не описано — дописать подраздел (уравнение исключения p_wf, ограничение `min_bhp`, закрытие скважины, какой p_wf входит в JT-вклад).

## Предлагаемый API

Конфиг (единицы СИ, как у `p_wf`):

```json
{"dt": 86400.0, "control": "rate", "q_oil": 2.083333e-04, "min_bhp": 101325.0}
```

- `bc.RateControl(q_oil: float, min_bhp: float)` — `q_oil >= 0` (добыча), `min_bhp > 0`.
- `HydroResult.p_wf: float`, Па — фактическое давление на забойной грани после шага. **Обязательное, без умолчания**: умолчание `None` с запасным обращением к `bc.well` в энергии вернуло бы второй источник.
- `PrototypeHydroAdapter.solve`: `RateControl` → `set_oil_rate_control(q_oil · 86400, min_bhp / BAR_TO_PA)`; `_build_result` заполняет `p_wf = model.well_rates(new_proto)['bhp_bar'] · BAR_TO_PA` — публичный метод, на том же состоянии, по которому считаны потоки.
- Валидация: `control = "rate"` требует `q_oil` и `min_bhp`; отвергает одновременное задание `p_wf` и `q_oil`.

## Анализ вариантов решения

**Откуда энергия и вывод берут фактический p_wf**

1. `RateControl.boundary_pressure` вычисляет p_wf сам по формуле прототипа из `state`. Минусы: формула дублируется в двух местах (болезнь DEBT-021: два пути расходятся в одной величине); оба рабочих вызова передают `relperm=None`, а λ_o без ОФП не вычисляется — нужна смена сигнатуры. **Отклонён.**
2. Модуль гидродинамики возвращает фактический p_wf в `HydroResult`, энергия и симулятор читают его оттуда. Плюсы: формула в одном месте, энергия не знает о типе управления, закрывается расхождение p_wf при закрытии скважины (FEAT-022/023) — в `well_history.csv` будет фактическое p[0], а не уставка. Минус: меняется контракт `HydroResult`, правка всех конструкторов. **Принят.**

**Судьба `WellControl.boundary_pressure`** (решить в плане). После перехода её вызывает только `compute_fluxes` (тесты):

- a) оставить в ABC, `RateControl` бросает исключение с пояснением — минимум правок, но метод в ABC, не имеющий смысла для одной из реализаций;
- b) убрать из ABC, `compute_fluxes` работает только с `PressureControl` — честный контракт, правка тестов и дублёров.

**p_wf для постобработки примеров** (`closed_form.py`, `two_phase_analytics.py`) (решить в плане):

- a) брать фактический p_wf последней записи `history.well_data[-1].p_wf` вместо конфига — единообразно для обоих управлений;
- b) отключать замкнутые решения для примеров с управлением по дебиту.

## План реализации

1. **Проектирование.** Подраздел «Управление по дебиту нефти» в `problem_statement.tex`. Решить судьбу `WellControl.boundary_pressure` и способ получения p_wf в постобработке.
2. **Замер до реализации.** Пробный прогон сценария примера 14 напрямую через прототип: сходимость при переходе ячейки 0 в двухфазный режим, дробление шага, p_wf(t) на последней записи — подтвердить, что `min_bhp` = 1 атм не срабатывает.
3. **Контракт `HydroResult.p_wf`.** Поле, заполнение во всех конструкторах; энергия (`tridiag.py:118`) и симулятор (`simulator.py:165`) читают его. Регрессия: все существующие тесты и примеры при управлении по давлению не меняются.
4. **`RateControl` + конфиг + фабрика + адаптер.** Валидация, `_create_well_control`, инициализация `p_bhp_bar`, ветка в адаптере, конверсия единиц.
5. **Тесты:**
   - **согласованность двух управлений (главный):** прогон по давлению с интервалом истории = один подшаг; дебит каждого подшага подаётся расписанием `q_oil` во второй прогон — оба через JSON-конфиг. Схема неявная, поэтому p, S_g, R_s, **T** и `HydroResult.p_wf` должны совпасть до допуска Ньютона на всей траектории. Проверяет чтение конфига, проброс управления и T через поля гидродинамики; какой p_wf получает энергия — отдельный тест с притоком через забой. Явно проверить, что A-retry не дробит шаги по-разному и `min_bhp` не срабатывает;
   - `HydroResult.p_wf`: при `PressureControl` и притоке — уставка; при `RateControl` — `well_rates()['bhp_bar']`, `−G_o[0] = q_oil`;
   - энергия не обращается к `bc.well`: управление, у которого `boundary_pressure` бросает исключение, проходит полный шаг `Simulator`;
   - `min_bhp`: недостижимый дебит → p_wf = p_min, урезанный дебит; p[0] ≤ p_min → q = 0, без реверса;
   - валидация конфига: нет `q_oil` / нет `min_bhp` / `q_oil < 0` / `min_bhp ≤ 0` / одновременно `p_wf` и `q_oil` → внятные ошибки;
   - баланс массы: добытая нефть = Σ q_k Δt_k.
6. **Пример 14** `examples/14_oil_rate_ramp_up/`: конфиг генерируется скриптом (DEBT-014), README, строка в `examples/README.md`. Проверки: `q_o` в `well_history.csv` совпадает с расписанием (0, 18, …, 270 м³ст/сут); p_wf(t) монотонно падает и выше `min_bhp`; баланс энергии в пределах порога. Прочие инварианты не постулировать (урок FEAT-021).
7. **Верификация.** Полный pytest, прогон примеров 01–13а без изменений результатов, прогон примера 14.
