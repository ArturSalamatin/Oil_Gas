# P4. Адаптивный шаг по времени

> ⚠️ **Пересмотрено 2026-09-19 в рамках [[BUG-010]].** Положение «EnergySolver не знает о внутренних подшагах гидро» отменено: теперь `HydroResult.n_substeps` сообщает наружу фактическое дробление, и `Simulator` дробит шаг энергии синхронно. Остальные положения (гидро как чёрный ящик по состоянию, потоки мгновенные при `n+1`) сохранены. Разбор — ниже, в разделе «Что пересмотрено».

## Принцип

Гидродинамический модуль — **чёрный ящик по состоянию**. Получает (state_n, dt, BC), возвращает (state_{n+1}, потоки). Как он приходит к state_{n+1} (Newton, active-set) — его дело; но **сколько подшагов ему на это понадобилось, он обязан сообщить** — см. «Что пересмотрено».

EnergySolver использует:
- p^{n+1}, Sg^{n+1}, Rs^{n+1} — из HydroResult (замороженные коэффициенты)
- p^n, Rs^n — из state_prev
- dt — шаг, **согласованный с дроблением гидро** (от Simulator)
- Потоки — мгновенные при state^{n+1}

## Решение: A-retry

Adapter при расходимости **сам уменьшает dt** и выполняет подшаги. Снаружи возвращает единый HydroResult на конец исходного dt.

### Алгоритм

```python
def solve(self, state, dt, bc) -> HydroResult:
    """Чёрный ящик: state_n → state_{n+1} за dt.
    
    При расходимости — автоматический retry с уменьшением шага.
    """
    max_retries = numerics.max_retries    # из JSON, default 9
    
    for attempt in range(max_retries + 1):
        n_sub = 2 ** attempt           # 1, 2, 4, 8, 16, 32
        dt_sub = dt / n_sub
        
        dev_log.debug(
            f"Hydro attempt {attempt+1}/{max_retries+1}: "
            f"{n_sub} substep(s), dt_sub={dt_sub:.2e} s")
        
        success = True
        current = state
        
        for step in range(n_sub):
            # Конвертировать → advance → конвертировать обратно
            proto_state = self._to_proto(current, bc)
            new_proto, report = self._model.advance(proto_state, dt_sub)
            
            if not report.converged:
                dev_log.debug(
                    f"  Substep {step+1}/{n_sub} failed: "
                    f"iters={report.iterations}, res={report.residual_inf:.2e}")
                success = False
                break
            
            current = self._from_proto(new_proto, current, dt_sub)
        
        if success:
            if attempt > 0:
                user_log.info(
                    f"Hydro: converged after {n_sub} substeps "
                    f"(dt_sub={dt_sub:.2e} s)")
            
            # Потоки — мгновенные при итоговом state.
            # n_sub уходит наружу (BUG-010): энергия дробится синхронно.
            fluxes = self._model.face_component_fluxes_sm3s(new_proto)
            return self._build_result(current, new_proto, fluxes, bc,
                                      n_substeps=n_sub)
    
    raise RuntimeError(
        f"HydroSolver не сошёлся после {2**max_retries} подшагов "
        f"(dt_sub={dt/2**max_retries:.2e} s). "
        f"Увеличьте numerics.max_retries (сейчас {max_retries}). "
        f"Более мелкие подшаги требуются при корреляционном PVT "
        f"(нелинейность B_g) и при высокой газонасыщенности "
        f"(обе фазы малоподвижны одновременно).")
```

### Параметры

| Параметр | Значение | Смысл |
|---|---|---|
| `max_retries` | 9 (`numerics.max_retries`) | Максимум удвоений числа подшагов; допустимо 0…20 |
| `n_sub` | 2^attempt | 1, 2, 4, …, 512 |
| `dt_sub` | dt / n_sub | Шаг подшага |
| Минимальный dt_sub | dt / 512 | При dt=3600 с → 7.03 с |

Значение по умолчанию 9 — измеренный порог (DEBT-007): пример 03 при двух
отягчающих факторах сразу ($N = 75$ и $p_{wf} = 6$ МПа) сходится ровно при
девяти удвоениях, при восьми ещё падает. Один фактор требует семи.
Порог **немонотонен по сетке** — в примере 05 $N = 100$ требует 11, а
$N = 140$ и $N = 200$ обходятся девятью.

### Пример

dt = 3600 с:
- Попытка 1: 1 шаг × 3600 с → расходимость
- Попытка 2: 2 шага × 1800 с → расходимость на 2-м
- Попытка 3: 4 шага × 900 с → все сошлись → возврат state после 4-го шага

## Что возвращается

### Состояние

State после **последнего подшага** — это state на момент t_{n+1} = t_n + dt. Не промежуточные.

### Потоки

`face_component_fluxes_sm3s(final_state)` — мгновенные потоки при p^{n+1}, Sg^{n+1}. Это то, что нужно EnergySolver для конвекции (неявная схема: потоки на уровне n+1).

### Δp/Δt и ΔRs/Δt для EnergySolver

EnergySolver вычисляет:
```
Q_ad ∝ (p^{n+1} - p^n) / dt          # адиабатический эффект
ṁ   ∝ (Rs^{n+1} - Rs^n) / dt         # темп дегазации (временная часть)
```

Здесь dt — **внешний** шаг (от Simulator), p^n — из state_prev, p^{n+1} — из HydroResult. Это конечная разность через весь интервал, не через подшаги.

Физически: средняя скорость изменения давления за интервал. Приближение первого порядка по времени — совместимо с первым порядком неявной схемы.

~~При достаточно малом dt_integration (из JSON) ошибка пренебрежима. Если dt_integration слишком велик — ошибка в температуре (не в гидродинамике).~~

**Это предположение оказалось неверным — [[BUG-010]].** Ошибка в температуре возникала не при «слишком большом» dt_integration, а при тех его значениях, где срабатывал A-retry, — и немонотонно: dt = 450 с давал результат в 11 раз хуже, чем dt = 900 с. Пользователь, измельчавший шаг, получал худший ответ без единого предупреждения.

## Что пересмотрено (2026-09-19, BUG-010)

### Что было не так

Положение «EnergySolver не знает о внутренних подшагах гидро» выглядело безобидной инкапсуляцией, но означало следующее: когда гидродинамика признавала dt слишком крупным и дробила его на n_sub подшагов, энергия всё равно решалась **одним** шагом по полному dt. Расщепление «гидро → энергия» имеет порядок O(dt) и применялось на интервале, который одна из его половин уже забраковала.

Измерено на примере 07, первый шаг dt = 450 с, при **идентичном** гидро-состоянии (p совпадает побитово):

| способ | T[0] | ошибка против эталона |
|---|---|---|
| эталон (9 × 50 с) | 352.322361 К | — |
| энергия 1 × 450 с (как было) | 350.934699 К | **−1.387663 К** |
| энергия 2 × 225 с | 352.262752 К | **−0.059609 К** |

Улучшение в 11.8 раза при тех же потоках — меняется только число шагов энергии.

### Что сделано

`HydroResult` получил поле `n_substeps` (по умолчанию 1). `Simulator._advance` при `n_substeps > 1` отбрасывает результат пробного шага и проходит интервал заново, дробя гидро и энергию вместе.

Порядок критичен: `EnergyBalanceAccumulator` — кумулятивный сумматор **без отката**, поэтому энергия решается только после того, как выяснено окончательное число подшагов. Иначе вклады отброшенного шага попали бы в баланс необратимо.

Вложенность ограничена одним уровнем: подшаг, сам потребовавший retry, принимается как есть с предупреждением в лог. На примере 07 этого не происходит ни разу (подшаги 225 и 200 с сходятся без дробления) — страховка для других конфигов.

### Что осталось в силе

- **Потоки — мгновенные при n+1.** Проверено: поток последнего подшага ближе к эталонному мгновенному потоку (расхождение 1.59e-04), чем среднее по подшагам (5.43e-04). Неявная схема требует именно слоя n+1. Отвергнутый вариант «осреднять потоки по подшагам» был подгонкой под симптом.
- **Состояние возвращается после последнего подшага** — оно и есть state на момент t_{n+1}.
- **Перезапуск с state_n на каждой попытке** — без изменений.

### Остаточный долг

Повторный проход считает гидро-подшаги дважды. Архитектурно верное решение — вынести A-retry на уровень `Simulator`, чтобы дробить шаг сразу целиком: [[DEBT-015]]. Критично при n_sub = 512 ([[BUG-008]]).

## Взаимодействие с TimeSchedule

Simulator определяет dt_actual = dt_hist / n_sub (из TimeSchedule). Adapter получает этот dt. Если Adapter справился без retry — один вызов advance.

~~TimeSchedule не знает о retry. Simulator не знает о retry. Только Adapter и логи.~~

**После [[BUG-010]]:** TimeSchedule по-прежнему не знает о retry, а **Simulator знает** — через `HydroResult.n_substeps`. Если Adapter раздробил шаг, Simulator отбрасывает пробный результат и проходит интервал заново, вызывая гидро и энергию на каждом подшаге. Состав истории при этом не меняется: записи по-прежнему делаются только на концах интервалов расписания (DEBT-013).

## Проверенные нюансы

### Перезапуск с state_n на каждой попытке

При каждой попытке retry все подшаги начинаются с исходного state_n. Ранее вычисленные подшаги не переиспользуются. Неэффективно (максимум 32 вызова advance вместо ~6 при smart retry), но просто и корректно. Оптимизировать при необходимости.

### Управление скважиной при retry

`set_bhp_control` / `set_oil_rate_control` вызывается перед каждым подшагом (идемпотентно). Дебит (OIL_RATE) — постоянный во времени, суммарная добыча за dt пропорциональна dt. Корректно.

### Roundoff при конвертации Па→бар→Па

При retry подшаги 2..n_sub конвертируют state обратно из Па в бар. Float64 roundoff ~1e-15. Не проблема.

### Первый подшаг всегда расходится

Если при dt/2^max_retries Newton не сходится — лимита не хватает либо задача действительно слишком жёсткая. RuntimeError с информативным сообщением. Первое, что делает пользователь, — увеличивает `numerics.max_retries`. Уменьшение `dt_integration` помогает **не всегда**: A-retry уже дробит шаг внутри с тем же лимитом, поэтому для случаев вроде BUG-003 (высокая $S_g$) внешнее уменьшение шага лишь повторяет ту же работу.

### Режимы (gas_active) между подшагами

При retry подшаг k передаёт state с обновлённым regime в подшаг k+1. advance использует gas_active как starting guess и сам определяет правильный mask через active-set. Корректно.
