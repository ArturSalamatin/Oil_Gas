# Перенос команд в навыки сохраняет контекст задач на всех этапах

План фиксирует договорённости о переносе команд проекта в `.agents/skills/` и дальнейшую доработку `draft` и `issue`. Пользователь переносит остальные команды последовательно. План предназначен для следующих сессий и не является планом реализации отдельной задачи с ID.

Уточнены навыки `draft` и `issue`, соглашения о метках и `issue_helper.py`. Добавлены тесты скрипта и перечень [[перенос команд проекта в навыки]]. Обновлены `vault/issues/README.md` и шаблон FEAT в реестре. Публикация на GitHub и сквозной запуск навыков не выполнялись.

Тесты `.agents/skills/issue/tests/` – 12 passed. Они включают поиск ID, обновление реестра и заметки, а также локальные проверки ветки, worktree и коммита общего реестра с настоящим Git в изолированном каталоге. Проверки поведения навыков при настоящей публикации и отсутствие сетевых побочных действий в отдельном сквозном сценарии не выполнялись.

При последовательном переносе остальных навыков остаётся проверить передачу черновика в `plan-*`, состав коммитов в `implement` и `merge`, а также сверить контракты по перечню. Сценарии завершения всего процесса и проверка фактического списка меток GitHub остаются невыполненными.

## Принятые решения

- `draft` регистрирует задачу в локальном реестре и сохраняет контекст в `vault/issues/<id-lowercase>/00-draft.md`. Навык не создаёт GitHub issue.
- `issue` публикует зарегистрированную задачу по ID после отдельного запроса. Произвольное описание само по себе не запускает публикацию.
- Все команды следует рассматривать как доступные навыки в `.agents/skills/`. Пользователь выполняет перенос последовательно. Временные проверки и правила на переходный период не добавляются.
- `.claude/commands/` остаётся архивом и не изменяется. `CLAUDE.md` также остаётся архивным и существенно не перерабатывается.
- Актуальное направление – `numerical_solver`, постановка – `numerical_solver/doc/problem_statement.tex`. Метод моментов завершён и сохраняется как справочный материал.
- Публикация issue и комментариев через `gh` изменяет GitHub. Это отдельная операция от `git push`. В обычном процессе push ветки задачи и базовой ветки выполняется при `merge`. `/implement` создаёт предусмотренные процессом коммиты без push.
- Перед переносом общих файлов vault в коммит нельзя автоматически включать незакоммиченные материалы других задач лишь потому, что на них есть ссылки в реестре.
- Общий реестр коммитится целиком без остановки из-за незакоммиченного черновика другой задачи (решение пользователя 2026-11-13). Незакоммиченный черновик остаётся в рабочем каталоге и восстанавливается средствами Git только после включения в коммит.
- Если подходящей метки на GitHub нет, её допустимо создать автоматически (решение пользователя 2026-11-13).
- Не разрабатывать специальные сценарии на случай недоступности Git, GitHub или сбоя сети при публикации задачи и комментария (решение пользователя 2026-11-14). При переносе вести перечень всех команд и соответствующих навыков.

## 1. Согласовать реестр и черновики при коммитах

При коммите общего реестра целиком в него может попасть ссылка на незакоммиченный черновик другой задачи. После отправки базы ссылка будет вести на отсутствующий в репозитории файл.

**Решение:** коммитить общий реестр целиком, не останавливаясь из-за незакоммиченного черновика другой задачи. Такой черновик не добавлять в коммит автоматически. До его последующего коммита ссылка в истории и на GitHub может вести на отсутствующий файл. Старым записям без ссылки на черновик новый файл не требуется.

Правило требуется учесть в навыках `implement` и `merge`, включая регистрацию задачи во время реализации и коммит отметки о влитии.

**Проверки:** текущая задача с новым черновиком, чужой неотслеживаемый черновик, уже закоммиченный черновик, отсутствующий файл, ссылка из задачи, найденной при реализации, и незакоммиченные изменения существующего черновика. Убедиться, что коммит реестра не включает чужой черновик автоматически. Использовать изолированный репозиторий внутри проекта без push.

## 2. Уточнить `draft`

1. Отделять проверенные факты с источником, условиями и датой проверки от сведений пользователя и гипотез.
2. Различать принятые, предварительные и отсутствующие решения. Сохранять открытые вопросы.
3. Если ветка или метки обсуждались, допускать их запись как предложений. При публикации проверять их заново.
4. Не выдумывать воспроизведение, эталон или допуск. Неизвестные сведения обозначать явно.
5. Явно запретить `draft` создавать issue, коммит и push. При найденном дубликате сообщать существующий ID без автоматического создания новой записи.

**Проверки:** четыре типа задач, краткое описание и итог обсуждения, задача без формул, предварительное решение и существующая задача. Проверить ссылку из реестра на черновик в Obsidian.

## 9. Граница этапов и состояние задачи

### 9.1. Локальная регистрация

`draft` получает описание задачи либо контекст обсуждения. Он определяет тип и регистрирует одну задачу в соответствующем реестре. Запись содержит ID, краткую постановку, необходимые для типа задачи сведения, статус и ссылку на черновик. Черновик содержит контекст, который не помещается в запись реестра. Оба файла относятся к одной задаче, но записываются в разные пути.

После регистрации задача существует локально. Наличие ID, черновика или предлагаемых меток не означает, что issue опубликован или ветка создана. `draft` не выполняет `gh issue create`, `gh issue comment`, `gh label create`, `git add`, `git commit` и `git push`.

### 9.2. Публикация

При отдельном запросе `issue <ID>` навык использует запись реестра, черновик при наличии, связанные материалы и актуальное состояние проекта. Навык подготавливает `01-issue-body.md` и `02-comment-open.md` в каталоге `vault/issues/<id-lowercase>/`, затем публикует issue и комментарий. После этого реестр получает ссылку на issue и предполагаемое имя ветки. Публикация изменяет GitHub немедленно, даже если локальные файлы ещё не закоммичены и ветки не отправлены на сервер.

Для ранее зарегистрированных задач `00-draft.md` может отсутствовать. Сам по себе этот факт не запрещает публикацию. При этом имеющейся информации должно хватать для содержательного описания задачи.

### 9.3. Планирование и аудит

`plan-*` читает запись реестра, опубликованный issue с относящимися к нему уточнениями, черновик при наличии и связанные заметки. Результат – самодостаточный план в `vault/plans/` и ссылка на него в реестре. Комментарий о готовом плане хранится в `03-comment-plan.md` каталога задачи и публикуется при наличии issue в соответствии с контрактом навыка.

`audit-plan` проверяет план, при необходимости исправляет его и сохраняет воспроизводимые пробы в каталоге задачи. Файл `04-comment-audit.md` содержит текст комментария об аудите. Если повторный аудит обновляет уже существующий комментарий, локальная копия должна соответствовать последнему отправленному тексту. Полный отчёт аудита и пробные файлы размещать так, как определено актуальным навыком аудита. Не считать создание отдельного отчёта обязательным до проверки его контракта.

### 9.4. Реализация и влитие

До создания рабочего дерева задачи `implement` включает подготовленные материалы текущей задачи в предварительный коммит базовой ветки. Затем код, результаты проверок и изменения vault текущей реализации фиксируются на ветке задачи. `05-comment-done.md` находится в рабочем дереве задачи и содержит публикуемый комментарий о реализации. Исходники проб, которые необходимы для воспроизведения, сохраняются по правилам проекта. Игнорируемые результаты проб не следует считать сохранёнными в Git.

`merge` по запросу пользователя сначала отправляет ветку задачи, затем выполняет слияние и предусмотренные проверки. После отметки в vault отправляется базовая ветка и закрывается issue. GitHub issue и комментарии могли существовать до любого из этих push.

## 10. Коммит общего реестра и связанные материалы

### 10.1. Почему ссылка может временно отсутствовать в Git

Рассмотрим две задачи: A реализуется, B зарегистрирована в другой сессии. Реестр содержит новые записи A и B. Черновик A подготовлен к включению в коммит, черновик B остаётся незакоммиченным. При принятом пользователем порядке общий реестр коммитится целиком. В результате коммит может содержать ссылку на `vault/issues/b/00-draft.md`, но не сам файл B.

Это допустимое временное состояние по решению пользователя. Реестр и файл B не становятся испорченными в локальном рабочем каталоге только из-за такого коммита. На другой машине или в состоянии репозитория, соответствующем этому коммиту, файл B отсутствует. Если файл B затем будет включён в коммит, Git сможет восстановить его содержимое на версии, содержащей этот последующий коммит. Наличие незакоммиченного файла само по себе не гарантирует возможность восстановления через Git.

### 10.2. Требования к переносу `implement` и `merge`

1. Сохранить действующее правило коммита общих реестров целиком, включая записи других задач, если оно относится к выполняемому шагу.
2. Не вводить остановку только потому, что черновик другой задачи отсутствует в текущем или будущем коммите.
3. Не добавлять чужой черновик автоматически вслед за реестром. Не удалять и не перезаписывать его в рабочем каталоге.
4. Файлы текущей задачи включать по контракту соответствующего этапа. Учитывать отдельно случай, когда новая задача обнаружена во время реализации и её запись фиксируется в базе.
5. Существующие правила защиты чужих изменений кода, планов и материалов других задач продолжают действовать. Решение о коммите общих реестров не распространяется на все файлы vault.
6. Если возникла другая ошибка Git, конфликт или ограничение действующего навыка, разбирать её по контракту соответствующего шага. Решение о черновике не отменяет эти правила.

### 10.3. Проверочные сценарии

Проверить сценарии в отдельном репозитории внутри проекта. Его файлы и `.git` не должны совпадать с рабочим репозиторием проекта.

| Сценарий | Подготовка | Ожидаемый результат |
|---|---|---|
| Черновик текущей задачи | Реестр и `00-draft.md` A подготовлены как материалы A | Коммит текущей задачи содержит предусмотренные материалы A. |
| Новый черновик другой задачи | В реестр добавлена B, файл B не отслеживается | Реестр попадает в коммит целиком. Отсутствие файла B в коммите не блокирует операцию. Файл B не добавляется автоматически и остаётся на диске. |
| Ранее сохранённый черновик | Файл B есть в предыдущем коммите | После коммита реестра файл доступен в дереве Git без добавления рабочей копии B. |
| Изменённый черновик другой задачи | Версия B есть в Git, в рабочем каталоге есть новые правки | Коммит реестра не включает эти правки B автоматически. Они остаются в рабочем каталоге. |
| Файл отсутствует и локально | Реестр содержит ссылку B, файла нет | Само отсутствие B не отменяет принятое правило коммита. В результате не возникает фиктивного файла. |
| Новая задача во время реализации | B зарегистрирована в основной рабочей копии во время A | Проверить фактические пути, состав коммита и сохранность файла B по контракту перенесённого `implement`. |

В отчёте о проверке указать версию навыка, на которой выполнялись сценарии, и содержимое тестовых коммитов. Не выполнять push даже в тестовом сценарии, если для проверки достаточно локальной истории.

## 11. Подробный план доработки `draft`

### 11.1. Подготовка и выявление существующей задачи

1. Получить описание из аргумента или контекста сессии. Определить наблюдаемую проблему, предлагаемое изменение либо проверку, которую требуется провести.
2. Просмотреть соответствующие реестры по ключевым словам, именам файлов, меткам формул и связанным ID. При необходимости прочитать связанные заметки. Поиск похожих слов – повод сопоставить задачи, а не доказательство дубликата.
3. Если установлено, что задача уже зарегистрирована, сообщить ID, состояние и ссылку на запись. Не создавать новую запись без отдельного основания. Если сходство не позволяет установить тождество, показать различия и сохранить неопределённость.
4. Выбрать `BUG`, `DEBT`, `FEAT` или `VAL` по смыслу задачи. Не добавлять тип `TOOL` из диссертационного проекта: задачи об инструментах Oil_Gas относятся к существующим категориям.

### 11.2. Минимальный состав записи

| Тип | Что необходимо зафиксировать | Что делать при недостатке данных |
|---|---|---|
| BUG | Симптом, затронутый файл и способ воспроизведения | Указать, что именно не установлено. Не описывать гипотезу как проверенную причину. |
| DEBT | Текущее состояние, мотив изменения и затронутые модули | Отметить неизвестные области влияния и сохранить основание задачи. |
| FEAT | Предлагаемую возможность, назначение, модуль и ссылки на формулы, если они нужны | Для задачи без формул указать их неприменимость. Для неизвестной формулы оставить вопрос открытым. |
| VAL | Эталон, сценарий и метрику | Не назначать неподтверждённый допуск и не объявлять эталон независимым без проверки. |

Следующий ID определяется отдельно для каждого префикса по существующему реестру. Перед записью проверить, что выбранный ID и каталог черновика не заняты. Наличие уже занятого каталога не даёт права перезаписать его. Если одновременно работают разные сессии, повторная проверка снижает риск совпадения, но сама по себе не является блокировкой параллельной записи. При обнаруженном конфликте не затирать ни одну версию.

### 11.3. Содержание `00-draft.md`

Черновик должен позволить следующей сессии понять, какие факты и решения легли в основу задачи. Для сведений, которые обсуждались, сохранить:

- формулировку проблемы, границы, связи с другими задачами и причину регистрации.
- проверенные факты с путём к файлу, командой, источником или другим способом повторить проверку. Для чисел – единицы и условия получения, если они известны.
- сведения, сообщённые пользователем, отдельно от проверенных результатов и предположений.
- рассмотренные варианты, их последствия и явно выбранный вариант, если пользователь его выбрал.
- предварительные решения с указанием, что они могут измениться.
- вопросы, источники неопределённости, известные ограничения и проверки, которые потребуются при планировании.
- дату обсуждения или проверки, если она установлена. Не приписывать прошлую дату из догадки.

Если варианты не обсуждались, достаточно явно указать это. Не заполнять разделы придуманных альтернатив ради формы. Имя ветки и метки могут сохраняться как предложения, если они уже известны или обсуждались. `issue` повторно проверяет их перед публикацией.

### 11.4. Порядок записи и проверка результата

Перед первой записью определить точные пути реестра и черновика. Создать каталог задачи и черновик, затем внести запись в реестр. Если операция прервалась между шагами, сообщить, что уже создано, и какой шаг не выполнен. При повторном запуске сначала проверить наличие частично созданных файлов и соответствие ID. Не создавать вторую задачу автоматически и не уничтожать ранее сохранённый контекст.

Убедиться, что ссылка в реестре соответствует принятому в проекте формату Obsidian и ведёт к нужному `00-draft.md`. Отчёт пользователю содержит ID, краткую суть, путь к реестру и черновику, существенные неизвестные сведения и указание, что issue не создан.

### 11.5. Матрица проверок `draft`

| Проверка | Ожидаемое поведение |
|---|---|
| Новая BUG с подтверждённым воспроизведением | В реестре есть симптом, файл и команда. В черновике – результат и условия проверки. |
| BUG с предполагаемой причиной | Причина обозначена как гипотеза. Неизвестные сведения не заполняются выдуманным значением. |
| DEBT по инструменту проекта | Задача классифицирована в существующем типе, отдельный `TOOL` не создаётся. |
| FEAT без формул | Поле формул явно описывает неприменимость, без ссылки на устаревший метод. |
| VAL без установленного допуска | Эталон, сценарий и метрика записаны по известным данным, допуск остаётся открытым. |
| Обсуждение с условным решением | В черновике явно указан предварительный характер решения. |
| Найденная существующая задача | Новый ID и второй черновик не создаются автоматически. |
| Повтор после сбоя записи | Сохранённый файл не перезаписывается, состояние двух частей регистрации показано пользователю. |
| Отсутствие внешних действий | Нет вызовов записи в GitHub, `git add`, `git commit` и `git push`. |

## 12. Подробный план публикации `issue`

### 12.1. Порядок публикации

1. По ID найти запись в соответствующем реестре. Если записи нет, завершить работу без публикации и направить к локальной регистрации.
2. Прочитать черновик при наличии, связанные решения и относящиеся к задаче материалы. Проверить актуальность путей, утверждений и ссылок.
3. Сверить поле GitHub в реестре и результат поиска issue по точному ID. Проверять открытые и закрытые задачи.
4. Если issue существует, сообщить его URL и состояние. Не создавать второй issue и не считать отсутствие комментария в старой задаче основанием для его публикации. Изменение существующего issue выполняется по отдельному запросу.
5. Определить предлагаемые метки и ветку, проверить их по действующим соглашениям. Имя ветки не означает её создание.
6. Сформировать `vault/issues/<id-lowercase>/01-issue-body.md` и `02-comment-open.md`. Если файлы уже существуют, проверить их содержимое и назначение, прежде чем изменять. Не затирать сохранённый текст без основания.
7. Создать issue, опубликовать комментарий, записать URL и имя ветки в реестр и обновить связанную заметку, если требуется. Сообщить URL, метки и имя ветки.

Создание issue и комментария через GitHub CLI и последующий `git push` – разные действия. Отдельный файл состояния публикации, автоматическое восстановление после сбоев и сценарии недоступности GitHub не требуются по решению пользователя.

### 12.2. Проверки публикации

Проверки выполняются с подменой ответов GitHub CLI без записи на GitHub:

1. Зарегистрированная задача без существующего issue – подготовлены оба файла, создаётся один issue и один комментарий, в реестр записаны URL и имя ветки.
2. Уже существующий открытый issue – URL сообщается, второй issue и комментарий не создаются.
3. Уже существующий закрытый issue – статус и URL сообщаются, задача не открывается заново и комментарий не добавляется автоматически.
4. В каталоге задачи уже есть подготовленные файлы – их содержимое проверяется до изменения.
5. `--dry` – выводится предусмотренный предпросмотр без изменения файлов, меток и issue.

## 13. Метки GitHub

### 13.1. Выбор и создание

При обработке задачи определить базовую метку типа и дополнительные метки по содержанию записи. По текущим соглашениям соответствие типов: `BUG` → `bug`, `DEBT` → `enhancement`, `FEAT` → `feature`, `VAL` → `validation`. Перед использованием проверить реальный список меток репозитория. Если в соглашениях и GitHub обнаружено расхождение названий или значений, не объявлять их равнозначными без проверки.

Метка `critical` требует явного основания для критичности. `workaround` требует установленного обходного решения, а не одного символа 🟡. `blocking` требует установленной блокирующей связи, а не просто непустого поля, которое может содержать «ничего».

Если подходящей существующей метки нет, пользователь разрешил создать её автоматически. До создания проверить название и назначение, чтобы не плодить синонимы. Цвет и описание брать из действующих соглашений, если они определены. Если подходящий цвет не определён, использовать обычное поведение доступного инструмента и не выдавать выбранный цвет за ранее принятое соглашение.

Новые метки указать в отчёте. В `--dry` не создавать их. Специальные процедуры восстановления после ошибок сети не разрабатывать.

### 13.2. Проверки

- В репозитории уже есть подходящая базовая и дополнительные метки – использовать существующие, не создавать новые.
- Нет одной необходимой метки, список получен полностью – создать одну метку и применить её к issue.
- `Блокирует: ничего` – не назначать `blocking` по одному наличию поля.
- 🟡 без установленного обхода – не назначать `workaround` по одному символу.
- `--dry` – показать предлагаемые метки без создания новых.

## 14. Точный контракт `issue_helper.py`

### 14.1. Определение следующего ID

Скрипт читает нужный реестр в UTF-8 и сопоставляет заголовки с точным префиксом. Он выбирает номер больше максимального среди записей данного типа. `BUG` и `DEBT` используют общий файл, но нумеруются независимо.

Проверить пустой реестр, смешанные типы, пропуски номеров и заголовки формата шаблона. Не переиспользовать пропущенные номера автоматически. Скрипт не обеспечивает блокировку параллельных сессий: вызывающий навык повторно проверяет выбранный ID перед записью и не перезаписывает занятый каталог.

### 14.2. Проверка дубликатов

При успешном выполнении `gh` результат должен быть корректным JSON ожидаемой структуры. Результат поиска должен различать найденный issue и отсутствие совпадений.

Сопоставление ID должно учитывать границы идентификатора: поиск `BUG-001` не должен совпадать с `BUG-0010`. Проверить реальные соглашения заголовков проекта и предусмотреть точное совпадение ID в начале заголовка с допустимым разделителем. Не полагаться на URL issue как на источник текстового ID: URL содержит номер GitHub issue. Убедиться, что ограничение числа результатов или неполная выдача не превращается в уверенное «дубликата нет».

### 14.3. Проверка ветки

Различать локальную ветку и локально известную ссылку `origin/<branch>`. Проверка локальной ссылки не доказывает актуальное состояние сервера без сетевого запроса. Для предпросмотра и обычной работы указывать, что именно было проверено.

### 14.4. Обновление vault

Обновлять только раздел с точным ID и только нужные поля. Рассмотреть три состояния каждого поля: его нет, присутствует заполнитель, присутствует содержательное значение. Отсутствующее поле можно добавить, заполнитель – заменить подтверждённым значением, совпадающее значение – оставить без изменений. При несовпадении существующего содержательного значения сообщить о конфликте и не заменять его молча.

Повторный вызов с теми же данными не должен добавлять строки повторно или изменять текст без необходимости. Сохранять остальные разделы, переносы строк и содержимое заметки настолько, насколько позволяет выбранный способ записи. URL валидировать по ожидаемому репозиторию и номеру issue. При отсутствии корректного номера не записывать `#?` как успешно синхронизированную ссылку.

Для связанной заметки проверять именно ссылку на issue данной задачи. Наличие в заметке другой ссылки на `github.com` не доказывает, что ссылка на текущую задачу уже есть. Учитывать, что поле `Подробности` может ссылаться на `00-draft.md`, а не на файл в одной из стандартных папок `knowledge/`. Не угадывать путь по имени, если ссылка неоднозначна.

### 14.5. Тесты и запуск

Рекомендуемое размещение – `.agents/skills/issue/tests/`. Тесты вызывают функции или CLI скрипта с управляемыми данными. Ответы GitHub CLI подменяются. Для проверки веток, worktree и содержимого коммитов использовать настоящий Git в изолированном репозитории внутри проекта. Для реестров использовать тестовые файлы под каталогом проекта. Проверить путь с кириллицей. Если тесты создают временные каталоги pytest, явно настроить их размещение внутри проекта, чтобы не нарушать правило о файлах.

Проверки должны покрыть успешный результат, изменение и повторное изменение реестра, сохранение соседних задач, точность ID, существующую и отсутствующую ветку, чужую ссылку GitHub и конфликт существующего URL. Проверять наблюдаемый результат, а не только внутренний вызов конкретной функции. Специальные проверки недоступности Git и сетевых сбоев не требуются.

## 15. Передача контекста при переносе остальных навыков

В ходе последовательного переноса вести [[перенос команд проекта в навыки|перечень всех проектных команд и соответствующих навыков]] в `.agents/skills/`. Для каждой команды указать имя, путь навыка, состояние переноса, дату проверки и результат сверки с назначением команды. Проверять не только навыки работы с задачами, но и литературные команды. Перечень помогает обнаружить пропущенную команду и не является дополнительной проверкой доступности при каждом вызове.

### 15.1. Навыки планирования

Для каждого из `plan-fix`, `plan-improve`, `plan-feature`, `plan-validate` при переносе проверить отдельный пункт загрузки контекста. Порядок работы:

1. Найти запись по ID, получить ссылку на GitHub issue и связанные материалы, если они есть.
2. Прочитать `vault/issues/<id-lowercase>/00-draft.md`, если файл существует. Старую задачу без такого файла не объявлять некорректной только по этой причине.
3. Сверить факты черновика с текущими файлами и решениями. Указать, что устарело, не переносить автоматически старые номера строк и неподтверждённые утверждения.
4. Записать в план основания задачи, принятые и предварительные решения, ограничения, зависимости и открытые вопросы. План должен оставаться понятным без истории чата.
5. Сохранить план в `vault/plans/`, обновить ссылку в реестре и подготовить комментарий `03-comment-plan.md` по контракту навыка. Не терять предыдущий контекст при публикации.

Проверить один пример для каждого типа задачи. Особое внимание уделить VAL: сведения об условиях применимости эталона и происхождении допуска не должны теряться при переносе из черновика.

### 15.2. Навыки реализации и слияния

Сопоставить перенесённые `implement` и `merge` с разделами 9 и 10 этого плана. Сохранить базовую ветку соответствующего направления. Для актуальной разработки решателя это `numerical_scheme/implementation`, а не `master` или `main`. До подготовки коммитов проверить реальные настройки и состояние рабочего дерева, не смешивать проверку с автоматическим изменением пользовательских файлов.

В проверочном сценарии проследить расположение `00-draft.md`, `01-issue-body.md`, `02-comment-open.md`, плана, `03-comment-plan.md`, `04-comment-audit.md`, проб и `05-comment-done.md`. Установить, какой из файлов входит в предварительный коммит базы, какой изменяется в рабочем дереве и какой доступен после слияния. Исключения для игнорируемых результатов проб проверять по действующему `.gitignore`.

## 16. Документация и проверка связей

### 16.1. `vault/issues/README.md`

Обновить назначение каталога: он содержит как локальный контекст задачи, так и копии публикуемых текстов и пробы. Для каждого файла указать создающий этап:

| Файл | Назначение | Этап |
|---|---|---|
| `00-draft.md` | Контекст регистрации, факты, варианты и решения | `draft` |
| `01-issue-body.md` | Текст создаваемого issue | `issue` |
| `02-comment-open.md` | Комментарий при открытии | `issue` |
| `03-comment-plan.md` | Комментарий о плане | `plan-*` |
| `04-comment-audit.md` | Комментарий об аудите | `audit-plan` |
| `05-comment-done.md` | Комментарий о реализации | `implement` |
| `probes/` | Воспроизводимые проверочные материалы | Соответствующий этап расследования, планирования или реализации |

Отдельно указать, что не каждый файл существует у каждой старой задачи, а публикация комментария и отправка Git-коммитов – разные операции. Указать принятое временное расхождение общего реестра и незакоммиченного черновика другой задачи.

### 16.2. Шаблон FEAT и правила vault

В файле `vault/roadmap/планируемые фичи.md` проверить только блок «Формат записи». Заменить устаревшее указание на формулы метода моментов ссылкой на актуальную постановку `numerical_solver/doc/problem_statement.tex` там, где задача относится к решателю. Предусмотреть задачи инструментов или документации, для которых формулы не применимы. Не менять исторические записи и не делать формулы обязательными для задач без математического содержания.

Сверить `.agents/project/vault.md`, шаблоны навыка `issue` и руководство каталога. Они должны одинаково описывать очередность регистрации, публикации и записи URL. Исторические записи, зарегистрированные без черновика, продолжают работать.

## 17. Порядок реализации, результаты и контроль

### 17.1. Последовательность работ

1. **Подготовка.** Проверить состояние Git и перечень файлов, относящихся к работе. Прочитать актуальные версии целевых навыков и тестовой инфраструктуры. Зафиксировать уже имеющиеся пользовательские изменения, не изменяя архивные команды.
2. **Тесты скрипта.** Подготовить тестовые случаи из раздела 14 рядом с `issue_helper.py`. Сначала убедиться, что проверки выявляют соответствующие недостатки существующей реализации, затем изменить скрипт и добиться прохождения тестов. Проверить отсутствие побочных действий в рабочем vault и GitHub.
3. **Навык `draft`.** Уточнить входы, источники, запись черновика и восстановление после частичной локальной регистрации по разделу 11. Проверить сценарии для четырёх типов задач.
4. **Навык `issue` и метки.** Внести правила из разделов 12 и 13. Сверить их с поведением скрипта и шаблонами. Проверить штатную публикацию, существующий issue, подготовленные файлы и `--dry` с подменённым GitHub CLI.
5. **Последующие навыки.** При последовательном переносе пользователем учесть требования раздела 15 и вести перечень команд и навыков. Не перезаписывать результат параллельной сессии и не менять архивные команды. Если навык уже перенесён, вносить только относящиеся к задаче изменения в согласованном объёме.
6. **Документация.** Обновить описание каталога задач и формат записи FEAT, сохранив исторические данные. Сверить правила vault с навыками.
7. **Сквозная проверка.** Выполнить сценарии новой и старой задач, проверить состав локальных артефактов и ожидаемые точки публикации и push. Сценарии с Git-коммитами выполнять только в отдельном тестовом репозитории внутри проекта.

Шаги 2–4 можно выполнять независимо от последовательного переноса остальных навыков, но сквозная проверка конкретного перенесённого навыка требует его фактической реализации. Не подменять проверку утверждением, что она автоматически выполнена при переносе.

### 17.2. Критерии завершения

- `draft` сохраняет проверенные сведения, решения и неизвестные данные и не публикует задачу.
- `issue` публикует только зарегистрированный ID и сообщает о существующем issue, не создавая второй.
- Метки выбираются по содержанию. Недостающая подходящая метка может создаваться автоматически по решению пользователя.
- `issue_helper.py` корректно обрабатывает штатные данные, сохраняет соседние записи и не дублирует поля при повторном вызове.
- Планирование читает черновик при наличии и сохраняет существенные сведения в плане. Старые задачи без черновика остаются допустимыми.
- При коммите общего реестра соблюдать решение пользователя из раздела 10. Чужой черновик не добавляется автоматически и сам по себе не блокирует коммит реестра.
- Описание артефактов, шаблон FEAT и актуальные навыки не противоречат друг другу. Архивные команды не менялись при реализации этого плана.
- В перечне отражены все проектные команды, соответствующие навыки и результаты сверки. Перечень ведётся по мере последовательного переноса.
- Проверки навыков, документации и кода выполнены в объёме, соответствующем изменению. Сбои и непроверенные интеграции перечислены в отчёте.

### 17.3. Ограничения проверок и открытые технические вопросы

Проверка локальной ссылки на удалённую ветку не заменяет проверку сервера. При описании результатов указывать, какое состояние проверено.

Изолированный тестовый репозиторий допускает собственные коммиты для проверки состава дерева. Это не означает разрешения создавать коммиты в рабочем репозитории проекта. Настоящие публикации issue, изменения меток и push не нужны для автоматизированных сценариев с подменёнными ответами GitHub.
