## Кратко

Сейчас четыре вида ошибок в `oil_pvt.csv` проходят молча:
- ветвь $R_s$ из одной строки;
- повтор давления внутри ветви;
- строки ветви не по возрастанию давления;
- давление насыщения $p_b$ не растёт от ветви к ветви.

`BlackOilPVT` строит из такой таблицы другие $B_o$, $\mu_o$ недонасыщенной нефти, а в последнем случае — другую кривую разгазирования $R_s^{sat}(p)$. XLSX-ридер прототипа отклоняет первые три вида ошибок.

После правки функция фабрики `_check_pvto_branches` отклоняет все четыре с `ValueError`. Сообщение называет файл, ветвь $R_s$ и давления. Пустую таблицу функция тоже отклоняет: сейчас она падает `IndexError` внутри `BlackOilPVT`.

Объём: 1 функция (~45 строк), 1 вызов, 8 тестов, 1 комментарий теста прототипа, 3 абзаца документации. Тестов: 1289 → 1297.

## Контекст для читателя без контекста

**Таблица PVTO** (формат ECLIPSE) задаёт свойства нефти с растворённым газом. Строки сгруппированы по газосодержанию $R_s$: каждая группа — «ветвь». Первая строка ветви — насыщенная точка: давление насыщения $p_b(R_s)$ и $B_o$, $\mu_o$ при нём. Следующие строки той же ветви — недонасыщенная нефть: тот же $R_s$, давление выше $p_b$. По ним определяются сжимаемость $c_o$ и рост $\mu_o$ с давлением. Из первых строк всех ветвей складывается кривая разгазирования: $R_s^{sat}(p)$ — обратная к $p_b(R_s)$.

CSV-формат проекта: `Rs_sm3_sm3,pressure_Pa,Bo,mu_o_Pa_s`, единицы СИ. Образец — `numerical_solver/configs/table_pvt/oil_pvt.csv`: ветви $R_s$ = 0 и 30, по две строки.

**Путь табличной PVT в фабрике** (`numerical_solver/gpn_multiphase_solver/factory.py`, функция `_create_pvt`, ветвь `pc.model == "table"`, строки 115–146):

```
_read_oil_pvt_csv (:371-395)   — разбор CSV → [(Rs, p_бар, Bo, mu_сП), ...], без проверок
_read_gas_pvt_csv (:398-421)
BlackOilPVT(oil_rows, gas_rows) (:126-127) — прототип, radial_blackoil/pvt.py
_check_rs0_in_table (:136, определена :152-162) — Rs0 в диапазоне ветвей (BUG-017); берёт proto_pvt.rs_values
PrototypePVTAdapter → TableFullPVT — те же B_o, μ_o идут и в гидродинамику, и в уравнение энергии
```

Дальше `from_config` проверяет пересыщенный старт (`_check_undersaturated_start`) и согласованность PVT (BUG-019, только предупреждение).

**Что делает `BlackOilPVT` с ошибочной ветвью.** `numerical_solver/HydroSolverPrototype/Prototype_1.0.3/radial_blackoil/pvt.py:13-33`:
- строки ветви сортируются по кортежу $(p, B_o, \mu_o)$;
- $p_b$ ветви — давление её первой строки после сортировки;
- $R_s^{sat}(p)$ = `np.interp(p, pb, rs_values)` (`pvt.py:35-36`). При немонотонных узлах `pb` результат `np.interp` не определён документацией numpy.

Замер 2026-10-07: тело issue #67 и пробы `vault/issues/debt-038/probes/red_state.py`, `pb_order.py`, выводы в `*.out.txt`:

**Правила формата PVTO.** OPM Flow Reference Manual 2025-10 (`Refs/incoming/OPM_Flow_Reference_Manual_2025-10_Rev-0_compressed.pdf`, §8.3.245 PVTO, табл. 8.133, с. 1131–1133):
- RS, PRSS (давление насыщения) и PRSU (давление недонасыщенных строк ветви) — «monotonically increasing down the column»;
- недонасыщенные строки не обязательны, но «there must be at least two entries for the last Rs value».

Ветвь из одной строки (кроме последней) OPM достраивает по следующей ветви с недонасыщенными строками («master table»), перенося относительный ход $B_o$ и $\mu_o$. Источник — код opm-common, `LiveOilPvt`: [исходник](https://opm-project.org/apidoc/latest/opm-material/html/_live_oil_pvt_8hpp_source.php), проверено при аудите 2026-10-07. Последнюю ветвь из одной строки OPM отвергает: «The last table must exhibit at least one entry for undersaturated oil». Прототип ветвь из одной строки не достраивает: $B_o$, $\mu_o$ выше $p_b$ у него постоянны.

**XLSX-ридер прототипа** (`numerical_solver/HydroSolverPrototype/Prototype_1.0.3/radial_blackoil/input_reader.py:54-64`) проверяет первые три правила: нет числовых строк → ошибка; в ветви не меньше двух строк; давление строго растёт внутри ветви по порядку файла. Ветвь — все строки с одним $R_s$, совпадение точное; смежность строк не требуется. Рост $p_b$ с $R_s$ XLSX-ридер не проверяет.

**Решения пользователя (2026-10-07):**
1. Место проверки — отдельная функция фабрики `_check_pvto_branches` до `BlackOilPVT` (вариант 1 issue). Прототип и ридер не меняются.
2. Ветвь из одной строки отклоняется любая, не только последняя: прототип её не достраивает.
3. Различные давления не по возрастанию отклоняются, как в XLSX. Отклоняется не только повтор.
4. Смежная проблема (CSV-ридеры молча пропускают нечисловые строки) — отдельная запись DEBT-042, в этот план не входит.
5. (Аудит.) $p_b$ строго растёт с $R_s$ — правило OPM (PRSS). В этом пункте CSV-путь строже XLSX-ридера.

### Шаг 3: Функция `_check_pvto_branches` и её вызов

**Цель:** фабрика отклоняет ошибочные ветви до построения `BlackOilPVT`.

**Файлы:** `numerical_solver/gpn_multiphase_solver/factory.py`

**Контекст:**
- Ветви группируются по точному значению $R_s$, давления сравниваются в порядке файла — как в XLSX-ридере (`input_reader.py:59-64`).
- Значения сравниваются в барах: так их получает `BlackOilPVT`. В МПа они переводятся только для сообщения, потому что CSV задан в Па, а бары пользователь не видит.
- Ветви перебираются по возрастанию $R_s$, как в XLSX-ридере, поэтому сообщение детерминировано.
- $p_b$ ветви — давление её первой строки. После проверки порядка внутри ветви это её минимум: так `BlackOilPVT` и берёт $p_b$ после сортировки. Поэтому рост $p_b$ проверяется после правил внутри ветвей (чеклист, ⚠️).
- Ошибка — `ValueError`, как у `_check_rs0_in_table`; тесты `from_config` ловят именно этот тип.

1. Вставить функцию после `_check_rs0_in_table` (после строки 162, перед пустыми строками и комментарием `# Допуск пересыщения на старте` на строке 165):

```python


def _check_pvto_branches(oil_rows: list[tuple], oil_pvt_file: str) -> None:
    """Ветви PVTO: ≥ 2 строк, p и p_b(R_s) растут, иначе ValueError (DEBT-038)."""
    # Правила формата PVTO (OPM Flow Manual, §8.3.245): в ветви — насыщенная
    # точка p_b(R_s) и строки недонасыщенной нефти по возрастанию давления;
    # p_b растёт с R_s. Первые два правила проверяет и XLSX-ридер прототипа
    # (input_reader.py:59-64). BlackOilPVT не проверяет ни одного, и ошибка
    # таблицы молча меняет свойства нефти — а через PrototypePVTAdapter и
    # уравнение энергии:
    #   - ветвь из одной строки: B_o, μ_o выше p_b постоянны (c_o = 0).
    #     OPM такую ветвь допускает (кроме последней) и достраивает по
    #     следующей ветви с недонасыщенными строками (opm-common, LiveOilPvt);
    #     прототип — нет;
    #   - повтор давления: BlackOilPVT сортирует строки по (p, B_o, μ_o), а не
    #     по порядку файла, — скачок B_o в этой точке;
    #   - давление не по возрастанию: сортировка исправила бы его молча, но
    #     XLSX-путь такую таблицу отвергает — правила двух путей одинаковы;
    #   - p_b не растёт с R_s: R_s^sat(p) интерполируется np.interp по узлам
    #     p_b, и при немонотонных узлах кривая разгазирования ломается.
    if not oil_rows:
        # Без строк BlackOilPVT падает IndexError без имени файла
        raise ValueError(f"{oil_pvt_file}: нет ни одной числовой строки.")
    # Ветвь — все строки с одним R_s (точное совпадение, как в BlackOilPVT);
    # давления в барах — как их получает BlackOilPVT, в порядке файла
    branches: dict[float, list[float]] = {}
    for Rs, p_bar, _, _ in oil_rows:
        branches.setdefault(Rs, []).append(p_bar)
    for Rs, p_bar in sorted(branches.items()):
        p_mpa = [p * BAR_TO_PA / 1e6 for p in p_bar]   # только для сообщений
        if len(p_bar) < 2:
            raise ValueError(
                f"{oil_pvt_file}: ветвь R_s = {Rs:g} м³ст/м³ст из одной строки "
                f"(p = {p_mpa[0]:g} МПа). Нужно не меньше двух: насыщенная точка "
                f"p_b(R_s) и хотя бы одна строка выше p_b — иначе B_o, μ_o "
                f"недонасыщенной нефти не заданы.")
        for k in range(1, len(p_bar)):
            if p_bar[k] <= p_bar[k - 1]:
                raise ValueError(
                    f"{oil_pvt_file}: в ветви R_s = {Rs:g} м³ст/м³ст давление "
                    f"не растёт строго: {p_mpa[k]:g} МПа после {p_mpa[k - 1]:g} МПа "
                    f"(строки {k} и {k + 1} ветви). Первая строка ветви — "
                    f"насыщенная точка p_b(R_s), дальше давление растёт.")
    # p_b — первая строка ветви, после проверок выше это минимум ветви
    rs_sorted = sorted(branches)
    for Rs_lo, Rs_hi in zip(rs_sorted, rs_sorted[1:]):
        pb_lo, pb_hi = branches[Rs_lo][0], branches[Rs_hi][0]
        if pb_hi <= pb_lo:
            raise ValueError(
                f"{oil_pvt_file}: давление насыщения не растёт с R_s: "
                f"p_b = {pb_hi * BAR_TO_PA / 1e6:g} МПа у ветви R_s = {Rs_hi:g} "
                f"при p_b = {pb_lo * BAR_TO_PA / 1e6:g} МПа у ветви R_s = {Rs_lo:g} "
                f"м³ст/м³ст. p_b — давление первой строки ветви.")
```

   Нумерация «строки {k} и {k + 1} ветви» — с единицы: `k` — индекс с нуля у второй из двух строк, поэтому номера $k$ и $k+1$. Самая длинная строка функции — 85 символов (в `factory.py` сейчас не больше 93). Оба блока кода плана (функция и тесты) компилируются — проверено при аудите.

## Обнаруженные проблемы

1. **DEBT-042** (зарегистрирован 2026-10-07 по решению пользователя). CSV-ридеры фабрики при нечисловом значении делают `continue`: опечатка в числе молча удаляет строку таблицы. Лишние столбцы отбрасываются без сообщения: десятичная запятая сдвигает значения. У `_read_relperm_csv` столбцы дописываются по одному, поэтому при ошибке во 2-м или 3-м столбце они получаются разной длины. `TabulatedRelPerm` такие столбцы принимает, отказ наступает позже: `np.interp: fp and xp are not of the same length`. `float()` к тому же принимает `nan` и `inf`, а сравнения с NaN ложны, так что правила DEBT-038 такую строку не ловят. Проверки DEBT-038 ловят пропуск строки, только если ветвь сократилась до одной строки. Не блокирует.
2. **`json-config-schema.md:64`** неверно описывает табличный путь («колонки p, Bo, Bg, mu_o, mu_g, Rs_eq»). Исправляется в шаге 5, отдельной записи не требует.
3. **Прямой вызов `BlackOilPVT`** с повтором давления по-прежнему даёт `RuntimeWarning: divide by zero` (`pvt.py:56`) без имени файла. Это осознанный минус варианта 1 (решение пользователя). XLSX- и CSV-пути до этого места не доходят.
4. **(Аудит) XLSX-ридер прототипа не проверяет рост $p_b$ с $R_s$.** В этом пункте CSV-путь после DEBT-038 строже. Для XLSX-пути GPN не используется (фабрика читает только CSV), отдельной записи не требует. Учесть, если XLSX-путь понадобится.
