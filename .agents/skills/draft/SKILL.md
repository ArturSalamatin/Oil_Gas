# Навык draft: локальная регистрация задачи

Применять, когда пользователь просит зафиксировать новую задачу по описанию или по итогам обсуждения. Результат – запись в реестре и черновик с контекстом в `vault/issues/<id-lowercase>/00-draft.md`. Публикация через `/issue <ID>` выполняется позже по отдельному запросу. Не создавать issue, комментарии, метки, ветки или коммиты, не выполнять `git add` и `git push` и не запускать планирование.

## Анализ и регистрация

1. Прочитать `.agents/project/vault.md` и определить суть задачи из запроса и контекста. Проверить связанные записи реестров и заметки vault, чтобы не зарегистрировать тот же вопрос повторно. Если задача уже зарегистрирована, сообщить её ID и состояние. Дополнять существующую запись только по запросу пользователя.
2. Выбрать тип: `BUG` – дефект, `DEBT` – технический долг или улучшение, `FEAT` – новая возможность, `VAL` – проверка по эталону. Использовать существующие категории проекта, включая DEBT или FEAT для инструментов. Если тип или содержание нельзя надёжно определить, уточнить у пользователя.
3. Выделить проверенные факты, ссылки на файлы и источники, решения пользователя, открытые вопросы и границы задачи. Проверять утверждения по доступным материалам соразмерно задаче. Для проверенного факта сохранять источник, команду или путь, условия и дату проверки, если известны. Отдельно указывать сведения пользователя и гипотезы. Различать принятые, предварительные и отсутствующие решения.
4. Подготовить обязательные поля реестра. Для BUG указать симптом, файл и воспроизведение. Для DEBT – текущее состояние, мотивацию и затронутые модули. Для FEAT – описание, ссылки на формулы при их наличии и модуль. Для VAL – эталон, сценарий и метрику. Для задач `numerical_solver` постановка находится в `numerical_solver/doc/problem_statement.tex`, ссылки на её формулы давать по меткам. Для задач без формул указать, что они неприменимы. Не выдумывать отсутствующие сведения: обозначить их как неустановленные и при необходимости уточнить.
5. Найти максимальный номер нужного типа в соответствующем реестре и выбрать следующий, не переиспользуя номера. Можно использовать `python .agents/skills/issue/scripts/issue_helper.py next-id <TYPE>`. Непосредственно перед записью повторно проверить, что ID свободен.
6. Создать `vault/issues/<id-lowercase>/00-draft.md`, сохранив полезный для будущей работы контекст:
   - постановку проблемы и её границы.
   - проверенные факты и источники с путями, командами, результатами и условиями проверок. Для чисел указывать единицы и условия получения, если известны.
   - обсуждённые варианты, их последствия и решение пользователя, если оно есть. Предварительное решение обозначать явно.
   - неизвестные данные, зависимости и вопросы для планирования.

   Не заполнять разделы предположениями. Если варианты не обсуждались или решение не принято, указать это. Предложенные в обсуждении имя ветки и метки сохранять как предложения: перед публикацией `issue` их проверит. Не заменять существующий черновик: совпадение ID требует разрешения конфликта до записи.
7. Добавить запись в реестр по его формату со статусом `🔴 ОТКРЫТ`, обязательными полями и ссылкой на черновик. Не заполнять поля GitHub, ветки и плана как уже существующие: они определяются на следующих этапах. Сохранить ранее существующие записи.
   Если запись прервана между созданием черновика и обновлением реестра, сообщить, что уже сохранено. При повторном вызове сначала проверить созданные файлы и ID, не перезаписывая их.
8. Сообщить суть задачи, ID, ссылки на запись реестра и черновик, а также существенные неизвестные сведения. Явно указать, что GitHub issue не создан. Предложить `/issue <ID>` как отдельный следующий шаг, когда пользователь решит опубликовать задачу.
