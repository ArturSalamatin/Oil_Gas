# Навык issue: публикация задачи из vault

Навык готовит и публикует GitHub issue по зарегистрированному ID. Первичная регистрация и сохранение контекста обсуждения выполняются навыком `draft`. Свободное описание проблемы само по себе не является запросом на публикацию.

## Вход и границы

- Принимать ID `BUG-NNN`, `DEBT-NNN`, `FEAT-NNN` или `VAL-NNN` и необязательный флаг `--dry`. Если ID не указан или записи в реестре нет, остановиться и предложить сначала зарегистрировать задачу. Не создавать запись и не публиковать issue по свободному описанию.
- `--dry`: выполнить доступный анализ и проверки, показать суть задачи, заголовок, метки, имя ветки и первые 20 строк тела issue. Не создавать и не изменять файлы, ветки, метки или issue. Запросы к GitHub для чтения допустимы. Если проверка недоступна, указать это.
- Работать последовательно, без субагентов. Коммиты и ветки не создавать. Артефакты публикации хранить в `vault/issues/<id-lowercase>/`. Текст передавать через `--body-file`.

## Подготовка

1. Найти запись в реестре по [conventions.md](references/conventions.md). Прочитать связанные заметки и, если существует, `vault/issues/<id-lowercase>/00-draft.md`: проверенные факты, обсуждённые варианты, решения пользователя и нерешённые вопросы. Отсутствие черновика у ранее зарегистрированной задачи не блокирует работу, если контекста достаточно.
2. Проверить поле GitHub в реестре и поиск по GitHub командой `python .agents/skills/issue/scripts/issue_helper.py check-duplicate <ID>`. Проверить, что найденный issue относится именно к этому ID. Если он уже существует, сообщить URL и остановиться. Изменение существующего issue или создание ещё одного требует отдельного указания. Ошибка проверки не означает отсутствие дубликата: не публиковать, пока проверка не выполнена.
3. Проверить связанные решения в `vault/knowledge/decisions/`, связанные задачи и их issue. Не представлять отвергнутый пользователем вариант как выбранный. Сопоставить контекст с текущим состоянием: существуют ли файлы, функции, метки и цитаты. Отметить устаревшие или непроверенные сведения.
4. По существу задачи проверить затронутые формулы, код, вызывающие места, тесты и документацию. Для `numerical_solver` актуальная постановка – `numerical_solver/doc/problem_statement.tex`. Ссылки на её формулы записывать по меткам. Метод моментов служит только справочным материалом. Для VAL проверить источник и независимость эталона, применимость условий, сценарий, метрику и обоснование допуска. Неизвестные данные обозначить как требующие определения.
5. Если применимо, сопоставить варианты: суть, затронутые места, достоинства и недостатки. Указать решение пользователя или рекомендацию с обоснованием. Не выдавать гипотезу за установленную причину. Если имеющихся данных недостаточно для содержательного issue, обозначить пробелы и остановиться до их выяснения.
6. Подготовить укрупнённые этапы и проверки по типу задачи. Подробный план создаётся на следующем этапе `/plan-*`. Не навязывать минимальное и архитектурное исправления как обязательные этапы каждой задачи.

## Ветка, метки и публикация

1. Сформировать или уточнить предложенные в черновике имя ветки и метки по [conventions.md](references/conventions.md). Проверить ветку командой `python .agents/skills/issue/scripts/issue_helper.py check-branch <имя-ветки>` и наличие меток в репозитории. Не считать запись в черновике доказательством их актуальности.
2. Подготовить тело issue и комментарий по шаблону соответствующего типа: [BUG](references/templates/bug.md), [DEBT](references/templates/debt.md), [FEAT](references/templates/feat.md), [VAL](references/templates/val.md). Сохранить границы задачи, факты и решения из черновика. Ссылки на связанные issue приводить при наличии.
3. При `--dry` показать предпросмотр и завершить работу. В обычном режиме сохранить `01-issue-body.md` и `02-comment-open.md` в каталоге задачи. Зафиксировать в комментарии фактические ветку и короткий SHA основного каталога отдельно от предполагаемого имени ветки задачи.
4. Создать issue в `ArturSalamatin/Oil_Gas` через `gh issue create` с `--body-file`, выбранными существующими метками и `--assignee @me`. Затем опубликовать комментарий через `gh issue comment --body-file`. Если публикация issue удалась, а комментарий или синхронизация не удались, сохранить URL и сообщить о незавершённых шагах. Повторный запуск не должен создавать дубликат.
5. Записать URL и имя ветки в реестр и связанную заметку знаний. При использовании `python .agents/skills/issue/scripts/issue_helper.py update-vault <ID> --issue-url <URL> --branch <имя>` проверить результат: существующие поля скрипт не заменяет. При расхождении исправить запись адресно, сохраняя остальные данные.
6. Сообщить суть задачи, URL, метки и предполагаемое имя ветки. Предложить следующий шаг: `/plan-fix` для BUG, `/plan-improve` для DEBT, `/plan-feature` для FEAT, `/plan-validate` для VAL.
