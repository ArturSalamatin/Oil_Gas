# Промпт: создание CLAUDE.md для нового проекта

> Этот промпт — инструкция для Claude Code. Скопируй его в чат при старте нового проекта, чтобы сгенерировать CLAUDE.md по файлам-примерам и контексту проекта.

---

## Промпт

В папке `example_files/` лежат файлы `CLAUDE_*.md` — примеры CLAUDE.md из других проектов. Изучи их структуру и подход, но не копируй содержание — каждый проект уникален.

Твоя задача — создать файл `CLAUDE.md` для текущего проекта. Действуй так:

### Шаг 1. Разведка

Прежде чем писать — изучи проект:

1. Прочитай все файлы `example_files/CLAUDE_*.md` — извлеки общие паттерны структуры.
2. Изучи структуру текущего проекта: `Glob("**/*")`, посмотри папки, ключевые файлы, языки.
3. Если есть vault/obsidian — прочитай `index.md` и `текущие приоритеты.md`.
4. Если есть README, TASK.md, существующие .md-файлы с описанием — прочитай.
5. Если есть код — определи язык, фреймворк, систему сборки, тесты.
6. Если есть LaTeX — определи преамбулу, пакеты, систему обозначений.

Не читай файлы целиком. Используй Grep → Read(offset, limit).

### Шаг 2. Спроси пользователя

Перед генерацией уточни следующее (если не очевидно из файлов):

- Краткое описание проекта (2–3 предложения): что делает, для чего.
- Текущая стадия: начало / активная разработка / поддержка.
- Какие задачи будут ставиться Claude чаще всего (код / математика / тексты / рефакторинг / исследование).
- Есть ли Obsidian vault или другая система заметок.
- Предпочтения по стилю общения (например: научный спарринг-партнёр / исполнительный помощник / ревьюер кода).
- Есть ли вещи, которые Claude точно НЕ должен делать (трогать определённые файлы, запускать агентов, и т.д.).

### Шаг 3. Собери CLAUDE.md

Файл должен содержать **только релевантные секции** из списка ниже. Не включай секцию, если она не нужна проекту. Порядок секций — от самого важного к справочному.

#### Обязательные секции

1. **Описание проекта** — 3–5 строк: что, зачем, на какой стадии. Без воды.

2. **Структура проекта** — таблица `| Папка / файл | Содержание |`. Только ключевые элементы (5–15 строк). Не перечисляй каждый файл — Claude может сделать Glob сам.

3. **Стиль общения** — как Claude должен вести диалог. Примеры:
   - Научный спарринг-партнёр: не соглашаться ради вежливости, указывать на слабые места.
   - Исполнительный режим: молча делать, отвечать кратко.
   - Ревьюер: фокус на ошибках и улучшениях.

4. **Экономия токенов** — обязательная секция. Включи правила:
   - Чтение файлов: offset+limit, не перечитывать после Edit, Grep перед Read.
   - Вызовы инструментов: batch независимых, Edit вместо Write.
   - Ответы: кратко по умолчанию, не описывать что собираешься сделать.
   - Если есть большие файлы (>200 строк) — перечисли их явно с пометкой «всегда offset+limit».

5. **Файлы и код** — минимальные правила: не трогать без просьбы, не добавлять лишнего, комментарии только для WHY.

#### Условные секции (включай, если есть в проекте)

6. **Обозначения и нотация** — для научных/математических проектов. Единый словарь символов в виде таблиц по группам (координаты, физические величины, индексы, и т.д.). Предотвращает рассогласование нотации между документами.

7. **Субагенты запрещены** — если пользователь явно запретил. Обязательно указать причину (например: параллельные агенты сжирают токены при поиске литературы). Без причины правило будет проигнорировано при edge cases.

8. **LaTeX** — для проектов с LaTeX-документами: язык, кодировка, пакеты, правила нумерации уравнений, команда сборки.

9. **Сборка и тесты** — для кодовых проектов: точные команды сборки, запуска тестов, линтинга. Копируй-вставляй без раздумий.

10. **Коммиты** — только если git инициализирован. Формат, типы, что не коммитить.

11. **Секреты** — только если в проекте есть ключи, .env, API-токены. Не добавляй для теоретических/математических проектов.

12. **Obsidian vault** — если есть vault: структура папок, что читать при старте сессии, ритуал завершения сессии, правила заметок.

13. **Литература / Refs** — для научных проектов: список доступных источников с аннотациями.

14. **Когда непонятно** — 2–3 пункта: куда смотреть в первую очередь, когда спрашивать пользователя.

### Шаг 4. Проверь результат

Перед тем как отдать файл пользователю, проверь:

- [ ] Нет секций, нерелевантных проекту (секреты в мат. проекте, сборка в текстовом).
- [ ] Нет повторов информации между секциями.
- [ ] Нет общих фраз, которые верны для любого проекта и не несут информации («пишите чистый код»).
- [ ] Каждое правило можно нарушить — и нарушение будет заметно. Если нельзя нарушить, правило бесполезно.
- [ ] Секция экономии токенов присутствует и конкретна.
- [ ] Описание проекта позволяет восстановить контекст с нуля за 30 секунд.
- [ ] Размер файла — 80–200 строк. Меньше — теряется контекст. Больше — сам файл жрёт токены.

## Антипаттерны — чего НЕ делать

- **Не копируй секции из примеров вслепую.** Пример с C++ сборкой не нужен Python-проекту. Пример с Obsidian vault не нужен проекту без vault.
- **Не добавляй секцию «рабочее окружение» (ОС, shell).** Claude определяет это автоматически из системного контекста.
- **Не пиши правила, которые дублируют дефолтное поведение Claude Code.** Например, «отвечай на русском» — Claude и так отвечает на языке пользователя.
- **Не используй эмодзи в заголовках.** Они тратят токены и не добавляют информации.
- **Не пиши «AI агент должен...»** — CLAUDE.md читается самим Claude, обращайся напрямую: «Не трогай...», «Используй...», «Читай...».
- **Не добавляй секцию про PR/MR**, если проект не использует git.
- **Не описывай файловую структуру до последнего файла** — Claude может сделать Glob. Опиши только семантику папок верхнего уровня.

---

## Принципы

1. **CLAUDE.md — это контракт, а не README.** Он не для людей, а для Claude. Каждая строка должна менять поведение.
2. **Пиши для восстановления контекста.** Каждая новая сессия начинается с чтения CLAUDE.md. Файл должен за 30 секунд ввести в курс дела.
3. **Токены — валюта.** Каждая лишняя строка в CLAUDE.md тратит токены при каждом запуске. Секция окупается, только если экономит больше, чем стоит.
4. **Правило без причины — мёртвое правило.** Claude будет соблюдать его буквально, но нарушать по духу. Пиши «почему», чтобы Claude мог экстраполировать на edge cases.
5. **Лучше не дописать, чем переписать.** CLAUDE.md можно дополнить в любой момент. Начни с минимума и добавляй по мере появления проблем.
