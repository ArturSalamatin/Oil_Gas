# /implement — реализация плана из vault

Аргумент: `$ARGUMENTS` — идентификатор задачи (`BUG-001`, `DEBT-003`, `FEAT-005`, `VAL-002`) или имя файла плана.

Результат: реализованный план — код, тесты, обновлённый vault, комментарий к GitHub issue.

**Рабочая директория зависит от направления задачи.** Определи её до начала работы:

| Направление | Каталог | Пакет / исходники | Тесты | Конфиги | Базовая ветка |
|---|---|---|---|---|---|
| **PDE-солвер** (текущая разработка) | `numerical_solver/` | `gpn_multiphase_solver/` | `tests/` | `configs/` | `numerical_scheme/implementation` |
| **Метод моментов** (завершён, только справка) | `method_of_moments/` | `src/` | `tests/` | `configs/` | `master` |

Все пути в планах и отчётах — от корня проекта (например `numerical_solver/gpn_multiphase_solver/factory.py`).

Команды pytest — из соответствующего каталога:
```powershell
cd numerical_solver ; .venv\Scripts\python -m pytest tests/ -v
```

⚠️ Для `numerical_solver` тестам нужен прототип `radial_blackoil` — его подключает `tests/conftest.py` через `sys.path`. Скрипты вне pytest должны делать это сами.

По умолчанию новые задачи относятся к `numerical_solver/`. Если задача явно про метод моментов — использовать вторую строку таблицы.

## Фаза 1: Подготовка

### 1.1. Найти план

1. Если `$ARGUMENTS` — ID: `ls vault/plans/<id-lowercase>*`
2. Если `$ARGUMENTS` — имя файла: `vault/plans/<имя>.md`
3. Если плана нет — предложи создать через `/plan-fix`, `/plan-feature`, `/plan-validate` или `/plan-improve`

### 1.2. Загрузить план

1. Прочитай план целиком
2. Извлеки из frontmatter: `issue`, `github`, `branch`, `status`
3. Проверь `status`:
   - `готов к реализации` → продолжай с шага 1.3
   - `в процессе` → возобновление, перейди к 2.6
   - `черновик` → предложи `/audit-plan`
   - `реализован` / `заблокирован` → сообщи пользователю, не продолжай без подтверждения
4. Запомни: количество шагов, ветку, зависимости, критерии завершения

### 1.3. Проверить зависимости

1. Предшествующие задачи завершены? Grep в реестрах по ID зависимостей
2. Ветка не существует? `git branch --list "<branch>"`
3. Нет незакоммиченных изменений? `git status`

### 1.4. Загрузить контекст

Выполни секцию «Как начать работу по этому плану» из файла плана:
1. Прочитай связанные vault-заметки
2. Прочитай формулы из `moments_method.tex` (offset + limit по нужному разделу)
3. Прочитай файлы, которые будут изменены (только нужные фрагменты)
4. Если есть GitHub issue — прочитай: `gh issue view <N> --repo ArturSalamatin/Oil_Gas` (могут быть комментарии с уточнениями от аудита или пользователя)

### 1.5. Создать ветку

Сначала определи **базовую** ветку. Если план её указывает (секция «Ветка») — использовать её. Если нет — определить по факту, а не по имени:

```powershell
# содержит ли ветка каталог, который правит план?
git ls-tree <кандидат> --name-only | Select-String <рабочий каталог>
```

Базовая ветка проекта зависит от направления работы:

| Направление | Базовая ветка |
|---|---|
| `numerical_solver/` (PDE-солвер) | `numerical_scheme/implementation` |
| `method_of_moments/` | `master` |

⚠️ `master` **не содержит** `numerical_solver/` — ветвление от него для задач солвера даст дерево без библиотеки. Ветки `main` в репозитории нет.

```powershell
git checkout <базовая-ветка>
git checkout -b <branch-from-plan>
```

Если ветка уже существует:
```powershell
git checkout <branch-from-plan>
```

Если план зависит от другой задачи, ещё не влитой в базовую (поле «Зависит от»), — ветвиться от ветки этой задачи и указать это в отчёте.

После создания/переключения:
1. Обнови frontmatter плана: `status: в процессе`
2. Коммит: `vault: <ID> начало реализации`

### 1.6. Baseline тестов

```powershell
cd d:\Lessons\Grants\2026\GPN\Oil_Gas\<рабочий каталог>
.venv\Scripts\python -m pytest tests/ -q
```

`<рабочий каталог>` — из таблицы в шапке (`numerical_solver` для задач PDE-солвера).

Запомни: количество тестов, pass/fail, время. Это baseline — с ним сверяется регрессия после каждого шага. Если план указывает baseline и он **не совпал** с фактическим — не игнорируй: план мог устареть, сверь и зафиксируй факт.

## Фаза 2: Реализация

### 2.1. Порядок шагов

Следуй плану **строго по порядку шагов.** Не перескакивай. Не объединяй шаги.

Для каждого шага:

### 2.2. Выполнение шага

1. **Прочитай описание шага** из плана
2. **Прочитай файлы,** которые будут изменены (offset + limit, не целиком)
3. **Проверь актуальность:** номера строк совпадают? Функции существуют?
   - Если план устарел — адаптируй шаг, но **не меняй цель**
4. **Реализуй изменения:**
   - Edit для модификации существующих файлов
   - Write для новых файлов
   - Docstrings: одна строка + `\eqref{eq:...}` (если формула)
5. **Тесты шага:**
   - Создай/обнови тесты, если шаг это предусматривает
   - Запусти тест шага: `.venv/Scripts/python -m pytest tests/<file> -k "<name>" -v`
   - Запусти регрессию: `.venv/Scripts/python -m pytest tests/ -v`
6. **Если тест падает:**
   - **Из-за текущих изменений** (новый тест или сломан существующий):
     - Прочитай ошибку
     - Исправь код (не тест, если тест корректен)
     - Повтори запуск
     - Максимум 3 итерации. Если не получается → п.6c
   - **По не связанной причине** (flaky, известный баг):
     - Проверь vault (`knowledge/debugging/`, реестр багов) — известная ли проблема?
     - Если известный flaky — продолжай, в коммите добавь: `(тест X flaky, см. BUG-NNN)`
   - **Не удаётся починить:**
     - `git stash -u` текущие изменения
     - Зафиксируй в `vault/inbox/` как новый BUG
     - Сообщи пользователю: что сломалось, почему, какие варианты
     - **Не коммить сломанное состояние**
7. **Коммит** — если шаг завершён и тесты зелёные (см. 2.3)
8. **Сообщи прогресс в чат:**
   ```
   Шаг N/M: <название> ✅
     Файлы: <список>
     Тесты: <passed>/<total> (baseline: <baseline>)
     Коммит: <hash> <message>
   ```

### 2.3. Стратегия коммитов

Каждый коммит — самодостаточный блок. Критерии:

- [ ] Тесты проходят (или failing тесты явно задокументированы)
- [ ] Изменения логически связаны (один шаг плана = один или несколько коммитов)

Формат сообщения: `<тип>: <краткое описание>`
- Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `vault`
- Vault-изменения — **отдельным коммитом** от кода
- Stage по имени файла, **не** `git add .` или `git add -A`
- **Не** упоминай Claude в коммитах (без Co-Authored-By)

Когда коммитить:
- После каждого завершённого шага плана (если шаг затрагивает код)
- После группы мелких связанных шагов (если каждый по отдельности не имеет смысла)
- При обновлении vault — отдельный коммит

### 2.4. Правила реализации

- **Минимальные изменения:** не рефактори попутно, не добавляй «улучшения» сверх плана
- **Формулы → код:** каждая вычислительная строка — из `moments_method.tex`
- **Docstrings:** одна строка + ссылка на уравнение, не больше
- **Типизация:** type hints для публичных функций
- **Import-ы:** в начале файла, сгруппированные (stdlib / third-party / local)
- **Тесты:** pytest-стиль, понятные имена `test_<что>_<при_каких_условиях>`
- **Не трогай** файлы, не упомянутые в плане

### 2.5. Обнаружение новых проблем

В ходе реализации могут всплыть неожиданные проблемы. Протокол:

1. **Не уходи в сторону.** Не начинай чинить найденную проблему, если она не в плане
2. **Зафиксируй** — добавь заметку в `vault/inbox/`:
   ```markdown
   ---
   tags: [inbox, обнаружено-при-реализации]
   date: <дата>
   source: <ID текущей задачи>
   ---
   # <суть проблемы>
   Обнаружено при реализации [[<план>]].
   <описание: что увидел, почему это проблема>
   ```
3. **Оцени блокирует ли** — мешает ли завершить текущий шаг?
   - Не блокирует → продолжай план
   - Блокирует → СТОП, сообщи пользователю, предложи варианты:
     a) Обходной путь в рамках плана
     b) Приостановить, создать `/issue` для блокера, вернуться после

### 2.6. Rollback-протокол

Если реализация зашла в тупик (тесты массово падают, блокирующая проблема):

1. **Не коммить сломанное состояние**
2. `git stash -u` — сохрани текущие изменения
3. Обнови frontmatter плана: `status: заблокирован`, добавь `blocker: <описание>`
4. Зафиксируй блокер в vault (`vault/inbox/` или реестр)
5. Коммит vault-изменений: `vault: <ID> заблокирован — <причина>`
6. Сообщи пользователю: что пошло не так, на каком шаге, какие варианты
7. Не используй `git checkout --` или `git reset` без явного разрешения пользователя

### 2.7. Возобновление после прерывания

Если сессия оборвалась (контекст потерян, пользователь вернулся позже):

1. Прочитай план — frontmatter покажет `status: в процессе`
2. `git log --oneline <базовая-ветка>..HEAD` — какие шаги уже реализованы
3. Сопоставь изменённые файлы с шагами плана — определи последний завершённый шаг
4. Проверь `git status` — есть ли незакоммиченные изменения (прерванный шаг)
5. Прогони тесты — убедись что текущее состояние зелёное
6. Продолжи со следующего шага

## Фаза 3: Верификация

### 3.1. Полный прогон тестов

```powershell
cd d:\Lessons\Grants\2026\GPN\Oil_Gas\<рабочий каталог>
.venv\Scripts\python -m pytest tests/ -q
```

Сравни с baseline:
- Количество тестов: было N, стало M (M ≥ N)
- Все pass: да/нет
- Время: не деградировало значительно

### 3.2. Чеклист критериев завершения

Проверь каждый пункт из секции «Критерии завершения» плана. Для каждого:
- ✅ выполнен — конкретное доказательство (номер теста, строка, файл)
- ❌ не выполнен — причина и план действий

### 3.3. Проверка по подводным камням

Пройди чеклист подводных камней из плана. Проверь каждый:
- Grep по изменённым функциям — все call sites обновлены?
- Граничные случаи покрыты тестами?
- Import-ы не создали циклов?

### 3.4. Обзор изменений

```powershell
git log --oneline <базовая-ветка>..HEAD
git diff --stat <базовая-ветка>..HEAD
```

Проверь:
- [ ] Нет случайных файлов (build-артефакты, __pycache__, .pytest_cache)
- [ ] Нет отладочного кода (print для отладки, временные хаки)
- [ ] Нет закомментированного старого кода

### 3.5. Визуальная верификация (если план предусматривает)

1. Запусти визуализацию (скрипт из плана)
2. Проверь: графики соответствуют ожиданиям (аналитика, предельные случаи)
3. Сохрани графики для отчёта

## Фаза 4: Финализация

### 4.1. Обновить vault

1. **Статус задачи:** в реестре (roadmap) → `✅ ГОТОВО` + дата
2. **Заметка результатов:** в `knowledge/validation/` или `knowledge/debugging/`
   - Что было, что стало, метрики
3. **План:** обнови `status: реализован` (Edit frontmatter)
4. **Index:** если создана новая заметка в `knowledge/` — обнови `vault/00-home/index.md`

### 4.2. Прокомментировать GitHub issue

Если у задачи есть GitHub issue — создай комментарий.
**Не закрывай issue** — issue закрывается при merge ветки в базовую.

1. Сохрани текст комментария в `vault/issues/<id-lowercase>/05-comment-done.md` (папка проекта, не scratchpad — запрет CLAUDE.md, раздел «Файлы и код»)
2. Формат:
```markdown
## Реализация завершена

**Ветка:** `<branch>`
**План:** `vault/plans/<файл>`
**Коммиты:** `git log --oneline <базовая-ветка>..HEAD`

### Изменения
- <файл 1>: <что изменено>
- <файл 2>: <что добавлено>

### Тесты
- Было: N тестов
- Стало: M тестов (+K новых)
- Все зелёные: ✅

### Метрики (если валидация)
| Метрика | Значение | Tolerance | Статус |
|---|---|---|---|
| ... | ... | ... | ✅/❌ |
```
3. Отправь:
```powershell
gh issue comment <N> --repo ArturSalamatin/Oil_Gas --body-file vault/issues/<id-lowercase>/05-comment-done.md
```

### 4.3. Обработать inbox

Если в ходе реализации были найдены новые проблемы (заметки в `vault/inbox/`):
1. Для каждой заметки: определи тип (BUG/DEBT/FEAT/VAL)
2. Добавь в соответствующий реестр с новым ID
3. Удали из inbox
4. Сообщи пользователю: «Обнаружено N новых проблем: <список>»
5. Предложи `/issue` для формализации на GitHub

### 4.4. Сообщить результат

Формат:
```
Реализация <ID> завершена.

Ветка: <branch>
Файлов изменено: N
Тестов: было M, стало K (+L новых)
Все тесты зелёные: ✅/❌

Новые проблемы: (если есть)
- <ID>: <краткое описание>

Следующие шаги:
- Проверь изменения: `git log --oneline <базовая-ветка>..HEAD`, `git diff --stat <базовая-ветка>..HEAD`
- Push: пользователь пушит сам
- Merge: `git checkout <базовая-ветка> && git merge --no-ff <branch>` (в ту же ветку, от которой ответвлялись)
```

## Примечания

- **Коммить по мере выполнения** — после каждого шага (см. 2.3)
- **Не пушь** — пользователь пушит сам
- **Не мержь** — предложи, но не делай
- Язык: русский
- Edit вместо Write для существующих файлов
- Читай файлы фрагментами (offset + limit)
- Не перечитывай файл после Edit
- Если план устарел — адаптируй шаги, но сообщи о расхождениях
- Если шаг сложнее ожидаемого — не молчи, сообщи
- PATH для gh: `$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User")`
