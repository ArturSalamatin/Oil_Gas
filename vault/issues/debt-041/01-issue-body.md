## Описание

В README примера 03 раздел «Сходимость Newton: $p_{wf}$ и $N$» приводит таблицу минимально достаточного `numerics.max_retries` при $N = 150$ (замер 2026-10-01). Для $p_{wf} = 0.5$ МПа в ней указано 9 удвоений, то есть 512 подшагов. На текущем решателе первый шаг при 0.5 МПа сходится на 16 подшагах, а это 4 удвоения.

Для счёта завышенный лимит безвреден: адаптер читает его только при отказе. Но README служит инструкцией пользователю примера, и сейчас он описывает решатель, которого уже нет.

Приоритет низкий.

**Замер.** Выполнен 2026-10-06 на `5ce2168` при планировании BUG-021 (`vault/issues/bug-021/probes/first_step.py`, вывод — `first_step.txt`). Первый шаг считается через адаптер с A-retry, как `_first_step` в `tests/test_prototype_globalization.py`; `max_retries` взят по умолчанию (9). Адаптер дробит шаг равномерно: попытка `attempt` даёт $2^{attempt}$ подшагов (`prototype_adapter.py:106-108`). Поэтому $n_{sub}$ из результата однозначно определяет минимальное число удвоений для первого шага.

| $p_{wf}$, МПа | подшагов (замер) | удвоений | README |
|---|---|---|---|
| 4.0 | 2 | 1 | 1 ✓ |
| 2.0 | 16 | 4 | 4 ✓ |
| 0.5 | 16 | **4** | **9** ✗ |

BUG-021 эти точки не меняет: столбцы «до → после» в `first_step.txt` совпадают.

**Чего замер не показывает.**
1. Он охватывает только первый шаг. Подпись таблицы обещает «минимально достаточный `max_retries`» для расчёта целиком. Это нужно подтвердить полным прогоном истории (72 интервала) с $k$ удвоениями, который должен пройти, и с $k-1$, который должен упасть.
2. Какое из изменений решателя после 2026-10-01 сдвинуло точку 0.5 МПа, не выяснялось. Кандидаты: BUG-018, DEBT-033, DEBT-036. Для README это не важно: он описывает текущий решатель.

## Анализ вариантов решения

**Вариант 1. Только README 03.**
- Суть: перемерить все 8 точек таблицы (первый шаг) и для ненулевых точек выполнить полный прогон с $k$ и $k-1$ удвоениями. Затем исправить строку таблицы, абзац под ней и дату замера.
- Плюсы: ровно объём записи в реестре.
- Минусы: в docstring теста и в комментарии `config.py` останутся утверждения «03 при 0.5 МПа — порог 9», «04a — 512 подшагов», «$N = 75$, $p_{wf} = 6$ — при 8 падает». Это та же величина, и она уже опровергнута замерами самого проекта.

**Вариант 2. README 03, docstring теста и комментарий `config.py` (рекомендуется).**
- Суть: вариант 1 плюс текстовая правка двух мест из таблицы выше. Комментарий к умолчанию сообщает, чем 9 обосновано сейчас: запасом над известными замерами (максимум 5 удвоений у примера 04 при 12 МПа, по таблице от 2026-10-01). Ссылку на сценарий, который больше не дробится, он не содержит.
- Плюсы: одно утверждение живёт в одном актуальном виде. Код и истории не меняются, нужен только прогон уровня «число тестов».
- Минусы: шире записи в реестре. Формулировку обоснования умолчания нужно согласовать.

**Вариант 3. Вариант 2 и перемер таблицы README 04.**
- Суть: в README 04 таблица `max_retries` по 10 точкам $p_{wf}$ имеет ту же дату замера (2026-10-01) и прошла через те же изменения решателя. Перемер первого шага стоит около 1 с на точку.
- Плюсы: закрывает класс устаревших таблиц, а не один экземпляр.
- Минусы: устарелость таблицы 04 не установлена. Если она подтвердится, это отдельная запись в реестре, а не расширение DEBT-041 без согласования.

Изменение самого умолчания `max_retries = 9` в задачу не входит. Если оно понадобится, нужна отдельная запись: значение защищено тестом `test_config.py`, и на него ссылаются README большинства примеров.

## План решения

1. **Подготовка.** Базовый уровень: число тестов (`pytest tests/ --collect-only -q`). Скрипт замера `vault/issues/debt-041/probes/` по образцу `first_step.py`, без подмены кода: первый шаг для 8 точек $p_{wf}$ при $N = 150$. Для 8 МПа добавляется $N$ = 50, 75, 100, 140, 200.
2. **Полный прогон.** Для каждой точки с ненулевым минимумом $k$ считается история целиком с `max_retries = k` (должна пройти) и `k − 1` (должна упасть на первом шаге или позже; шаг отказа записать). Если отказ при $k-1$ происходит не на первом шаге, это опровергает текст README «падает на первом же шаге» и меняет формулировку.
3. **Правка README 03.** Таблица, абзац под ней, дата и коммит замера.
4. **Вариант 2 (по решению).** Docstring `test_factory_standing_hydro.py:119-123` и комментарий `config.py:149-154`.
5. **Верификация.** Изменения только в документах и комментариях: прогон уровня «число тестов», количество тестов не меняется. Сквозная проверка: числа README 03 совпадают с выводом скрипта замера, сохранённым рядом.
