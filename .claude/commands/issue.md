# /issue — создать GitHub issue из записи в vault

Аргумент: `$ARGUMENTS` — идентификатор записи (например `BUG-001`, `FEAT-003`, `DEBT-002`) **или** свободный текст описания новой проблемы. Флаг `--dry` в начале аргументов включает dry-run режим.

## Определение режима

- Если `$ARGUMENTS` начинается с `--dry` — режим **dry-run**: выполнить все шаги анализа, показать что будет создано (title, labels, первые строки body, имя ветки), но НЕ создавать issue, НЕ менять vault. Оставшаяся часть аргументов — ID или свободный текст.
- Если аргумент (после `--dry`, если есть) соответствует паттерну `BUG-NNN`, `DEBT-NNN`, `FEAT-NNN` или `VAL-NNN` — режим **existing**: найти запись в vault и создать issue по ней.
- Иначе — режим **new**: создать запись в vault с новым ID и одновременно создать issue.

---

## Режим existing

### 1. Проверка дубликатов на GitHub

Перед любой работой проверь, нет ли уже issue для этого ID:

```
gh issue list --repo ArturSalamatin/Oil_Gas --search "<ID>" --state all
```

Если issue уже существует — сообщи пользователю URL и спроси, нужно ли обновить существующий issue или создать новый.

### 2. Найти запись в vault

1. Открой реестр по префиксу ID:
   - `BUG-` или `DEBT-` → `vault/roadmap/известные баги и технический долг.md`
   - `FEAT-` → `vault/roadmap/планируемые фичи.md`
   - `VAL-` → `vault/roadmap/валидационные кейсы.md`
2. Найди секцию с указанным ID (`$ARGUMENTS`)
3. Если запись не найдена — сообщи пользователю и выведи все доступные ID (grep по `### BUG-`, `### DEBT-`, `### FEAT-`, `### VAL-`)

### 3. Собрать контекст из vault

1. Из найденной записи извлеки поле **Подробности** или **План** — это wiki-ссылка `[[...]]` на заметку в vault
2. Прочитай эту заметку:
   - BUG → обычно `knowledge/debugging/`
   - DEBT → обычно `knowledge/decisions/`
   - FEAT → обычно `knowledge/science/` или `knowledge/decisions/`
   - VAL → обычно `knowledge/validation/`
3. Из заметки извлеки контекст по типу:
   - BUG: симптомы, причину, воспроизведение, связанные файлы
   - DEBT: текущее состояние, мотивация, затронутые модули
   - FEAT: физическое обоснование, уравнения из `moments_method.tex`, зависимости, фаза roadmap
   - VAL: эталонное решение, сценарий, метрики, tolerance
4. Если заметки нет — работай только по записи в реестре
5. Найди связанные BUG/DEBT/FEAT/VAL: если есть wiki-ссылки `[[...]]` на другие заметки, проверь — есть ли для них записи в реестрах. Если есть и для них создан GitHub issue (поле `**GitHub:**`) — запомни номера для раздела «Связанные issues»

### 4. Валидация упомянутых файлов (BUG/DEBT/FEAT)

Для типа VAL — пропустить шаги 4–6 (у них нет «проблемных файлов» и «вариантов решения»). Перейти к шагу 7.

Для каждого файла, упомянутого в vault-заметке:

1. Проверь, что файл существует (Glob/Read). Если файл переименован или удалён — отметь в issue: `⚠️ файл X не найден, возможно переименован`
2. Если указаны конкретные строки — проверь, что на этих строках находится ожидаемый код (grep по ключевым символам). Если строки сдвинулись — укажи актуальные номера строк в issue

### 5. Проанализировать код (BUG/DEBT/FEAT)

Для каждого **валидного** файла из шага 4:

1. Grep по ключевым символам (имена функций, переменных) — найди точные строки
2. Read фрагменты кода (offset + limit), чтобы понять контекст
3. Проследи цепочку вызовов: кто вызывает проблемную функцию, что происходит при ошибке
4. Найди связанные тесты: grep по именам функций в `method_of_moments/tests/`

### 6. Проработать варианты решения (BUG/DEBT/FEAT)

Для каждого варианта опиши:
- **Суть** — что именно менять / добавлять
- **Изменения** — конкретные файлы и строки
- **Плюсы/минусы** — trade-offs
- Рекомендуй комбинированный вариант, если применимо

### 7. Составить план решения

Этапы зависят от типа задачи:

**BUG:**
1. **Минимальный фикс** — чтобы тест перестал падать
2. **Архитектурное исправление** — правильное решение
3. **Верификация** — тесты, сценарии, сравнение с аналитикой

**DEBT:**
1. **Подготовка** — baseline (тесты, производительность, API)
2. **Реализация** — инкрементальные изменения
3. **Верификация** — все тесты зелёные, поведение не изменилось

**FEAT:**
1. **Проектирование** — API, структуры данных, формулы из `moments_method.tex`
2. **Реализация** — ядро → тесты → интеграция
3. **Верификация** — unit-тесты + проверка по формулам + граничные случаи

**VAL:**
1. **Эталон** — подготовить/импортировать эталонное решение
2. **Сценарий** — создать тест-кейс, задать параметры из `configs/`
3. **Сравнение** — прогнать, собрать метрики, визуализировать

### 8. Определить labels

Автоматическое определение labels по содержимому записи:

| Условие | Label |
|---|---|
| ID начинается с `BUG-` | `bug` |
| ID начинается с `DEBT-` | `enhancement` |
| ID начинается с `FEAT-` | `feature` |
| ID начинается с `VAL-` | `validation` |
| Статус содержит 🔴 | добавить `critical` |
| Статус содержит 🟡 (обход есть) | добавить `workaround` |
| Поле **Блокирует** непустое | добавить `blocking` |

### 9. Создать GitHub issue

**В dry-run режиме:** вывести preview (title, labels, имя ветки, первые 20 строк body) и остановиться. Не создавать issue, не менять vault.

Сформируй тело issue в формате markdown и сохрани во временный файл (scratchpad).

Структура issue зависит от типа задачи:

**BUG:**
```
## Описание
(что происходит, критичность)

## Симптомы
(наблюдаемое поведение)

## Корневая причина
(цепочка вызовов, что именно ломается)

## Воспроизведение
(pytest-тест, команда запуска)

## Затронутые файлы
(таблица: файл | строки | роль)
(⚠️ пометки для файлов, которые не прошли валидацию на шаге 4)

## Анализ вариантов решения
(для каждого варианта: суть, изменения, плюсы/минусы)

## План решения
(этапы: минимальный фикс → архитектура → верификация)

## Связанные issues
(Related: #N)

## Связанные заметки в vault
(ссылки на заметки)
```

**DEBT:**
```
## Описание
(что именно и почему нужно улучшить)

## Текущее состояние
(как работает сейчас, что плохо)

## Целевое состояние
(как должно работать после)

## Затронутые файлы
(таблица: файл | строки | роль)

## Анализ вариантов решения
(для каждого варианта: суть, изменения, плюсы/минусы)

## План решения
(этапы: baseline → инкрементальные изменения → верификация)

## Связанные issues
(Related: #N)

## Связанные заметки в vault
(ссылки на заметки)
```

**FEAT:**
```
## Описание
(что добавляется и зачем)

## Мотивация
(какую задачу решает, фаза roadmap)

## Физическое/математическое обоснование
(уравнения из moments_method.tex, \eqref{}, ссылки на литературу — если применимо)

## Предлагаемый API
(новые функции/классы, параметры, значения по умолчанию)

## Зависимости
(FEAT/BUG, которые должны быть сделаны раньше)

## Затронутые файлы
(таблица: файл | строки | роль — точки интеграции)

## План реализации
(этапы: проектирование → ядро → тесты → интеграция → верификация)

## Связанные issues
(Related: #N)

## Связанные заметки в vault
(ссылки на заметки)
```

**VAL:**
```
## Описание
(что верифицируем и зачем)

## Эталонное решение
(аналитика / конечные разности / OPM Flow — формулы, ссылки)

## Сценарий
(параметры из configs/, ГУ, время моделирования)

## Метрики сравнения
(что измеряем, tolerance)

## Зависимости
(BUG/DEBT/FEAT, которые блокируют)

## План валидации
(этапы: эталон → сценарий → прогон → сравнение → визуализация)

## Связанные issues
(Related: #N)

## Связанные заметки в vault
(ссылки на заметки)
```

Создай issue через `gh`:
```
gh issue create --repo ArturSalamatin/Oil_Gas \
  --title "<ID>: <краткое описание>" \
  --body-file <path-to-temp-file> \
  --label "<labels>" \
  --assignee "@me"
```

### 10. Добавить комментарий к issue

Сразу после создания issue добавь комментарий с краткой сводкой — фиксация контекста на момент открытия:

**BUG:**
```
### Контекст при открытии

- **Обнаружено:** <дата>
- **Ветка:** `<текущая ветка>`
- **Коммит:** `<короткий SHA>`
- **Корневая причина:** <одно предложение>
- **Рекомендуемый вариант:** <номер варианта из анализа>
- **Оценка сложности:** <простой / средний / сложный>
```

**DEBT:**
```
### Контекст при открытии

- **Ветка:** `<текущая ветка>`
- **Коммит:** `<короткий SHA>`
- **Мотивация:** <одно предложение>
- **Затронутые модули:** <список>
- **Оценка сложности:** <простой / средний / сложный>
```

**FEAT:**
```
### Контекст при открытии

- **Ветка:** `<текущая ветка>`
- **Коммит:** `<короткий SHA>`
- **Фаза roadmap:** FEAT-NNN (+ зависимости)
- **Формулы:** <список \eqref{} из moments_method.tex>
- **Модуль:** `src/<module>.py`
- **Оценка сложности:** <простой / средний / сложный>
```

**VAL:**
```
### Контекст при открытии

- **Ветка:** `<текущая ветка>`
- **Коммит:** `<короткий SHA>`
- **Эталон:** <тип: аналитика / численный / OPM Flow>
- **Tolerance:** <значение>
- **Блокирующие зависимости:** <список ID или "нет">
```

Сохрани текст комментария во временный файл (scratchpad) и добавь через:
```
gh issue comment <номер> --repo ArturSalamatin/Oil_Gas --body-file <path-to-comment-file>
```

### 11. Обратная связь в vault

После успешного создания issue:

1. Добавь поле `- **GitHub:** [#<номер>](https://github.com/ArturSalamatin/Oil_Gas/issues/<номер>)` к секции в реестре:
   - BUG/DEBT → `известные баги и технический долг.md`
   - FEAT → `планируемые фичи.md`
   - VAL → `валидационные кейсы.md`
2. Если есть подробная заметка в `knowledge/` — добавь в неё строку `**GitHub issue:** [#<номер>](https://github.com/ArturSalamatin/Oil_Gas/issues/<номер>)`

### 12. Предложить ветку

После создания issue предложи пользователю создать рабочую ветку:

```
Создать ветку fix/bug-001/краткий-slug для работы над этим issue?
```

Формат имени ветки: `<prefix>/<id-lowercase>/<slug>`
- `BUG-*` → prefix `fix` (например `fix/bug-001/pvt-negative-viscosity`)
- `DEBT-*` → prefix `refactor` (например `refactor/debt-001/split-pvt-module`)
- `FEAT-*` → prefix `feat` (например `feat/feat-001/standing-pvt`)
- `VAL-*` → prefix `val` (например `val/val-001/dupuit-steady-state`)

Правила для slug:
- 2–5 слов через дефис, латиница, lowercase
- Отражает суть проблемы, не ID
- Без артиклей и предлогов

**Не создавай ветку** — это делает `/implement`. Здесь только фиксируешь имя.

После подтверждения пользователем — добавь поле `- **Ветка:** <имя ветки>` к секции в соответствующем реестре (рядом с **GitHub:**). Это позволит `/plan-*` и `/implement` найти ветку без обращения к GitHub.

### 13. Сообщить результат

Выведи:
- URL созданного issue
- Присвоенные labels
- Краткую сводку по типу:
  - BUG: корневая причина, рекомендуемый вариант решения, количество этапов
  - DEBT: текущее состояние, целевое, количество этапов
  - FEAT: суть фичи, формулы, модуль, количество этапов
  - VAL: эталон, метрики, tolerance

## Режим new (свободный текст)

Когда `$ARGUMENTS` — не ID, а описание проблемы (например: `/issue PVT-корреляция даёт отрицательную вязкость при p > 30 МПа`).

### 1. Определить тип и ID

1. Спроси пользователя: это баг (`BUG`), технический долг (`DEBT`), новая фича (`FEAT`) или валидация (`VAL`)?
2. Найди максимальный номер в соответствующем реестре:
   - BUG/DEBT → grep `### BUG-` и `### DEBT-` в `известные баги и технический долг.md`
   - FEAT → grep `### FEAT-` в `планируемые фичи.md`
   - VAL → grep `### VAL-` в `валидационные кейсы.md`
3. Присвой следующий свободный ID

### 2. Собрать информацию

Задай пользователю уточняющие вопросы (через AskUserQuestion, одним блоком). Вопросы зависят от типа:

**BUG:**
- Симптомы: что наблюдается?
- Воспроизведение: как вызвать?
- Связанные файлы: какие модули затронуты?

**DEBT:**
- Что именно плохо в текущем состоянии?
- Какие модули затронуты?
- Есть ли обходные пути или workaround-ы?

**FEAT:**
- Какую задачу решает?
- Какие уравнения из `moments_method.tex` реализует?
- Есть ли зависимости от других FEAT/BUG?
- Есть ли аналитическое решение для верификации?

**VAL:**
- С чем сравниваем (аналитика, конечные разности, OPM Flow)?
- Какой сценарий (параметры, ГУ)?
- Какие метрики и допустимая ошибка?

Если пользователь уже дал достаточно информации в тексте — не спрашивай повторно.

### 3. Проанализировать код (BUG/DEBT/FEAT)

Для типа VAL — пропустить (аналогично шагам 4–6 режима existing).

Для BUG/DEBT/FEAT: аналогично шагу 5 режима existing — grep по упомянутым функциям и файлам в `method_of_moments/src/`, прочитать контекст.

### 4. Создать запись в vault

1. Добавь секцию в соответствующий реестр (по формату существующих записей):
   - BUG/DEBT → `известные баги и технический долг.md`
   - FEAT → `планируемые фичи.md`
   - VAL → `валидационные кейсы.md`
2. Если задача сложная — создай подробную заметку и добавь wiki-ссылку:
   - BUG → `knowledge/debugging/`
   - DEBT → `knowledge/decisions/`
   - FEAT → `knowledge/science/` или `knowledge/decisions/`
   - VAL → `knowledge/validation/`
3. Обнови `vault/00-home/index.md` если создана новая заметка

### 5. Создать GitHub issue

Аналогично шагам 7–13 режима existing (для BUG/DEBT/FEAT дополнительно шаг 6).

## Примечания

- Если `gh` не авторизован — предложи `gh auth login --web`
- Не используй спецсимволы PowerShell в теле issue — пиши в файл, передавай через `--body-file`
- Язык issue и vault-записей: русский
- Не создавай коммитов — только issue, комментарий и vault-записи. Пользователь коммитит сам
- Тело issue и комментария сохраняй в scratchpad-директорию, не в проект
- PATH для gh может потребовать обновления: `$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User")`

## Следующий шаг: план

После завершения всех шагов (включая сообщение результата) — предложи пользователю создать план.

Определи команду по типу ID:
- `BUG-*` → `/plan-fix`
- `DEBT-*` → `/plan-improve`
- `FEAT-*` → `/plan-feature`
- `VAL-*` → `/plan-validate`

Спроси пользователя:
> Запустить `<команда> <ID>`?

Если пользователь подтвердит — вызови Skill tool с соответствующим именем и передай ID как аргумент.
