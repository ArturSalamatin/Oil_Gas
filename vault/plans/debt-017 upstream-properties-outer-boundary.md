## 1. Суть задачи

### Что не так

На контурной грани ($f = N$) уравнение энергии выбирает ячейку выше по потоку **без разбора знака потока**. `energy/tridiag.py:189-196`:

```python
# Контур (f=N): upstream = ячейка N-1 (приближение).
Phi_o[N] = rho_o[N - 1] * c_p_o[N - 1] * Q_o[N]
Phi_g[N] = rho_g[N - 1] * c_p_g[N - 1] * Q_g[N]
```

и `energy/tridiag.py:269-273`:

```python
J_face[N] = (mu_JT_o[-1] * Phi_o[N] * p[-1]
             + mu_JT_g[-1] * Phi_g[N] * p[-1])
```

При **притоке** с контура ($\mathcal{Q}_\alpha[N] < 0$ — штатный режим добычи) выше по потоку физически находится контур, и свойства должны вычисляться при условиях ГУ, а не при $p_{N-1}$, $T_{N-1}$.

### Почему это долг, а не просто неточность

Задача — прежде всего про **единообразие**. В том же файле `compute_degassing` (стр. 315-326) обрабатывает ту же грань **строго**:

```python
if G_o[N] >= 0:
    R_conv[N] = G_o[N] * Rs[N - 1]      # отток: upstream — ячейка N-1
else:
    R_conv[N] = G_o[N] * Rs_ext         # приток: состав задан ГУ
```

Два разных уровня строгости для одной грани в одном файле. **Эталон — `compute_degassing`** (решение пользователя, 2026-09-19).

### Главный аргумент: Φ собран из двух разных состояний

Гидродинамика на той же грани при том же знаке потока берёт контурные значения. `fluxes.py:124-145`:

| Величина | `fluxes.py` при притоке | `energy/tridiag.py` при притоке |
|---|---|---|
| $\rho_o$ | `rho_o_ext = pvt.rho_o(p_ext, Rs_ext)` (стр. 51, 143) | `rho_o[N-1]` ❌ |
| $\rho_g$ | `0.0` — газовой фазы на контуре нет (стр. 145) | `rho_g[N-1]` ❌ |
| подвижность | `mob_o_ext`, `lam_o_ext` при $S_g = 0$ | — |

Следствие: $\mathcal{Q}_\alpha[N]$ **уже посчитан** по свойствам контура, а в энергии домножается на $\rho_\alpha c_{p,\alpha}$ из ячейки $N-1$. Величина $\Phi_\alpha = \rho_\alpha c_{p,\alpha} \mathcal{Q}_\alpha$ оказывается собрана из двух разных термодинамических состояний — это не «приближение», а рассогласование.

### ✅ Правило уже принято как проектное решение — код ему не соответствует (найдено аудитом, раунд 1)

Аудит обнаружил заметку, которую план не учитывал: **`vault/knowledge/decisions/P1-адаптер-единицы.md`, раздел «3a. Upstream на контуре — не ячейка N-1»** (стр. 430-440). Заголовок раздела дословно формулирует тезис DEBT-017. Содержание:

> «При типичном притоке ($p_{ext} > p_{N-1}$) жидкость течёт **из контура в пласт**. Upstream = контур: свойства ($B_o$, $B_g$, **ρ**) берутся при `p_ext`, `Rs_ext`, `Sg=0`.
> В исходной версии заметки было написано "upstream = ячейка N-1" — **неверно**.»

Это меняет статус задачи: план **не вводит новое правило**, а приводит `energy/tridiag.py` в соответствие с решением, принятым и задокументированным ещё на этапе P1. Более того, та же заметка завершается утверждением:

> «Все модули (Adapter, **EnergySolver**) получают один объект HydroPVT → $B_o$, $B_g$, ρ согласованы везде.»

Согласованность EnergySolver была **заявлена как достигнутая**, но фактически не выполнена — именно это и есть содержание DEBT-017.

**Четвёртый независимый источник — прототип коллеги.** `HydroSolverPrototype/Prototype_1.0.3/radial_blackoil/blackoil.py:122` (сверено дословно):

```python
dpo = p[-1] - self.p_outer_bar
p_up, rs_up, sg_up = (p[-1], rs[-1], sg[-1]) if dpo >= 0 else (self.p_outer_bar, self.outer_rs, 0.0)
```

⚠️ **Прототип обнуляет `sg_up = 0.0` при притоке** — то есть решает вопрос Р-1 через **газонасыщенность**, а не через $\rho_g$. См. уточнение Р-1 ниже.

**Итого источников целевого поведения: 5** — постановка (принцип), `fluxes.py`, `prototype_adapter.py`, решение P1, прототип. Все согласны между собой; расходится только `energy/tridiag.py`.

### Требования постановки

`numerical_solver/doc/problem_statement.tex`:
- **строки 1461-1473** — общий принцип: «На граничной грани в операторе против потока значения за границей заменяются граничными условиями»; далее перечислены $p_{\text{конт}} = \ppl$ и $R_s = R_s^0$;
- **строки 1480-1485** (`ssec:bc_disc`, подпараграф «Температура»): на $r = \Rext$ против потока берётся $T = \Tpl$;
- **строки 1436-1437, 1450-1455** (`eq:bc_flux_ext`): на контуре $S_g\big|_{\Rext} = 0$, $k_{rg} = 0$, подвижность из условий ГУ.

То есть принцип применён к $T$, $p$, $R_s$ и к подвижностям, но **не** к $\rho_\alpha$, $c_{p,\alpha}$, $\mu_{\mathrm{JT},\alpha}$. Явной формулы для $\Phi_\alpha$ на контурной грани постановка не даёт — см. шаг 2.

## 3. Целевое состояние

`compute_convective_coefficients` и `compute_jt` разбирают знак $\mathcal{Q}_\alpha[N]$:

- $\mathcal{Q}_\alpha[N] \geqslant 0$ (отток наружу) — свойства из ячейки $N-1$, как сейчас;
- $\mathcal{Q}_\alpha[N] < 0$ (приток с контура) — свойства при условиях ГУ:
  - $\rho_o(p_{ext}, R_s^{ext})$, $c_{p,o}(p_{ext}, T_{ext})$, $\mu_{\mathrm{JT},o}(p_{ext}, T_{ext})$;
  - **газовая ветка обнуляется**: на контуре $S_g\big|_{\Rext} = 0$, свободного газа нет (решение Р-1, см. ниже);
  - в `compute_jt` давление в операторе против потока — $p_{ext}$, а не $p[N-1]$.

Оба метода берут контурные значения из **одного** приватного метода `_ext_properties(bc)`.

### Инфраструктура готова — контракты не трогаем

`BoundaryConditions` (`state.py:96-106`) уже несёт всё нужное:

```python
well: WellControl
p_ext: float            # давление на контуре, Па
T_ext: float            # температура на контуре, К
Rs_ext: float           # газосодержание притока, м³ст/м³ст
Sg_ext: float = 0.0     # газонасыщенность на контуре (обычно 0)
```

`bc` приходит в `solve` целиком (контракт ABC `energy/base.py:26-30`, расширен в рамках DEBT-009). **ABC менять не нужно** — в отличие от DEBT-009, где этого не хватало.

### Решение Р-1: чем считать газовую ветку при притоке

Два гидро-пути делают это **по-разному** — обнаружено при составлении плана:

| Файл | При притоке | $\rho_g$ |
|---|---|---|
| `fluxes.py:145` | `rho_g_up_e = 0.0` | ноль, «нет газовой фазы на контуре» |
| `hydro/prototype_adapter.py:212` | `rho_g_up_N = pvt.rho_g(p_ext)` | плотность при контурном давлении |

Формально расхождения в результате нет: при $S_g\big|_{ext} = 0$ и $k_{rg} = 0$ имеем $\mathcal{Q}_g[N] = 0$, поэтому $\Phi_g[N] = \rho_g \cdot c_{p,g} \cdot 0 = 0$ при любом $\rho_g$. Но брать значение «наугад» нельзя — оно станет видимым, если появится конфиг с $S_{g,ext} > 0$.

**Принятое решение:** считать $\rho_g^{ext} = \rho_g(p_{ext})$ и $c_{p,g}^{ext} = c_{p,g}(p_{ext}, T_{ext})$ по формуле (как адаптер), **не** подставляя ноль руками. Обоснование: физически корректно при любом $S_{g,ext}$; обнуление получается само через $\mathcal{Q}_g[N] = 0$; не придётся переделывать при появлении $S_{g,ext} > 0$. Плюс это единственный вариант, симметричный `compute_degassing`, где никакого «руками ноль» нет.

✅ **Проверено аудитом (раунд 1): $S_g$ в `_ext_properties` не нужен вовсе.** Прототип (`blackoil.py:122`) обнуляет `sg_up = 0.0` при притоке, и это выглядит как третий вариант решения Р-1. Но сверка ABC `FullPVT` (`pvt/base.py:60-107`) показывает: **ни одна** тепловая PVT-величина не зависит от $S_g$ —

| Величина | Аргументы |
|---|---|
| `rho_o` | $(p, R_s)$ |
| `rho_g` | $(p)$ |
| `c_p_oil`, `c_p_gas` | $(p, T)$ |
| `mu_JT_oil`, `mu_JT_gas` | $(p, T)$ |

Насыщенность входит в поток **не** через свойства, а через $k_{rg}$ внутри $\mathcal{Q}_g$, который энергия получает готовым из `hydro_result`. Поэтому `sg_up` прототипа относится к вычислению подвижностей (`_phase_mobilities_surface`), а не к $\Phi$. Передавать `bc.Sg_ext` в `_ext_properties` не требуется; вариант Р-1 остаётся в силе без изменений.

⚠️ Расхождение `fluxes.py` ↔ `prototype_adapter.py` **само по себе** — отдельная находка (раздел 9, П-7), в этой задаче не чиним.

## 4. Варианты решения

### Вариант 1. Ветвление прямо в двух методах

**Суть.** Передать `bc` в `compute_convective_coefficients` и `compute_jt`, в каждом вычислить контурные PVT и выбрать ветку.

**Изменения.** Две сигнатуры + два вызова в `solve` + ветвления; ~25 строк.

**Плюсы.** Прямолинейно.
**Минусы.** Контурные PVT считаются дважды за шаг; **два места, делающие одно и то же** — ровно тот дефект, который задача устраняет. Через полгода они разойдутся.

### Вариант 2. Прокинуть контурные свойства через `HydroResult`

**Суть.** `fluxes.py` уже посчитал `rho_o_ext`; добавить контурные свойства в `HydroResult`.

**Изменения.** `state.py`, `fluxes.py`, `hydro/prototype_adapter.py`, `energy/tridiag.py` + их тесты.

**Плюсы.** Единственный источник истины для $\rho_\alpha^{ext}$.
**Минусы.** Энергии нужны ещё $c_{p,\alpha}$ и $\mu_{\mathrm{JT},\alpha}$, которых гидродинамика не считает — единство источника получится **неполным** (часть из `HydroResult`, часть из PVT на месте). Расширяет контракт, затрагивает адаптер прототипа и его тесты. Цена высокая, выгода частичная.

### Вариант 3 (выбран). Приватный `_ext_properties(bc)`

**Суть.** Вариант 1, но контурные свойства считаются **одним** приватным методом, возвращающим словарь; оба публичных метода берут значения оттуда.

```python
def _ext_properties(self, bc):
    """Свойства флюида при условиях контура — upstream при притоке.

    Возвращает dict: rho_o, rho_g, c_p_o, c_p_g, mu_JT_o, mu_JT_g, p.
    ГУ: p_ext, T_ext, Rs_ext (state.py:96-106, eq. bc_Sg_ext).
    """
```

**Плюсы.**
- одна точка истины внутри модуля энергии — `compute_jt` и `compute_convective_coefficients` не могут разойтись;
- PVT на контуре — один вызов на шаг;
- контракты `HydroResult` и ABC не трогаются;
- симметрия с `compute_degassing`, которая берёт `Rs_ext` одним значением.

**Минусы.** +1 метод в классе.

### Критерии выбора (для DEBT)

| Критерий | В1 | В2 | В3 |
|---|---|---|---|
| Минимальность diff | ✅ | ❌ | ✅ |

    def _ext_properties(self, bc):
        """Свойства флюида при условиях контура — против потока при притоке.

        На контуре задано: p = p_ext, T = T_ext, Rs = Rs_ext, Sg = 0

        грань N выше по потоку находится контур, поэтому ρ, c_p и μ_JT

        PVT принимает массивы — скаляры оборачиваем, как в fluxes.py:47-52.

        T_a = np.array([bc.T_ext])
        Rs_a = np.array([bc.Rs_ext])
        return dict(
            p=bc.p_ext,
            rho_o=self._pvt.rho_o(p_a, Rs_a)[0],
            rho_g=self._pvt.rho_g(p_a)[0],

            mu_JT_o=self._pvt.mu_JT_oil(p_a, T_a)[0],

### Шаг 5: Перевести `compute_jt` и обновить эталон DEBT-016

| `08_degassing_jt` | — | **1.19e-4** | **5.47e-3** |

**Это ключевое отличие от DEBT-009.** Там дефект был невидим на штатных примерах ($|R_{s,N-1} - R_s^0| \le 7\cdot10^{-15}$), потому что расхождение возникало только при разгазировании у контура. **Порядок работ (решить с пользователем до шага 3):**
