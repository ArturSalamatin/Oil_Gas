## Описание

Три тепловых скаляра конфига — теплота дегазации `thermal.L_degas` ($L$), коэффициенты Джоуля–Томсона `thermal.mu_JT_oil` ($\mu_{JT,o}$) и `thermal.mu_JT_gas` ($\mu_{JT,g}$) — не проверяются на конечность. Литерал JSON `NaN` в любом из них проходит `load_config` и `from_config`, а `run` падает в `scipy.linalg.solve_banded` с сообщением `ValueError: array must not contain infs or NaNs` — без имени параметра. Пользователь ищет причину в схеме энергии, а не в конфиге.

Молча неверного расчёта нет: `check_finite` scipy ловит NaN в правой части СЛАУ энергии. Страдает только сообщение. Приоритет низкий.

## Текущее состояние

После DEBT-047 (#76) `_validate` проверяет на конечность шесть тепловых параметров: $c_{p,o}$, $c_{p,g}$, $(\rho c_p)_s$ (условие `0 < v < inf`) и $\lambda_s$, $\lambda_o$, $\lambda_g$ (`0 <= v < inf`). Для трёх оставшихся:

| Параметр | Проверка сейчас | Замер с NaN |
|---|---|---|
| `thermal.L_degas` | только знак: $L < 0$ — предупреждение (`config.py:381`) | `run`: отказ scipy |
| `thermal.mu_JT_oil` | нет | `run`: отказ scipy |
| `thermal.mu_JT_gas` | нет | не запускалось; по коду тот же путь (`energy/tridiag.py:216`) |

Замер: проба `vault/issues/debt-047/probes/red_state.py`, случаи `L_degas_nan`, `mu_JT_oil_nan`; вывод до и после DEBT-047 — `red_state.out.txt`, `green_state.out.txt` (строки 18–19 и 36–37): `run: ValueError: array must not contain infs or NaNs [_function_base_impl.py:684]` при $p_{wf}$ = 10 и 6 МПа. Значение `Infinity` по коду идёт тем же путём, не запускалось.

Знак у $\mu_{JT}$ по физике любой (жидкость при дросселировании греется, газ охлаждается), у $L$ — тоже (P8 §5), поэтому проверка возможна только на конечность.

Путь параметров: `load_config` → `_validate` (`config.py:330`) → `from_config` → конструктор PVT (`factory.py:111-113` — Стендинг, `factory.py:150-152` — табличная) → `pvt.mu_JT_oil/mu_JT_gas/L_degas` → `energy/tridiag.py:215-217, 261-262`. Обе модели PVT берут значения из одной секции `thermal`, значит одна проверка в `_validate` закрывает обе.

## Целевое состояние

- В `_validate` — проверка конечности $L$, $\mu_{JT,o}$, $\mu_{JT,g}$: `not (-inf < v < inf)` → `ValueError` с полным именем параметра (`thermal.L_degas` и т. д.), как у шести параметров DEBT-047. Знак не ограничивается.
- Проверка конечности $L$ — **до** предупреждения о $L < 0$: иначе при $L = -\infty$ в журнал попадёт предупреждение о знаке, а следом отказ.
- P8 §5 перечисляет девять тепловых параметров, отвергающих `NaN` и `Infinity`.

## Анализ вариантов решения

### Вариант 1. Проверка трёх скаляров в `_validate` (рекомендуется)

- **Суть.** Цикл по трём параметрам с условием `-inf < v < inf` после цикла по λ, перед предупреждением о $L < 0$.
- **Изменения.** `config.py` — около 5 строк и комментарий; `test_config.py` — случаи в `TestValidationThermal`: NaN, `+inf`, `-inf` для каждого параметра, плюс проверка, что конечные значения любого знака принимаются (в частности $\mu_{JT,o} > 0$, $\mu_{JT,g} < 0$); P8 §5.
- **Плюсы.** Минимальная правка в стиле DEBT-047; закрывает все три параметра и обе модели PVT.
- **Минусы.** Остальные числовые поля конфига по-прежнему пропускают NaN (см. вариант 2).

### Вариант 2. Конечность всех числовых полей конфига

- **Суть.** Общая проверка: обход полей dataclass-секций, для каждого числа — конечность, имя `<секция>.<поле>` в сообщении.
- **Наблюдение при анализе.** Большинство существующих проверок имеет вид `if v <= 0: raise` — NaN их проходит, сравнение с NaN всегда ложно. По коду (не запускалось) `_validate` пропускает NaN в `geometry.r_well`, `geometry.h`, `rock.porosity`, `rock.permeability`, `initial_conditions.p0`, `T0`, `Rs0`, `time.dt_integration`, `pvt.rho_o_std`, `pvt.co_undersaturated` и др. Чем это кончается дальше — у прототипа или в энергии — не проверялось.
- **Изменения.** `config.py` — новая функция обхода; поля `Optional` (`p_wf`, `q_oil`, `min_bhp`, имена файлов) и строковые пропускать; интервалы истории проверяются в `_expand_history` с номером блока JSON — общий обход этот номер потеряет.
- **Плюсы.** Закрывает класс ошибок целиком.
- **Минусы.** Шире задачи. P8 §5 отдаёт проверку гидродинамических данных прототипу — решение о переносе части её в `_validate` нужно принять отдельно. Больше тестов и правок сообщений.

### Вариант 3. Запрет литералов `NaN`/`Infinity` при разборе JSON

- **Суть.** `json.load(f, parse_constant=...)` с отказом на `NaN`, `Infinity`, `-Infinity` (`config.py:279`).
- **Плюсы.** Одна строка, все поля сразу.
- **Минусы.** `parse_constant` получает только сам литерал — имени параметра в сообщении не будет, а ради имени задача и заведена. Переполнение `1e999` модуль `json` превращает в `inf` через `float()` и `parse_constant` не вызывает — нужен ещё `parse_float`.

**Рекомендация:** вариант 1. Вопрос о варианте 2 — решить при планировании: либо в рамках этой задачи, либо отдельной записью DEBT.

## План решения

1. **Исходный замер.** Число тестов (`--collect-only -q`) и быстрый уровень (`-m "not slow"`). Красный замер: проба по образцу `vault/issues/debt-047/probes/red_state.py` — NaN, `+inf`, `-inf` в каждом из трёх параметров; достаточно одной модели PVT — путь через `_validate` общий; ожидание — отказ scipy без имени параметра.
2. **Реализация.** Сначала тесты в `TestValidationThermal` (красные), затем проверка в `_validate` с комментарием (почему только конечность, почему до предупреждения о $L < 0$), затем P8 §5.
3. **Верификация.** Новые тесты зелёные; `test_negative_L_warns`, `test_nonnegative_L_no_warning` — без изменений; быстрый уровень — прежнее число прошедших плюс новые; все конфиги `examples/` загружаются (фикстура `results` в `test_examples.py`, полный уровень в конце); зелёный замер пробы — `load_config: ValueError: thermal.<параметр> …` во всех случаях.
