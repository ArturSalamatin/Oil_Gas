# FEAT-013: Папка examples — сценарии использования и единый запуск

## Цель

Создать папку `numerical_solver/examples/` со структурированными сценариями
использования солвера. Каждый сценарий — отдельная подпапка с полным pipeline:
JSON-конфиг → Factory → Simulator.run() → графики (.png) + таблицы (.csv).

Единый `run_all.py` запускает все сценарии последовательно.
Каждый сценарий запускается индивидуально.

**Главная задача examples** — показать пользователю все допустимые комбинации
конкретных модулей (реализаций) библиотеки. Пользователь берёт ближайший
к своей задаче пример и модифицирует конфиг.

### 1.2 PVT: тепловая часть (скаляры)

Тепловая часть PVT — одинакова у `StandingFullPVT` и `TableFullPVT`:
скалярные константы из секции `thermal` JSON-конфига.
Каждый эффект включается/выключается числом.

| Коэффициент | JSON | = 0 означает |
|-------------|------|-------------|
| $\mu_{JT,o}$ | `thermal.mu_JT_oil` | нет JT нефти |
| $\mu_{JT,g}$ | `thermal.mu_JT_gas` | нет JT газа |
| $L$ | `thermal.L_degas` | нет теплоты дегазации |

$c_{p,o}$, $c_{p,g}$ — всегда > 0 (знаменатель).

### Выбор $p_{wf}$ (проверено численными прогонами при аудите)

Давление насыщения зависит от PVT-модели и $R_{s,0}$:

| PVT | $R_{s,0}$ | $p_b$ | Источник |
|-----|-----------|-------|----------|
| Standing | 0 | $-0.18$ МПа | корреляция: газа нет, однофазность при любом $p > 0$ |
| Standing | 50 | 9.43 МПа | корреляция Standing |
| Table | 30 | 15.0 МПа | первая строка ветки $R_s{=}30$ в `oil_pvt.csv` |

Отсюда $p_{wf} = 8$ МПа для всех двухфазных сценариев:
- Standing $R_s{=}50$: $p_{wf} = 8 < p_b = 9.43$ → разгазирование, $S_g^{max} = 0.080$
- Table $R_s{=}30$: $p_{wf} = 8 < p_b = 15$ → разгазирование, $S_g^{max} = 0.017$

⚠️ **При $p_{wf} = 15$ МПа разгазирования не происходит ни в одном варианте**
(проверено: $S_g \equiv 0$, $R_s \equiv$ const). Исходная версия плана задавала
15 МПа для сценариев 03–09 — это делало их физически однофазными вопреки замыслу.

**Устойчивость Newton** (диагностика при аудите, см. §11b): при $\Delta t = 3600$ с
Standing $R_s{=}50$ расходится нерегулярно (9.3, 9.0, 7.5, 6.5, 6.0 МПа — отказ;
8.5, 8.0, 7.0 — успех). Table устойчив на всём диапазоне 14…3 МПа.

Причина — не в PVT-модели, а в крутизне фронта разгазирования при большом шаге.
При $\Delta t \leq 600$ с Standing сходится везде, включая 6 МПа.

Поэтому: сценарии 03, 05 (Standing, $p_{wf} = 8$ МПа) работают при $\Delta t = 3600$ с;
сценарий 10 ($p_{wf} = 6$ МПа) — на Table PVT, где $\Delta t = 3600$ с безопасен.

## 5. Описание семейств

### Семейство 1: однофазные

**01 — Однофазная без JT.** $R_s = 0$, все тепловые скаляры = 0.
Нефть несжимаема ($B_o = 1.0505$ = const, $\mu_o = 2.48$ мПа·с = const,
$p_b = -0.18$ МПа < 0 → газ не выделяется при любом $p > 0$).

Фактическое поведение (проверено прогоном при аудите):
- $S_g \equiv 0$, $R_s \equiv 0$, $q_g \equiv 0$ — строго однофазный режим.
- Давление выходит на стационар **за один шаг** (несжимаемая жидкость —
  мгновенный стационар): $p(r_w) = 15.05$ МПа со 2-го шага, $dp/dt = 0$ далее.
- $T(r_w)$: провал до 349.43 К на первом шаге (адиабатический эффект от
  скачка $dp/dt = -1375$ Па/с), затем медленное восстановление
  теплопроводностью — за 3 суток только до 349.71 К, **не до $T_0$**.
- $q_o = 1.94 \times 10^{-3}$ м³ст/с = const.

**02 — Однофазная + JT.** Добавлен $\mu_{JT,o} = 4 \times 10^{-7}$ К/Па.
Гидродинамика идентична 01. Появляется стационарный JT-источник:
оценка $\Delta T(r_w) \sim \mu_{JT,o} \cdot (p_0 - p_{wf}) = 2$ К охлаждения
поверх адиабатического провала из сценария 01.

### Семейство 2: комбинации модулей

Все четыре сценария (03–06) — разгазирование с полной термикой при $p_{wf} = 8$ МПа.
Пользователь видит, как задать каждую комбинацию PVT × ОФП в конфиге.
Все четыре проверены численно при аудите — работают, дают $S_g > 0$.

**03 — Standing + Corey.** Вся физика из параметров JSON, никаких CSV.
$R_s = 50$, $p_b = 9.43$ МПа. Результат: $S_g^{max} = 0.080$, $R_s^{min} = 42$,
$T^{min} = 346.2$ К.

**04 — Table + Table.** Полный набор CSV. Лабораторные данные.
$R_s = 30$, $p_b = 15$ МПа. Результат: $S_g^{max} = 0.017$, $R_s^{min} = 9.5$,
$T^{min} = 346.9$ К.

**05 — Standing + Table ОФП.** Корреляции PVT, но лабораторные ОФП (relperm.csv).
Типичная ситуация: PVT по корреляциям, ОФП из керновых экспериментов.
Результат: $S_g^{max} = 0.014$, $R_s^{min} = 42$, $T^{min} = 346.2$ К.

**06 — Table PVT + Corey ОФП.** Табличные PVT из лаборатории,
ОФП неизвестны — используется аналитическая модель Кори.
Результат: $S_g^{max} = 0.081$, $R_s^{min} = 9.5$, $T^{min} = 344.4$ К.

### Чувствительность: что именно меняется при смене модуля

Прогон всех 10 сценариев при аудите (раунд 4) дал систематическую картину.
Числа обязательны в README — иначе пользователь не поймёт, на какой график смотреть.

| Что меняем | Пара | $S_g^{max}$ | $T(r_w)$ | $q_o$ | $r_b$ |
|---|---|---|---|---|---|
| **ОФП** (Corey ↔ Table) | 03↔05 | **−83 %** | 0.001 К | 0.4 % | без изменений |
| **ОФП** (Table ↔ Corey) | 04↔06 | **+80 %** | 0.002 К | 1.9 % | без изменений |
| **PVT** (Standing ↔ Table) | 03↔04 | −79 % | **0.65 К** | **46 %** | **0.20 → 2.39 м** |
| **Термика** ($\mu_{JT}$) | 07↔08 | 0 % | **4.21 К** | 0 % | без изменений |

Три чётких вывода для README:

1. **Смена ОФП видна только на $S_g(r)$.** Профили $T$ и дебиты практически
   не меняются. Причина (проверено): разные ОФП компенсируют разницу
   насыщенности до одной подвижности. В 03 $S_g = 0.080$ при
   $k_{rg} = 0.00132$; в 05 $S_g = 0.014$ при $k_{rg} = 0.00140$ — подвижность
   почти та же, поэтому потоки и температура совпадают.
   $S_g$ различается в 6 раз, $T(r_w)$ — на 0.0013 К.

2. **Смена PVT меняет всё** — и насыщенность, и температуру, и дебит,
   и положение фронта (0.20 м против 2.39 м, разница в 12 раз).

3. **Смена термики не трогает гидродинамику** — $S_g$, $q_o$, $r_b$ идентичны
   до последнего знака. Это следствие расщепления (splitting): `HydroSolver`
   не видит тепловых коэффициентов, `EnergySolver` работает на замороженных
   $p$, $S_g$, $R_s$. Полезно показать пользователю явно.

⚠️ В README сценариев 03 и 05 (и 04, 06) обязательно предупредить: графики
$T$ и дебитов у пары будут выглядеть одинаково — **это правильно**, смотреть
надо `saturation_profiles.png`. Иначе пользователь решит, что перепутал конфиги.

### Семейство 3: изоляция тепловых эффектов

Одна комбинация модулей (Table + Table), $p_{wf} = 8$ МПа,
варьируются только тепловые скаляры.

**07 — Только адиабатика.** $\mu_{JT} = 0$, $L = 0$.
Единственный источник изменения $T$ — адиабатический эффект
$Q_{ad} = \phi \sum_\alpha S_\alpha (1 + \rho_\alpha c_{p,\alpha}\mu_{JT,\alpha}) \, dp/dt$,
который при $\mu_{JT} = 0$ сводится к $\phi \cdot dp/dt$.
Результат прогона: $T(r_w) = 352.77$ К — **нагрев** на $+2.77$ К.

**08 — + JT.** $\mu_{JT} > 0$, $L = 0$. Результат: $T(r_w) = 348.56$ К.
Чистый вклад JT: $T_{08} - T_{07} = -4.21$ К (охлаждение).

**09 — + скрытая теплота.** $\mu_{JT} = 0$, $L > 0$. Результат: $T(r_w) = 351.08$ К.
Чистый вклад дегазации: $T_{09} - T_{07} = -1.69$ К (охлаждение).

**Проверка суперпозиции** (выполнена при аудите): сумма изолированных вкладов
$(-4.21) + (-1.69) = -5.90$ К в точности равна полному эффекту сценария 04
относительно 07: $346.87 - 352.77 = -5.90$ К. Эффекты линейно складываются —
это ключевой результат, ради которого построено семейство 3.

def save_well_csv(history: SimulationHistory, path: str | Path) -> None:
    """Скважинные данные: одна строка на сохранённый шаг.

    Столбцы: time_s, time_day, q_o_m3st_s, q_g_m3st_s,

### 9.5 Раздел «Как модифицировать»

Обязателен во всех 10 README. Содержит два блока.

**Что менять безопасно:**

| Параметр | Секция JSON | Эффект |
|---|---|---|
| $R_e$ | `geometry.R_ext` | шире область; фронт $r_b$ растёт |
| $h$, $k$, $\phi$ | `geometry`, `rock` | дебит; фронт почти не двигается |
| $N$ | `grid.N` | детальность профилей |
| длительность | `time.history[].dt` | ⚠️ гидродинамика выходит на стационар за 8–12 ч, дольше меняется только $T$ |
| `save_every` | `output.save_every` | прореживает вывод: 1 → 73 шага (0.22 МБ), 6 → 13, 24 → 4 |
| тепловые скаляры | `thermal` | только $T$; гидродинамика не меняется вовсе (splitting) |

**Что требует осторожности — $p_{wf}$:**

Это самый чувствительный параметр. Два ограничения с обеих сторон:

1. **Сверху:** при $p_{wf} > p_b$ разгазирования не будет вообще
   ($S_g \equiv 0$), расчёт пройдёт без ошибок — молча однофазный.
   $p_b$: 9.43 МПа (Standing $R_s{=}50$), 15 МПа (Table $R_s{=}30$),
   отрицательное при $R_s = 0$.

2. **Снизу:** Newton может разойтись с
   `RuntimeError: HydroSolver не сошёлся после 32 подшагов`.
   Граница нерегулярна — проверено на сценариях 03 и 05:

   | $p_{wf}$, МПа | 8.5 | 8.0 | 7.5 | 7.0 |
   |---|---|---|---|---|
   | результат | OK | OK | **отказ** | OK |

   Лечится `"dt_integration": 600` в секции `time` (подробности — DEBT-007).
   Table-путь (сценарии 04, 06–10) устойчив в диапазоне 14…3 МПа.

**Не трогать:** `grid.type` и `output.format` — поля объявлены в
`io/config.py`, но нигде не читаются (проверено при аудите: мусорное
значение `grid.type` проглатывается молча, всегда создаётся `LogRadialGrid`).
В конфигах примеров `output.format` не включён; `grid.type` оставлен
как `"log_radial"` для наглядности, но менять его бессмысленно.

### 9.6 Раздел «Как увеличить газонасыщенность»

Обязателен в README сценариев **04, 07, 08, 09, 10** (табличная ОФП,
$S_g^{max} \approx 0.017$) и в сокращённом виде в **06** (Corey, $S_g \approx 0.081$).

Причина: пользователь видит на графике $S_g$ порядка 1–2 % и может решить,
что расчёт неверен. Нужно объяснить, что это свойство демонстрационных данных,
и дать рецепты.

Структура раздела:

**(1) Почему $S_g$ мала.** В стационаре действует баланс
«сколько газа выделилось = столько унесено». GOR всегда равен $R_{s,0}$ —
весь поступающий с контура газ уходит в скважину, накопления нет.
$S_g$ — это насыщенность, при которой газовый поток выносит поступающее
количество. При подвижном газе (табличная ОФП даёт $k_{rg} = 0.01$
уже при $S_g = 0.1$) достаточно малой насыщенности.

**(2) Что НЕ помогает** — с числами, чтобы пользователь не тратил время:

| Изменение | $S_g^{max}$ | Комментарий |
|---|---|---|
| базовый | 0.017 | 3 суток |
| время 10 / 30 / 90 суток | 0.017 | **без изменений** — стационар за 8–12 ч |
| $R_e = 500$ м | 0.017 | фронт шире (2.4 → 7.7 м), $S_g$ та же |
| $k/10$ | 0.021 | слабо |
| $\phi = 0.05$ | 0.015 | слабо |

**(3) Что помогает** — по убыванию силы:

*Подвижность газа* (главный рычаг, до ×25). Заменить секцию `relperm`:
```json
"relperm": {"model": "corey", "S_or": 0.2, "S_gc": 0.05,
            "n_o": 2.0, "n_g": 3.0, "kro_max": 1.0, "krg_max": 0.3}
```

| ОФП | $S_g^{max}$ | $T^{min}$, К |
|---|---|---|
| табличная (текущая) | 0.017 | 346.9 |
| Corey $n_g{=}2$, $k_{rg}^{max}{=}0.8$ | 0.081 | — |
| Corey $n_g{=}3$, $k_{rg}^{max}{=}0.3$ | 0.165 | 342.1 |
| Corey $n_g{=}4$, $k_{rg}^{max}{=}0.1$, $S_{gc}{=}0.1$ | 0.305 | 342.5 |

Пояснить контринтуитивность: **менее подвижный газ даёт бо́льшую $S_g$**,
потому что для выноса того же расхода нужна бо́льшая насыщенность.

*Газосодержание* $R_{s,0}$: 10 → 0.0005, 20 → 0.008, 30 → 0.017.
Выше 30 не задать — в `oil_pvt.csv` только ветки $R_s \in \{0, 30\}$.
Для больших $R_s$ нужна своя PVTO-таблица.

*Депрессия* $p_{wf}$ (слабый рычаг): 14 МПа → 0.002, 8 МПа → 0.017,
4 МПа → 0.027.

**(4) Предупреждение об устойчивости.** При крутой ОФП и/или низком $p_{wf}$
возможно `RuntimeError: HydroSolver не сошёлся после 32 подшагов`.
Лечится `"dt_integration": 600` в секции `time`. Подробности — DEBT-007.

## 11b. Почему Newton хуже сходится на Standing, чем на таблицах

Диагностика выполнена при аудите 2026-09-07. Вывод: **PVT-модель сама по себе
ни при чём** — дело в крутизне фронта разгазирования относительно шага по времени.

### Что расходится

`BlackOilNewtonReport` при отказе: `active_set_iterations = 2` (лимит 12),
`iterations = 2…4` (лимит 15). Активный набор **не** зациклен — Newton
останавливается досрочно. Виновата строка `blackoil.py:200`:

```python
if not accepted: return z, BlackOilNewtonReport(False, it, float(nrm))
```

Line search перебирает 12 половинных шагов ($\alpha$ до $2^{-12}$). Если ни один
не уменьшил невязку — отказ. Это происходит, когда направление $dz$ из линейного
решения указывает «не туда»: якобиан не описывает поведение невязки на том
масштабе, на котором Newton пытается сделать шаг.

### Отвергнутые гипотезы (проверены численно)

| Гипотеза | Проверка | Результат |
|---|---|---|
| Излом $R_s^{eq}(p)$ на узлах таблицы портит FD-якобиан | Варьировали `n_knots` адаптера: 3, 5, 10, 20, 40 | **Картина идентична.** Защита `_pressure_fd_step` (blackoil.py:137–154) работает |
| Standing численно «хуже» | $dR_s/dp$: Standing 5.3…6.9, Table 3.0 (м³/м³)/МПа, обе гладкие и монотонные | Патологии нет |
| Разные PVT-свойства | $B_g$ отличается на 6–12 %, $B_o$ близки | Не объясняет |

### Действительная причина

Ключ — формула активации газа (`blackoil.py:215–216`):

$$S_g = \frac{d \cdot B_g}{B_o + d \cdot B_g}, \qquad d = R_s^{\text{общ}} - R_s^{eq}(p)$$

$S_g$ ячейки при переходе в двухфазное состояние определяется «перенасыщением» $d$.
А $d$ растёт тем быстрее, чем круче $dR_s^{eq}/dp$ и чем дальше $p$ ушло за $p_b$.

Сравнение первого шага при $p_{wf} = 8$ МПа:

| PVT | $p_b$ | Перешло ячеек | $S_g^{max}$ | $S_g$ на ячейку |
|-----|-------|---------------|-------------|-----------------|
| Standing $R_s{=}50$ | 9.43 МПа | 6 | 0.080 | **резкий скачок** |
| Table $R_s{=}30$ | 15 МПа | 27 | 0.017 | плавно |

У Table фронт «размазан» по 27 ячейкам малыми порциями — Newton идёт мягко.
У Standing 6 ячеек скачком получают $S_g \approx 0.08$ — сильное возмущение,
линеаризация не справляется.

Вклад вносят два фактора Standing: вдвое более крутая $dR_s^{eq}/dp$ и близость
$p_b = 9.43$ к рабочему $p_{wf}$ (у Table $p_b = 15$ — фронт стартует раньше
и успевает распределиться).

### Корень: кривизна $B_g(p)$

Newton строит линейную модель; ошибка модели пропорциональна **второй
производной** PVT-функций. Здесь модели расходятся принципиально:

| | $B_g(p)$ | $d^2 B_g/dp^2$ |
|---|---|---|
| Standing | $B_g = p_{std} T_0 / (T_{std}\, p)$ — гипербола $1/p$ | $\neq 0$ (при 6 МПа: $1.1 \times 10^{-5}$) |
| Table | линейная интерполяция по 3 узлам | $\equiv 0$ внутри сегмента |

У Table линейная модель Newton **точна** внутри сегмента таблицы.
У Standing — приближённа, и тем хуже, чем ниже давление: при 6 МПа
$dB_g/dp$ втрое круче табличной.

Измеренная нелинейность вдоль направления Newton
(отношение «фактическая невязка / линейный прогноз», 2-я aset-итерация):

| $\alpha$ | Standing $p_{wf}{=}6$ МПа | Table $p_{wf}{=}4$ МПа |
|---|---|---|
| 0.25 | **126×** | 1.76× |
| 0.0625 | **12×** | 0.98× |
| 0.0156 | 1.00 | 1.00 |

Table линеен уже при $\alpha = 0.0625$ — line search берёт $\alpha = 0.125$ и
уверенно снижает невязку (−8 % за итерацию). Standing линеен лишь при
$\alpha \leq 0.016$; такой микрошаг почти не двигает невязку
(0.01192 → 0.01178 за три итерации), затем line search проваливается.

Обусловленность **не** виновата: $\text{cond}(J)$ у Standing $6 \times 10^4$,
у Table $5.7 \times 10^5$ — у Standing она на порядок лучше.

### A-retry работает корректно, но лимита не хватает

Проверено ручным дроблением одного шага 3600 с (Standing, $p_{wf} = 6$ МПа):

| Подшагов | $\Delta t_{sub}$, с | Результат |
|---|---|---|
| 1…64 | 3600…56 | отказ на первом же подшаге |
| **128** | **28** | **OK**, $S_g^{max} = 0.099$ |

`PrototypeHydroAdapter` имеет `max_retries = 5` → максимум $2^5 = 32$ подшага
(112 с). Этого не хватает: нужно 128. При `max_retries = 7` расчёт проходит.

Механизм A-retry (`prototype_adapter.py:66–104`) реализован верно: каждый подшаг
стартует с состояния предыдущего, что эквивалентно уменьшению `dt_integration`.
Ограничение — только в значении лимита.

### Практический вывод

Два равнозначных способа (проверены):
- `dt_integration = 600` с в конфиге (Simulator дробит до вызова солвера), либо
- `max_retries = 7` в `PrototypeHydroAdapter` (автоматическое дробление внутри)

Для сценариев 03, 05 при $p_{wf} = 8$ МПа хватает штатных настроек.
Рекомендация в README: при снижении $p_{wf}$ уменьшать `dt_integration`.
Сообщение `RuntimeError: HydroSolver не сошёлся после 32 подшагов` — сигнал
именно об этом.

Зарегистрировано как **DEBT-007** — вынести `max_retries` в `NumericsConfig`
и поднять значение по умолчанию до 7.

   GOR всегда равен $R_{s,0}$ (весь газ с контура уходит в скважину),
   а $S_g$ — это та насыщенность, при которой поток газа выносит ровно
   поступающее количество. Отсюда три рычага, измеренных прогонами:

   **Рычаг 1 — подвижность газа $k_{rg}$ (решающий, ×25):**

   | ОФП | $S_g^{max}$ | $T^{min}$, К |
   |---|---|---|
   | табличная (`relperm.csv`) | 0.0166 | 346.9 |
   | Corey $n_g{=}2$, $k_{rg}^{max}{=}0.8$ | 0.0811 | — |
   | Corey $n_g{=}3$, $k_{rg}^{max}{=}0.3$ | **0.1647** | 342.1 |
   | Corey $n_g{=}4$, $k_{rg}^{max}{=}0.1$, $S_{gc}{=}0.1$ | **0.3055** | 342.5 |
   | Corey $n_g{=}5$, $k_{rg}^{max}{=}0.05$, $S_{gc}{=}0.15$ | 0.4115 | — |

   Чем менее подвижен газ, тем бо́льшая насыщенность нужна для выноса того же
   расхода. Демонстрационная `relperm.csv` даёт $k_{rg} = 0.01$ уже при
   $S_g = 0.1$ — газ «слишком текучий», не накапливается.

   **Рычаг 2 — газосодержание $R_{s,0}$:** 10 → 0.0005, 20 → 0.0077, 30 → 0.0166.
   Ограничен таблицей (ветки только $R_s \in \{0, 30\}$).

   **Рычаг 3 — депрессия $p_{wf}$:** 14 МПа → 0.0018, 8 МПа → 0.0166,
   4 МПа → 0.0273. Слабый рычаг, к тому же упирается в устойчивость.

   **Вариант (d): оставить CSV, задать Corey-ОФП в JSON.**
   Правка только конфига, никаких новых файлов:

   ```json
   "relperm": {"model": "corey", "S_or": 0.2, "S_gc": 0.05,
               "n_o": 2.0, "n_g": 3.0, "kro_max": 1.0, "krg_max": 0.3}
   ```

   Результат: $S_g^{max} = 0.16$ вместо 0.017 (×10), тепловые эффекты
   заметнее ($T^{min}$ 342 К против 347 К). Устойчивость проверена:

   | Конфиг | $\Delta t{=}3600$ с | $\Delta t{=}600$ с |
   |---|---|---|
   | Table $R_s{=}30$, $p_{wf}{=}8$ МПа | 0.1647 | 0.1647 |
   | Table $R_s{=}30$, $p_{wf}{=}6$ МПа | 0.1745 | 0.1745 |
   | Standing $R_s{=}50$, $p_{wf}{=}8$ МПа | расходится | 0.1622 |

   Ограничение: Standing с крутой ОФП требует `dt_integration = 600` с
   (проявление DEBT-007).

   ### ✅ ПРИНЯТО: вариант (a)

   Параметры сценариев не меняем. Демонстрационные CSV остаются как есть,
   $S_g^{max} \approx 0.017$ в Table-сценариях — это нормально для примеров,
   назначение которых показать комбинирование модулей, а не реалистичную физику.

   Вместо этого README сценариев с табличной ОФП получают раздел
   «Как увеличить газонасыщенность» с измеренными числами (см. §9.6).
