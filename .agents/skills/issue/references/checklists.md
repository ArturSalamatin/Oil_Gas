# Контрольные списки публикации issue

Применяй вместе с [соглашениями](conventions.md) и шаблоном соответствующего типа. Действующие пользовательские решения и содержимое реестра имеют приоритет над примерами шаблонов.

## 1. Допуск и поиск дубликата

- [ ] Указан зарегистрированный ID допустимого типа. Запись прочитана целиком от её заголовка до следующего заголовка того же или более высокого уровня.
- [ ] Поля статуса, GitHub и ветки принадлежат этому ID. Противоречивые поля не исправляются догадкой до установления их принадлежности.
- [ ] Проверены локальная запись и поиск по GitHub. Найденный issue сопоставлен с ID и содержанием. Ошибка сети или инструмента не считается отсутствием дубликата.
- [ ] Если issue уже создан, повторный вызов не создаёт второй. При частично выполненной публикации сообщи существующий URL и незавершённые шаги.

## 2. Предметный анализ

- [ ] Прочитаны черновик при наличии, связанные решения, задачи и источники. Для старой задачи отсутствие черновика само по себе не блокирует публикацию.
- [ ] Существование файлов, кода, меток и приведённых фактов проверено по актуальному дереву. Различаются установленный факт, гипотеза и сообщение пользователя.
- [ ] Для BUG описаны условия, проявление, воспроизведение и подтверждённость причины. Для DEBT – текущее и целевое состояние, мотивация и ограничения.
- [ ] Для FEAT установлены сценарий, зависимости, интерфейс и физическая основа, когда они применимы. Для VAL – источник и независимость эталона, сценарий, метрика и обоснование допуска либо открытый вопрос.
- [ ] Обсуждённые варианты и принятое решение переданы без подмены. Неизвестные данные обозначены, а недостаток данных для содержательного issue останавливает публикацию до его устранения.

## 3. Подготовка артефактов

- [ ] Имя ветки и метки определены по [conventions.md](conventions.md), проверены существующие имена и метки. Локально известная удалённая ссылка может быть устаревшей.
- [ ] Тело и комментарий подготовлены по шаблону типа, сохранены решения и границы из черновика, добавлены применимые ссылки. Подробный план реализации не выдаётся за результат `issue`.
- [ ] В комментарии фактические ветка и короткий SHA основного каталога отделены от предполагаемой ветки задачи. Уже существующие файлы артефактов не затираются без проверки назначения.
- [ ] В `--dry` нет записи файлов, создания меток, issue, веток или комментариев. Предпросмотр включает заголовок, метки, ветку и первые 20 строк тела.

## 4. Публикация и сверка

1. Сохрани `01-issue-body.md` и `02-comment-open.md` в каталоге задачи, передавай текст через `--body-file`. Проверь ID, репозиторий, метки и назначение исполнителя до создания.
2. Создай issue один раз и сохрани URL. Затем опубликуй комментарий. При частичном сбое не повторяй создание issue: сообщи выполненную стадию и восстанови только отсутствующую по отдельному указанию.
3. Обнови ссылку и ветку в реестре и связанной заметке штатным помощником. После обновления прочитай полные границы записи и проверь, что новые поля относятся к нужному ID, остальные поля сохранены, а заметка обновлена корректно.
4. Сообщи URL, метки, предполагаемую ветку и результат синхронизации. Следующий этап – соответствующий `plan-*`, запускаемый отдельно.
