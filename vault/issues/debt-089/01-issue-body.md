## Описание

Выпуск `tools/release.py X.Y.Z` (FEAT-038) публикует в Releases колёса, архив примеров, README и HTML-документацию, а архив поставки для разработки `gpn-multiphase-solver-X.Y.Z.zip` собирает отдельный запуск `tools/handover.py vX.Y.Z` (FEAT-031) уже после push и публикации. Поэтому архив передачи к выпуску не привязан и в Releases не хранится, а проверки передачи (сборка PDF постановки и сверка таблицы номеров уравнений с `.aux`) не защищают выпуск: при их отказе выпуск уже опубликован, и исправление требует нового номера.

Решение пользователя 2026-10-27: выпуск включает оба шага, подготовку колёс и передачу. Архив передачи становится шестым файлом выпуска, и отказ передачи откатывает выпуск до push.

## Текущее состояние

Выпуск идёт шестью шагами (докстринг `tools/release.py`):

1. проверки без изменений – `preflight`;
2. локальные коммит `release: X.Y.Z` и метка `vX.Y.Z`;
3. сборка из метки в `dist/vX.Y.Z/` – `build`: архив примеров, `README.md`, `docs-vX.Y.Z.zip` (`sphinx -W`), `notes.md`, самопроверка `tests/test_packaging.py`, два колеса;
4. коммит `release: начало X.Y.(Z+1).dev0`, самопроверка рабочего каталога;
5. `git push --atomic` ветки и метки;
6. `gh release create` с пятью файлами.

Отказ на шагах 2–5 откатывает коммиты и метку (`rollback`), отказ шага 6 печатает команду повтора.

Передача `tools/handover.py [<метка>] [--acceptance]` запускается отдельно. Она берёт срез `git archive` метки, собирает PDF постановки (`pdflatex` дважды), сверяет `doc/source/eq_numbers.json` со свежим `.aux` (`tools/eq_numbers.py --check`), собирает HTML и упаковывает срез в `dist/handover-<версия>/gpn-multiphase-solver-<версия>.zip`. С ключом `--acceptance` на распакованной копии идёт приёмка `tools/acceptance.py`.

Что плохо:

- выпуски 1.0.0–1.0.6 содержат по пять файлов; `dist/handover-1.0.6/` собран через 18 мин после публикации 1.0.6 и лежит только локально;
- `release.py` строит `docs-vX.Y.Z.zip` по таблице номеров уравнений без сверки с `.aux`, поэтому выпуск может выйти с устаревшими номерами в HTML-документации;
- проверка чистоты в шаге 1 охватывает только `numerical_solver/` (`git status --porcelain --untracked-files=no -- numerical_solver`): незакоммиченная правка `tools/handover.py` после встраивания передачи изменила бы файл выпуска без следа в метке.

## Целевое состояние

Одна команда выпускает и колёса, и архив передачи:

- **шаг 1**: дополнительно проверяется `pdflatex` в PATH; проверка незакоммиченных правок охватывает весь репозиторий, неотслеживаемые файлы по-прежнему не учитываются (`--untracked-files=no`);
- **шаг 3**: последним действием, после колёс и до push, `release.py` запускает `tools/handover.py vX.Y.Z` отдельным процессом и добавляет архив к файлам выпуска;
- **шаг 6**: `gh release create` с шестью файлами; описание выпуска (`NOTES_TAIL`) называет архив поставки для разработки;
- **ключ `--acceptance`** у `release.py`, по умолчанию выключенный: передаётся в `handover.py`, приёмка идёт до push, и её отказ откатывает выпуск;
- README решателя описывает папку выпуска из шести файлов, в которой лежат обе поставки; выпуск скачивается целиком, без фильтра.

Решения пользователя 2026-10-27: HTML по-прежнему собирается дважды (для `docs-vX.Y.Z.zip` и для среза); архив в опубликованный выпуск 1.0.6 не досылается; длинное тире в `tools/*.py` исправляет отдельная задача DEBT-090.

## Анализ вариантов решения

### Вариант A. Отдельный процесс (выбран пользователем)

**Суть.** В шаге 3 `release.py` запускает `sys.executable tools/handover.py vX.Y.Z [--acceptance]` из корня репозитория и берёт архив по известному пути. Интерпретатор тот же – venv решателя с Sphinx и packaging. Метку передача читает локально (`git show`, `git archive`), push для неё не нужен.

**Изменения.** `release.py`: функция `run_handover`, вызов в конце `build`, проверки в `preflight`, ключ в `main`. `handover.py`: докстринг и общий путь архива.

**Плюсы.** Малый объём правок, нет цикла импорта, передача остаётся самостоятельной командой с прежним поведением.

**Минусы.** Путь архива – соглашение двух скриптов (снимается общей функцией пути в `release.py`, которую уже импортирует `handover.py`), HTML собирается дважды (оценка около 10 с).

### Вариант B. Функция сборки среза (отклонён)

**Суть.** Тело `handover.main` выносится в функцию `build_handover(treeish, out)`, `release.build` вызывает её напрямую.

**Минусы.** Цикл импорта: `handover.py` импортирует `release`, а `release.py`, запущенный как скрипт, – модуль `__main__`. Импорт `handover` внутри выпуска загрузил бы `release.py` второй раз как модуль `release`, с другим классом `ReleaseError` и вторым набором констант. Обход – отложенный импорт или общий модуль, то есть переделка двух скриптов ради одного вызова.

### Подводные камни варианта A

- **Кодировка вывода.** `release.run` перехватывает вывод и ставит `PYTHONUTF8=1`, а прогресс передачи (с приёмкой около 15 мин) нужен в консоли сразу. Предложение: `subprocess.run` без перехвата и без `PYTHONUTF8`, дочерний процесс наследует канал и кодировку; проверка – проба с выводом через `Tee-Object`.
- **Окно без push.** С `--acceptance` локальные коммиты и метка живут без push около 17 мин вместо примерно 2 мин; `/merge` другой сессии в это окно сломает выпуск. Предупреждение – в докстринге «Запуск».
- **Каталоги `dist/`.** После отказа `dist/handover-X.Y.Z/` остаётся для разбора, как `dist/vX.Y.Z/`; сообщение отката называет оба. Команда повтора шага 6 содержит путь архива, поэтому до повтора каталог не удаляется.
- **Код возврата 1** у передачи означает и отказ сборки, и непройденную приёмку; выпуску различать их не нужно – в обоих случаях откат.
- **Проверка без настоящего выпуска.** `REPO` зашит в скрипт, полная эмуляция `main` опубликовала бы выпуск. Проба вызывает `release.build` на метке `v1.0.6` с выводом в `vault/issues/debt-089/probes/`.

## План решения

**Подготовка.** Baseline на `386cb9a`: `pytest tests/ --collect-only -q` из `numerical_solver/` – 2677 тестов; `tests/test_release_notes.py` – 6 passed.

**Реализация** (порядок уточняет `/plan-improve`):

1. общий путь архива – функция в `release.py`, `handover.main` пользуется ею;
2. `release.py`: проверка `pdflatex` и чистоты всего репозитория в `preflight`, ключ `--acceptance` и разбор аргументов, `run_handover`, архив в файлах `build`, сообщение отката с обоими каталогами, `NOTES_TAIL`, докстринг; тесты разбора аргументов (неверный набор → код 2 без обращения к git);
3. докстринг `handover.py`;
4. README решателя – шесть файлов, обе поставки в папке выпуска;
5. CLAUDE.md – строки `tools/release.py` и `tools/handover.py`;
6. пункт журнала в «Не выпущено», раздел «Изменено».

**Верификация.** Проба `release.build` на `v1.0.6`: шесть файлов; в архиве верхний каталог `gpn-multiphase-solver-1.0.6/`, есть `doc/problem_statement.pdf` и `doc/build/html/index.html`, нет `__pycache__` и `acceptance.py`. Отказ при PATH без `pdflatex` – `ReleaseError`. Вывод через `Tee-Object` без смешения кодировок. Один прогон с `--acceptance` – вывод приёмки в консоль и код возврата. Замер времени передачи и второй сборки HTML. Регресс – быстрый уровень: код пакета и прототип не изменяются.
